# north-star-review：改动是否守住了目标和边界

读 `AGENTS.md`、`docs/architecture.md`、`docs/glossary.md`，以及改动涉及领域的 `docs/decisions/<领域>.md`；再读差异：已经提交的是 `git diff <基线>...HEAD`，交付之前还在工作区里的是 `git diff $(git merge-base <基线> HEAD)` 加上 `git status --short` 列出的新文件。编译器、分析器、`scripts/gate.py` 和测试已经检查的不用重复。只看下面这些需要判断的地方，每一条都要落到具体的文件和行。

1. **目标。** 这个改动让系统更好用、更好改或更快了吗？有没有为了一个边缘需求加进与“不做”清单（`AGENTS.md` 第 1 节、`docs/decisions/scope.md`）冲突的东西，或者为业务形态加了框架概念？
2. **更简单的路。** 同样的目的，有没有少一个概念、少一个配置项、少一个分支的做法？新加的抽象删掉以后，复杂度是集中了还是只是搬了家？有没有只有一个实现的接口、没人读的声明、没人用的扩展点？
3. **一条规则一个实现。** 同一条规则有没有在两处各写一遍（编译期和运行期、两个算子、校验和执行）？新逻辑是不是放在了拥有这块知识的类型里？漏改一处会被编译、校验或测试暴露吗？
4. **不变量。** 对照 `docs/architecture.md` 的表：缺失有没有被静默变成值；失败的尝试有没有留下东西；请求期有没有解析配置或按名字查找；有没有不带上界的外部等待；边界上有没有隐式转换；计划有没有交出可变的东西。
5. **热路径。** 新增的工作和分配随候选数或特征数增长吗？有没有按行的分配、闭包、装箱、字符串拼接？做了性能上的取舍时有没有测量（`.agents/skills/perf-check`）？
6. **使用者看到的。** 新的配置键和错误：名字和 `docs/glossary.md` 一致吗？错误有没有精确位置和一句修法，会不会同一个错报两次？默认值让常见情况正确吗？公开 API 变了时，`samples/StrataRec.Samples.Host` 和 Schema 跟着改了吗？
7. **测试。** 修缺陷的测试在旧代码上失败过吗（`scripts/red-on-base.sh`）？改了复杂逻辑时，把它改坏有测试发现吗（`scripts/mutate.sh`）？断言的是行为还是照抄了实现？有没有和时钟赛跑、对内部协作者打桩、复制一套夹具只为多一个用例？
8. **记录。** 反直觉的写法、刻意没处理的情况，旁边有一行原因或者在 `docs/decisions/` 有一条吗？
9. **文档的改动。** 差异里 `README.md`、`AGENTS.md`、`docs/`（决定除外）和技能的每一处新增都要能回答：读代码、Schema 或 `--help` 看不出来吗？对这份文档的读者（`README.md`：第一次看到项目的人；`AGENTS.md`：每个会话）值得吗？答不上来的建议删掉：“实现了新功能”不是改文档的理由，把实现写进文档更不是（`.agents/skills/edit-docs`）。反过来，没改文档不算问题，除非文档里现有的话因为这个改动不对了。
10. **规则文件。** 有没有哪一个提交同时动了规则文件（`AGENTS.md` 第 6 节）和代码（一个改动里分成两个提交是对的），或者用放宽门禁来通过检查？

**输出。** 只列实质问题：位置、会造成什么、建议怎么改（优先给更简单的改法）。按严重程度排序。没有问题就只回一行“通过”，不凑数。对每条建议说明它是必须修、建议修，还是可以记成不处理。
