# edit-docs：默认不改文档

代码和测试是“现在怎么做”的唯一来源。文档里的每一行都有人付上下文去读，却没有测试保证它一直是对的；人已经很少读文档，他们让 agent 读代码再讲。所以改动本身不是改文档的理由：修了一个缺陷、加了一个小功能、多了一个选项，通常什么文档都不用动。

## 1. 先问三件事

1. **读代码、配置的 Schema、`stratarec <命令> --help`、错误信息或测试，能知道它吗？** 能：不写进文档。话要说，就说在那里：注释、`[Description]`、报错里的修法。
2. **它对谁有用？** 只对做某一类任务的人有用：进那个领域的 `docs/decisions/` 或一个技能，不进人人都读的页面。
3. **它过时了谁会发现？** 没有测试或门禁会发现：不写，或者只写一个指向代码或命令的指针。

三问之后还剩下的，才是文档该有的：读代码看不出来的理由，和对它的读者处处有用的东西。

## 2. 每份文档给谁读，什么时候才改

| 文档 | 谁读、什么时候 | 只放 | 什么时候才改 |
| --- | --- | --- | --- |
| `README.md` | 第一次看到这个项目的人 | 它是什么、怎么跑起来、接着去哪里看 | 新用户的头几步变了（定位、安装、头几个命令）。不写内部实现，不逐个列新功能和选项 |
| `AGENTS.md` | 每个 agent，每个会话 | 目标、边界、验证命令、什么时候停下来问 | 一条对所有任务都成立的规则变了。只在某类任务里用的做法进技能，机器能查的进 `scripts/gate.py` |
| 技能的 `description` | 每个会话都加载；正文用到时才读 | 什么时候该用这个技能 | 触发条件变了 |
| `docs/architecture.md` | 改执行器、候选表、计划编译之前 | 要读很多文件才拼得出的：请求的路径、依赖方向、不变量 | 多了或少了一个项目、扩展点、不变量 |
| `docs/glossary.md` | 起名字的时候 | 一个概念的规范叫法和不该用的词 | 新概念有了名字并且会在几处用到，或者发现一个词被混用 |
| `docs/development.md` | 拿不准方向的时候 | 原则和它们的理由 | 原则变了。具体的决定不进这里 |
| `docs/guide/` | 使用者，多半经过 agent | 工具问不出来的：从哪里开始、表达式的语义 | 写在里面的话不对了。字段的说明在 Schema，算子在 `stratarec operators` |
| `docs/decisions/` | 改一个领域之前 | 为什么、没选什么、代价 | 见 `record-decision`：这是唯一鼓励多写的地方，也只写读代码看不出来的 |

## 3. 确实要写的时候

- 找到已有的那句话改写它，不在末尾追加。一件事只写在一处，别处用指针。
- 每加一行，看能不能删掉一行因此多余或过时的。
- 写结论和它成立的条件，不写经过：经过在提交说明里。术语按 `docs/glossary.md`。
- 提交说明里用一句话说明这次变化为什么值得进文档；“实现了某个功能”不是理由。这些页面变长时 `python3 scripts/gate.py` 会提示一次，用来再问一遍，不是错误。
