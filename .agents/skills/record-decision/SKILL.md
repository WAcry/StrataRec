# record-decision：只记代码说不出来的

代码和测试说明系统现在怎么做。这里记的是三个月后只读代码的人会改坏的东西：为什么这样、没选什么、代价是什么。

## 1. 先判断要不要记

问一句：以后有人只读代码，把它改成另一种做法（或者补上刻意没处理的情况），会付出真实代价吗？

- **不会**（等价的写法、普通的内部结构）：不记。留白就是留给以后重构的自由。
- **会，但只影响一个函数或文件**：在代码旁写一行注释说明原因（例：`// Linear scan on purpose: at N <= 8 it beats a dictionary`）。不写进文档。
- **会，而且跨模块、反直觉，或者依赖代码里看不出的前提**（规模、延迟要求、上下游的习性、用户的明确要求）：现在就记，和代码同一个提交。前提离开这次对话就没人记得了。
- **只是两种都说得通的做法里选了一种**：先不记；第一次有人问“为什么不用另一种”时，把回答记下来。

拒绝或推迟一个能力：记在 `docs/decisions/scope.md`，写持久的原因，不写“暂时没空”。

## 2. 写在哪、怎么写

写进 `docs/decisions/<领域>.md`（领域的划分见 `docs/decisions/README.md`），一条是一个列表项：

```markdown
- **决定本身，一句话。** 为什么：要解决的问题和约束（给出数字和来源）。没有选的：另一种做法，和它落选的原因。代价：接受了什么。什么情况下重新考虑。
```

- 一个决定只写在一处。改变一个已有的决定时改写那一条，不追加一条新的让两条并存；旧文字在 git 历史里。
- 不写实现的步骤和修了几轮：那是代码和提交历史。不引用仓库外的东西（评审轮次、聊天记录）。
- 反引号只包仓库里现有的名字（类型、成员、配置键、错误码、路径）。已经删掉或设想中的名字不加反引号，否则门禁报悬空。
- 术语按 `docs/glossary.md`。
- 一条写不短（超过六七行）时，多半是把实现也写进去了，或者其实是两个决定。

如果决定的是一条全局成立、任何改动都不能打破的规则，把它加进 `docs/architecture.md` 的不变量表（所有者和测试都要有），理由仍然写在领域文件里。

## 3. 完成的标准

决定和代码在同一个提交；`python3 scripts/gate.py` 通过（它检查文档里的名字都存在、单个文件没有超出体量上限）。文件超限时不是放宽上限，而是删掉已经由代码和测试说明的条目，或者把一个领域拆开。
