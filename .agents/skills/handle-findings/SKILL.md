# handle-findings：逐条判断，不逐条打补丁

每条发现都加一个分支，逻辑会越来越复杂，下一个缺陷就出在这些分支之间。一个缺陷常常说明这里的规则太复杂。

## 1. 对每一条先回答三个问题

1. **这段逻辑或限制本身必要吗？** 不必要就简化或删掉，缺陷随之消失。修的时候优先加约束或换一条更简单的规则（例：算子对“这一行没有 id”“这一列没有产出”各处理错了一次，改成要求 id 列不可空，两个分支都删掉）。
2. **是必要功能的真实缺陷吗？** 修，并带回归测试。先看根因在哪一层：在执行器里修一处，好过让每个算子各自记得。
3. **是罕见场景，处理的成本远大于收益吗？** 不改，在 `docs/decisions/<领域>.md` 记下判断和理由（见 `record-decision`）。发现对了不等于必须改。

发现本身也可能不成立：先在代码里确认它说的行为，再判断。

## 2. 修复的证明

1. 先写一个失败的测试，测的是对外可见的行为，不是内部怎么调用。
2. 确认它在修复之前的代码上失败：

   ```sh
   scripts/red-on-base.sh <修复之前的提交> -- --project tests/StrataRec.UnitTests --filter-class <类的全名>
   ```

   它在一个临时检出里放上你现在的测试文件、跑给定的测试，要求失败。在旧代码上也通过的测试证明不了什么。
3. 修复，`scripts/check.sh` 全绿。
4. 提交说明里写清每一条的结论：修了什么、简化了什么、哪条不改和原因。

## 3. 不要做的

- 不为了让测试通过去改弱断言、删测试或加跳过。测试错了就说明它错在哪，再改。
- 不在修缺陷的提交里顺手放宽门禁或改规则文件（见 `AGENTS.md` 第 6 节）。
- 不把“以后再处理”留在代码注释里：要么现在处理，要么记成不处理的决定。
