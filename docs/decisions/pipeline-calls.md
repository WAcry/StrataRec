# 流水线调用

- **算子可以调用另一条流水线，跨流水线的拓扑因此是配置**（2026-11-25）。原来一个页面要用几条流水线的结果，只能由宿主先后调用、自己拼接：拓扑在代码里，实验的开关在框架之外，分配、触发、校验、`explain-plan`、回放都看不到。把引擎包成服务客户端来调也能跑，但被调用的流水线拿不到这个请求的实验分配，不共享截止时间和种子，回放对不上。缺的只是算子手里的一个入口：编译时 `TryCallPipeline` 声明，执行时 `CallPipelineAsync` 调用，拿到被调用方的结果行、输出列和 `output.values`。拿到之后做什么（并入候选、按位置安放、组成栏目、跨栏目去重）是算子的事，内置的或用户自己写的都行。
  - **只加了这一个入口，没有加别的概念。** 考虑过并否决的：栏目作为框架的概念（栏目算子、挂在一行下面的嵌套结果、分组的输出），节点的行视图，一张表里同一个键出现多次，一条流水线里多张表，用户画边的 DAG，以及“一组流水线一起发布”。它们要么是替用户做的特化，要么是为一类页面改内核，只用一条流水线的用户也要跟着承担。用户写专用的算子不是缺陷，框架要保证的是写它的时候不用绕。
  - **内置算子有两个**，`PipelineSource@1` 和下面的 `PipelineColumns@1`，一个把结果变成行，一个变成列。`PipelineSource@1`：调用一条流水线，把结果行追加为候选，映射几个列。它只用公开的接口，同时是自定义算子的范例（宿主示例的 `SlotBlend@1` 是另一个：并发调用两条流水线，按自己的规则把一条的行放进另一条）。它是行源，所以行源的规则照常：
    - `limit_param` 必填（行数上限决定请求的内存），数的是追加的行：请求已经有的行不占名额；参数没有值（映射的键设成 null）时一行也不追加，而不是在第一个节点之前抛异常。
    - 请求见过的键跳过。在一个非空的列产出之后追加行、又不写这个列，而后面有读取依赖它覆盖所有行，仍然是 `ROW_SOURCE_AFTER_COLUMN`；`mark` 标记列在其他行源的行上没有值（默认值不替别的行源补），所以声明成 `bool?`，读的时候写 `?? false`。
    - 映射的列要先声明：被调用方的接口在只加载一个发布的引擎里编译时不可见，同一份配置在两种编译下要给出同样的列类型。值按检查允许的转换写入（整数列表读进浮点列表会转换）。
- **一个页面有几个栏目时，行是栏目，栏目的内容是这一行的列表：`PipelineColumns@1`**（2026-11-26）。要解决的是两件事：同一个物品要能出现在几个栏目里（“继续游玩”和“我的收藏”必然重复），栏目本身要像物品一样被打分、排序、过滤和做实验。一张候选表里一个键一行，所以按“每行一个物品、用一列标记栏目”做不到第一件，第二件也只能把栏目的分数抄到每一行上。做法是分两层，每一层都是普通的流水线：页面流水线的行是栏目；它对每一行调用一条流水线，把返回的行写进这一行的列表列（id 一个列表，每个输出列一个列表，逐个元素对齐），`output.values` 写进这一行的普通列。各行的列表互不相干，所以重复是自然的；栏目是行，所以排序、过滤、探针、实验都是已有的。
  - **没有加新的结果结构，也没有放开“一个键一行”。** “每个栏目一串物品、每个物品几个属性”用几个对齐的列表列就能表达，而类型、输出、日志、回放、内存预估都已经支持列表；给结果加一层（栏目下面再挂一张物品的表）要把这些全部再做一遍，表达的东西没有多。“每行一个展示位、物品 id 放在列里”也能查到特征（实体的键可以是任意列），但它解决不了栏目的排序，各栏目还被迫走同一组节点。
  - **这个做法的边界**记在“范围调整”里组和成员的那一条：页面层对所有栏目的物品一起做列式的计算，以及一个物品要带很多属性。现在各有做法，不预先定下一步的结构。
  - **它不是栏目专用的**：对每一行调用一条流水线、把结果留在这一行，“看过这个的人还看了”之类每个种子一个列表的场景也是它。栏目、标题、样式都不是框架的概念。
  - **节点写什么是所有流水线共有的，一条流水线怎么调用是它自己的。** 不同的行可以调用不同的流水线（`pipelines`，按 `by` 的值选，默认是行的键）。`ids`、`columns`、`values` 写在节点上对每条流水线生效，条目可以追加（只有广告流水线才有的 `track_id`）或者按名字替换（分数在这条流水线里叫 `bid`）；`inputs` 不继承，节点上的 `inputs` 只属于节点上的 `pipeline`。输入如果也继承，默认流水线的输入会被塞给不声明它的流水线，而默认流水线没有自己的条目可以放。没有条目、节点也没有 `pipeline` 的行不调用，这不是失败（一个没有内容来源的栏目）。
  - **没有结果的行**：列表列不可空时是空列表，可空时缺失；不是列表的列必须声明为可空，编译时检查。调用失败的行、超过 `max_calls` 的行、没有条目的行、条目没有映射这个列的行都按这一条。空列表是这个算子写下的值（“这个栏目没有东西”），不是默认值顶替缺失，节点同时报告降级；每次调用都失败时节点失败，和 `MultiSourceRecall@1` 对召回源的规则一样。
  - **只有一部分栏目、或者一部分物品才有的属性，谁有谁写，没有的那一行缺失。** 栏目自己的属性（只有活动栏目有倒计时）是页面流水线的一个可空列，值来自按栏目的键查的特征，或者条目的 `values`（那条流水线的 `output.values`）；栏目里物品的属性（只有广告有 `track_id`）是条目追加的列表列，其他栏目的行没有值。几百种栏目里大多数共用一条流水线（节点上的 `pipeline`，把行的键或者别的列作为输入传给它），特殊的几种各有条目，这就是 `pipeline` 和 `pipelines` 并存的原因。
  - **列表的元素不会缺失**，所以映射成列表的输出列必须不可空（被调用方用 `?? 默认值` 给出；同一条流水线里只有部分物品有的属性也是这样，使用方的算子把一个栏目并进另一个时，没有这个属性的位置同样要填占位值），按元素类型检查转换；id 的列表按被调用方的主键类型检查（`CallReadsKeys`，和 `CallAppendsRows` 并列：调用方自己的主键是栏目 id，和物品的主键无关）。
  - **`max_calls` 必填，调用同时发出，没有并发上限。** 每一行是一次流水线运行，节点必须说它最多发起几次；超过的行不调用，节点降级。调用按行的名次依次发起、一起等待：一次调用在节点里的次序就是行的次序，种子和回放因此是确定的。并发上限会让发起的次序依赖完成的次序，而要限制的量已经由 `max_calls` 限制了。
  - **页面展示了什么由页面流水线自己记**：栏目流水线的日志是它返回了什么，页面层的规则（去重、合并）之后实际展示的是页面流水线的行和它们的列表，输出探针把列表列原样写出。
  - **跨栏目的规则是使用方的算子**（宿主示例的 `DistinctHeads@1`：上面的栏目没有在开头展示过的物品排到这个栏目的开头）。示例的算子要求 id 列不可空（“没有物品”只有空列表这一种写法），可空时在配置的那个键上报错：可空的时候，它对“这一行没有 id”“这一列整个没有产出”先后处理错过，加约束比逐个补分支简单。框架给的是 `ListColumn.SetTaken`：按给定的位置从另一行的列表取元素，不管元素类型，所以几个对齐的列表按同一组位置取就保持对齐，算子只需要从 id 决定一次顺序。
  - **示例只演示最小的形式**（宿主示例的 `shelves`：固定的几个栏目，按行的键选流水线，一条跨栏目的规则）。先挑栏目再取内容、多数栏目共用一条带输入的流水线、按一个列区分栏目的种类、条目有自己的输入和值，这些由集成测试覆盖（`PipelineColumnsEndToEndTests`），不放进示例：示例是给第一次读的人看的，框架能支持什么由测试证明。
  - **其他几条。** 所有行的输入在发起第一次调用之前准备好：输入读不出来（参数的某个键没有值）时节点失败，没有调用留在途中，录制里也就不会时有时无。定长列表没有“空”这个值，所以不可空的定长列表不能作 `values` 的目标，要声明成可空。`timeout_ms` 是被调用的那一次运行的截止时间，和 `CallPipelineAsync` 的约定一样：被调用方到时失败，这一行就没有值；它自己降级返回（它的节点 `on_failure: skip`）时，返回什么就是什么。一次调用的 id 只按一种主键类型读，`CallReadsKeys` 的第二个不同的声明是配置错误：原来后一个声明覆盖前一个，只加载一个发布的引擎里只检查到最后一个。`ListColumn.SetTaken` 先检查位置再建立新的列表，位置越界时这一行保持原样。
  - **条目的输入读到的特征，按节点的规则在节点运行之前取齐，不在按行选路之后再取**（不改）。只有某一种行才用的特征，数据源失败时节点失败，这次请求里没有那种行也一样。节点读什么由配置决定，特征在节点之前按这个集合取齐，预取、拉取屏障和回放都建立在这上面；先选路、再只为命中的行取特征，是执行器里只为这一个算子存在的两段执行。这种失败是看得见的（节点失败，`on_failure` 决定之后怎么办），不是悄悄错的数据，出现的条件也少（条目有自己的输入，读的特征来自单独的数据源，而且那个数据源失败）。需要隔离时不必把上下文特征当输入传：被调用的运行是同一个请求，自己读 `ctx.*`，数据源失败时失败的只是那一次调用、那一行。
  - **没有做的**：表达式里对列表求和、取最大值（栏目分数要用到内容的统计时，现在由被调用方的 `output.values` 给出，那里数据还是列）；输出时把对齐的列表合成对象的数组（宿主自己合）；一个请求里同一条流水线、同样输入的调用，节点没有声明缓存时不合并（声明了的共用一次运行，见 [`external-calls.md`](external-calls.md) 的“同一个请求对同一条缓存记录只问一次源头”）。
- **讨论过、现在不做的两件事**（2026-11-26）。都有真实的收益，但现有做法已经自然，或者能用上的情况少而代价大；出现真实需求时再做。
  - **一个实验同时改两条流水线。** 实验属于一条流水线（`pipeline_id`）。两条流水线有调用关系时通常不需要：调用方的臂可以改传给被调用方的输入（`PipelineSource@1`、`PipelineColumns@1` 的 `inputs` 读参数，自定义算子自己传），可以换一条被调用的流水线，也可以换掉节点，都是普通的补丁；要改的是被调用方内部、又没有做成输入的东西时，给它加一个输入。两边各自要改内部细节时配两个实验，由实验平台放在同一层一起分配：请求的臂列表对整棵调用树共用，所以这样能生效，代价是两个文件要保持一致。统一成一个实验要让补丁的校验、足迹和联合计划跨流水线编译，而发布是按流水线分别进行的，一个实验横跨两次发布会有一条已经换了、另一条还没换的时刻要处理。将来要做，最小的形式大概是调用方的臂附带它调用的流水线的补丁，归属仍在调用方。
  - **调用提前启动**（请求一开始就发起后面节点才用的调用）。节点一个接一个运行，一个节点里可以同时发起几次调用；能从提前启动得益的只有“调用在靠后的节点、前面的节点慢、调用又不依赖前面的结果”，而行源本来就排在写列的节点之前。节点可能被 `when`、后备或实验臂跳过，提前发出的调用白跑不说，被调用方的探针已经写了日志，记下了没有人用的运行；截止时间和调用的次序（种子和回放靠它）也要另外定义。延迟成为问题时，更通用的方向是让互不依赖的节点并发，不是给调用开特例。
- **节点可以缓存它对一条流水线的调用：命中的这一次，被调用方没有运行**（2026-11-27）。多久写在调用的节点上（`cache`：`ttl_ms`、`stale_if_error_ms`、`version`），放在哪写在绑定里（`pipelines.<id>.cache`，`memory` 和 `distributed` 各自可选）：同一条流水线，一个调用点可以缓存一小时而另一个不缓存，放在哪是环境的事。只保留完整的结果：成功、没有降级，请求的运行会写日志（强制臂、捕获日志的请求只读不写；带配置覆盖的请求不读也不写），而且算键用到的那些计划到运行结束时仍在服务。被调用方失败时，过期的结果在 `stale_if_error_ms` 之内仍然交付，节点记为降级，和服务的缓存一样。没有选的：做成被调用方自己的属性（多久因调用点而异）；做成一个独立的算子（调用边界本来就是结果，回放也在这里录制）。不个性化的列表定期算好放进本地表仍然更简单；这个缓存是给按用户、按查询这类提前算不完的结果的。
  - **键是“会算出同样结果”的条件，不是配置的字节。** 流水线和它输出的形状、它收到的每个输入，加上会运行什么：被调用方和它一路能调用到的流水线各自的基线（流水线产物、它读的特征的定义、数据表、它的数据源和服务各自的身份），和请求在其中每条流水线里的臂连同那个实验的内容（`CallIdentity`）。所以发布调用方、改超时或缓存的设置、发布一个请求不在其中的实验，结果都留着；被调用方变了才重算。配置更新频繁、重算又贵时写 `version`：只认这个名字，发布不再让结果重算，改名才重算；这时一路上的流水线只有请求在其中有臂的才进键，所以给被调用方加一个调用也不让不在那个实验里的请求重算。输入按值进键，不按表示：没传和显式缺失、`float32` 的 1 和 `float64` 的 1、两种元素类型的空列表、正负零是同一次调用；被调用方的算子要区分这些，就不该缓存它。请求 id、种子、时间和调用方不进键：被调用方里随种子和时间变的东西在 `ttl_ms` 之内是冻结的，这是声明缓存的人的选择。表不随配置更换，记录是什么由键说明。代价：实验第一次读一个新特征、绑一个新服务、或者多了一条能调用到的流水线时基线变一次，所有人重算一次；写了 `version`，输出的形状变了仍然不命中，免得把记录读成别的列。
  - **没运行的不报告，看到的照常报告，结果从哪来查得到。** 命中时被调用方的探针、节点结果和请求指标都没有：它们在算出结果的那个请求名下。请求仍然暴露在算出这个结果的臂之下，所以结果里有这些臂和触发，算出它的每一次运行（被调用方的，和它调用的）各写一条 `$experiments`，带 `cached_from`（那个请求的 id、时间，和算出它的那次调用）和这次运行在本请求里的 `called_by`；不写，曝光数就随命中率变。来源要带调用：一个请求可以运行同一条流水线很多次（每行一次调用），只有请求 id 分不出是哪一次。结果里的某次运行当初自己也是缓存回答的，它的 `cached_from` 仍指向更早算出它的那个请求，不改成上一层的：上一层那个请求没有运行过它。来源在四处查得到：调用结果的 `Cached`，追踪里 `calls` 的 `cached_from`，回放包，和算子写在行上的列（`computed_by`）。`computed_by` 是按行的列（请求 id、时间、调用），没命中时写本请求的：混排之后每一行各有来源，离线把展示日志关联到被调用方的探针时只认这一列，不用区分命中与否。
  - **键要用到请求在被调用方一路能调用到的流水线里的臂，查缓存之前先问到**（一条流水线问到之后同一个请求不再问）；问不到，这次调用不读也不写缓存。一个请求在一条流水线里只有一个答案：同时开始的几次调用各问一次，都用先到的那个，否则同一个请求的几行在不同的臂里，键里的臂也和实际运行的对不上。代价：命中时也向分配提供方问了那些没有运行的流水线的臂；同时开始的调用多问了几次。
  - **“完整”在每一层都成立，所以降级向上传。** 被调用方的运行降级了，或者交付的是过期的结果，调用它的节点就记为降级，它所在的运行也因此降级，上一层的缓存不保留；输出读到一个只答了一部分的特征，结果同样记为降级（原来只有节点读到才算）。这改的是所有调用，不只是带缓存的。不传的话，中间一层的缓存会把建立在残缺回答上的结果按 `ttl_ms` 交付到下游恢复之后。运行途中，被调用方下面的某条流水线换了计划，或者有一条在途中才开始服务，这次的结果也不保留：它可能是新计划算的、调用了键里没有的流水线，键却是开始时的（后一种，没轮到这次发布的实例会从共用的分布式层读到一条自己不服务的流水线的行）。没有选的：请求开始时把一路上的计划都固定住（改的是所有调用怎么找到被调用方，为的只是发布那一刻的一次写入）。运行里有一次流水线调用没有被回答（没在服务、嵌套太深、调用成环，或者那次运行失败了），结果同样不保留，不管节点没有它怎么继续：算子按约定可以不理会一次失败的调用，节点也就不是降级，但结果缺了那次调用要的东西，缺不缺取决于这次运行在调用树的哪里、在哪个时刻，键里没有这些。代价：可选的被调用方持续失败期间，调用它的那一层每次都重算。一路能调用到的流水线里有引到这次调用的那些流水线之一时（各自发布的流水线互相调用，运行到才发现），这次调用不读写缓存，也不等同请求的别的调用：结果取决于环从哪里进入；两条分支各自等对方正在算的结果，会一直等到时间用完，而不带缓存时闭环的那次调用立刻被拒绝。
  - **刻意不处理的几种。** 命中不看调用还剩多少时间，也不检查它下面本来会嵌套多深：这两个上限保护的是运行，命中什么都不运行；分布式层的读被调用的时间截断之后仍然可以交付过期的记录，这正是 `stale_if_error_ms` 的用途。被调用方失败、交付过期结果时两样都报告：失败的那次运行真的运行了，请求暴露在它的臂之下；交付的行来自记录，带 `cached_from`；只留一样，要么少算一次真实的运行，要么展示的行查不到来源。引擎没有配日志的去处时照常读写：有没有去处是部署的选择，这样的引擎自己算的结果同样没有日志；同一个分布式层里混着写和不写日志的实例，是部署要避免的。分布式层里一条记录留多久由写它的节点决定：两个调用点共用一个键而时长不同，长的那个读不到被短的那个写下、已经到期删掉的记录，直到它自己写一次；影响的是命中率，不是正确性。
- **被调用方的接口不随实验变化，调用只检查一次。** `request_schema`、`output` 和主键类型都不能打补丁，列和参数的声明只能新增，所以一条流水线对调用方来说是签名固定的函数：调用方对着它检查输入、读到的输出列和值、主键类型，不需要逐组合检查，各条流水线的联合计划也仍然各自编译。
  - 没有处理的一种：映射参数的键设成 null 时，这个叶子没有值，但它在表达式里的类型仍然是非空的，所以把它传给必需的输入能通过检查，运行时读它报错，写 `??` 也不起作用。这是参数本身的既有行为，不只在调用输入上；内置和示例的行源把没有值的行数上限当作 0。
  - 输入的类型和可空性分开判断，和后备流水线的输入一样：类型决定哪些值能转换，可空性决定能不能不传。可能缺失的值不能传给被调用方必需的输入，算子传的（写 `?? 默认值`）和按名字传下去的都一样；原来这两种都能编译，请求不带这个输入时调用才失败。
  - 算子传的输入按它读到的东西的声明类型算，不按表达式运算时提升的类型：原样传一个 int32 输入就是 int32。
- **编译时知道被调用方就在编译时检查，不知道就在调用时检查。** 工作区里所有流水线都在（`validate`、`build`、`run`、服务工作区的宿主），编译请求带一个目录（`IPipelineDirectory`），错误报在声明它的配置键上：`PIPELINE_CALL_UNKNOWN`、`PIPELINE_CALL_INPUT`、`PIPELINE_CALL_OUTPUT`、`PIPELINE_CALL_KEY_TYPE`、`PIPELINE_CALL_CYCLE`、`PIPELINE_CALL_FAILED`（被调用方自己编译不过）。引擎按发布逐条加载流水线时没有目录，算子声明的需要留在句柄里，调用时对着正在服务的那个计划检查，每个计划只检查一次（缓存对计划是弱引用，不调用的调用方不会留住已经换掉的计划）；不合就是一次失败的调用。两处用的是同一个判断（`PipelineCall.Mismatch`）。没有为了在加载时检查而把几条流水线绑成一个发布：那要改发布、manifest 和切换的单位，而 `fallback_pipeline` 今天也是按 id 找正在服务的那条。
  - 目录里的被调用方按它的发布编译，带实验：实验改不了接口，但臂可以加调用，成环要把臂里的调用算上（原来只编译基线，两条流水线各在一个臂里互相调用能通过校验）。各个臂不再单独校验一遍，那是它自己编译时的事。
  - 目录查到的结果按编译环境保存，编译器复制请求时目录跟着走：同一个请求换一个二进制的算子再编译会重新查，`CompileMerged` 和 `build` 不会因为丢了目录而放过拼错的流水线名。
  - 按发布服务的宿主在启动和每次换计划之后检查调用：被调用的流水线没在服务是 `RELEASE_CALLED_NOT_SERVED`（启动时是错误，之后是警告，和后备流水线一样），在服务但接口不合是 `RELEASE_CALL_MISMATCH`。按工作区加载时，被调用的流水线和后备流水线一样随调用方一起加载，所以 `stratarec run` 只给一条流水线的请求也能跑；`validate -p` 校验的也是这个范围（被调用的流水线和它们的后备流水线），否则校验通过的流水线一运行就因为被调用方的后备流水线不存在而失败。在一个 manifest 上 `run` 时给出 `RUN_CALLED_NOT_LOADED`，和后备流水线的提示各报各的。
- **调用失败是一个结果，不是异常，也不换后备流水线。** 没有在服务、接口不合、输入被拒绝、分配失败、运行失败、没有时间，都返回失败的结果和原因，由算子决定（`PipelineSource@1` 让节点失败，于是 `on_failure` 决定请求要不要继续）。被调用方的 `fallback_pipeline` 不参与：它的输出列可能不同，调用方的列映射对不上，而且节点已经有自己的失败策略。只有调用方取消请求时抛出，而且取消优先：调用之前已经取消的请求得到的是取消，不是一次算子可以不理会的失败。
  - **调用等被调用的运行结束，不在节点的截止时间上放弃它**（没有改）。被调用的运行拿到的截止时间就是节点剩下的预算，它的外部调用都是有界等待，到点就结束；只有被调用方的算子自己不理会取消时才会拖住调用方，而这样的算子在宿主直接请求它时一样拖住请求。为它在调用边界再加一层放弃和后台收尾，是为一个违反契约的算子加机制。
- **被调用的运行是同一个请求。**
  - 请求 id 和时间相同。种子由调用方的种子、节点、被调用的流水线和这次调用是节点在这次运行里的第几次派生：同一个请求每次都用同样的种子，一个节点的两次调用种子不同。次序按运行数，不按尝试数：一个后备节点可以为几个节点各跑一次，原来每次都从 0 数，录制里出现两个相同的调用，回放拒绝。每次尝试记下它发起了几次调用：回放不重跑记为超时的尝试，要把它占的次序一起跳过，否则后备节点第二次运行的调用会拿到第一次的失败，而且不报缺口。几个线程同时发起的调用各有自己的次序，但不可重复。
  - 输入：算子传的优先；被调用方声明的其他输入，调用方的请求里有同名的就传下去（后备流水线取输入也是这样）。
  - 时间：节点预算里剩下的就是被调用方的截止时间，所以节点的 `timeout_ms` 管得住它的外部调用。算子可以给一次调用更短的时限（`CallPipelineAsync` 的 `timeout`）：节点没有它也能继续的调用（页面的赞助内容）慢的时候作为一次失败返回，节点还有时间往下走；不给的话慢的可选调用会把整个节点拖到超时。这个时限是被调用运行的截止时间，和请求的截止时间是一回事，不是“过了就丢掉答案”：被调用的流水线自己规定某个节点超时就跳过、照样返回已有的结果时，调用方拿到的就是这个结果，和宿主用同样的截止时间直接请求它一样（没有改）。
  - 成环：工作区编译时拒绝。逐条加载的流水线编译时互相看不见，运行时沿调用链检查，并且嵌套不超过 8 层，超过的调用失败。没有在编译时检查“无环但深过 8 层”的链：运行时的错误已经说明原因，而这样深的嵌套不是我们要优化的情形。
- **实验分配传给被调用方，它运行自己认识的臂。** 来源和请求自己的一样：调试的强制臂、调用方传的平台分配、或者分配提供方（按被调用流水线的层再问一次，用请求原来的输入，分流单元才一致）。
  - 一个共用的臂 id 列表（强制的，或者调用方传的）里有几条流水线的臂是正常的，所以“不认识”要按整棵调用树判断：被调用方不认识的臂是别的流水线的，不计入它的忽略；请求自己的流水线不认识、但它（间接）调用的流水线认识的臂，不算忽略，强制时也不拒绝。没有任何流水线认识的臂照旧。提供方是按流水线问的，它为被调用流水线答出的不认识的臂是它的错，照常记为忽略。
  - 强制臂对被调用的流水线同样严格：强制了被调用流水线同一层的两个臂是调试者的错，请求被拒绝，而不是那一层悄悄跑基线。“被调用的流水线”包括后备流水线的节点调用的：后备流水线自己不带实验，它调用的流水线照常运行请求的臂。后备流水线同时又被节点调用时，它自己的臂照常算在内；后备流水线的调用按它所有臂的算，比实际能到达的略多（它接管时跑的是基线），多出来的只是把一个用不到的臂当成“有主的”。
  - 提供方为被调用的流水线抛异常，是这次调用的失败（一个结果，录制里有），不穿过算子抛出去；请求自己的提供方异常仍然抛给宿主。
  - 请求的结果里，`Experiments` 在自己的臂和触发之后接上被调用流水线的（按序数排序，去重），宿主上报曝光时不用自己去找；忽略的臂每个 id 和原因只列一次，按 id 排序。“已分配”是实际运行了的臂：声明了调用但这次没有调用（`when` 为假），被调用流水线的臂既不在已分配里，也不算忽略。回放包里记的仍然只是请求自己流水线的：回放不运行被调用方。
  - 进入被调用流水线的每一次调用都计入它的请求指标和它各个臂的指标，包括在运行之前就失败的（输入被拒绝、分配失败）：它的实验健康度要从这些运行里读。
- **被调用方自己写日志。** 它的探针和 `$experiments` 记录以它自己的流水线 id、同一个请求 id 写出，带 `called_by`：从请求自己的流水线一路到这次运行的调用，每一段是调用方的流水线、节点和次序，例如 `home/blend#0`，被调用的运行再调用时是 `home/blend#1 > inner/blend#0`。一个请求里同一条流水线运行两次时靠它区分；只写最近一段不够，被调用两次的流水线两次都从 0 数自己的调用。记录的是它交给调用方的结果，不是最终展示了什么；最终展示由调用方的探针记录，离线按请求 id 关联。没有做成“调用节点提交时才发布”：那要缓冲另一次运行的日志，而被调用方确实运行了、也确实返回了这些行。捕获的日志批次里，被调用运行的排在请求自己的（和后备流水线的）之后，不按时间插进去（没有改）：每个批次带着流水线和 `called_by`，顺序不是用来还原先后的。
- **带追踪的结果列出被调用的运行**（`RecResult.Calls`，JSON 的 `calls`，文本输出在 trace 下面）：谁调用、调用了哪条、成功与否、它运行的臂和它自己的节点结果。调试一个页面时不用再对每条流水线单独发请求。
- **回放按结果录制调用，不重新运行被调用方。** 调用方的运行记录里有每次调用（节点、次序、流水线、算子传的输入、返回的行和值），回放时同一个节点、同一个次序、同样输入的调用由记录回答，和服务调用一样；记录里没有、或者输入变了，是一个缺口，调用失败。所以回放一个请求不需要引擎服务它调用的流水线。代价是换了被调用方的配置再回放，看不到它的变化：要看，对被调用方单独录制和回放。没有把被调用的运行整个嵌进回放包：那要让回放递归地重跑、比较每一层，报告也要嵌套，而调用边界本来就是结果。回放包格式因此升到 `2026-11-25.1`，调用的次序改成按运行数、尝试记下调用次数之后是 `2026-11-26.1`（次序的含义变了，旧包按新含义读会对错答案），调用带上缓存结果的来源之后是 `2026-11-27.1`，来源带上调用、调用带上降级之后是 `2026-11-27.2`。
  - 输入在发起调用时记下，按值比较：算子在一次调用还没返回时改了输入对象去发下一次，两次各记各的；从文件读回的包里列表的写法（换行、缩进）不影响比较。
  - 没有做的三处，都是录制之外的情形：换了调用方的配置回放时不按记录里的列类型重新检查接口（工作区里这样的配置编译就过不了）；请求中止时还在途的调用不在快照里（正在运行的节点已经记了）；手改过的包里一次调用的结果有重复的键时不拒绝（引擎写的包不会有）。
- **配置覆盖（`DebugOptions.ConfigOverride`）编译时没有目录。** 引擎保存的“计划的来源”是加载时配置的一份序列化副本，目录不是配置（它指向宿主的工作区对象，宿主之后可以改），所以不在里面；覆盖出来的计划里的调用在调用时检查。覆盖把调用改到原计划没有的流水线时，请求开始时还不知道那条流水线的臂是谁的；结果里一个被调用运行实际跑了的臂不再同时列为“不认识”。
