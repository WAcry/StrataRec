# 外部依赖：服务调用、缓存与等待

- **外部依赖收敛成一个概念：服务**（原来是四种各自一套的 IO）。原来框架能调用的外部依赖只有四种（特征源、召回源、模型、特征源的分布式缓存），每种各有工厂接口、基类、注册表、解析代码、遥测类别和回放；使用方要接一个过滤服务、执行业务逻辑的服务或另一种缓存时没有地方放，加第五种要改十来处、三五百行。四种的划分是沿袭下来的，不是需要：它们共同的部分（有界等待、超时和失败的语义、录制和回放、遥测、生命周期）本来是同一件事，差别只在调用的形状。方向是：绑定里只有一种外部依赖 `services`，一个契约（一次调用：可选的逐项键、按行或共享的张量、要的输出、选项；回答：逐项输出、共享输出、追加的项、`ok | partial | failed`），一个有界调用的实现，对算子公开；有键的调用逐项录制输出（不再推断布局），其他调用按整次调用的摘要匹配；声明了 `cache` 的服务都能用通用的两级缓存。特征、召回、模型都变成服务的用法：特征仍有规划器的预取、延迟物化、去重和本地表，`ModelScorer@1` 是“逐行调用并写列”。分五步：(1) 统一绑定的基础设施；(2) 服务契约和调用原语，迁移模型和召回，逐项录制（回放包格式升级）；(3) 通用缓存；(4) 特征连接器变成服务，只留一个有界等待的实现、一个逐项回放，用分配测试和基准把关；(5) 上下文特征可选的参数。
  - 放弃的：三个领域客户端接口合成一个；召回专用的回放借用和它的缺口原因；按类别的指标名（`stratarec.source.*`、`stratarec.model.*`）；模型录制改为逐项（格式变）；声明了缓存的服务总是取全部输出。这些不是使用方必需的，换来的是任何新依赖只写一个工厂、一个契约。
  - 不做的：保留四种再加一个“逃生舱”（两套机制并存，四种之间的重复照旧，逃生舱得不到缓存和逐项回放）；不透明的负载加使用方的编解码（像 Temporal 的 activity：框架看不懂负载，就做不了逐项录制、缓存和张量校验）；所有 IO 都放进节点（像 Product Mixer：丢掉规划器跨节点的预取和去重，而这是特征拉取性能的来源）；请求路径上的写（写走日志 sink：请求路径只读，回放才确定）。只依赖请求的业务逻辑做成上下文特征（`geo_store` → `region` 的链是先例）。
- **服务调用只读，写在 `IServiceClient` 的契约里**。原先只说节点对外的唯一作用是写候选表，理由只提了回放和预览；收敛成服务之后，所有外部依赖都经过同一个契约，引擎决定一次调用发不发、回答用不用的地方更多了：缓存命中和回放不调用，超时后不再等待而服务可能照样执行完，后备节点可能再调一次，没有读取方的节点、强制臂的调试请求和转到后备流水线的主流水线都调用了、回答却不给用户。会写状态的服务在这些情况下漏写、重写或者为没人看到的结果写。框架判断不了一个服务写不写，所以这是对实现方的约定，写在契约注释里。要对外写的，走日志管道（`durable` 探针，下游消费后作为特征读回），或者由宿主在响应之后写。
- **第 1 步：一个工厂接口、一个注册表、一条解析路径**。五种工厂（模型客户端、召回源、连接器、更新来源、分布式缓存存储）原来各有几乎一样的接口、泛型基类、注册表和解析代码，类型名属性有四种拼法（ClientType、`ConnectorType`、`StoreType`、`SourceType`）。现在只有 `IBindingFactory<TInstance>` 和基类 `BindingFactory<TInstance, TSettings>`，`PlanEnvironment.Bindings` 一个注册表，宿主不分种类 `Add` 自己的工厂；`BindingResolver` 是从绑定条目到实例的唯一路径，错误码、位置和措辞对每种绑定都一样。召回源、模型的实例接口这一步不动，第 2 步合并成服务契约。
  - **类型名在所有种类之间唯一**：一个类型名指一个实现，注册表按名字存，按契约取时用协变判断。按（契约，名字）存的话，按具体类声明的工厂（`IBindingFactory<TInstance>` 的 `TInstance` 写成具体类）会被推断成另一个契约，按 IModelClient 取不到，错误要到加载时才出现；按名字存没有这个坑，种类写错（模型绑定写了 `memory_list@1`）还能说出“不是模型客户端”。代价是两种绑定不能用同一个类型名：内置的本来不重名，服务合并之后更不会。一个工厂可以同时服务两种契约（显式实现两个接口），每种绑定通过自己的接口读它的设置类型，Schema 和运行时一致；能力只列出有某种绑定能用的类型，只问工厂的契约，不读设置类型（那是 Schema 的事，清单的能力预检不该因为一个没用到的工厂的设置类型加载失败）。
  - **未知类型报在绑定的选择器上**：`BINDING_TYPE_UNKNOWN`，位置如 `/services/ctr_model/client`，提示相近的名字或已注册的类型，另有建议时接在列表后面（`redis@1` 在哪个包）。原来模型和召回源的未知类型报在引用它的节点上（MODEL_UNBOUND、CANDIDATE_SOURCE_UNBOUND），没有拼写提示；要改的是绑定，不是节点。一个计划的编译（一个 `PlanBuilder`）里解析结果按名字缓存，失败也缓存，几个节点读同一个坏绑定只建一次、只报一次；基线和每个实验臂的独立校验各编译一次，各自再试一次工厂，不共享失败；它们的诊断按臂归属的规则合进联合编译。只在某个臂里用到的坏绑定，诊断标上臂（`bindings:local with exp/arm`），和原来的设置错误一样：它说明哪一臂依赖这个绑定，CLI 定位时去掉后缀。几条流水线（或一条和它的后备）各自编译、合并诊断时（`DiagnosticBag.AddRange`），完全相同的条目只留一条，所以都从基线读同一个坏绑定时只报一次；一条从基线读、一条只在臂里读时标签不同，仍是两条。是否失败由每次加载自己的诊断判断，不看合并后的错误数（相同的错误不会再加一遍）。工厂报的设置错误统一为 `BINDING_SETTINGS`，代替原来按种类的五个码；名字不在绑定里仍报在节点上；分布式缓存的 `timeout_ms` 是框架自己的设置，仍是 `DISTRIBUTED_CACHE_CONFIG`。
  - **绑定的布局只有一张表**（`BindingKinds`）：每种绑定在产物里的段、成员、选择器和称呼，身份、指针、Schema（按段和成员走到每种绑定的位置）和错误都读它；能力提取（`SourceBindingArtifact.AddTypes`）读强类型的绑定模型，在模型那一层维护。更新来源是生命周期的例外：每张表运行一个（编译时检查设置可能建出从不运行的），不在共享实例里，没有密钥存储，不加载也不释放，I/O 和清理都在它自己的 `RunAsync` 里，工厂接口的文档写明了。哪个契约对应哪种绑定在 `PlanEnvironment` 的一张表里，Schema 按它把注册的工厂分到各段；不对应任何种类的工厂没有绑定能用，Schema 不描述它。
- **遥测按角色区分，所有外部调用用同一组指标**（第 1 步）。原来封闭的 IoKind 决定指标名（`stratarec.source.*` 或 `stratarec.model.*`）、标签（`stratarec.source` 加 `stratarec.source.kind`，或 `stratarec.model`）、span 名和事件（每类两个），加一种依赖要改五处 switch。现在调用的目标是（角色，绑定名）：内置角色 `fetch`、`cache`、`recall`、`model`、`assignment`（实验分配的 provider，第 4 步加入，目标名是 `provider`），扩展用自己的，角色必须是小写字母、数字和下划线组成的标识符（有空格时 `fetch geo` + `shard` 和 `fetch` + `geo shard` 会成为同一个汇总主体）；指标是 `stratarec.io.duration`、`stratarec.io.errors`、`stratarec.io.keys`（只记有键的调用），标签 `stratarec.io.role`、`stratarec.io.target`；span 名是“角色 名字”，内置角色取的正是原来的动词，span 名不变（`fetch item_store`、`recall popular`）；事件只有 `IoTimeout`、`IoFailed`，主体也是“角色 名字”；健康状况按（角色，名字）判断，同名的两种依赖互不影响。生成类服务的指标（`stratarec.io.output_tokens`、`stratarec.model.answers` 等）沿用调用的标签，一个依赖的指标都用同一个标签键关联。特征源的值、表和缓存的指标属于特征运行时，仍用 `stratarec.source`；缺失比例去掉了恒为 `feature` 的 `stratarec.source.kind`。
- **第 2 步：一个服务契约、一个调用原语，模型和召回都是它的用法**（回放包格式 `2026-11-21.4`，后来 `2026-11-21.5`）。`IServiceClient`（`StrataRec.Core.Services`）取代 IModelClient 和 ICandidateSource：`CallAsync(ServiceCall, IServiceResponse, CancellationToken)`，签名 `DescribeAsync` 可选，默认抛出，只有模型算子要它。一次调用是服务名、版本、命名输入（张量、文本或缺失）、批大小、可选的逐项键（`Items`）、要读的输出（`Outputs`）、最多追加几项（`Limit`）、请求 id 和选项（种子、`max_output_tokens`）；回答写进调用方的缓冲：张量输出、文本输出、追加的项；状态是成功或失败，带 token 数和截断标记。模型是“送行的张量、读每行的输出”，召回是“送查询的值、读追加的项”，过滤服务是“送候选作 `Items`、读每项一个 bool”，别的业务服务按自己的形状收发，用的是同一个调用。
  - **算子调用服务只有一个入口**：编译时 `OperatorCompileContext.Service(name, key, role)` 解析绑定（`Signature` 取签名），执行时 `OperatorContext.CallAsync(BoundService, ServiceCall, ServiceResponse)`。有界等待（调用的 `timeout_ms`、节点截止时刻、调用方取消）、异常变成失败状态、遥测、录制和回放都在这一处，内置算子和自定义算子走同一条路，`RetrieveAsync` 和 InvokeModelAsync 去掉了。`ServiceResponse` 是框架的回答缓冲（从请求内存租），调用结束时关闭，被放弃的客户端之后写的东西不进入回答。`KeysOf(rows)` 给出行的实体作 `Items`。
  - **绑定只有一个 `services` 段**，取代 `models` 和 candidate_sources；同一个服务可以被模型节点和召回节点调用。错误码一类问题一个：`SERVICE_UNBOUND`（原 MODEL_UNBOUND、CANDIDATE_SOURCE_UNBOUND），`SERVICE_SIGNATURE`（原 MODEL_SIGNATURE：签名取不到，或签名里没有节点映射的输入、输出）；消息里仍按调用的角色称呼（“Model 'llm' version 'v2' has no input …”）。张量的宽度或形状不符（`MODEL_TENSOR_MISMATCH`）、没有映射必需的输入（`MODEL_INPUT_MISSING`）仍是模型算子的码：它们说的是节点怎样把列映射成张量，不是服务。
  - **缺失是显式的输入**。召回的查询值缺失时作为缺失的输入发送（`NamedInput.IsMissing`），带查询值的类型对应的元素类型和形状，而不是不发送：服务分得清“这个请求没有值”和“配置没给这个输入”，类型和形状的检查也不取决于请求有没有值（`memory_vectors@1` 收到类型不对的缺失值照样失败）。摘要里缺失既不是 0，也不是没有这个输入。
  - **只录制要读的输出**。调用带上算子读的输出名，录制和回放只按这些。服务可能算出很多输出（多头模型、生成式服务的附加字段），全部录制会让回放包变大，合成时还要推断不读的输出的布局（一行的批次里调用级的 loss 曾被当成逐行输出）。代价：回放时配置读了录制时没有要的输出（实验多映射一个输出），回放包里没有它，报这个输出的 `not_recorded` 缺口（`Field` 是输出名），节点按服务没返回它处理。
  - **回放先用节点自己的录制，再借能回答它的**（两种调用同一条规则）。节点自己下一次输入相同（有逐项键时项也相同）的录制调用被占用；它失败了就原样失败，它能回答这次调用（有调用读的每个输出，项数够，或者录制时服务就只有这么多）就原样回放。否则用任何节点输入相同、能回答它的成功调用，不占用；没有能完全回答的，用读的输出最多、项最多、说不清的项最少（`Shortfall`）的那次，缺的报缺口：两次都只有文本 `a`、都没有项的录制，一次要了 0 项（什么也说明不了），一次要了 3 项（服务没有），原来取前一次，多报了 3 项的 `limit_exceeds_recording`。有逐项键时这里的“输入相同”是项和每项的输入都相同的整次调用：它按录制回答（文本、重复项的位置都在），只有缺的输出报缺口，不改为逐项合成；反例是多读一个未录的输出，文本就丢了，重复项 `[1, 1]` 的两个分数变成了同一个。只为缺的张量逐项合成、其余保留精确录制的做法：不做。一次调用的回答只来自一次录制，拼出来的回答没有哪次调用返回过；多读的输出是配置的变化，缺口如实说明了它，回放报告也就分得清配置差异和服务的回答。要的项数是否够用同一条规则判断和报缺口：录制的调用项数够，或者它在自己的正数上限之前就停了（服务没有更多）；`Limit` 为 0 的调用什么也说明不了，不回答要项的调用，原节点把上限从 0 调大时报 `limit_exceeds_recording`。两个反例：两个节点用同一模型、同样的行和输入、读不同的输出，换了先后，先跑的节点占用了另一个节点的录制，缺了自己的输出；两次召回同一查询、要的数量不同，新节点要得多，借到的是第一条、较短的那次。节点自己的录制即使不如别的完整也要占用，后面的调用才能依次遇到自己的录制。
  - **有逐项键的调用逐项合成**：录制里没有同样的项和输入的调用时，每项每个输出的值取自任何一次有这个项、输入相同、有这个输出的成功调用，分批变了也能回答。每个张量输出都是逐项的（`BatchSize × k`），这样的调用不追加项（`Limit` 必须为 0，`CallAsync` 检查），这是契约的一部分：追加的项属于整次调用，合成不出来，原来会被静默丢掉。只在别的输入下出现过的项是 `inputs_changed`，没出现过的是 `not_recorded`；项在录制里有、却没有调用读的某个输出（文本属于整次调用，或者录制时没有要它）是这个输出的 `not_recorded`。录制里有、但不是整行的输出（客户端写得比形状多，录制时节点就失败了）只在匹配到它的那些项上不报缺口，节点照样失败；别的调用里匹配到的项没有这个输出，照样是缺口。只读状态、不读输出的调用（逐项校验）一项都没有匹配到时失败：只有状态的回答没有缺口值可填，原来合成成功，调用方就把没有录制担保的候选当成通过了。读输出的调用，只要有录制带着它读的输出（由此知道布局：类型和每项的宽度），没有匹配的行得到缺口值（浮点是 NaN），调用仍成功；没有任何录制有这些输出时失败。
  - **没有逐项键的调用（召回、生成式召回、一次性的业务调用）按整次调用的输入摘要回放**；都没有就失败并报缺口：这个节点只在别的输入下录制过这个服务时是 `inputs_changed`，否则是 `not_recorded`（同样输入的录制已经用完，比如录制的失败已经回放过，不算输入变了）。摘要不含种子（属于请求，回放包里有），也不含 `Limit`：录制的列表回答要得更少的调用，要得更多而录制当时已到上限时报 `limit_exceeds_recording`；读命名输出的调用只从同样限额的录制拿到这些输出，否则每个输出报 `limit_changed`；录制的失败只回答同样限额、要同样输出的调用，只有别的限额的失败时整次调用报 `limit_changed`，只有要别的输出的失败时报 `outputs_changed`；录制要过、服务没写的输出照样缺失，但只对同样限额、同样输出的调用算数：要别的输出的调用里没写，不挡住别的录制写了的值；含 `max_output_tokens`。缺口的 `Kind` 是调用的角色（`model`、`recall` 或扩展自己的）。
  - **服务只看到调用送的输入**。`ServiceCall` 原来带着整个请求的输入（`Request`，从 CandidateQuery.Inputs 沿用），服务可以读任何请求字段，而摘要不含它们：回放的配置去掉一个请求字段后，`memory_list@1` 按它选的列表仍借到旧的答案，报告却说一致；内置的模型算子还漏传了它；每次调用多分配一个空对象。把请求输入放进摘要的话，请求里加一个无关的字段，所有录制都成了输入变了。现在服务要的请求值由算子作为输入送出（召回节点的 `queries`：`"region": "ctx.request.region"`），摘要覆盖服务看到的一切；`memory_list@1` 的 `by_input` 和示例的 `trending@1` 读的是调用的输入，调用里没有这个输入时失败并给出写法；`by_input` 的值是字符串、整数、bool 或浮点（按值打印的写法，`1.25`），和原来读请求值时一样：查询值是一个引用时按它声明的类型发送（规则同“出口交付声明的类型”），float32 的请求字段是 float32，`0.1` 仍选 `"0.1"` 的列表；原来查询按表达式提升后的 float64 发送，打印成 `0.10000000149011612`，选了另一个列表。−0 和 0 选同一个列表，与摘要的等价一致（摘要把它们当作同一个值，原来 `"-0"` 的列表在线选得到，回放却借到 0 的回答还说一致）。双塔召回的嵌入因此是声明的 `list<float32,N>`，`memory_vectors@1` 接受 float32 和 float64 的向量。含义变了，格式升到 `2026-11-21.5`（布局不变）：`.4` 的包里召回可能按请求字段选了答案，摘要不含它，新版本回放这样的包会说一致。请求 id 仍随调用传递，它不改变回答。
  - **调用的其他约束在入口检查**：`ServiceCall.Service` 必须是绑定名（原来算子写错时线上照常、回放按另一个名字找不到）；`Outputs` 为空表示不读命名输出（召回只读追加的项），原来被当作“全部”，召回把服务顺带返回的输出也录了下来。`NamedInput` 构造时拒绝负的维度和少于形状的数据（数据可以是更长的池化缓冲，形状说了算；乘积在超过数据长度后不再相乘，不会溢出），值就是形状的那些元素，余量不属于它：原来摘要按缓冲长度算每行的宽度，形状 `[2]`、缓冲 4 个值时第一行的摘要读了两行的值，第二行读的是余量，回放把改了输入的行当作没变。`Shape` 对服务是只读的（`ReadOnlySpan<int>`）：输入属于调用方，可能被别的调用共用，原来是公开的数组，服务改了它就改了别的调用。工厂不复制形状和数据，调用进行时调用方不改它们，这是契约；反例是调用方构造之后把形状改大，`random@1` 按形状读越界，得到的是客户端异常变成的失败状态，不再为此在每个客户端重复核对。输出名不能重复：回放按名字数一次录制有多少调用读的输出，重复的名字算了两次，选错了录制。客户端不用各自防越界：`memory_vectors@1` 原来按数据长度、不按形状判断向量长度；`linear@1` 先检查缺失，原来读缺失值的空缓冲抛出异常。
  - **放弃调用不等回答的锁**：客户端可能正在 `GetValues` 里从宿主的缓冲池租用（`PipelineExecutor` 接受宿主的 `IBufferPool`，租用可能阻塞），放弃只发布“已关闭、已放弃”两个标志，读取先看标志；正在进行的写入完成到调用仍持有的缓冲里，没有人读。正常结束的关闭仍取锁，保证之后不再从已释放的请求内存租用。生成的 token 数和截断的计数各自隔离监听器的异常，和调用的其他指标一样：原来监听器在这里抛出，成功的召回被当成失败，录成未结束。有逐项键的调用计入 `stratarec.io.keys`（原来只有特征拉取），只在真正发出时：发出前时间已到的调用没有项到达依赖，只计它的超时。
  - **放弃的**：不再录制召回的查询值，只录摘要；查询变了的调用不再“仍按录制回答、报 query_changed”，而是不回答、报 `inputs_changed`。那样回答的列表是对另一个查询的答案，在对比报告里和真正的配置差异分不开；读回放包时校验查询值类型、定长和写法的那套逻辑也随之去掉。新加的节点只借摘要相同的调用，不再在没有时借“最长的列表”，理由相同。回答的状态只有成功和失败，没有本节第一条设想的 `partial`：部分键失败只有特征拉取有，留到第 4 步连接器变成服务时再定。
  - **生成的 token 数和截断对所有服务调用计数**：`stratarec.io.output_tokens`、`stratarec.io.truncated`（原 `stratarec.model.*`），标签是调用的目标；客户端在 `ServiceStatus` 里回报，录制随调用保存，回放返回同样的状态。
- **第 3 步：任何服务都能声明缓存**。服务的绑定可以有 `cache`，形状和含义与特征源的缓存一样（`ttl_ms`、`stale_if_error_ms`、`version`、`memory`、`distributed`）：每个键的寿命是 TTL ±10%（按键的哈希，各实例一致），服务失败或超时时 `stale_if_error_ms` 内的过期值还能用（节点 Degraded），回写不在请求路径上，超过 `memory.max_bytes` 时沿用特征缓存的淘汰规则。实现复用特征缓存的全部机器：进程内的层是一张 cache 模式的本地表，由表的宿主托管和运行写入器；分布式层是同一个存储契约 `ICacheStore`（原 IFeatureCacheStore，它不再只给特征用）和同一个写回队列；记录是同一种缓存记录。服务的表用一个固定的通用布局：每种元素类型一个列表字段（bool、int32、int64、float32、float64、string），再加一个整数列表描述记录里有哪些输出、各是什么类型、多少个元素。这样表的托管、淘汰、压缩、计量和分布式格式都不用为服务另写，服务也不用声明输出的类型。
  - **缓存的单位是调用或项**。没有逐项键的调用（召回、生成、一次性的业务调用）整次缓存；有逐项键的调用（模型打分、逐项校验）逐项缓存：命中的项直接回答，没命中的项合成一次只含它们的调用发给服务，按行的输入按行切出、共享的输入整个送，回答按行拼回。逐项是为了在候选集合不断变化时仍然有用：整次缓存要求同一批项再次出现，一千个候选里只要一个是新的就全部重算。键是 128 位哈希，包含服务版本、调用读的输出（按序）、输入的摘要（和回放用的同一种编码，含 `max_output_tokens`），逐项时再加项的实体；64 位的话，上亿个不同查询的缓存里会有可观的概率把一个查询的答案给了另一个。值的等价和摘要一样（−0 等于 0，NaN 都相同），所以回放认为相同的两次调用，缓存也认为相同。键里还有记录格式的标签（现在是 `stratarec.service_cache/2026-11-21.7`）：记录的布局或键的构成变了就换标签，旧的记录都成了未命中，不会被误读，不需要读旧格式的代码。
  - **键里有绑定的回答身份**：客户端类型和它的设置（不含 `timeout_ms` 和 `cache`）按 RFC 8785 规范化后的内容 id，同一配置在每个实例上一样；绑定写了 `cache.version` 时身份就是它（见 local-tables.md 的“缓存的表只在记录从哪来变了时才换”）。进程内的表也按这个身份区分。原来热加载改了模型的偏置（名字和版本不变）之后，新计划从分布式层读到旧模型的分数，直到 TTL 到期；滚动发布时新旧两种配置的实例也会互相读到对方的回答。超时和缓存设置不改变回答是什么，不在身份里，改它们不会让共享的缓存全部失效。不同部署共享一个后端时，各用自己的键前缀（`redis@1` 的 `key_prefix`）。
  - **键里没有种子、请求 id 和 `Limit`**。内置算子的每次调用都带请求的种子，含了它就不会有跨请求的命中；按种子采样的服务声明了缓存，就是接受同一个答案在 TTL 内被复用。请求 id 不改变回答。`Limit` 和回放同一条规则：记录的列表回答要得更少的调用，或者服务当时就没有更多；要得更多时是未命中，服务的新回答覆盖记录。这假定服务较短的列表是较长列表的开头（契约写在 `ServiceCall.Limit` 上）。读命名输出的调用例外，`Limit` 在它的缓存键里：输出或文本可能说明它被要了几项（“选了 3 项”），原来要 1 项的调用从要 3 项的记录拿到 3 项的张量和“选了 3 项”，要 6 项的调用从已耗尽的、要 5 项的记录拿到“要了 5 项”。回放不把 `Limit` 放进摘要，而是在匹配时要求同样的限额：摘要放了它之后，配置只多读或少读一个输出，整次调用就成了 `inputs_changed`，原来能交付的列表也丢了；缓存只能按键查找，所以放在键里。服务在上限之外多加的项数（`ServiceResponse.Dropped`）只对它被要的那个限额有效：要得更少的命中只写列表的开头，不算丢弃，和守限额的服务一样（原来把记录里超过新限额的项也送进回答，凭空多出丢弃的项）；录制保存这个数，回放同样限额的调用时恢复。覆盖沿用缓存表的规则，版本是写入时刻，本地层只有更新的写入替换记录（慢的旧调用不覆盖新的回答）；同一毫秒里先后写入的两个回答，后一个不替换，代价只是之后再未命中一次。分布式层不保证这个顺序：各进程各有写回队列，存储无条件地写（`redis@1` 是 `SET`），慢的旧回答可以覆盖新的。不改：两个都是同一配置对同样输入的回答，旧的那个写入时刻更早，按它自己的版本更早过期，陈旧仍以 TTL 为界；严格的顺序要存储原子地比较版本，每次写都多一次脚本执行，换来的只是 TTL 之内少一点陈旧。整次缓存的回答生成被截断（`max_output_tokens`，在键里）时照样缓存，命中时状态同样是截断的；逐项的回答被截断时不缓存，截断属于整次调用，不属于哪一项（原来逐项写回，命中时说没有截断）。命中不计 `stratarec.io.output_tokens`，因为没有生成。
  - **命中要有调用读的每个输出**。整次缓存的记录也记下服务没有返回的输出，命中时同样没有，和服务直接回答一样。逐项的回答里有文本（文本属于整次调用）或者输出不是整行时不写回，这样的调用每次都发给服务。命中和服务的回答按输出拼在一起时，元素类型和每项的宽度必须一致：不一致说明服务换了输出却没换版本，调用失败并说明是哪个输出，记录在 TTL 内过期。
  - **按行切输入要求共享的输入首维是 1**。有逐项键的调用里首维等于批大小的输入是按行的，其他输入是共享的，首维必须是 1（或者是标量、文本）；`CallAsync` 对所有有逐项键的调用检查，不只是有缓存的。否则一个首维恰好等于批大小的共享向量会被切开，服务收到错的值；回放的逐行摘要也依赖同一个划分。内置的模型算子本来就把广播的输入送成 `[1, d]`。一行的摘要和缓存键取这一行看到的值：逐项输入取它的那一片，共享的 `[1, d]` 取整个，两者都去掉首维；所以批大小为 1 时（这时共享输入按形状也是逐项的）和多项的批里同一项的摘要相同（原来批大小为 1 时保留了首维，回放把这一项的分数换成了缺口值，缓存多一次未命中；回放包格式 `2026-11-21.11`，缓存键格式 `2026-11-21.3`）。服务按契约把共享输入用于每一项，所以按“看到的值”认同一项是对的；没有选让调用显式标出共享输入，那要给 `NamedInput` 加一个标记，而首维为 1 已经说清楚了。
  - **失败不缓存，过期值只在失败时用**。服务失败或超时，所有没命中的部分都有 `stale_if_error_ms` 内的过期记录时用它们回答，节点记为 Degraded（和特征缓存的读者一样）；有一项没有就整次失败，状态是服务的错误。节点的预算用完或调用方取消照样抛出：节点已经没有时间用任何回答。
  - **录制的是节点得到的回答**：命中和服务的回答拼好之后才结束录制，回放从不读缓存，所以开着缓存录的包回放结果一样。遥测只计真正发给服务的调用：全部命中的调用不是 IO 调用，没有 duration、errors 和 span；拼出的子调用按它自己的项计 `stratarec.io.keys`。分布式层的读是角色 `cache`、目标为服务名的调用，受分布式的 `timeout_ms`（默认是服务 `timeout_ms` 的一半）约束，整个读（分布式层、再到服务）在服务的 `timeout_ms` 内；服务没有 `timeout_ms` 时分布式层必须写自己的。缓存指标和特征缓存的同一组：`stratarec.source` 是服务名，`stratarec.entity` 是 `answers`。
  - **本地层的命中按调用分配，不按项**：本地层全部命中的调用约 1.5 KB（含测试里的请求状态和回答），10 项和 1000 项一样，和一次发给服务的调用相当（不计服务自己的分配）；键、行状态和回答的缓冲从请求内存租用，逐项的记录在钉住的表版本里原地读，不复制。`ServiceCacheAllocationTests` 守住这一点。分布式层的读按项分配（每个键一个文本、记录的数组、解码出的记录，1,000 项约 130 KB），和它的网络往返相比可以忽略；要去掉得让存储接收结构化的键，只在传输时编码，现在不做。
  - **记录只有格式完全是这份代码写的才读**（种类、头部、每个输出的类型和元素数，以及各列表恰好有那么多值）。存储也有别的进程在写，外层合法、类型码越界的记录原来在拼回答时抛出，回写还把它复制进本地层，之后每次命中都抛。节点已经不能发出调用（预算用完、调用方取消）时缓存也不回答，和没有缓存的调用一样抛出取消；原来本地命中照样回答。服务的 `timeout_ms` 是一个绝对截止时刻，分布式层和服务共用：读取在服务的截止处被截断时不再调用服务，原来服务又拿到至少 1 ms 的新截止被调用。分布式的记录按读取应答的时刻判断新鲜，服务失败时过期值按失败的时刻重新判断是否还在 `stale_if_error_ms` 之内（和特征的缓存一致）。服务没写的字符串槽（null）原样交付、不缓存，原来编码时抛出，已经成功的调用失败。回答里服务在上限之外多加的项数（`ServiceResponse.Truncated`）随记录保存，冷调用和命中都和服务直接回答时一样。有逐项键的调用里，形状是逐项的缺失输入按行切，子调用收到子批大小的形状；缺失输入的形状也受逐项或共享的检查（原来原样转发整批的形状，服务拒绝）。缓存用过期值回答使节点 Degraded 时，原因随调用录制，回放时节点同样 Degraded；失败的回答按服务给的状态录制（生成的 token 数、截断），和没有缓存时一样。回放包格式因这些变为 `2026-11-21.6`（`.5` 在负零和 float32 查询上的发送方式也和现在不同，旧包可能回放出“一致”）。广播输入（`[1, d]`）在批大小为 1 时的键见上一条。

  - **不做的**：按服务的签名建类型化的表（签名是可选的，读的输出和宽度在回答时才知道；通用布局什么都能放，代价是记录里多一个小的描述列表）；缓存失败（失败不是回答）；部分输出的合并（两个节点读不同的输出时是两条记录，不会互相覆盖）。
- **同一个请求对同一条缓存记录只问一次源头**（`RequestReads`，2026-11-27）。页面的每一行调用一条栏目流水线时，这些运行读同一个用户的特征、调同一个不带项的服务、甚至以同样的输入调同一条流水线。缓存层给不了一次运行正在向源头要的、和刚要到还没回写的记录，所以各层都没有新鲜记录的读，在去问源头（连接器、服务、流水线的运行）之前加入这个请求对这条记录的读：第一个去问，同时到的等它，之后到的直接拿。只有声明了缓存的读才共用：没有缓存的调用没有键，合并它等于替使用者决定两次调用是一次。范围是一个请求自己的调用树，或者宿主结成一组的几个请求（见下）；回放不共用（回放不读缓存）。每个请求都有这份共用，不看它的计划里有没有调用别的流水线的节点：原来只在有这种节点时才建，一次运行里两次相同的调用合不合并，就取决于计划里一个可能从不运行的节点。代价是每个请求多四个小对象（共用对象、它的组、一把锁和一张还没有分配桶的字典），是请求级的固定开销。顶层流水线失败后改跑的后备流水线在同一个请求里，接着用它。
  - **各读各的缓存层，只合并问源头的那一次。** 每次读按自己的计划和时效读进程内层和分布式层，所以它手里有自己失败时回退用的过期记录。没有选在读分布式层之前就合并（能少几次存储读）：等的一方要到读的一方问完源头才拿得到那一层的过期记录，自己的时间先到就什么都没有；同一张表在两个计划里还可以绑不同的存储。代价：N 次运行在进程内层未命中时读 N 次分布式层。
  - **只共用成功的记录，拿的一方按自己的时效判断。** 共用的记录和缓存层的记录一样对待：按自己的 `ttl_ms` 还新鲜、回答得了这次调用才拿，否则自己去问。所以拿到的是这张表里一条成功的记录，不保证和自己去问源头一样：自己的计划发给连接器的字段会被拒绝时，它照样拿到别的计划读到的记录，和从缓存层读到时一样。记录留到请求结束；它在请求途中过期之后（`ttl_ms` 比请求还短）到的读各自问源头，不再共用，回写落地后它们在缓存层命中。失败不共用：一次失败是一次调用在自己的预算里、按自己的计划得到的（流水线为后备留出时间而提前失败；同一张表的两个计划发给连接器的字段不同），等的各方自己去问，得到自己的结果和完整的失败状态。没有选把源头的失败发给等的各方（服务刚失败时少问几次）：做过，等的一方因此得到了它单独调用时不会得到的失败。代价：源头故障时每次运行各失败一次，和不合并时一样，只是晚一次等待。读的一方没有拿到可共用的记录就撤回，等的各方自己去问并且不再等别人，所以每个读最多等一次，不会排成一串。等的这一次算在自己的时间里：读的一方慢而自己的预算短时，它在等待里超时，单独去问本来来得及。
  - **只合并整条记录、同样条数的读**：上下文实体的特征、没有逐项键的服务调用、流水线调用。逐项的读（候选的特征、带项的服务调用）不合并：两次运行的候选只是部分重叠，按键等待是按行的开销。服务调用的条数（`Limit`）不在记录的键里（长的回答能答短的调用），但在合并的键里：服务会拒绝大的条数而回答小的，先到的短回答留在请求里，后面要得更多的几次调用就无从共用。
  - 等待和一次调用的等待一样受自己的上界约束：自己的定时器加调用方的令牌（`BoundedCall` 的做法），不靠上界的令牌回调，那个令牌算子也能登记回调；时间已到的读不拿已有的记录，它本来也发不出调用。共用到的命中在 `stratarec.cache.keys` 里算在 `request` 这一层，按自己的时效已经过期的算 `expired`。流水线调用共用到的结果和跨请求的命中走同一条路：带 `cached_from`，曝光照常写。
  - **一层也不写的缓存（`"cache": {}`）不保留记录，只让一个请求里的读共用**（2026-11-28）。合并需要的三样东西（记录的键、记录的格式、使用者说过“两次相同的调用可以当一次”）正是声明缓存给出的，所以没有另设开关，而是让缓存可以不带层：数据源和服务的绑定、调用流水线的节点都这样写，节点不需要绑定里的 `pipelines`。它不写 `ttl_ms`：记录只活到读到它的那个请求结束。绑定上给了时间或 `version` 却没有层，报一个错误（`CACHE_TIERS`），不管那些值本身对不对：先要定的是它们还用不用得上；提示里加层的那条路在没写 `ttl_ms` 时带上它（给出的值本身合法时，照着改一次就过）。节点上没写 `ttl_ms` 却给了另两样，同样只报一个（`CACHE_TTL`）；写了 `ttl_ms` 就是要保留结果，各个值照常各自校验，绑定里没有层仍是 `PIPELINE_CALL_CACHE_UNBOUND`。没有选的：和另两层并列的第三层（另两层一声明请求内就共用，它只在单独出现时才有意义）；无层也要求 `ttl_ms`（一个没有意义的必填项）。
    - **只对合并得了的读生效**（`FeatureSourceResolver.Caches`、`ServiceCallPath`）：上下文实体的特征、不带项的服务调用、流水线调用。候选的特征按没有缓存的 `fetch` 读（只拉节点要的字段，照常预取），带项的服务调用走没有缓存的路径：它们本来就不合并，走缓存路径只是给每个键编一条没有人保留的记录。代价：上下文实体那一组仍然拉整条记录，只有一次运行的请求也一样；共用的是整条记录，读不同字段的几条流水线才用得上同一次读取。
    - **它的表是它自己的**（`CacheTableOptions.Kept` 进表的身份），和同一来源、只有分布式层的缓存不是同一张表，两种缓存的读不合并：合并了，保留记录的一方会拿到不保留的一方读到的记录，自己的层没有写入，下一个请求再问一次源头。表总是空的，不报大小（它的零会盖掉另一份绑定里同一来源、保留记录的那张表的读数，两者的指标标签相同）；读照常查它一次，没有为“宿主自己往这张表里写了记录”加分支，没有东西会往里写。
  - **宿主同时发起的几个请求可以结成一组（`RequestGroup`），共用的规则和一个请求内相同**（2026-11-28）。一页的信息流和推广位各是一个请求时，它们同时到、读同一个用户，缓存层这时都还没有记录，各问一次源头。宿主给这几个请求同一个组对象（`RecRequest.Group`），它们的读按上面的规则合并，只有一次运行的请求也一样；流水线调用拿到组里别的请求算出的结果时，`cached_from` 写的是那个请求。每个请求仍有自己的截止时间、输入、臂和结果。
    - **一条记录只在读到它的那个请求还在进行时属于这个组**（`RequestReads.End`）：那个请求结束，它就离开，不管有多少别的请求拿过它。没有选让记录跟着组对象存活（那样先后发出的请求也能共用）：宿主把组做成单例、或者按会话长期持有时，不保留记录的缓存永不过期，内存只增不减，而且很难发现。也没有选“用过它的请求还有一个在进行就留着”（做过）：一个接一个重叠的请求会把同一条记录一直传下去，不保留记录的缓存在持续的流量下再也不问源头，记录能活多久说不出一个界。现在一条记录活不过读到它的那个请求，组留着的只有字典到过的容量，组对象不需要释放，怎么持有都一样。代价：先后发出的请求不通过组共用，那是缓存层的事；读到记录的请求先结束、别的还在进行时，后面的读再问一次源头。
    - **请求结束时还在途的读不撤回，只是离开组**。算子发起调用却不等它就结束时，请求返回了，这次调用还在进行：框架不在尝试结束时终止它，它照常进行到自己的时限，写日志，写缓存层；它读的还是请求的内存（调用方给的列表输入、响应的缓冲），所以带缓存的服务调用和流水线调用从开始到结束都持有请求内存，和特征拉取一样。组和缓存层一样对待它：后来的读在组里找不到它，已经在等它的读照样拿到它读到的记录，`cached_from` 写的是这次运行所在的请求，和这次运行自己写进缓存层的那条记录写的一样（那次运行的日志在那个请求名下；那个请求自己的追踪和录制里没有这次调用，节点结束时它还没有回答）。撤回做过：等着的读各自再问一次源头，同一个结果算两遍，后写进缓存层的可能是先开始的那一遍；同一个请求里等着它的另一次调用，还会在请求返回之后才去发自己的调用。请求结束之后才开始的读只为自己读（单独的请求也一样），所以组里不留已结束请求的东西；请求结束时也放开它读过的记录，一次没等的调用留住请求的对象时不会连带留住它们。
    - **不写日志的请求不入组**（强制臂、配置覆盖、捕获日志）：别的请求拿了它算的结果，按 `cached_from` 去查，日志里没有那次运行。它仍然在自己的调用树里共用。
    - 没有选一次传入几个请求的批量接口（不需要新类型，也没有存活期的问题）：每个请求要有自己的截止时间和取消，宿主也常在不同的地方发起它们。
- **第 4 步：所有外部调用共用一份有界等待，特征连接器保留自己的契约**。服务调用、连接器调用和分布式缓存的读取都经过 `Core.Threading.BoundedCall`（规则和合并的理由见“所有外部调用共用一份等待实现”一条），原来的三份（`Pipeline` 的 `BoundedCall`、`FeatureFetcher` 的 FetchCancellation/IoLease、缓存读取的 `StoreCall`）去掉，源码净减约 150 行。原计划这一步把连接器改成服务、让逐项回放也只剩一份；做的时候判断这两件不值得做：
  - **连接器不改成服务**。连接器通过 `IFeatureBatchWriter` 按键写有类型的值：每个值可以缺失，列表长短不一，有字符串，键可以有多个部分，部分键失败（`FailedKeys`）。服务契约传的是张量；要承载特征，每个字段得带存在掩码、列表偏移，键的各部分作为输入，每个写连接器的人都要手写这些编码，引擎再解回来。代价落在写连接器的人身上，热路径上每个值多一次编解码，使用方得不到新能力：预取、跨节点去重、延迟物化和回填本来就在 `FeatureFetcher` 里，和契约无关。两者真正要共用的都已共用：有界等待（这一步）、遥测和工厂注册（第 1 步）、缓存的两层（第 3 步：cache 模式的本地表和 `ICacheStore`）。
  - **逐项回放不合并成一份**。两份守同样的规则：先用录制里同样的那次调用（占用），否则逐项取自任何一次成功的录制调用，缺口名字一致（`not_recorded`；服务的项带输入，多一个 `inputs_changed`；特征的值可以放宽类型，多一个 `type_changed`）。不同的是值：特征的值是每个（键，字段）一个 `ScalarValue`，可以缺失（这是回答，不是缺口）或是列表，字段的类型放宽时写入前转换；服务的输出是每项定宽、类型固定的张量切片，原样复制，录制里没有的填缺口值（NaN、零）。合成一份要在两种值模型之上加一层抽象，比任何一边的循环都大；修复需要共用的是规则，记在这一条和“回放”一节。特征调用有了键以外的输入时（第 5 步）再看：那时特征的回放也要按（键，输入摘要）匹配，共用索引才划算。
  - **行为变化**：没来得及发出的服务调用不再计一次超时（特征一直如此）；被作用域的上界截断的调用的错误是 `timed out: the time budget ran out`，健康和请求事件里每次超时都有原因（原来服务调用的这种超时没有，特征的是 `source '…' timed out after N ms`，抛出的异常现在写成 `threw IOException: …`，带类型名）；分布式层的令牌带上分层自己的截止（在拉取的截止之前时，每块一个取消源和计时器，约 210 B）：`redis@1` 在令牌上等待，慢的读取到分层的截止就结束并归还请求内存，原来要等到拉取的截止；调用点先记录调用，宿主的监听器后看到它（见“宿主监听器……”一条）。
  - **实验分配的 provider 也走这份等待**。请求路径上自己等待的只剩它：约 120 行，守着和 `BoundedCall` 一样的规则（同步的回答按观察到的时刻判断，等待超时之后才到的回答不用，令牌活到 provider 结束，回调在线程池上运行），是一条条修出来的第二份。现在它是一个调用点（`RecEngine.ProviderCall`），上界是请求的截止；分配在执行之前，provider 不写请求的任何东西，所以 `RunAsync` 的请求内存可以为空。随之变化的：provider 有了外部调用的遥测（`assignment provider` 的 `stratarec.io.*`、span、健康状况和请求事件），实验平台变慢或不可用第一次能在指标里看到；令牌回调的失败和其他令牌的一样计数并进入请求事件的汇总（主体 `assignment`），不再单独写事件 1102；引擎去掉了等待计时器的测试钩子（AssignmentWaitTimers），竞争的先后由 `BoundedCallTests` 守住，引擎这边只测行为。provider 回答 null 仍然是没有臂（`ExternalArms` 本来这样读，契约说回答里的问题都不是错误）。顺带修了截止时刻的溢出：开始时刻加上极长的截止（`TimeSpan.MaxValue`）溢出成过去的时刻，执行器的每个节点立即超时，等待 provider 时 `WaitAsync` 抛出 `ArgumentOutOfRangeException`；现在超过计时器上限（约 49.7 天）的截止就是没有截止（`CallBound.DeadlineAfter`）。
  - **两道截止都过了才返回的同步客户端，归给先到的那一道**：调用自己的超时只在发出时就早于作用域的上界（它有自己的取消源），或者按它自己的时钟过了而上界没过时才算；原来先检查它，节点预算先到时也算服务超时，算子拿到失败状态而不是预算的取消。等待一开始就结束（调用方在分批的同步部分取消）而连接器还在跑的分批，视图不交给下一批：连接器可能还在写，原来按“调用已完成”把视图重绑到下一批的键。连接器抛出的异常只由共用的等待读一次，拉取的错误用它抽出的文本（`source '…' failed: threw IOException: …`）；原来又读一次 `Message`，第二次读会抛的异常从拉取里逃了出来。缓存这边：比本地过期值更新的分布式过期记录留着，服务失败时兜底；记录头的字段之间的关系也校验（项数不超过当时被要的限额，列表满了才有丢弃的项），丢弃的项数到 `int.MaxValue` 为止；只由缓存回答的调用交付前再判断一次节点还能不能发出，和服务的同步回答一样。回放摘要又只描述输入，见第 3 步的 `Limit` 一条；回放包格式变为 `2026-11-21.7`，录制带上丢弃的项数。`ServiceResponse.Truncated` 改名 `Dropped`：它是丢弃的项数，和 `ServiceStatus.Truncated`（生成被截断）是两回事，同名容易看混。不改的：分布式层的回答身份只含绑定写的内容，不含它引用的文件（`memory_list@1` 的 `data_file`）的内容。两个部署共用前缀而同名文件不同，或者同一部署更新了文件，TTL 内仍读到旧的回答。这是声明缓存接受的：服务背后的数据（文件、模型服务的权重）在 TTL 内变了，缓存都看不到。要让一次数据发布作废缓存，按数据怎么发布来定：按文件发布的（`memory_list@1`）换一个带版本的 `data_file` 路径，路径在绑定里，进身份，新实例读新文件，键也跟着变（这个客户端在创建实例时读文件，不换路径的话，不开缓存也读不到新内容）；模型的版本由算子放进调用（`ServiceCall.Version`），进身份；滚动发布时还可以换部署的键前缀隔开新旧实例，但前缀不让已经在跑的客户端重读什么。把文件内容放进身份，要每个客户端报告它依赖的外部内容，现在只为一个示例客户端，不值得。
  - **发出的边界在调用开始之后再看一次上界**：开始调用会运行宿主的代码（`ActivityListener` 的采样和开始回调），它可能取消请求或用掉剩下的时间，原来采样器取消了请求，provider 照样被调用（拿到的是已取消的令牌）；这样没发出的调用有一个宿主已经看到开始的 span，以 cancelled 结束，指标和健康不计。哪道截止先到在宿主的代码运行之前判定：两道都在宿主的代码里过去时，调用算先到的那道截断，和发出的调用一样（第一版算作作用域的上界，算子看到的是预算用完，而不是服务超时）。调用方取消时，`ExecuteAsync` 抛出的取消带调用方的令牌：客户端或 provider 遵守了引擎给它的令牌（和调用方的相连）时，抛的是那个令牌，宿主按自己的令牌匹配会漏掉；在引擎的边界换成调用方的，原来的作为内部异常，所有路径一处处理；文字是固定的，不读原来异常的 `Message`，扩展的异常可能在那里抛出。`ObservedCancellationSource.CancelAfterObserved` 把延迟截到计时器接受的上限（负数立即取消，`Timeout.InfiniteTimeSpan` 仍是不设时间，和 `CancelAfter` 一样）：`TimeSpan.MaxValue` 的截止在配置覆盖的编译里还会抛出，而且那时刚开的租约还在清理范围之外（现在在 try 里）。回放：节点的录制先取同一限额的那次（失败也照录制交付），再取别的限额里能回答它的成功（列表够长，或者服务当时就没有更多）；别的限额录到的失败或截断不回答这个调用：服务可能只在超过某个限额时失败（上限、开销），那次失败说明不了这个限额。这时别的节点在这个限额录到的成功回答它，都没有时是整次调用的 `limit_changed` 缺口。原来先录的另一限额的失败盖住了同一限额的完整回答；第一版修复让只读列表的调用仍取别的限额的失败（理由是限额只限制列表），它同样盖住别的节点在这个限额的成功，才改成上面的规则。不能回答的录制也不占用：原来先占用再发现回答不了，之后同一限额的调用就拿到它后面那次录制。另一限额的录制只交出列表的开头，不带它的生成细节（token 数、生成截断），那些描述的是它在自己的限额下生成的东西。录制的丢弃项数要合乎服务能给的样子（正数，回答成功，列表是满的），否则在 `/dropped` 报 `ReplayBundleException`，和缓存记录头的校验一致。服务的时间被分布式层用完之后用过期值兜底，交付前也判断一次节点还能不能发出，和只由缓存回答的调用一样。等待是否设置好用任务的身份判断（`WaitAsync` 对已完成的任务返回它自己），不再用“两个都完成了”：设置好的等待和客户端在判断之前都完成时，原来按“没设置等待”观察客户端；两条路径都按同样的条件判谁先到，只在计时器的抖动之内结论不同，所以没有专门的测试。不改的：缓存的过期命中在 `cache.keys` 的同步监听器里被取消时仍然交付：复查通过的那一刻就是框架接受回答的时刻，和直接调用观察到回答之后才运行遥测一样。
  - **度量**：请求的耗时在误差之内（`FeatureSupplyBenchmarks` 5,000 个候选的拉取 1,951 → 1,977 µs，误差 ±100 µs；`PipelineBenchmarks` 基线 5,000 个候选 2,100 → 2,059 µs）。每个请求多分配约 50 B：每次拉取的上界多存两个令牌（自己的和调用方的，原来拉取的取消源不存，调用方的令牌另外传），一个请求有两三次拉取。同步回答的分批仍然不分配。异步回答的分批约 1.19 KB，原来 1.14 KB，多出的是状态机里的调用结果（比 `FetchStatus` 大）和调用自己的截止；合并后的第一版是 1.31 KB，状态机把结果、请求内存和客户端的令牌也留过了等待，现在只留等待之后要用的，`AnAsynchronouslyAnsweredChunk_CostsItsWaitAlone` 守住这一点。
- **第 5 步：实体可以由参数计算，不只按键查找**（回放包格式 `2026-11-21.8`）。实体声明 `args` 代替 `key`：参数名到请求输入或上下文特征（`ctx.user.ctr_30d`，先取到），类型不限（列表、浮点数、文本）；它的特征来自 `"mode": "service"` 的来源，来源指向一个服务（`"service": "engagement_model"`），每个请求调用一次：没有项、不追加，参数是输入（标量的形状 `[]`，列表 `[n]`，缺失的值照常作为缺失送出），每个特征的 `field` 是它读的输出。键最多 8 部分、只能是 int64 或 string，业务服务要的输入超出键（一段查询、一个向量、最近点击的列表）时原来只能写算子；现在它是普通的上下文特征，表达式、条件、日志、输出和召回的查询都能读，计划只在有人读它时调用。
  - **走服务的调用路径，不扩展连接器**。有参数的特征本身就是一次服务调用：缓存（按参数的摘要做键，参数相同的请求共享答案）、回放（按整次调用的摘要）、有界等待、遥测都用服务那一份。为此把算子的调用路径抽成 `ServiceCallPath`：调用方只提供作用域（上界、请求内存、录制或回放、Degraded 报给谁），节点和特征来源各一个，回放、缓存、录制、等待只有一处。连接器的契约是按键批量的，塞进参数要扩展 `EntityKeyBatch` 和每个连接器；第 4 步说的“特征有了键以外的输入时共用逐项回放的索引”因此不需要做：有参数的实体每个请求一次调用，不逐项。
  - **有参数的实体没有键**，所以只有 `service` 来源能供给它，`service` 来源也只供给它（`SOURCE_SERVICE_ENTITY`）：表、连接器和特征缓存都按键寻址，要缓存就在服务的绑定上声明 `cache`。一个 `service` 来源可以供给几个实体，每个实体一次调用，录制记下来源和实体，回放时每个实体的调用像节点的一样先用自己的录制（只按来源和摘要匹配时，读另一些输出的实体拿到了对方录制的失败；第一版修复限制一个来源一个实体，换一次配置照样会串；按要的输出分开也不够，参数和输出都相同的两次调用，回放时预取的先后一变，一次瞬时失败就交给了另一个实体）。服务缓存不分实体：参数和输出都相同的调用共用成功的应答，那是同一个回答。参数读的特征和键读的特征一样先取，环的检查也一样（`ENTITY_KEY_CYCLE`）；参数的错误是 `ENTITY_BAD_ARGS`，指到那个参数，候选级的值（`col.*`、候选特征）不能作参数，因为调用每个请求只有一次。
  - **失败**：参数读的特征失败时，实体的特征失败，不调用服务，和外键一样：失败的特征没有可信的值，作为缺失送出会把“不知道”说成“没有”；参数 Degraded 时特征 Degraded；值缺失（特征正常而没有值、请求没带）照常送出，由服务决定。服务失败、超时、回答了特征接不住的输出（另一种类型，标量给了多个值）时特征失败，原因里有来源、服务和输出名；缓存用过期值回答时特征 Degraded，回放一样。输出的类型就是特征声明的类型，和模型输出是它的列的类型一样：不放宽、不舍入（development.md 的边界规则；原来 int32 放宽成 int64、float64 舍入成 float32 特征，训练那边未必这样转）；类型不对时调用失败，错误里说特征要什么类型。文本输出和字符串张量都给字符串特征，这不是转换。一个字段的两个特征因此要同一个类型。
  - **来源的 `timeout_ms` 约束整次调用**（默认 50 ms，和 `fetch` 一样），服务自己的 `timeout_ms` 在它之内：原来只受请求截止约束，慢服务让读它的节点一直等到截止，输出就没有时间了。
  - **录制为来源的调用**：`source` 是来源名，`entity` 是算的实体，没有 `node`，角色 `fetch`；回放先用这个实体自己的录制，节点和来源都有、或者只有其中一个的录制被拒绝。调用方在回放里的键是节点 id 或 `source:<来源>/<实体>`，两个名字各按 JSON 指针的分段转义，因为名字里可以有斜杠（原来来源 `a/b` 的实体 `c` 和来源 `a` 的实体 `b/c` 拼成了同一个键），匹配时连同调用方的种类一起比较：不经计划编译器检查的节点 id 可以拼出来源的键。
  - **示例**：`engagement` 实体由用户的 CTR 计算，`linear@1` 接受不带批的标量调用，算一次；读它的 `engagement_boost` 是单独的节点，`on_failure: skip`，算不出来时照常排序，不让排序多一个硬依赖。
  - **失败的上下文调用不再读暂存区**（重构时把读取挪到了判断失败之前，被放弃的连接器还可能在写；原来先判断）。节点的服务调用直接交回共用路径的任务，不再多一层 `async`（同步回答的调用从 176 B 回到 88 B）。同一个字段的两个特征只向服务要一次这个输出，各自按自己的类型取。服务没写的字符串列表元素让特征失败（写进上下文的空元素到了下一个调用的摘要里，录制抛异常）。调用带上请求 id 和种子，和节点的调用一样。录制里被调用方取消的来源调用回放时仍是取消（回放的调用方没有取消，原来按超时报告），回放抛出的截断带上录制的结局。来源的调用没有同步完成时交给拉取的 I/O 跟踪，`WhenIoCompleteAsync` 等它结束，和连接器的一样。目录的环检查不再把派生特征当作边：派生特征读什么在它的表达式里，不在它的实体上，经过它的环由计划编译时检查（原来参数读本实体的、只由请求输入算出的派生特征也被报成环，键的部分一样）。目录 Schema 要求实体恰好有 `key` 或 `args` 之一，`args` 至少一个参数。回放按调用方的种类和键一起匹配：不经计划编译器检查的节点 id 可以拼出来源的键。
  - **录制记下每次调用要的输出**（回放包格式 `2026-11-21.9`）。服务没写的输出是它的回答：同样配置的回放照样缺失，不报缺口，也不从别的调用借这个输出（原来报 `not_recorded`，另一个来源录到过这个输出时还借来改了值）；录制的失败只回答要同样输出的调用，因为服务可能只对某些输出失败（不认识的名字），只有要别的输出的失败时整次调用报 `outputs_changed`。格式升级也挡住了来源开始带种子之前的包：那时的服务没收到种子，回答不能当作现在的。追踪里的截断按真正过期的那道截止归因，两道都过期才用追踪之前的先后；给客户端的令牌按追踪之后剩下的时间重新选，缓存的时钟可以被宿主拨动（原来用追踪之前的先后，分布式层没有自己的计时，迟到的记录盖过了连接器的值；只过了作用域的上界却算成调用自己超时）。验证调用时遇到的取消仍是取消的任务，和 `async` 方法一样。目录 Schema 把写成 null 的成员当作没写，和目录一致，`key` 只能是引用或引用的列表。不改的：来源的超时判定之后、在遥测回调里才到的调用方取消，线上报“取消”（重读了令牌）、回放报录制的“超时”，只有错误文字不同；要一致得让截断的结局一路传到来源，为一个只在遥测回调里出现的时序不值得。
  - **来源的调用录下实体**（回放包格式 `2026-11-21.10`），理由见上面“有参数的实体没有键”一条。服务没写的输出只回答要同样输出的调用：服务可以看要了哪些输出再决定写什么，要 `[label, score]` 时没写 `score`，不说明只要 `score` 时也不写，原来这个省略挡在了正好写了 `score` 的录制前面。重组批次的调用同理：每一行的录制里服务没写的输出，照样不写，不报缺口，也不再因为“没有录制的输出”失败；同一次调用里有的行有这个输出、有的行没写，应答只能整列有或整列没有，没写的行拿缺口值并报缺口。另一个限额下没写的输出报 `limit_changed`，和写了的一样。索引拒绝录制器写不出的录制：`requested` 里重名、录了没要的输出或文本、只有来源或只有实体。缺了 `requested` 读作空列表，不另外要求：它和录下的输出对得上就是自洽的记录，对不上的组合都已经拒绝。验证调用时的取消用异步方法的任务构建器，任务是取消的，等待时抛出原来的异常。
  - **另一个限额下没写的输出**，只有要的输出也相同时才报 `limit_changed`，要的是别的输出就是 `not_recorded`。一笔录制和当前调用要的输出是否相同，按调用记住结果（回放在锁里，一次只比一个调用）：原来每看一个没写的输出就比一次两个列表，512 个输出要读 1,027 次列表、回放一次 359 ms，重组的调用还要乘上行数。
  - **结局、上界、摘要和回放的细则**（每条是一处改正，和它之前的行为）：
    - 客户端自己取消、框架的令牌都没有触发时，是客户端的失败（`Threw`，结局 timeout），不是调用自己的截止到了：分布式缓存的存储用自己的令牌取消了读，原来被当成服务的截止，服务还有时间却没被调用。只有真正的截止才用掉服务的时间。
    - 一次拉取的上界在建暂存区之前开始计时：原来建完才开始，暂存区花的时间加到了截止上，分批在请求截止之后还发了出去，迟到的值写进了表。
    - 存储的读由一处（`DistributedCacheTier.ReadAsync`）发出并消费，同步完成的也取一次结果：存储可以把背后的对象放进池里，取结果时才收回；服务的缓存原来只看了状态。
    - 回放记住“这笔录制要的输出和当前调用是否相同”只到这次调用结束（按调用的序号，不按调用对象）：调用的内容归调用方，可以复用对象和数组去做下一次调用，原来按对象记住，复用的调用拿到了上一次的回答。
    - 回放把 `service` 来源供给的字段计入特征统计（比较报告的缺失率），规则和拉取的一样：每个字段读一次，调用失败或服务没写时算缺失，在默认值之前。原来不计，缺失率偏低。
    - 键（或参数）读上下文特征的组，在其中一个失败时立即失败，不等其他的：等组的任务的读者（召回的查询值）和依赖它的链式组马上知道。按闭包等待的读者（`EnsureAsync`）仍等闭包里的每个特征，因为它返回整个闭包最差的状态，要每个都已确定，和提前计算的衍生特征一样。
    - 重分批回放的行索引按服务和版本只建一次：录制只读不改，占用过的也还有它的行；原来每次调用都重建，4,096 行按 32 一批回放分配了 187 MB。
    - 一个组要的输出名（字段去重）由组建一次：一个来源供给几个实体时，原来只记住最后一个组的，每次换实体都重建。
    - 一项看到的每个输入先各自摘要成 128 位，再按名字顺序组成这一项的摘要或缓存键；所有项看到的都一样的输入（共享的 `[1, d]`、标量、文本）每次调用只算一次，只有按行切的输入逐项算。43bdf97 把共享输入按“这一项看到的全部”放进逐项的摘要，结果每一项都把整个共享向量重新哈希一遍：2,048 项、4,096 维的共享向量全部命中缓存时也要几十毫秒，用完了节点的预算；录制和回放同样如此。摘要的编码变了，回放包格式升到 `2026-11-21.12`，缓存键升到 `stratarec.service_cache/2026-11-21.4`。多一层哈希的代价是每个按行的输入每项多一次 128 位的收尾，比重复哈希共享向量小得多。
    - 拉取的上界由一个绝对时刻建立：取预算的同一时刻算出截止（来源的超时和请求截止里早的那个），之后无论隔多久建上界都在那时结束。43bdf97 先算预算再建上界，中间读录制钩子的时间仍会加到截止上。暂存区在释放上界的 `try` 里建立：宿主的缓冲池在租借时抛异常，原来留下上界的计时器和调用方令牌上的注册。上下文拉取和缓存读同样改了。
    - 客户端自己取消时，错误信息是固定的“它自己取消了调用，在截止之前”，不读异常的 `Message`：取消异常的消息通常只是 “The operation was canceled.”，说不出是谁取消的；`Message` 又是异常可以重写的属性，在请求线程上读它没有必要。别的异常仍读 `Message`，那是说清失败原因的唯一来源；异常类型由客户端决定，`Message` 阻塞的客户端是它自己的缺陷，不为它设防。
    - 同一个服务来源、同一个实体的两个特征读同一个输出、而没有一个回答能同时满足它们时，是加载错误 `SERVICE_OUTPUT_TYPE_CONFLICT`（按名字顺序报在后一个特征的 `type`）：服务对一个输出只回答一次，特征只接受声明的类型，原来计划能加载，每次调用都失败。只比较计划读的特征，不比较目录里所有的：服务的调用只问读到的输出。
    - 回放给每次调用一个从未用过的序号，调用期间发出的另一次调用（算子的代码可以在交出的输出名的 getter 里再调用）结束后，恢复外层调用的序号。原来只有一个计数器，外层接着用内层的序号，把内层对另一组输出的比较当成自己的，错过了自己的录制。
    - 提前计算的上下文依赖检查在都已存好时不分配：等待是静态的局部函数，参数显式传入，原来闭包每次都分配 32 B。
    - 一项看到的输入只有超过 16 个值（或是文本）时才摘要成 128 位，少的直接编码进这一项的摘要或键。f0f6871 把每个输入都摘要一次，逐行的标量每项多一次哈希：2,048 项、32 个逐行标量的调用，键和行摘要都慢了约一半。用哪种形式只取决于这一项看到的内容（值的个数），所以一批和多批里同一项仍然相同；大的共享向量仍然每次调用只哈希一次。现在 32 个逐行标量的键 1.75 ms（f0f6871 是 2.63 ms），1,024 维共享向量加 8 个逐行标量 0.51 ms（0.74 ms）。也试过把输入的名字、类型、形状每次调用只编码一次作为每行哈希的种子，没有可测的收益，没有采用。格式升到 `2026-11-21.13`，缓存键升到 `2026-11-21.5`。
    - 同一个输出的几个读者冲突的条件是元素类型不同，或者都约束了长度且长度不同（标量算 1，定长列表算它的长度，变长列表不约束）。f0f6871 比较整个类型，把同一个 `topics` 读成 `list<int64>` 和 `list<int64,2>` 的计划也拒绝了，而一个长度为 2 的回答两者都能接受。
    - 缓存读先读宿主的时钟、再建上界：宿主的 `TimeProvider` 抛异常时原来留下上界的计时器。
    - 字符串张量和文本一样总是摘要：字符串的大小不是它的个数，一个共享的 196 KB 字符串按“一个值”内联，每一项都重新编码，2,048 项的全命中要 27 ms。内联的上限从 16 个值降到 4 个数值或布尔值：32 个 16 维的共享向量逐项内联比摘要慢 7 倍（分段之后又回到 16，见下面“内联的上限回到 16”一条）。
    - 每次调用先把各项的摘要或键排成若干段（`Segments`）：一段是所有项都一样的字节（共享输入的编码或摘要、按行输入的头部），在调用开始时编码一次，每一项只复制它，再接上这一项自己的那部分（几个值，或切片的摘要）。字节和逐个输入编码完全一样，只是不再每项重复编码相同的部分。和 3a0d9e8 比（2,048 项）：32 个逐行标量 1.75 → 1.26 ms，32 个 16 维共享向量 3.69 → 0.11 ms，32 个逐行标量加 20 个共享标量 2.96 → 1.30 ms，共享的长字符串 27.4 → 0.41 ms。格式升到 `2026-11-21.14`，缓存键升到 `2026-11-21.6`。
    - 一次服务调用的输入名必须唯一，调用入口拒绝重复的名字（`ArgumentException`，和重复的输出名一样）：服务按名字读输入，取第一个；摘要和键按名字顺序取所有输入，两个同名的输入换个顺序就是同一个键，服务看到的却不同。先比较名字的哈希（256 个以内不分配），只有哈希相同时才逐个比较。
    - 内联的上限回到 16 个数值或布尔值。上限定为 4 的理由（共享的内联视图每一项都重新编码）在分段之后不存在了：共享的视图只编码一次，每项复制它的字节再一起哈希，16 个值也只是 0.4 ms 对 0.1 ms（2,048 项、32 个共享向量）；而上限为 4 时，5 到 16 个值的逐行向量每项多一次哈希，32 个 5 维逐行向量 6.5 ms，内联只要 1.8 ms。逐行摘要的头部也只编码一次。格式升到 `2026-11-21.15`，缓存键升到 `2026-11-21.7`。
    - 输入名的哈希冲突时只比较哈希相同的那几个名字：原来一次冲突就两两比较所有名字，16,384 个输入的调用要 381 ms。
    - 空段不追加字节，也就不租缓冲；恰好 32 个输入时，分段数组也放在栈上（上限放宽到 64 个输入）。
  - **开销**：示例每个请求因此多分配约 1.3 KB（不算新节点本身），不随候选数增长：调用的上界和它的计时器 264 B，回答 312 B，调用和它的输入、输出数组约 320 B，其余是调用方的结构和参数数组。上界和 `fetch` 来源的一次拉取一样（来源的 `timeout_ms` 要有自己的计时器），回答和调用对象和节点的一次服务调用一样：回答的对象、它的锁和按需分配的输出列表是所有服务调用共有的，要省得改 `ServiceResponse` 的形状，为每个请求一次的调用不值得。
  - **不做的**：加载时不按服务的签名检查参数和输出的名字。模型算子会检查，但它要求服务实现 `DescribeAsync`，而特征的服务多半是业务服务，不描述自己；“不描述”和“描述了但不匹配”要分开处理，还要接上签名的异步等待和二次编译。代价是拼错的名字不一定报错：服务没写的输出是缺失（服务用它表示“没有值”），所以 `field` 拼错的特征读作缺失、取默认值，只有拒绝未知输出的服务让调用失败（内置的 `linear@1` 不拒绝，它写出配置的全部输出）；参数名拼错同样取决于服务。要分开“没有值”和“没有这个输出”，契约就得说出服务有哪些输出，那就是签名检查；有了需要时再加。特征的缺失比例指标会显示一直缺失的特征。
- **`linear@1` 按输入名的顺序累加权重**。float32 的和取决于相加的顺序，而设置是 JSON 对象，成员顺序不属于内容：两份内容哈希相同、只是 `weights` 成员顺序不同的绑定，原来能给同一个请求打出 0 和 1。排序放在客户端的构造里，直接用代码构造的客户端也一样。
