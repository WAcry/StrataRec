# 表达式

- **向量就是定长列表 `list<E,N>`，没有单独的向量类型**。原来有 `vec<float32,N>`，在存储（VectorColumn）、表达式、暂存、本地表、缓存编码、日志、回放、结果、模型输入每一层都有一条与列表平行的分支，约 80 处；元素只能是 float32，用户的模型和数据却可能是 float64 或整数。列表每行的元素本来就连续存放，SIMD 点积可以直接读，`vec` 多给的只是编译期知道长度：`dot`、`cosine` 长度不同时编译报错，模型输入的形状确定。现在长度是列表的可选参数，每层对列表只处理一次，任何元素类型都可以定长。取舍：
  - 长度在写入存储时检查（回填、本地表、缓存读取、衍生特征、节点输出、上下文值），长度不对与 int32 越界同样处理；暂存、录制和缓存记录保存连接器写入的原值，回放时再检查一次。配置和请求给出的值、字面量长度不对时在给出的位置报错；snapshot 加载器和 memory_feed 与它们对 int32 越界的处理一样，报加载错误。
  - 列表没有单独的定长布局，定长列表也是每行一个起点和长度（每行多 8 字节）：省掉一套布局和它在每层的分支，比这点内存值得。
  - `float16`、`bfloat16`、`int8` 量化仍由连接器解码成 float32 写入暂存区：它们的好处在存储和传输的体积，计算时仍要转换。本地表或缓存里的 embedding 占用的内存成了问题时（例如 100 万个物品 × 64 维 float32 约 256 MB），在表的存储编码上压缩，列类型不变。
  - embedding 在日志里按声明的类型记，`list<float32,N>` 就是 `float[]`（见“出口交付声明的类型”）。原来记成 `list<float64,N>`，和 float32 标量列记成 float64 一样，批次里的 embedding 大一倍；当时认为改采集路径不值得，后来为了让使用者的日志系统收到声明的类型而改了。
- **`dot`、`cosine`、`l2_norm` 的精度跟随声明的元素类型**。参与运算的列表都是 `list<float32>` 时用 `TensorPrimitives` 的 float32 `Dot`、`Norm`，余弦在 float64 中由这三个结果算出；有 `list<float64>` 或字面量时按 float64 计算，float32 的一侧精确扩宽。精度由绑定器按声明类型决定一次，记在 IR 节点上，所有后端一致。改成列表时曾让所有列表都走一个自写的 float64 内核（两个后端自然逐位一致，混用也不复制），实测上下文 embedding 对 5,000 个候选打分比 `vec<float32,N>` 慢 1.6–2.4 倍（64–768 维），余弦慢 2.2–3 倍；embedding 本身是 float32 精度，float32 累加的误差与之相当，要 float64 的使用者声明 `list<float64>`。现在（AVX-512，5,000 行）上下文 embedding 的点积在 64/256/768 维是 52/180/533 μs，原来的 `vec` 是 68/192/534 μs：请求级的 float32 列表每次求值收窄成一个 float 数组，之后每行是一次对两个 span 的调用。两个后端逐位一致的根据：`TensorPrimitives` 的结果只取决于数值和个数，与内存对齐无关（实测 1–4,096 个元素、512 位内的每个偏移）；标量后端把以 double 保存的 float32 列表精确收窄后调用同一个函数。如果将来的 `TensorPrimitives` 按对齐改变累加顺序，300 个元素的后端对照测试会失败。不同 CPU（AVX2、AVX-512）的向量宽度不同，末位可能不同，跨机器回放用到 dot 的分数可能有末位差异，原来的 `vec` 也是这样。
- **列表是类型构造器 `list<E>`，元素可以是 `bool`、`int32`、`int64`、`float32`、`float64`、`string`**。原来是三个各自独立的存储类型 `list<int32>`、`list<int64>`、`list<string>`，每一层都按种类各写一遍：存储、表达式的两个后端、连接器、暂存、本地表、缓存记录、日志、回放、结果、模板。加一种元素要改十几处，所以一直没有浮点列表和布尔列表；权重、价格、分数序列和点击标志序列只能拆成多列，或者塞进定长的向量。现在是 `StorageKind.List` 加元素类型，每层对列表只有一处泛型实现（`ListColumn<T>`、`CacheRecordWriter.List<T>`、`RecordBuilder.SetList<T>`、`ColumnValues.ListValue<T>`），标量能是什么类型，元素就能是什么类型。取舍：
  - 元素的提升和收窄与标量相同。`list<float32>` 读作 `list<float64>`，读取时不复制：向量化后端的 `FloatListLane` 直接读 float32 或 float64 存储。写入时逐元素收窄。浮点列表只要有一个元素是非有限值，整个列表就被替换并计数，理由与 `list<int32>` 越界时整体替换相同。
  - 不支持嵌套列表和逐元素可空。写错时，提示直接给出正确的写法：`list<int32?>` 提示 `list<int32>?`，`list<double>` 提示 `list<float64>`，`array<long>` 和 `int64[]` 提示 `list<int64>`。
  - 连接器的写入接口每种元素一个具名方法（如 `SetFloat32List`），没有一个泛型的 `SetList<T>`。理由：
    - 这是连接器作者用的公开接口，具名方法在 IDE 里一眼就能看到；
    - 元素类型不匹配时，异常直接说出该调用哪个方法；
    - 内部实现仍然共用一个泛型方法。
  - 整数列表字面量在需要浮点列表的地方就是浮点列表，在编译期转换，相当于无类型常量；只在这样的字面量之间选择的 `?:`、`??` 也一样，否则 `col.x > 0 ? [1, 2] : [3]` 写进浮点列表列会报错。有类型的整数列表（列、特征、输入）不做隐式转换：id 列表和权重列表是不同的数据，混用多半是写错了。没有为非常量的转换增加运行期操作：它要按行分配元素缓冲，而且没有场景需要它。
  - 缓存记录的格式版本不变。已有三种列表的编码字节没有变，新的元素类型只是新的类型名；记录头的指纹包含字段的类型名，类型变了的记录会读作不匹配，按未命中处理。
  - 布尔列表的写法跟随各自格式里的布尔标量：日志写成 0/1，结果 JSON 写成 `true`/`false`。
  - `ColumnType` 保持 8 字节。`Element` 和 `Kind`、`Nullable` 两个单字节字段放在一起，排在 `int Dimension` 之前；反过来排会补齐到 12 字节。这个类型到处按值传递，大小由测试锁定。
  - 列表暂时不能作为模型输入。
- **超出 float32 范围的配置值和请求输入直接拒绝，与 int32 的处理相同**。`[1e300]` 原来可以作为 `list<float32>` 列的默认值：用它替换一个非有限值，得到的仍是 ±∞，被替换的那一行于是留下一个坏值。标量 `float32` 的默认值和输入也有同样的问题。现在配置值、宿主传入的有类型输入、编译期常量都在给出时按 float32 范围检查，报错说明位置，并提示改成 `float64`。NaN 和 ±∞ 在两种宽度下都是它们自己，仍按原来的规则处理。范围判断只有一份实现（`Float32Range`），配置、转换、回放、编译期检查共用。
- **上下文级衍生特征的值按声明的存储类型取值**。逐候选计算的特征写进 float32 列，上下文级的直接发布 float64 结果，同一个声明于是得到两种数据：`0.1` 在两边精度不同，`1e300` 一边被替换并计数，另一边原样发布。现在发布前先按存储类型取值（`ColumnValues.AsStored`：浮点类型的整数结果转成浮点，float32 再舍入），再按非有限值规则检查；替换用的默认值也一样，目录在构建时就把默认值转成存储形式，请求期不再转换。请求输入仍按提升后的值保存，这是原有的选择，没有改。
- **不可空列只在写入的值可能被替换时才必须声明 `default`**。被替换的值有三种：浮点存储里的 NaN、±∞，`int32` 存储里超出 int32 范围的值，以及含有这样一个元素的列表（整个列表被替换）。所以要求覆盖浮点列、`int32` 列和这两种元素的列表。原来的条件是“数值列”，有两处不对：
  - `list<float32>` 这样的不可空列不带默认值也能编译通过，遇到第一个 NaN，节点就在提交时失败。
  - `int64` 列的值不会被替换，却也被要求声明默认值，提示里写的还是 `0.0`。
  现在的提示按类型给出：浮点列是 `0.0`，`int32` 列是 `0`，列表是 `[]`。
- **用 CEL 的语法，不用它的语义**。用标准语法是因为 AI 和工程师已经熟悉它；但 CEL 的值模型是逐行求值、出错得错误值、没有缺失值，与按列求值、运行期不抛错、缺失显式这三条硬要求冲突，所以只取语法，差异列在 `docs/guide/expressions.md`。不支持的写法都在编译期报错，对写配置的 AI 是好事：写错立刻知道。在 CEL 里能正常求值、结果却不同的只有 `/`（总得 `float64`）；CEL 运行期报错的溢出、对 0 取模、越界 `int()` 在这里得到值或缺失。`/` 保留，因为照 CEL 改成整数除法，打分公式里两个整数特征相除得 0 才是静默的错误；需要整数结果的地方会因类型不符报错。照 CEL 写的 `cel.bind`、宏、`math.greatest` 等暂时只得到 “unknown function”，没有为它们做专门的诊断：语法以后可能还会调整，现在不在这些提示上投入。补了 `endsWith`：和 `startsWith` 对称，字典列上同样按不同取值各算一次。不补 `matches`（逐行正则太贵）和宏（一行之内的循环不能按列计算）。
- **哈希的规范编码**。`float64` 中 −0.0 按 0.0、所有 NaN 按 `0x7FF8000000000000` 编码。IEEE 754 不规定定义域错误产生的 NaN 的符号和载荷，优化器和 SIMD 重写都可能改变它，`hash01` 结果不能随之变化。离线复算哈希也要这样规范化。字符串按它的 UTF-8 字节编码；不成对的代理项没有 UTF-8 字节，按 U+FFFD 写，和所有把文本存成 UTF-8 的地方（存储的键、缓存里的文本、日志）一样，所以这样的字符串和那个位置是 U+FFFD 的字符串是同一个键（哈希、分布式层的键和请求内的共用都这样；只有进程内的表按它存的字节比对，分得开）。给它单独的标签、按 UTF-16 码元哈希做过一版，撤回了：`hash01`、存储自己的键和缓存里的文本仍然按 UTF-8，只改哈希让同一个字符串在几处有不同的身份，别的语言也算不出那种编码；这样的字符串不是合法的文本，只能是宿主自己截断出来的。
- **`hash01` 有两份编码实现**。表达式后端用栈上缓冲区写编码，标量路径不经过数组池；与 `StableHash.Builder` 的一致性由测试锁定。
- **int32 越界的派生特征，不可空又没有默认值时整个特征失败**。和节点输出、非有限值是同一条规则：不可空的列装不下替换出来的“缺失”，读取方按不可空编译、不检查有效位。没有选择让类型推断因为“可能越界”而变成可空：那样所有 int32 派生特征的读取方都得写 `??`，而越界在实践中很少见。失败的特征对所有读取方都一样：节点按 `on_failure` 处理；输出读到它时，只要返回的行上有越界值，请求就失败（之后由后备流水线兜底；输出只为返回的行补齐，没返回的行不计算）；探针不让请求失败，读到它的列记为缺失，过滤条件视为 false。
- **`int(x)` 向零截断，没有 `int64` 值时是缺失**。`float64` 的 NaN、±∞ 和截断后超出 `[-2^63, 2^63)` 的值没有对应的 `int64`；CEL 在这里报运行期错误，这门表达式语言不抛错，所以结果是缺失，`float64` 的 `int()` 结果总是可空，用 `??` 给替代值。没有选：饱和到边界或按补码回绕（编出一个数，等于把缺失静默变成数）；像 int32 窄化那样保持不可空、越界时让整个特征失败（窄化越界很少见，浮点运算里的 `x / 0.0`、`log(0.0)` 却很常见，一行的 NaN 不该让整列失败）。`int()` 只接受数值，bool 写 `b ? 1 : 0`，也不解析字符串（文本到数值的转换属于特征生产）。`double()` 和 `int64` 参与浮点运算时一样取最近的 double。它和除数可能为 0 的 `%` 是两个能把有值的输入变成缺失的提升运算：向量化后端先把操作数的有效位合到输出的有效位上，再在输出的有效位上清掉这些行（不改操作数的），差分测试覆盖。旧二进制加载用到新函数的配置时报 `EXPR_UNKNOWN_FUNCTION`，不会静默算错（函数集合不是能力，见 manifest 的能力一条）。
- **`lookup(table, key, default)` 在 key 缺失时返回 `default`**（“参数缺失则结果缺失”的例外）。第三个参数本身就是调用方给出的缺失处理；改成缺失会让现有打分表达式变成可空类型而无法编译。
- **结果可空的提示不再建议 `has()`**。提示原来是“追加 `?? 默认值`，或者用 `has(x)` 判断”，但 `has()` 不收窄类型：照着写 `has(x) ? f(x) : 0.0`，结果仍然可空，再报同一个错。现在只给 `??`。让 `has()` 在条件分支里收窄类型（流敏感的可空性）是更完整的做法，代价是绑定器要跟踪分支条件，`??` 已经能表达同样的意思，暂时不做。
- **`x % 0` 是缺失，不是 0**。原来让它得 0 并计入 expr_int_mod_zero_total，但这个计数从来没有导出，于是取模的除数一旦为 0，就悄悄变成 0 参与后面的计算，违反“缺失不静默变成 0”。现在除数为 0 的行结果缺失；除数不是非零常量时结果类型可空，写入不可空的位置要用 `??` 说明缺失时用什么（`(hash % param.buckets) ?? 0`），除数是非零常量（最常见的 `x % 100`）时不可空，写法不变；除数在绑定时就是 0 时（`x % 0`、`x % int(0)`）编译报错（`EXPR_INVALID_ARGUMENT`，指向除数）。只在折叠后才是 0 的除数（`x % (1 - 1)`）在运行期得到缺失。计数、只为它存在的“存活行”位图和 `_countsEvents` 一并删除。代价：用参数做除数的取模要多写一个 `??`；没有按参数的 `min` 推断非零，参数范围不进入表达式的类型系统。
- **只有一种字符串类型 `string`，列不做字典编码**。原来 `string` 按字典编码存（DictStringColumn），`text` 每行一个字符串（TextColumn）。原来还给两者分了互不相交的运算，后来表达式里 `text` 已经按 `string` 读，区别只剩存储，用户却要按基数在类型里选，选错只体现在性能上；`list<string>` 的元素又一直是普通字符串，名字和存储对不上。字典编码省不下分配：查字典之前值就得已经是字符串，而字典本身每列每请求新建（`Dictionary` 加 `List`，不从请求内存租借，低基数几百字节，高基数可达上百 KB）；它的好处只是和常量比较时比整数，5,000 行差几十 μs。现在只有 `StringColumn`（每行一个从请求内存租借的引用）：`==` 按序数比较，共享的实例靠引用相等直接短路；`in` 的常量不超过 8 个时逐个比较，更多时在编译期建一次 `HashSet`；分组经临时键索引。示例流水线每请求的分配从 18.2 KB 降到 16.3 KB。重复的值由产生它的一方共享实例：本地表和缓存进程内层的字典、连接器的 `Intern`、缓存读取的去重。写 `text`、`text?`、`list<text>` 报错，提示对应的 `string` 写法。格式：回放包升为 `stratarec.replay_bundle/2026-11-16.4`（类型名变了）；缓存记录格式不升，string 和 text 的编码本来相同，原来声明为 text 的字段类型串变了，指纹不同，旧记录按未命中处理；日志不受影响：日志列的类型取表达式结果的类型，`text` 列原来就记成 `string`，schema 和 id 都不变。
