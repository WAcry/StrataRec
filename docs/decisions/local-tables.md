# 本地特征表

存储引擎在 `src/StrataRec.Features/Local/`（表、写入器、读取 API、更新来源的契约、`snapshot_files@1`、测试用的 `memory_updates@1`）；`local` 和 `cache` 两种供给方式接在它上面（绑定、宿主里的表生命周期、请求读取路径、回放和指标）。Kafka 来源和节点本地磁盘快照没有做。

- **单写线程、读取无锁：读者能碰到的东西要么发布后不再改，要么整体替换**。记录先写进页末尾的空闲区，再用一次 release 写把位置发布到索引槽；索引、页目录和字符串字典增长时复制到新数组、填完整之后再发布引用，旧数组不再写；读者用 acquire 读到位置之后才读键、页和记录，页号或字符串码超出手里的目录或字典时重新加载一次。完整规则写在 `LocalFeatureTable` 的注释里。没有选的做法：读写锁或 seqlock（读者在按行的路径上要重试，写得频繁时读者会被饿死）；每条记录一个对象（几百万个对象都要被垃圾回收器扫描）。x64 是 TSO，普通读写本来就有 acquire/release 语义，`Volatile` 只是不让 JIT 重排，所以压力测试（一个写线程、三个读线程，专用线程、固定工作量，`taskset -c 0,1` 下也通过）在 x64 上证明不了硬件重排类的错误。故障注入改的是程序顺序：先发布位置再写记录、读者不重新加载页目录、索引或字典在复制完成前发布，都能被测试抓到；字典那一项要把不同字符串的数量提高到百万级才稳定复现。CI 没有 ARM64，ARM64 上的内存序没有经过测试。
- **索引是一个键和位置交错的 `long[]`**（不是键和位置各一个数组）。一次探测只碰一个缓存行，两个数组要碰两个。位置是 `(页号 + 1) << 32 | 页内偏移`，0 表示空槽，新数组不用初始化。装载率不超过一半；条目从不删除（删除是墓碑记录），读者的探测序列不会断开。int64 键分块查找：先读一块键的初始槽，再完成探测、解析记录，让一块键的缓存未命中同时进行，而不是一个键一个键地等。
- **哈希键用 XXH3-64（种子 0）对规范字节求哈希，字节存在记录里比对**。单个 int64 部分以外的键都是哈希键；规范字节的定义在 `TableKeys` 的文档里，单个字符串键的字节就是它的 UTF-16 码元，和改成元组之前一样。字符串部分存 UTF-16，查找时直接比较 `ReadOnlySpan<char>` 编成的字节，读写都不用转码。代价：以 ASCII 为主的键多占一倍空间。哈希相同的键靠记录里的原字节区分。字符串值不在页里，是表内字典里的 .NET 字符串，记录只存 4 字节的码。
- **记录头带整条记录的长度，变长数据和定长部分在同一页里相邻**。记录是一段自包含的字节，压实时整段复制，只需要把字符串码重新编码。`list<string>` 的元素也存成表内字典的码。
- **字符串字典属于版本，压实时重建**。压实把记录复制到新版本时，字符串码重新编码进新版本的字典，不再使用的字符串随之丢弃。没有选全表共用一个只增不减的字典：高基数的字符串字段会让字典无限增长。
- **本地表的所有字符串都存表内字典的码，压实和淘汰把字典字符串算进去**。原来 `text` 以 UTF-16 存在页里，每次回填每行新建一个字符串（5,000 行读一段描述，每个请求约 2 MB）；去掉 `text` 后所有字符串字段都存码，回填直接取字典里的实例，每个请求 0 分配。代价是每个不同的值是一个长期存活的字符串对象，加上字典槽位（12 字节：引用和引用计数），计入 `max_bytes`：1,000 万行、每行一段描述，比放在页里约多 400–500 MB 和 1,000 万个 gen2 对象。按“问题在于每请求的分配”选了后者；将来真有超大的长文本表，可以在表内部对长值换回页内存储，类型不变。字符串在记录里只占 4 字节的码，原来只看记录字节的两处计算就看不到它：
  - 自动压实：一个字段改成很长的新值，被替代的记录很小，旧值却留在字典里，按原来的条件永远不压实，死字符串一直攒到 `max_bytes`。现在写线程为每个码维护引用计数（记录成为键的当前记录时加一、被替代时减一，压实时重建），条件改为（被替代的记录字节 + 没有记录引用的字符串字节）× 2 > 记录字节 + 字符串字节。
  - `cache` 按写入时间淘汰：按记录字节估算能腾出的空间，为腾出一点会删掉远多于需要的记录（`CacheTableTests` 的淘汰测试因此失败）。现在从最旧的记录往后数，每条记录算自己的字节，加上它带走最后一个引用的字符串：还被留下的记录引用的字符串，压实时整个保留，一个字节也不释放。曾经按引用数分摊（字符串字节 ÷ 引用数），把共享长字符串的一部分算成已释放，删掉的记录不够，要写回的记录仍然放不下、被丢弃；现在按淘汰前缀的引用数精确计算，写线程上每次淘汰一个按码计数的数组。
- **压实按字节触发，墓碑一直保留到 reload**。被替代的记录（加上只有它们引用过的字典字符串，见上一条）超过记录和字典总字节数的一半、并且不少于 `CompactionMinBytes`（默认 1 MiB）时压实。按字节而不按条数，是因为变长记录大小不一；有下限是为了不让小表每几次更新就重建一次。压实在写线程上同步进行，期间更新等待，读者不受影响。压实按记录原来的页序复制，每个新页只开到装下剩余记录所需的大小（不超过 `PageSize`），通常不比原表大；按索引槽的顺序复制会把大小不一的记录混在一起，每页末尾空得更多，副本常常比原表还大。按页序复制也不保证不变大：新开的页按剩余字节开满一页，下一条记录比这页剩下的空间大时只能另开一页，开好的页就几乎空着。例如 `PageSize` 64 KiB，键 1 是空列表、键 2 是 80 KB 的 `list<int32>`：原表是一个小页加一个装键 2 的页，84,696 B；副本先开一个 64 KiB 的页放键 1，键 2 放不进，再开一页，146,136 B。墓碑在压实时保留，否则晚到的旧更新会让已删除的键复活；reload 从空表开始，快照就是那个位置上的全集，所以 reload 之后墓碑不再保留。
- **`max_bytes` 计当前版本的页、索引、页目录和字典，按字节精确执行**。写入之前算出它实际会增加的字节：新页、索引增长、字典里还没有的每个不同字符串（同一记录里重复的只算一次），以及加入它们时经过的每一次字典扩容。一次写入会超出、又有被替代的记录时，在旁边建一个不发布的压实副本，按副本重新计算；副本加上这次写入放得下才换上，否则丢弃副本并抛 `LocalTableFullException`，表完全不变（版本、字节数、generation）。自动压实和显式 `Compact` 用同一个构建过程，副本单独放得下才换上：自动压实放不下就静默放弃，被替代的字节翻倍之前不再尝试；显式 `Compact` 放不下就抛异常。副本可能比原表大（压实时页按剩余字节开满，下一条大记录放不进就要再开一页），所以这两处检查都会走到，各有回归测试。试算用的副本不能被写入器留住：提交内复用的字符串查找结果只在一次 `Commit` 里有效，由同一个 `finally` 清掉。代价：副本的最后一页正好装满，表离上限不到一页、又没有被替代的记录时，写入会失败，直到调大 `max_bytes`；上限通常比页大几个数量级，不为此缩小新页。空表本身超过 `max_bytes` 时建表就失败。压实和 reload 期间新旧两个版本同时存在，进程短时间需要约两倍的内存，`max_bytes` 不算这部分。`cache` 的记录头版本就是写入时间，按写入时间淘汰的入口是 `Compact(dropWrittenBefore)`；`cache` 写回的版本取拉取发起的时刻，否则发起得早、返回得慢的拉取会盖掉较新的结果。
- **读取是一次查找加按块填充**。`Lookup` 为每个键给出一个记录引用，同一张表的所有特征共用；多字段 `Fill` 把行按 128 行分块，先把每块记录要用到的缓存行都读一遍，让未命中同时进行，再逐个字段填这一块，记录在 L1 里被所有字段复用。按行的循环不做边界检查，安全靠每次调用开头的一次检查，检查的是副本：行、记录引用和读取说明先复制进从 `ArrayPool` 租来的数组，检查副本，循环只读副本。只检查调用方的 span 不够：行可以就是某个目标列自己的数组，写进第一个值就改了还没用到的行，下一行就落到列外（评审的例子）；行也可以和非有限值计数重叠，或者在检查之后被别的线程改写。复制的代价在 500 行时每次调用约 1 μs，约占 30 个特征热缓存填充的 3%。缺失时填缺失的列在循环开始前就建好有效位图，即使最后没有缺失的行：循环里只要有一次调用，JIT 就把循环的状态放到栈上。填充位由调用方处理：每一行的每个字段都会被填，同一张行位图 OR 进每个槽位即可。`float32`/`float64` 的 NaN 和 ±∞ 原样存储，读取时按缺失处理并计数，与暂存区回填一致。字符串读取直接给出表内字典的实例，不新建字符串（见“本地表的所有字符串都存表内字典的码”）。
- **读取测量没有达到设计估计的 20 μs**。`LocalFeatureTableBenchmarks`：100 万条记录、每条 30 个特征（25 个 `float32`、2 个 `int64`、1 个 `bool`、1 个 `string`、1 个 64 维 embedding，约 400 B；测量时向量还是单独的定长类型，直接放在记录里），一成的键不在表中，0 B 分配。在开发机（Xeon 6975P-C，KVM 虚拟机，.NET 8）上：同一组键反复读（数据都在缓存里）500 键 34 μs、5,000 键 490–505 μs；每次换一组随机键 500 键 51 μs、5,000 键 830–860 μs，其中查找本身 10 μs 和 120 μs。每个字段单独调用一次 `Fill` 时，500 键慢一倍多，5,000 键慢两倍（每个字段都把全部记录再走一遍，还要各复制一次行和记录引用）。热缓存时一个 `float32` 值约 1.5 ns，按列的循环每个值二十来条指令，已经到了这种做法的下限；换键之后多出来的部分主要是 TLB 未命中：4 KB 页随机访问 400 MB，虚拟机里还要走两级页表。要再快，可以试大页（.NET 的 GC 堆默认不用透明大页），或者为连续的同类型字段写按行读取的内核，等接入请求路径、有真实的特征组合之后再决定。
- **快照是 JSON Lines 数据文件加一个 manifest**（`snapshot_files@1`）。设计提到 Arrow 等列式格式；第一阶段选 JSON Lines：标准格式、能手写，错误能指到“文件:行”和 JSON 指针，也不引入 Arrow 依赖。快照覆盖的更新流位置写在 manifest（`snapshot.json` 的 `position`）里，不写在数据文件头：数据文件可以由多个任务并行写，最后写入 manifest（先写临时文件再 rename），读者不会看到半个快照。每次加载都是一次 reload：在读者看不到的新版本里构建，完整之后整体替换；失败就放弃新版本，读者继续用旧的。manifest 内容没变就不重新加载；第一次运行时，如果表的位置已经等于 manifest 的位置也跳过（从本地磁盘恢复之后接着跑）。`reload` 写 ISO 8601 时长（`PT1H`），不写 `1h`：配置只用标准语法。超出 `float32` 范围的数读成 ±∞，与 `memory@1` 一致（两者都用 System.Text.Json），之后按非有限值处理。加载吞吐（`LocalFeatureTableLoadBenchmarks`，10 万条上面那样的记录，每行约 1 KB）：经 `RecordBuilder` 直接写约 240 万条/秒，解析 JSON Lines 约 20 万条/秒，`RecordBuilder` 只占其中不到十分之一，其余是 JSON 解码（每行约 90 个数）。一行先写 `key` 和 `version` 时字段只扫描一遍，否则先跳过 `fields`、读完整行之后再解码它。
- **写入器的接口（`IFeatureTableWriter`）为解码器的实际用法多给了几样。**`Begin` 和 `Delete` 另有 int64 键和 `ReadOnlySpan<char>` 键的重载，解码器不用为每条消息建 `EntityKey` 或字符串。`RecordBuilder` 是值类型句柄，要显式 `Commit`：解码到一半出错的消息不提交就是放弃，下一次 `Begin` 会丢弃它。`Delete` 返回是否因版本过旧被忽略。`BeginReload`、`CompleteReload`、`AbortReload` 做的是“建好新版本后整体替换”；reload 期间不能 `Checkpoint`，位置只随完整的 reload 前进。
- **实体键是有序元组，1–8 个部分；任何实体都能放进本地表和缓存**。原来的键是一个引用，或一个请求输入加一个候选列（“交叉实体”），由此分出上下文、候选、外键、交叉四种类别和 `Single`/`Many`/`Cross` 三种拉取形态，交叉实体还不能放进本地表和缓存，只能每个请求远程拉取。真实的特征存储常按组合键存：按（国家, 性别, 年龄段）的人群特征、按（游戏, 广告）的特征、按（物品, 国家）的统计。这些在连接器里也做不了，连接器只收到实体的键，看不到别的请求输入和候选列；而（物品, 国家）这类有界的表正适合放进本地表。现在键是部分的元组，类别只剩上下文范围和候选范围两种，由部分是否全是 `ctx.*` 推导；`KeyShape`、`ForeignKey`、`Cross`、`CONNECTOR_SHAPE`、`LOCAL_CROSS_ENTITY` 都删掉。取舍：
  - 最常见的单部分键不能变慢。单个 int64 部分照旧直接进索引；其他键对规范字节求哈希。改动后实测（20 万条记录，读 5,000 行 × 8 个 float32 特征）：单个 int64 键 226–235 μs → 226–228 μs；单个字符串键 444–458 → 389–406 μs（哈希键的批量查找改成每 64 个键一块，先读主槽位再探测，和 int64 路径一样）；两部分键（物品 id + 共享的国家）400–413 μs。读取的分配不变（每次 448 B）。
  - 请求输入和上下文特征的部分对整批相同，批里只放一次并标为共享（`EntityKeyBatch.IsShared`），去重和哈希只看随行变化的部分，存储端可以按共享部分分区一次读取：原来 `Cross` 形态的用途由此保留下来。
  - 请求内去重：单部分键照旧用 `EntityKeyIndex`；多个随行变化的部分用 `EntityKeyTupleIndex`，计划读到这种实体时在请求开始就建好，读取不分配。每次拉取的键状态是结构体（`FetchKeys`），示例每请求多 120 B（每次拉取约 24 B）。
  - 分布式层的键是引擎生成的文本，存储只收字符串：单部分键照旧（int64 写十进制，字符串原样），多部分用 `:` 连接，字符串部分里的 `%`、`:` 转义成 `%25`、`%3A`（`10042:US`）。同一个 keyspace 里所有键的部分数相同，所以单部分键不转义也不会混淆，升级前写进 Redis 的单部分键照样命中。`redis@1` 原来自己格式化键，现在用引擎给的文本，每个未命中的键同样是一次字符串拼接。
  - 缓存记录的指纹加入键布局的类型串，单部分时和原来相同，记录格式不升；回放包升为 `stratarec.replay_bundle/2026-11-16.5`（键写成值或数组，不再有 `shape` 和 `context_key`）。
  - 包含候选的组合键键空间可能很大，放进本地表或缓存由使用者决定，`max_bytes` 限制内存、TTL 和淘汰限制流转；拒绝它反而把有界的情况也挡在外面。
  - 键的部分可以是上下文特征，见下一条。
- **键可以读上下文特征（链式的上下文键）**。真实系统常先用登录键、设备或国家查出另一个存储使用的 ID（`user_key` → `user_id`、国家 → 地区），原来上下文实体的键只能是请求输入，写不出来；候选侧早就能经候选特征链式作键，上下文侧不对称。放在连接器里做也不合适：下游的源用不上本地表和缓存，指标和回放不再按源区分，还要自己处理并发。现在上下文特征（物理或衍生）可以做键的部分，和请求输入一样是共享部分。取舍：
  - 调度不分波次：每个链式分组一个任务，只等它的键读到的特征（和作为键的衍生特征的输入），在写入最后一个键特征的线程上发出，无关的慢源既不拖它发出，也不拖读它的节点。按波次的请求级调度更简单，但第二波要等第一波里所有的源，链上的延迟就取决于最慢的那个无关源。
  - 键状态的规则与候选特征做键相同：没有值就不查找、特征取缺失或默认值；上游失败时依赖它的特征失败、不发请求；上游降级时它们降级。
  - 生命周期延续评审：预取一直持有请求内存，直到它建的每个任务都完成，不管发出阶段怎么结束，然后重新抛出第一个异常；上游以异常失败时链式分组不发出；请求结束（`FeatureFetcher.EndRequest`，执行器在 finally 里调用）或取消之后才写入键的分组不发出，但它的任务照样完成，没有东西一直挂着。键在结束之前就写好的分组，可能在 `EndRequest` 返回之后才真正发出调用（检查和发送之间的窗口）：它持有请求内存，`WhenIoCompleteAsync` 一轮一轮地等，直到某一轮没有新登记的调用（原来只取一次快照，会漏掉这时才登记的调用）；要做到结束后绝不发起调用，得在发送和结束之间再加一道同步，没有这个需要。候选缓存读取解析未命中的任务也登记：请求不再读取它时（同一波另一个数据源的调用失败），它在第二层应答之后才发出回源调用，这时之前登记的调用都已完成，排空原来会提前返回。异步调用登记的任务在连接器完成且调用点记录完毕之后才完成（`BoundedCall` 的租约）：原来只登记连接器的完成，没人读的预取还在记录调用、持有请求内存时排空就返回了。
  - 链式分组在连接器的线程上开始，所以录制钩子的 `Begin` 可能被并发调用，录制里的 seq 顺序取决于键写入的时刻；回放按（源、实体、键、字段）匹配，不受影响，回放包格式不变。上游的值变了，下游是 `not_recorded` 缺口。
  - 预取仍按“整份计划的上下文特征都预取”：只有某个臂读这条链时，控制组的请求也会调用它（可预期的多拉）。
  - 代价：上游异步完成时每个链式分组多一个状态机对象；示例的地理链（`country` → `region`）让不带国家的请求多 120 B。
- **绑定写成 `"mode": "local"`，`max_bytes` 和 `bootstrap` 与 `mode` 平级**（没有放进嵌套的 `local` 对象）。每个设置只属于一种模式，写了另一种模式的设置是错误，指针指到那个设置，提示删掉它或者改模式：从 `fetch` 改成 `local` 的绑定不会留下一个静默失效的 `timeout_ms`。平级之后每个设置只有一个位置，错误指针也短。设置和模式的对应关系只写在 `FeatureSourceResolver.ModeSettings` 一处，测试用反射核对它覆盖绑定类型的每个属性：以后加的设置忘了归属，测试就失败，而不是被另一种模式默默接受。连接器自己的设置（绑定里没有声明的成员）只属于 `fetch`；来源自己的设置写在 `bootstrap` 里面。`max_bytes` 写整数加 IEC 单位（`16MiB`），JSON Schema 的 `pattern` 和解析器接受同样的写法。`max_lag_ms` 和 `updates` 不做，见下一条。绑定的每个问题一次报完（另一种模式的设置、缺少的 `max_bytes` 或 `bootstrap`、未注册的来源类型、来源设置的错误），`stratarec validate` 不加载表，所以不需要快照文件。同一个数据源的每个实体一张表，每张表一个来源实例：来源可以有状态（流消费者），不能在两张表之间共用。
- **`max_lag_ms` 和 `updates` 不在框架里做**。设计让框架在追上更新流之前不就绪、运行期延迟超限时把读取方标成 `degraded`，并用 `updates` 把快照来源和更新流来源串起来。都不做：（1）先追上再服务，现有契约就能做：来源在 `BeginReload` 之后加载快照、把更新流消费进这个版本，追上之后才 `CompleteReload`，然后继续写线上表；失败后引擎从表的位置重新运行来源，来源看到非空位置就跳过快照。追到什么程度算追上，由最了解更新流的来源决定。（2）延迟由来源测量和告警：Kafka 这类来源由宿主实现，消费者自己有按 offset 和按时间的延迟；框架要测，就得改契约让来源报告时间，测到的也不比来源自己的准。（3）运行期标 `degraded` 不改变行为（值照常使用），却要在每个请求的读取路径上检查，回放还要记录当时的延迟状态；按表聚合的告警已经回答“特征是不是变旧了”。（4）`updates` 只是把两个来源串起来：一个来源本来就可以既加载快照又消费更新流（`IFeatureUpdateSource` 的文档写了这个做法），现在也没有内置的更新流来源。有了内置的更新流来源，或者多个宿主重复写同一套串联，再把它做进框架。
- **表的身份只有一条规则，在 `LocalTableSpec.Identity`**。身份是 RFC 8785 规范化的 {数据源、实体、键布局的类型串、物理字段和它们的存储类型（按字段名排序）、整个绑定、相对路径的基准目录（绝对路径）}。身份相同的计划共用一张表，切换计划时直接接手已经加载的表，不重新加载；改特征名、默认值、声明顺序、其他数据源、流水线和实验都不改变身份。绑定整体放进身份，而不是挑选几个设置：以后加的设置自动成为身份的一部分，不会因为漏加，让设置不同的两个计划共用一张表。代价是绑定的任何改动都会重新加载一次（例如只改 `reload` 周期）。快照的内容不在身份里：同一个绑定的新快照由来源按 `reload` 自己发现，不靠重新发布配置。身份只描述配置，共享还要求同一个运行时所有者（`LocalTableSpec.Owner`，按引用比较，和实例只在同一个工厂对象之间共享是同一条规则）：`local` 表是 bootstrap 来源的工厂，`cache` 表是连接器实例。原来只按身份共享，两个注册表不同的引擎共用一个宿主时，第二个引擎的来源从不运行，`cache` 表里是另一个引擎的连接器取回的行，最终分数改变，没有任何错误（外部评审）。所有者不放进身份：身份是规范化、稳定的配置描述。代价：两个引擎各自 `new PlanEnvironment()` 时内置工厂是不同的对象，不再共用表，各加载一份，和实例一致；要共用就共用同一个环境。分布式层（Redis）的键不含所有者：跨进程本来就要共享，进程之间只能比较配置，隔离边界是配置和 `key_prefix`。
- **基准目录在创建 spec 时固定成绝对路径，来源和身份用同一个值**。`LocalTableSpec.Create` 把基准目录按当时的当前目录变成绝对路径（为空就是当时的当前目录），用它创建来源，也把它写进身份；来源自己也把 manifest 路径在创建时变成绝对路径，直接用工厂创建的来源同样不会留着相对路径。原来身份里存的是传入的原值：为空或是相对路径时，相对的 `uri` 实际按读取时的当前目录解析，身份却一样，宿主会让指向两个目录的计划共用一张表，静默地服务另一个目录的数据；编译之后、后台开始加载之前改变当前目录，读的位置也跟着变。没有选“相对 `uri` 必须配绝对基准目录”：公开 API 本来就接受空的基准目录，固定下来就够了，不用给调用方加一条规则。spec 的构造函数改成私有，创建来源和计算身份只有这一个入口。
- **`uri` 的语法错误是配置错误，在 `/uri`**。`snapshot_files@1` 的工厂解析 `uri` 时，把预期的格式错误（`UriFormatException`，以及路径里的非法字符等 `ArgumentException`）转成 `FeatureUpdateException`，指针 `/uri`，hint 说明接受本地路径或合法的 `file://` URI；解析器统一映射到 `bindings:<环境>` 的 `/sources/<数据源>/bootstrap/uri`。原来 `file://%` 这样的值让 `new Uri` 直接抛异常，越过诊断流程，`validate --format json` 没有任何 JSON 输出。转换放在工厂的解析边界，不在解析器里捕获所有异常：解析器不知道哪些异常是配置错误。测试在单独的进程里运行真正的 `stratarec validate --format json`，快照目录删掉，确认输出是带指针和 hint 的 JSON，且不读快照文件。
- **就绪按计划判断，表的生命周期只在 `BindingHost`**（不是按节点；`BindingHost` 也管绑定的实例，见 `bindings.md`）。引擎加载计划时开一个 `BindingLease`，编译时向它取表（身份相同就取已有的），然后等这个计划的所有表完成首次加载，才把它设为当前计划；在此之前旧计划照常服务。按节点判断就绪的话，一个新计划的表还在加载时，节点要么停止服务，要么用还没有数据的表服务新计划，两者都不对。表的创建、共享、后台运行、重启、释放和停止都在 `BindingHost` 里，计划和请求只通过租约拿表，`Features` 只依赖 `ILocalTableProvider` 这个接口。
- **引擎的加载、发布和释放由一把锁排序**（`RecEngine` 的 `_publishGate`）。加载开始时在锁里登记自己和自己的租约，发布也在锁里；释放在锁里把引擎标成已释放，并取走所有登记中的加载和已发布的计划。于是：释放之后不会再有发布（发布前在锁里检查）；释放会取消还在进行的加载，它们抛 `ObjectDisposedException`；每个租约只由当时的所有者归还一次：发布之前属于加载，没有发布就在加载唯一的 `finally` 里归还，发布之后属于服务中的计划，计划被替换时或引擎释放时归还。释放会先归还在途加载的租约，不等它们自己结束，这样卡在编译里的加载也不会让表一直运行；之后加载的 `finally` 再归还一次是空操作。原来释放只遍历已发布的计划：等表加载的那个租约不在里面，发布时也不检查是否已释放，使用外部宿主时，加载完成后照样发布，释放过的引擎重新开始服务，这张表和它的来源永远不会被释放。外部传入的宿主仍然不由引擎关闭：它可能同时服务别的引擎，引擎只归还自己的引用，测试用两个共享一个宿主的引擎验证。
- **取消加载：开始时、等表时、发布前在锁里各检查一次**。`LoadAsync` 一开始就检查令牌；`WaitLoadedAsync` 在没有表、宿主不加载表、表已经就绪时也检查（原来只在等待循环里检查，这几种情况直接成功）；发布锁里在修改当前计划之前再检查一次。取消的加载抛 `OperationCanceledException`，当前计划不变，没有发布的租约在 `finally` 里归还，共享的表只少一个引用，别的计划照常用它的来源。原来表已经就绪或没有表时，取消的加载仍然返回 `Applied = true` 并替换当前计划，结果取决于表需不需要等。为了让测试确定地把取消和释放放进“等完表、发布之前”这个窗口，`RecEngine` 有一个内部的 `Publishing` 回调，只给测试用。
- **首次加载失败：计划不生效，下一次加载才重试**。诊断是 `LOCAL_TABLE_LOAD_FAILED`，位置是绑定（`bindings:<环境>` 加 `/sources/<数据源>`），消息里有数据文件和行号，hint 来自来源。表超出 `max_bytes` 时不“按数据源不可用处理”，而是拒绝计划：从没加载成功的表会让每个请求读它的特征都失败，在加载时拒绝，错误出现得更早、更清楚，旧计划也不受影响。失败的表不再交给任何计划，同一个配置再加载时建新表，真正重新读一遍；后台不自动重试首次加载：配置或数据有错时，自动重试只会不停地写日志，重新发布（或者修好数据后再加载）是更明确的重试时机。还没有服务过任何计划的引擎，这条流水线就一直没有计划，宿主看加载结果决定是否就绪。没有 `max_lag_ms`：现在只有快照来源，首次加载完成就是就绪。
- **首次加载之后来源失败：表继续用已有的数据服务，来源从 `Position` 重启，间隔加倍**（从 `RestartDelay` 1 s 开始，最长 `MaxRestartDelay` 5 min）。一次运行有进展（完成过一次 reload 或 checkpoint）就把间隔重置。进展看表的完成次数（`LocalFeatureTable.Completions`），不看位置：没有更新流的快照来源每次 reload 都停在空位置，按位置判断会永远认为没有进展。失败写日志（事件 1203，带位置、间隔和连续失败次数），计入 `stratarec.local.load.failures`；数据有多旧看 `time() - stratarec_local_load_last_success`，来源一直失败时这个值一直增长。
- **释放和关闭**。计划被替换后，它持有而新计划不共用的表停止来源；还在旧计划上执行的请求读自己钉住的版本，停止来源不用等请求结束。宿主关闭时取消所有来源，最多等 `ShutdownTimeout`（10 s），超时写日志。来源在单独的长期线程上启动：`snapshot_files@1` 在第一次 await 之前同步读完整个快照，不能占用调用方的线程或线程池。
- **停止来源不在调用方线程上运行来源的代码**。取消用 `CancellationTokenSource.CancelAsync()`：令牌立即进入取消状态，来源注册在令牌上的回调在线程池上执行。原来用 `Cancel()`，回调在释放租约或关闭宿主的线程上同步执行：回调阻塞时，关闭要等它返回之后才开始计时，`ShutdownTimeout` 不起作用；计划替换释放旧表也走这条路，新计划已经发布，`LoadAsync` 却可能一直不返回。一张表的“已停止”是来源的运行和取消回调都结束（`TableEntry.Completion`），关闭在同一个 `ShutdownTimeout` 里等所有表，包括之前被释放、还没停完的表；超时之后条目和它的 `CancellationTokenSource`（从不释放）留到两者都结束，表才离开宿主的集合。回调抛出的异常写日志（事件 1206），不抛给释放或关闭的调用方，也不会成为未观察的任务异常。测试覆盖阻塞和抛异常的回调，分别经过租约释放（计划替换）和宿主关闭两条路径，引擎层面另测一次计划替换。
- **请求读取路径集中在 `FeatureFetcher.Local.cs`**。一个节点需要某张表的特征时：取存活行中还缺这些特征的行，键去重之后 `Lookup` 一次，每行从这次查找里取自己键的记录，多字段 `Fill` 一次，再把行位图 OR 进各个槽位的填充位。不预取、不受拉取屏障约束、不经过暂存区：读取是同步的内存访问，预取只会提前占用请求内存，读到之后可能被过滤掉的行。同一个 wave 里先发出拉取，再做本地读取，本地读取和拉取的 I/O 重叠。每个请求每张表 `Pin` 一次，所以 reload 和压实不会让一个请求的几次读取看到不同的版本；更新流逐条写入的记录在同一个版本里可见（以后有 Kafka 时，同一个请求先后两次读取可能读到同一个键的新旧两条记录，每条记录本身是完整的）。已经部分填充的特征（行追加之后再读）只填没填过的行，节点读到的值在请求内不变。读取不分配，测试和同一请求的第二次 `Ensure` 比较字节数，抵消 Debug 构建里异步状态机的分配；去重用的 `EntityKeyIndex` 由 `FeatureFetcher` 在构造时建一个，每次读取 `Reset`。
- **一次本地读取是一个批次，填充和录制都只用这一批记录**（`LocalReadBatch`）。批次是：要填的行、它们去重后的键（首次出现的顺序）、这些键一次 `Lookup` 得到的记录引用、每行的记录。`Pin` 固定的是版本对象，写入器在同一个版本里原地更新时会把索引槽改指新记录，同一个键查两次可能得到两条记录。原来录制时按键再 `Find` 一次，更新落在填充和录制之间时，请求用的是旧记录，回放包里却是新记录，回放和线上不一致；原来也不去重，共用一个外键的几行在一次 `Lookup` 里分别查找，可能拿到不同的记录。现在每个键只查一次，共用键的行拿到同一条记录，录制直接用这批记录引用，不再查索引。回归测试在 `stratarec.local.keys` 的 `MeterListener` 回调里更新 author 表（这个计数正好在填充之后、录制之前），再回放同一份录制，要求逐项相同。命中率按去重后的键计数，和拉取的 `stratarec.io.keys` 一样。
- **缺失和默认值只有一个定义：`FeatureDefinition.Absent`**（有默认值取默认值，否则缺失）。拉取的回填、非有限值替换、上下文特征和本地读取都用它，原来散在 `FeatureFetcher` 里的 `DefaultOrMissing` 去掉了。键不在表中、记录没有这个字段、外键或上下文键缺失、非有限值，都得到 `Absent`；外键失败时读它的本地特征失败，外键降级时它们降级，与拉取相同。测试把同一批记录分别通过 `local` 和 `memory@1` 读出来逐值比较，示例流水线两种绑定的结果和回放记录也逐项相同。
- **表没有加载就读：特征失败，不当作缺失**。空表会把每个键都答成“没有值”，结果看起来正常但全是默认值。只有不经引擎加载的计划会遇到（`validate`、`build`、`explain` 用 `UnloadedLocalTables` 编译），错误文字说明这一点。
- **回放：本地读取记成特征调用，回放包格式不变**。录制时每次读取记一次调用：键是读取的行的键，按存活行顺序去重，值是这次读取用的记录里存的值，没有记录就是缺失；回放时本地组和拉取组一样由录制回答，走暂存和回填，不读表。格式没变，旧的回放包和工具照常可用；回放专用的引擎（`stratarec replay`、`compare`）用 `Load = false` 的宿主（表和实例都不加载），不需要快照文件，表变了也照样逐项复现。同一配置上录制和回放取的是同一批行，键完全一致。录制时额外分配（键列表、记录数组），只有录制的请求付这个代价。
- **表的指标**：字节数和记录数（gauge，每次 reload 或 checkpoint 时记录）、压实次数、加载耗时（直方图）、加载失败次数、最近一次成功的时间（gauge，Unix 秒），读取命中率用 `stratarec.local.keys` 的 `outcome = hit | miss` 两个计数相除。最近成功写时间戳而不是年龄：年龄要有人定时刷新，时间戳只在成功时写一次，告警规则自己算 `time() - x`。标签（`stratarec.source`、`stratarec.entity`）建表时缓存，记录时不分配。计划加载的结果多了 `bindings_failed`（原名 `tables_failed`，现在也包括实例的加载失败）。
- **`stratarec schema bindings` 的两处修正**。原来带扩展字段的类型（连接器设置、来源设置）也生成 `additionalProperties: false`，合法的绑定会被编辑器标成错误；现在去掉。`mode` 的 `enum`、`max_bytes` 的 `pattern` 由代码里的 `AllowedValues`、`RegularExpression` 特性生成，不手写第二份。
- **组的供给方式只有一个描述：`GroupSupply`**。`FeatureSourceResolver.Group` 为每个组生成它：模式，以及这个模式持有的东西（`fetch` 是连接器、超时和分批，`local` 是表）。组直接存这个描述，计划构建、读取路径和拉取路径都按 `Mode` 判断。原来组只存连接器和表，模式由“表是不是空”推出来，`FeaturePlan.Create` 自己再按模式分支：加一种同时有表和连接器的模式时，这样推出来的模式就错了，而且没有任何地方会报错。现在按模式的判断都是列出每个取值、没有默认分支的 switch 表达式（解析器 4 处、`FeatureFetcher` 2 处）；全局关闭了 CS8524（没有覆盖未命名的枚举值），所以加一个模式时，每个要处理它的地方都编译不过（CS8509，警告视为错误）。编译器看不到的是绑定里模式的拼写和 JSON Schema 的 `enum`，由测试核对：每个模式的名字都能解析回它自己，`AllowedValues` 正好是这些名字。
- **`cache`：两层缓存在连接器之前，读取路径集中在 `FeatureFetcher.Cache.cs`**。第一层是进程内的本地表（`LocalTableMode.Cache`，记录版本就是写入时间），第二层可选（`cache.distributed`，契约是 `ICacheStore`，服务的缓存也用它）。只配第一层也完整可用。一次读取：表里新鲜的键直接填充，全部新鲜时就是一次本地读取，不分配；其余的键查第二层，第二层未命中、过期、记录不匹配或出错的键合并成一次连接器调用；回填之后写回，第二层来的只写本地表，连接器来的写两层。整次读取在数据源的预算之内（第二层和连接器返回任务之前的同步部分除外，见“请求路径上的扩展点在请求线程上直接调用”），第二层默认最多等预算的一半（`cache.distributed.timeout_ms` 可改），剩下的留给连接器。
  - **未命中时拉取表的全部字段**，不只是这个节点要的：写回的必须是完整记录，否则下一次读别的字段会把缺的字段当成“没有值”。代价是第一次多拉几个字段。
  - **写回不在请求路径上**。两层各有一个有界队列（本地默认 `max_bytes` 的 1/16、限制在 1 到 64 MiB；分布式固定 16 MiB），满了就丢弃并计数，下次未命中再拉。比整个上限还大的一批在队列为空时照样入队（同日志管道），队列因此最多超出上限一批：一次请求的未命中合成一批写回，不管 `max_batch` 把调用拆成几块，候选多时这一批可能超过上限；原来空队列也会每次丢弃它，这些键每次都回源。一批写回按它等待期间留住的内存计数：记录字节、键的字符串、键和记录的数组（分布式层是条目和键文本）。同一批里连续的键共用同一个字符串对象（复合键里来自请求输入或上下文特征的部件）时只算一次：原来按键各算一次，4,096 个候选共用一个 128 字符的部件计成约 1.44 MiB（实际约 0.32 MiB），空的 1 MiB 队列整批丢弃。按引用比较，不分配；内容相同的不同对象各算一次，它们确实各占内存。原来只算记录字节，组合键一类的长字符串键配短记录时，队列实际留住的内存是上限的好几倍（预发布评估 2026-11-18）。记录是一次读取共用的数组的切片，所以这个计数必须约束住它们留住的数组：写回的记录不到数组的一半时（多数分块失败或只回答了一部分，或者预留的空间没用上），复制到一个只装它们的数组里（一次外部审阅：原来一条 33 字节的记录留住了为 4096 个未命中编码的 135 KB 数组，队列的上限形同虚设）。正常的读取写回的就是大半个数组，不复制；没有改成按数组容量计数，那样预留空间估多了也会挤占队列。本地表的写线程作为这张表的更新来源运行，表的加载、取消和释放都沿用 `local` 的生命周期；空表就算加载完成（每个键都未命中）。
  - **只写回确定的结果**。连接器部分失败的分块不写回；请求不再等待的调用（第二层或连接器超时之后才返回的）结果既不读也不写回：可能不完整，写入时间也已经不对。连接器确认没有值的键写一条全部缺失的记录（负缓存），寿命相同。版本相同时保留先写的那条：同一毫秒内两次拉取同一个键，后到的写回被忽略（两次读到的值可能不同，这是按毫秒计版本的平局规则）。
  - **过期**：TTL 按键的稳定哈希浮动 ±10%，同一批写入的键不会同时过期。连接器失败时，`stale_if_error_ms` 窗口内的过期记录照常使用；窗口按选择兜底值的那一刻判断，不按读取开始时，等连接器期间越过窗口的记录不用。用了过期值的读取状态是 `Partial`，错误信息说明有几个键用了过期值；只有一个键都没有拿到值时读取才 `Failed`。超出 `max_bytes` 时先丢弃过了窗口的记录，仍超过上限的四分之三再按写入时间丢弃最早的，免得下一次写入又触发淘汰。配置了第二层时，最长保留时间（`ttl_ms` × 1.1 + `stale_if_error_ms`）要放得进 `TimeSpan`（约 2.9 万年），否则在绑定的那个设置上报错；原来能通过校验的配置在第一次写回时抛溢出异常。只有本地表时没有这个转换，不检查。
  - **第二层的记录自带写入时间和字段集指纹**（`StableHash` 的规范编码，每个字符串带标签和长度前缀，覆盖记录格式、键布局的类型串、字段名、类型和顺序；原来用制表符和换行拼接，字段名里含这些字符时两套不同的字段可以拼出同一个串，一套的值被当作另一套读出，评审。改编码让升级前写的记录都成了不匹配，代价等于一次目录版本变更），新鲜度按记录里的写入时间判断，多个实例写同一个键时后写的胜。每个分块按它的调用被观察到按时应答的那一刻（缓存时钟）判断，不按读取循环处理到它的时刻：后面的分块可能在记录过期之后才应答（预发布评估），也可能早已应答、只是排在慢的第一块后面，按处理时刻判断会被误判为过期、送去回源，回源失败时特征失败。这个时刻在判定按时应答后立即读取，早于完成调用时的指标、健康和 span：宿主的监听器在完成调用时运行，它的耗时会让应答时还新鲜的记录被判为过期。指纹不同当作未命中（`mismatch`），不会读错；代价是两个目录版本同时在线（灰度）时互相覆盖对方的记录，命中率下降。存储的过期时间是记录可能的最长寿命（TTL 加最大浮动）加 `stale_if_error_ms`，减去已经过去的时间：过了这个时间，没有读者还能用它。已经过去的时间不取负值，结果至少 1 ms：等连接器期间时钟回拨，写入时间晚于当前时间，原来算出的过期时间超过上面校验过的最长保留时间，最长的合法设置溢出成负值；现在当作刚写入。
  - **第二层是绑定实例，身份只含存储自己的设置**（`store` 和 `timeout_ms` 之外），改等待时间不重连；本地表的身份含整个绑定，改任何 `cache` 设置都会换一张空表。第二层的时间用完后不再发送后续分块，余下的键直接交给连接器。释放第二层时先等写线程真正退出，开始释放后不再发新的批次（剩下的丢弃并计数），存储在 `finally` 里恰好释放一次；途中取消回调或指标监听器抛出的异常收集起来交给宿主记日志，监听器的异常不让写线程停下。
  - **`redis@1` 在单独的包 `StrataRec.Redis` 里**，核心包不依赖 StackExchange.Redis，宿主用 `AddRedis()` 注册。客户端用 StackExchange.Redis 3.x 的最新正式版（3.4.35）：原来停在 2.13，理由是 3.0 换了传输层（RESPite）、当时太新；3.x 已经发布五个月、出了多个补丁版本，再停在旧的大版本，修复和支持只会越来越少。升级没有改代码，它依赖的 `Microsoft.Extensions.Logging.Abstractions` 等 10.0.x 包本来就在用。Redis 不可达不让加载失败（它只是优化：计划先用连接器服务，客户端在后台重连，断线时命令立即失败、不排队）；秘密缺失、设置错误、服务器拒绝凭据让加载失败。拒绝凭据包括 NOAUTH/WRONGPASS，以及配置了 `user` 而 `ACL WHOAMI` 显示的不是它：默认用户没有密码的服务器会把认证失败的连接退回成 default 用户继续工作，只看连接是否失败抓不到；回答不了 `WHOAMI` 的服务器（Redis 6 之前、没有权限）信任这个连接。连上了就发一条命令判断（配置了 `user` 用 `ACL WHOAMI`，否则 `PING`），命令到达服务器，结论可靠；失败在整棵异常树里（含聚合异常的每个分支）找客户端的认证失败或服务器的 `NOAUTH`/`WRONGPASS`。没连上时客户端的失败说明不了原因，CI 里出现过一次要求密码的服务器、不带密码却加载成功。Codex 调查确定了两个原因（StackExchange.Redis 2.13 的源码，并用真实 Redis 确定性复现；升级到 3.4.35 后用旧逻辑仍然复现）：（1）收到拒绝时，客户端先通知连接结束、再发布拒绝的异常，连接返回、紧接着的命令在本地快速失败，拿到的异常里还没有认证失败；（2）客户端只保留一个连接的第一次失败，前面的连接被断开时，之后收到的拒绝永远不会出现在命令的失败里。所以拒绝要从看到它的那个连接读：“连不上就抛异常”的连接（`AbortOnConnectFail`）在放弃时读取客户端在它自己的连接上记下的拒绝，不受这两个问题影响。原来先建普通连接，没连上再用这种连接探测；但探测也可能在读到拒绝之前就超时或被断开，而主连接已经收到拒绝、还没发布（第三次 CI 偶发失败；评审用门控固定了“主连接未发布 + 探测在认证前失败”的组合，加载成功）。上一版跨连接保留证据（探测前后各在主连接上发命令、订阅它的 `ConnectionFailed`），只抓得到已经发布的拒绝，补不上这个组合。现在顺序反过来：先做“连不上就抛异常”的连接，最多两次、每次只试一次；连上了它就是存储的连接（这个设置只影响首次连接，之后照常重连），再发一条命令判断凭据；被拒绝就让加载失败；两次都是普通失败（宕机、认证前被断开）才按宕机处理，再建一个在后台重连的普通连接，它已经发布的失败仍然读一次。第二次针对第二个原因：最初的连接被断开，之后的连接才收到拒绝。剩下分不清的只有一种：服务器在握手前断开两次连接、第三次才拒绝，这时按宕机处理，读请求走连接器，与允许 Redis 宕机时启动的取舍一致。无论从连接还是命令的失败里读，都先找 TLS 握手失败：客户端把它也报成认证失败，上一版新增的命令检查曾把证书不受信任报成缺少密码；TLS 握手失败报在 `/tls`，提示检查证书或关掉 `tls`。代价：服务器接受连接却不回答时，加载最多等三次连接超时（原来两次）。没有选读取客户端内部记下的拒绝（不是公开 API），也没有选看客户端的日志（同样有发布顺序的问题）。测试复现了三种情况：门控卡住客户端发布拒绝之前的日志、代理重置最初两个连接、门控加上代理重置之后的所有连接；旧实现都加载成功。测试里的门控每卡一次就占住一个线程池线程，客户端读回拒绝也在线程池上，所以测试提高了线程池的最小线程数。加载被取消后晚到的连接随存储一起释放，释放最多等一次连接超时。每个连接只试一次（`ConnectRetry = 1`）：3.x 的初连默认试 3 次，服务器接受 TCP 却不回答时一次加载要等约 8 s；没连上的连接本来就在后台继续重连，初连多试几次没有好处。读是每块一次往返：单机 `MGET`；集群的 `MGET` 不能跨槽，改为一批流水线 `GET`，键不加 hash tag，一个键空间分散到各分片。CI 只测单机，集群路径没有测试。每个 `cache` 数据源一个 Redis 连接（实例身份含数据源名），同一个 endpoint 也不共享：数据源通常只有几个，按 endpoint 共享要把连接放到实例身份之外、另管引用计数，等连接数成了问题再做。固定的默认值：加载时连接超时 2 s（服务器不回答时最多三次，见上），分布式层的写队列 16 MiB。
  - **回放**：一次缓存读取录成一次特征调用（键、读到的值、结束状态），回放和 `local` 一样从录制经拉取路径回答，不碰表、第二层和连接器；录制的是读取实际用到的值，不管来自哪一层。缓存组不预取：预取发生在读取之前，那时还不知道哪些键会命中。
  - **分配**（`CacheAllocationTests`，Release）：全部新鲜 0 B（100 和 4000 个键）；本地未命中、第二层命中每键约 32 B（键和记录引用交给写线程）；本地未命中、连接器回答每键约 65 B（另加编码后的记录）。
  - **示例没有改成 `cache`**：`user_store` 的特征流水线没有用到；`item_store` 改成 `cache` 会改变示例的表数量、事件计数和计时相关的测试。端到端测试在示例副本上把 `item_store` 改成 `cache`（`CacheEngineTests`，Redis 的在 `RedisCacheTests`）。
- **`local` 与 `memory@1` 的请求耗时**（`FeatureSupplyBenchmarks`：示例流水线、无实验，`item_store` 每个候选 8 个特征、`author_store` 经外键每个候选 1 个，两种方式用同一批记录，拉取方式每个数据源每次只调用一次）。开发机（Xeon 6975P-C，.NET 10）上，500 候选：拉取 188 μs、20.2 KB，本地 81 μs、15.5 KB；5,000 候选：拉取 1,714 μs、36.1 KB，本地 596 μs、16.3 KB。本地方式的分配基本不随候选数增长。差距主要是 `memory@1` 自己的成本（每个值从 `JsonElement` 解码，`string` 值每次新建），再加上暂存和回填；真实的远程连接器还要加上网络往返，所以这个比例只说明请求路径本身的开销，不是两种部署的对比。
- **记录引用不带版本，按记录读取的接口不公开**。`LocalRecordRef` 只对查出它的版本有意义：同一张表的另一个版本经过压缩，字符串编码重新编号，拿旧引用去读会静默读出别的字符串（越界由 `FillCore` 挡住，不会读到页外）。没有让引用记住版本、读取时逐行核对：每行多一次比较，结构体变宽，而唯一的调用方本来就对每个请求钉住一个版本、所有记录都从它读。`TableVersion` 的查找和填充（`Find`、`Lookup`、`Fill`、`Read`）以及 `LocalRecordRef`、`LocalFieldRead` 改为内部，公开的只剩统计；用户读本地表的特征走特征目录。以后要开放按记录读取，再让引用带上版本。
