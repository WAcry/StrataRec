# 配置错误

- **JSON 绑定错误只在一处翻译，用 JSON 的说法**（`JsonBindingErrors`）。产物、算子配置、日志探针、实验补丁的各段和 `run` 的请求文件都经过它，同一种错误在哪里都是同一句话：未知键（有接近的就给 did you mean，否则列出允许的键）、值的种类不对（`'order' must be an integer or null, got the string "350".`，长值截断）、整数越界或带小数、缺少必需的键（提示里给出这个键的含义，取自 `[Description]` 或程序集旁的 XML 文档；单文件发布没有 XML 文档，只是少了这条提示）。翻译沿着错误路径同时走目标类型的 `JsonTypeInfo` 和文档本身，期望的种类来自类型、实际的值来自文档，不解析 System.Text.Json 的英文消息：那些消息里有 .NET 类型名，行号是重新序列化之后的；只有我们自己的转换器写的消息直接采用。错误码和指针不变。值的错误（特征默认值、参数值、enum、表条目、请求输入）统一用 “must be …, got …”。只在出错时运行，绑定成功的路径不受影响。翻译用 System.Text.Json 实际读值的契约：多态类型按 discriminator 取派生类型；字符串枚举用读值的那个转换器写出每个值，得到真实的名字；看不出形状的第三方转换器给通用消息，不猜种类。描述错误本身从不抛异常：文档里读不出的部分（非法 Unicode、重复的键）先作为带位置的错误报告，字符串入口失败后用严格的 JSONC 重读；不是 `JsonException` 的异常只在文档能解释它时翻译，否则照常抛出，当作程序错误。键里有 `'`、`]`、`.` 时错误路径可能有几种读法，只采用文档里恰好成立的那一种；零种或多种时报它们共同的祖先和通用消息，宁可笼统也不给一个错误的具体结论。
- **同一份文档，从哪个入口读都是同一个结论**。工作区文件先由 `Jsonc` 严格读取（语法、重复的键、Unicode、深度）再绑定；字符串入口（发布清单、回放包、内容存储里的产物）原来直接交给序列化器，序列化器默认保留重复键的最后一个值，只在绑定失败后才严格重读：同一份带重复键的文档，作为文件被拒绝，作为字符串被接受。现在 `ArtifactSerializer.Deserialize(string)` 先做同样的检查（不建树，只走一遍读取器），再从同一份字节绑定；`ArtifactSerializer.Options` 也设 `AllowDuplicateProperties = false`，给自己用这套选项的宿主。`memory@1` 和 `memory_list@1` 的数据文件原来各自用宽松的 `JsonDocument` 读（两份相同的代码），现在共用 `DataFile.Read`，同样严格。`Jsonc` 只负责读取：它原来还有一套没有被任何产品代码用到的反序列化选项和 `Deserialize`，注释却说“每个产物都用它”，两套规则只会分叉，删掉了。保留的差异各有用途：手写的文件是 JSONC，HTTP 请求体是严格 JSON（重复键由 `RequestSchema` 拒绝）；产物成员用 snake_case，字典键原样；产物省略可选的 null，结果文档用 null 表示缺失；回放包保留非有限浮点，服务结果写成 null；内容哈希用独立的 RFC 8785 规范化。没有接入源生成：绑定只在加载时发生，不在请求路径上；宿主的自定义算子配置也要绑定，源生成会要求扩展作者把类型登记进一个上下文；目标也不是 AOT。
- **位置在打印时计算，编译不读文件**。产生诊断的代码只报产物、JSON 指针和表达式偏移（`ConfigDiagnostic.Offset`，可选）；CLI 打印时才读对应的 JSONC 文件（`JsoncLocator`），把指针换算成行列，输出 `file:line:col: error CODE /pointer: message`，终端和编辑器能直接跳转；`--format json` 多出可选的 `file`、`line`、`column`，读输出的程序不受影响。对象成员定位到键（编辑器在键上标拼错和缺少），数组元素定位到值，表达式错误定位到字符串里那个字符（算上转义和多字节字符）。指针在文件里找不到时（合并或补丁之后的视图）回到最近的祖先，绝不猜一个行号。显示的路径是 `-c` 给的目录加上工作区内的相对路径，从当前目录就能打开。没有文件的诊断（store 里的 manifest、臂新增的列和参数）照旧打印。产物标签到文件先按完整标签匹配（ID 可以含空格），找不到才去掉格式明确的臂组合后缀，找不到就不给文件，绝不指向另一个文件。表达式偏移以 UTF-16 单位计，原样写的非 BMP 字符的低代理有自己的列。文本输出在定位到的诊断下面打印那一行（去掉缩进）和指向列的 `^`：表达式的错误常在一个很长的字符串的中间，终端里的读者不必去数第 93 列。超过 100 个字符的行只显示列附近的一段，用 `...` 标出截断；`^` 前的填充按码点计算：制表符照抄；组合符、格式字符不占位，不管它在哪个区段；宽字符（中日韩文字、全角符号、emoji 区段、补充表意平面）填一个全角空格；其他字符占一格，补充平面里窄的字符也是一格（原来把所有代理对都算宽，也把宽区段里的组合符算宽）。所以中文配置里也对得上。只在文件里找到了位置时才打印（找不到时位置是文件的第一行，不画一个错误的箭头）；JSON 输出不变。表达式错误的消息为了单独阅读引用了整个表达式（“at offset 53 in '…'”），打印了源码行时改用 `ConfigDiagnostic.Brief`，不再把表达式重复一遍：多行的 `let` 公式原来会把整段公式连同换行塞进第一行。消息本身不变，日志、JSON 和没有源码行的输出照旧带着偏移和表达式。
- **类型错误指向出错的部分**。二元运算只有一边错时指向那一边，两边都错或各自合法、组合起来不合法时指向运算符；函数指向从左往右第一个类型不对的参数，从不指向函数名；参数各自合法但彼此不符（`dot`、`cosine` 声明的长度不同）时指向后一个；`contains`、`in` 的容器不是列表时指向容器，否则指向元素；`??` 指向右边，`?:` 指向 else 分支；参数个数不对指向整个调用。
- **一个错误只报一次：出错的声明标为不可用，引用它的地方不再报错**（`PlanSchema.MarkUnusable`）。类型写错的列、参数、请求输入、特征，配置错误的节点、漏斗组（每一条报了错的路径）、实体键，无效的臂都这样处理；原来一个 `int46` 会连带报出四到七个错误。没有给出错的声明注册一个占位类型：占位类型要么引出不存在的类型错误，要么让本该失败的引用编译通过。编译照样失败，因为声明本身的错误已经报了。代价：修好第一个错误之后，可能冒出原先被遮住的错误。
- **类型名的拼写只在一处规定**（`ConfigTypes`）：列和请求输入、特征、参数各自接受哪些类型，拼错时给出 did you mean（`int46` → `int64`，`double` → `float64`），提示列出的就是这个位置实际接受的类型。提示只推荐这个位置真正接受的写法：参数写成 `int32?` 时建议 `int64`，不建议同样不被接受的 `int32`。
- **JSON 整数按原文精确判定**（`JsonIntegers`）。`.0` 和指数写法只在恰好等于一个整数时接受，判断不经过 double，也不经过 decimal：double 分不清相邻的大整数，decimal 超过 28 位有效数字会舍入，两者都会把一个非整数或另一个整数当成写下的值（`[9007199254740993.0]` 原来被读成 9007199254740992）。普通整数先直接读 int64，不分配。它是公开的 API，所以自己也按 RFC 8259 的数字语法检查，不依赖调用方先用 JSON 解析器过一遍：前导零（`01`）、小数点后没有数字（`1.`）不是数字。指数的绝对值超过“原文长度 + 19”才直接判为越界或非整数：很长的尾数能抵消同样大的指数（`1` 后面两千个 `0` 再 `e-2000` 就是 1），固定的界限会在尾数足够长时判错；超过这个界限时，尾数的有效数字无论怎样排列都到不了 int64 的范围，也补不成整数。这条只适用于请求：配置会以 RFC 8785 规范形式存进 manifest，在那里 `.0` 或指数写法的整数是 double，超过 ±2^53 时最短表示可能是另一个整数（2^60 写成 `1152921504606846976.0`，从 manifest 读回是 1152921504606847000），工作区和 manifest 跑出不同的值。所以配置值（参数、默认值、枚举、查找表）的这类整数在绑定时报错，位于值的指针、用各自的错误码，提示写成字符串；规范形式不变的（`1e18`）照常接受。普通数字写法由规范化器拒绝（`ARTIFACT_NOT_CANONICAL`）。
- **`run` 的请求文件和产物一样严格绑定**：拼错的成员（`inptus`）原来被静默忽略，到运行时才报“输入缺失”，现在是带位置的错误。
- **CLI 的 JSON 输出不做 HTML 转义**：输出给终端和程序，不嵌进网页，默认编码器会把 `'` 写成 `\u0027`，消息就难读了。
- **内置客户端（`linear@1`、`memory@1`、`memory_list@1`）严格检查设置**：不认识的设置和类型不对的值都是错误，位置是绑定里的 JSON 指针，提示相近的名字（数据文件里的成员报在 `/data_file`，消息写出文件和文件内的位置）。原来拼错的设置被忽略、用默认值，`"activaton": "sigmoid"` 静默变成恒等激活；类型不对时抛出没有位置的异常。`init` 和示例绑定的正是它们，也是用户最先改的地方。包装它们的客户端只把它们认识的设置转过去。客户端创建时的其他异常（读不到文件等）报在绑定上（`BINDING_SETTINGS`，各种绑定同一个码）；原来候选源的这类错误报在引用它的召回节点的 `/quotas_param` 上。召回节点有源绑定失败时，仍然声明自己的列，并报告每一个失败的源，读这些列的节点不再连带报 `EXPR_UNKNOWN_NAME`。拼写建议的规则移到 Core（`Spelling`），产物和绑定共用一条规则，Artifacts 因此引用 Core（依赖方向不变）。
- **引擎保存的配置副本比文件多留几层嵌套深度**。恰好 64 层的绑定文件能通过 `validate` 和 `build`，加载计划时却在序列化副本那一步抛 `JsonException`：产物被包进编译请求之后深了几层。
