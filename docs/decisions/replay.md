# 回放

回放包的结构见 `stratarec schema replay_bundle`（`src/StrataRec.Artifacts/Model/ReplayBundle.cs`），这里只记取舍。

- **回放包的布局一变就升格式版本，读取时先看版本再解析结构**。不在同一个版本号下原地修改布局，哪怕那个版本只在主干上出现过：已经录下的包无从分辨自己是哪种布局。读取器只读当前版本；其他版本在 `/format` 处拒绝并提示用当前构建重新录制，不把旧布局当作当前版本的结构错误报告。先读版本时和完整解析一样跳过开头的 BOM（字符串入口原来没跳，带 BOM 的旧包报成了布局错误）。没有选择兼容读取旧版本：回放包是调试用的短期产物，重新录制的代价小于维护多套读取逻辑。
- **1.0 之前公开 API 直接不兼容地改，不保留旧重载**。只发 NuGet 包，宿主升级时重新编译；不考虑只替换 DLL 的二进制兼容，所以去掉或改签名的公开方法（例如 `StrictJson.Check` 的单参数和双参数重载）不留转发的旧入口，评审不再把它算作问题。要改的调用在编译时就报出来。
- **持久化格式的版本是日期加当日序号**（`stratarec.replay_bundle/2026-11-21.7`；缓存记录头是 `uint32` 的 `2026111601`）。日期说明一份数据是什么时候的布局，同一天再改就是 `.2`，按文本也能排序；布局不变、记录的含义变了（例如调用的分批规则）也要改版本，否则旧数据会被按新含义读错；原来的 `/1` 到 `/4` 不保留任何兼容读取（1.0 之前）。算子和客户端的类型版本（`TopK@1`、`memory@1`）仍是序号：它是每个节点都要写的标识，短、常见，只在破坏性地改配置时加一。
- **在框架的调用点录制和回放，不在连接器里**。特征拉取由 `FeatureFetcher` 的调用点经 `IFeatureCallHook` 录制（读连接器解码后的暂存缓冲区，按键记录值），其他外部调用经 `OperatorContext.CallAsync`。宿主注册的连接器、服务客户端和算子不用实现任何东西就能录制和回放。没有选择包装 `IFeatureSourceConnector` / `IServiceClient`：包装层看不到超时、跳过等执行决定，回放时也要重写按键匹配。代价：自定义算子如果绕过它直接调用客户端，不会被录制，回放时会真的调用外部服务。
- **录制按请求开启，关闭时只多几个字段**。`DebugOptions.Record` 默认关闭；关闭时每次外部调用多一次空检查，每请求多约 40 B（请求状态和拉取器上的字段），不做任何按行的工作。开启时分配与请求拉取的数据量成正比，示例请求约 95 KB、多约 0.4 ms，不适合全量常开；按比例常开录制以后再做。
- **计时决定取自录制，回放不计时**。回放的截止时间是 1 小时，不设节点超时：节点的 `min_remaining_ms` 比较用录制时该节点的剩余时间，每次尝试按录制的结果（`ran`、`deadline_exceeded`、`timed_out`）处理，外部调用按录制的状态返回。没有用录制的耗时驱动虚拟时钟：配置一改，调用的顺序和并发就变了，模拟出来的决定在线上从未发生过。代价：修改后的配置里新增的节点没有录制的时间，视为时间充足，永远不会因时间被跳过或超时。
- **数据先按调用精确匹配，再按值合成**。同一数据源、同样的键和顺序、并且包含全部所需字段的调用原样重放，包括超时和失败。只覆盖部分字段的调用不算精确匹配：否则其余字段会被报成缺口，而录制里别的调用其实取到过它们。配置改变了键、字段或分批时，按（数据源、实体、键、字段）从录制中成功的调用取值；取不到的值是缺失，并按原因计入缺口报告（`not_recorded`、`type_changed`、`limit_exceeds_recording`、`inputs_changed`）。录制的值换成新类型时有损（例如超出 float32 范围）也算 `type_changed`，精确匹配和合成用同一条规则，不让溢出变成 ±∞ 混进结果。合成的调用状态是 `ok`：录制中超时的分批不会映射到新的分批上，那些键的值只是缺失。失败调用的数据从不使用。服务调用的匹配见“外部依赖”第 2 步。
- **模型输出按实体和输入摘要匹配**（第 2 步起是所有有逐项键的服务调用）。每行输出按实体 id 和该行全部输入的 XXH3 摘要记录，只在输入没变时使用；输入变了算缺口（`inputs_changed`），输出缺失。没有选择忽略输入直接复用：那会在特征改动后静默地显示旧分数。哪些输入按行切分只看张量约定：首维等于 `batch_size` 的输入每行取自己的切片，其余输入（共享的用户向量、文本）整体计入每一行的摘要，不按长度能否整除来猜。摘要包含每个输入的元素类型和形状，按行切分的输入不计批维度，所以换一种分批仍然匹配，而同样的数值换一种形状不会。同一实体可能以不同输入被打分多次，合成时按（实体、摘要）查找。回放也不调用模型客户端。因此修改模型绑定（例如线性模型的权重）不改变回放结果；评估模型本身的改动要用实时模式或草稿预览。
- **模型输出按类型记录，回放包格式升到 `2026-11-21.1`，同一天又升到 `.2`、`.3`**（2026-11-21，随“模型张量的元素类型就是声明的类型”）。`.2`、`.3` 的布局和 `.1` 一样，含义变了：`.2` 的结果列按声明的类型记录，float32 请求输入按最近的 float 回放（见“转换到 float32 类型的值舍入成 float”）；`.3` 的请求输入按宿主给的值的类型记录，被绑定器化简成名字的运算不再算引用（见“出口交付声明的类型”）。同一个包在前一个构建里回放出的是另一个值，按版本规则升级。每个张量输出记成 `{ "type", "values" }`：`type` 是元素类型（`bool`、`int32`、`int64`、`float32`、`float64`、`string`），`values` 按值编码写（int64 超过 2^53 也精确，float64 不舍入，非有限值写成字符串）。原来输出只有 float32，记成一个浮点数组。类型写在值旁边，和特征调用一样：读取时按记下的类型解码，客户端写的是什么类型，回放交给节点的就是什么类型，节点因此做出和录制时相同的判断（包括类型不一致时失败）。合成调用时，录制里找不到的行在浮点输出里是 NaN（列写入时换成默认值，和任何非有限值一样），在其他类型里是这个类型的零值（false、0、空字符串），两种情况都报成缺口；整数和字符串没有“非有限值”可用，零值会照样写进列，回放报告里的缺口说明这些行不可信。考虑过让合成的整数行缺失：那要给张量加有效位图，只为回放的缺口，所有客户端都要多处理一种情况，不值得。合成的输出布局（每个输出的类型和每行元素数）取自这次调用匹配到的录制行，其次才是同一模型的其他调用：两个节点调用同一个模型，把同名输出写进 `list<int32,2>` 和 `list<int32,3>` 两种列时，原来按最先录下的那次调用定宽度，另一个节点的行全成了缺口。一行也没匹配到时（输入都变了），先取同一节点的录制调用，再取任何调用。录制里元素数不是行数整数倍的输出不按行切，合成时不写它：算子读的输出是客户端多写了（录制时调用成功、节点失败），节点照样因为缺了它失败；算子不读的输出（签名里调用级的值，如一个 loss）本来就不需要。原来按“元素数 / 批大小”切，换一种分批后请求反而成功了；中间一版让匹配到它的合成调用整体失败，又让带调用级输出的合法调用换一种分批就失败（两轮）。
  - 有意不处理：回放不知道算子读哪些输出（ModelCall 不带输出名），只能从录制推断。所以两种情况不完全如实：一批多写了已映射的输出、另一批同名输出正常时，换一种分批回放，前一批的行按缺口填充，节点成功，而录制时它失败、走了后备；一行的批次里调用级的 loss 看起来像逐行输出，多行批次的行就被报成缺少它的缺口（结果不受影响）。两种都不静默：缺口和节点的成败差异都在回放报告里。前一种要客户端越过形状写值（它本身是缺陷，在线时节点就报了），第 2 步之后调用带上要读的输出（`ServiceCall.Outputs`），只录制这些，后一种不再出现。
  - 两处有意不处理：输入摘要把 −0.0 和 0.0 当作同一个值（和 `hash01` 一样按规范编码）；模型的回答几乎从不依赖零的符号，而一个等价的表达式改写可能得到另一个零，按位区分会把它报成输入变了。字符串输出里的孤立代理项（.NET 字符串可以有，UTF-8 和 JSON 不能）在录制时变成 U+FFFD，回放拿到的是替换后的字符串；只有自己构造这种字符串的扩展会遇到，为它在每行输出上校验 UTF-16 不值得。
- **模型客户端抛出的异常是失败状态，不是异常**。`CallAsync` 把客户端抛出的异常变成失败的 `ServiceStatus`，错误文本是 `threw <类型名>: <消息>`，模型、召回和其他服务都一样；录制只记状态和错误文本，回放原样返回。原来异常原样抛给算子：为了让按异常类型处理的算子在回放时走同一条路，录制要记下异常类型的身份（完整名、程序集、泛型参数），回放在已加载的程序集里按身份找回类型、用消息重新创建，找不到时换成 ReplayedCallException。这套反射约 230 行，还要防止回放包让回放进程加载程序集，而算子判断 `status.Succeeded` 就够了：框架的约定本来就是失败是结果。仍然抛出的只有取消：节点预算用完或调用方取消时，算子收到 `OperationCanceledException`，录制的 `threw` 只表示这一种，回放也抛出它。代价：按异常类型区分处理的算子要改为看错误文本（类型名在文本里）；回放包格式改为 `2026-11-16.1`，不读旧包（1.0 之前）。
- **回放用录制的臂，不重新查询分配**。实验平台的分配变了，同一请求在线上会进入别的臂，但回放要比较的是同一处理下配置的差别。`--arms` 可以指定别的臂；回放计划里没有的臂和请求输入会被去掉，并写进报告的说明。
- **回放不是流量**。回放不记指标、事件日志和 span，不写持久日志（探针捕获到结果里）。否则回放录制下来的失败（例如特征源报错）会把一个健康的依赖判为失败，CI 的批量回放也会混进延迟分布。没有选择加 `replay` 标签区分：所有看板和告警都得过滤它。录制则不改变任何观测：被录制的请求照常计入。
- **后备流水线是包里单独的一次运行**（`role: fallback_pipeline`）。回放时主流水线失败，就用这份录制回放后备流水线；录制中主流水线失败却没有运行后备流水线（时间已用完），回放也不运行。
- **中止的请求也交付回放包，内容是中止那一刻的快照**。被调用方取消或因缺陷中止的请求没有结果，`RecResult.Recording` 带不出回放包，所以录制经回调交付：`DebugOptions.OnRecording` 收到整个请求的回放包（执行器在每次运行退出时把这次运行的录制交给引擎，由引擎组成回放包）。返回和中止都会调用回调；回调抛出的异常只记日志，不改变请求的结果，取消照常传给调用方。中止时立即构建录制，不等任何调用。召回源和模型调用的等待在调用方取消时就结束，调用点把它记为 `cancelled`，这正是请求看到的；快照时调用点还没有记录的调用（例如算子发出后没有等待的调用）记为 `outstanding`，它的键和模型输入摘要在调用开始时就已记下；之后才完成的调用的数据不在包里。中止的包只用来查看，不回放（见下一条）。没有选择等在途调用完成再交付：不理会取消的连接器会让取消迟迟到不了调用方。也没有选择把录制挂在异常上（`Exception.Data` 或专用异常类型）：调用方得改写 catch 才拿得到，取消的异常类型也会变。代价：快照之后才返回的数据丢了；在查询分配阶段就中止的请求还没有运行流水线，没有回放包。
- **被放弃的调用按请求看到的录制**。超时被放弃的召回源和模型调用记为 `timeout`，不带数据（召回源不记返回的 id，模型不记输出），因为请求没有用到它们；客户端之后才返回的东西不进入录制。节点按超时结束、晚到的成功被丢弃时，调用本身照实记为 `ok`，节点尝试记为 `timed_out`，回放按尝试的结果处理，不使用这次调用的输出。回放时这些调用直接按录制的结果返回，不等待。
- **中止的请求不回放**（审计 E6）。原来回放中止的包时，引擎复现录制里每个已完成位置的决定，在录制没有完成的第一个位置停下，把正在执行的节点再记一次 `aborted`，并按录制恢复这个位置已经触发的实验；为此录制要在中止的节点上记下 `triggered`，被录制的请求在每个位置开始时都要复制一份触发状态。这套机制价值很小：调用方取消的请求没有结果可比；缺陷导致的中止也复现不了，回放停在出错的节点之前，修好的二进制照样报告“按录制中止”。现在回放中止的包什么都不执行，只报告录制的中止原因、当时正在执行的节点和各节点的决定（`ReplayOutcome.NotReplayed`），结果是占位的失败，差异不算相同；不需要引擎，`RecEngine.Aborted(bundle)` 直接给出，所以 `replay -s` 不必先为它找到录制时的配置。录制和交付不变，中止请求的 `$experiments` 记录和已捕获的探针照常发布。`replay` 和 `compare` 把这类包单独计数：它们不算读不出来的包，也不进入两边的统计（不再计入错误率）；一个包都没回放成时仍以 2 退出。回放包格式改为 `2026-11-16.2`（节点不再有 `triggered`），不读旧包。代价：中止的请求不能在修改后的配置上重跑观察差异；要重现缺陷，用同样的请求输入重新执行（`run` 或草稿预览）。
- **值编码复用日志编码，类型写在值旁边，但保留非有限值**。`null` 是缺失；NaN 和 ±∞（包括浮点列表的元素）写成字符串 `"NaN"`、`"Infinity"`、`"-Infinity"`，日志里仍然写成 `null`。回放包必须如实保留请求看到的值：并不是每条路径都会先把非有限值换成缺失或默认值，暂存的原始列表和直接求值的输出表达式就不会，按缺失录制会让回放走另一条路（`has()` 变成假、结果出现差异）。两者共用同一个编码器，回放包只是打开一个选项，没有另写一套。每个值按旁边记录的类型解码，类型不兼容时报出 JSON 指针。
- **对比指标的定义**。Top-K 重合度 = 交集 / 两个 Top-K 中较长者，短列表不会抬高重合度；Kendall τ 只在两边共有的条目上计算，少于两个时为空；分数分布变化用双样本 KS 统计量，另给同一条目的分数差；两者都只用有限的分数，NaN 和 ±∞ 按每一边单独计数报告：它们没有位置可排，混进去会让 KS 失去意义，NaN 还会让排序比较不再自洽。降级率的分母是全部请求，分子只算成功但降级服务的请求；失败的请求只算错误，不算降级。特征缺失率包括数据源本身缺失和回放包里没有的值。录制模式下外部 I/O 立即返回，延迟只反映引擎计算，不能用来评估依赖延迟。配置增删的输出列在差异中单独列出，不逐条重复。
- **`replay` 和 `compare` 只有用上了每个包才算通过**。没有包、包全部读不出来、或者一个都没比较成，以 2 退出；部分包读不出来也以 2 退出，但照常输出报告，JSON 里带 `status`（`ok`、`partial`、`failed`）和读不出来的包数。CI 用退出码判断对比是否通过，只覆盖一部分包（或一个都没覆盖）的指标不能当作干净的结果放行。中止请求的包不回放，不算没用上，但一个包都没回放或比较成时仍以 2 退出。没有选择部分成功时返回 0 只在报告里标出：CI 步骤通常只看退出码。
- **批量对比里，只有一侧回放了的包不计入任何一侧的比率**。逐对比较本来就只算两侧都有结果的包，两侧各自的汇总却各算各的：基线能跑、候选没有这条流水线的包，让基线显示 2 个样本 50% 错误率，候选显示 1 个样本 0%。这样的包仍然在请求明细里，带着它的错误。
- **算子的行为变了，不升录制的格式**（2026-11-26，不改）。格式版本说的是包里数据的布局和含义：一次调用按节点、它在这次运行里的次序和被调用方记录，这些没有变。`PipelineColumns@1` 改成先读完所有行的输入再发起调用之后，一次读输入失败的尝试不再留下调用，所以旧构建录下的这种请求在新构建上回放时，后面的调用对上的是另一个序号的答案，结果不同而没有缺口。这是两个构建的行为差异，回放给出的正是结果的差异，跨构建回放本来就是用来看它的；一个包并不保证换了构建还能回放出同样的结果。按算子的每次修正升格式，会让所有已有的录制在每次修正之后作废。只有录制本身的布局或者字段的含义变了才升。
