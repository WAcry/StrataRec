# 特征拉取

- **输出只为返回的行补齐特征**（预发布评估 2026-11-18）。原来先选出前 K 行，再为全部存活行补齐输出读到的特征：没有返回的行上一个存不下的派生值会让请求失败（候选 1、2，`limit` 为 1，item 2 的值存不进不可空 int32），K 为 0 时也一样，而且为没人看的行拉取和计算。现在 `FeatureFetcher` 有按行补齐，和整表补齐走同一条路径，只标记给定的行已填充。状态仍是每个请求每个特征一个，由每次补齐按同一规则写入；失败一经记下就保留到请求结束，不降级：按行补齐记下的失败，之后的整表补齐照样报告，即使失败的行已被淘汰（一次补齐同样的行时可能只是降级）；它记下的成功只覆盖它的行，其余行留给下一次补齐。按行补齐只等待请求过它的行的键的在途预取：这些行里有一行在预取携带的特征上还没填，并且这行的键在预取的键里，才等待。查键的方法和预取回填时相同：可变部分在预取的键索引里查，共享部分（请求输入、上下文键）在同一请求内对所有拉取都相同，所以复合键和读候选列的键不用另写。否则预取是为别的行发起的（例如追加行之后后备算子声明的读取），留到之后的整表补齐或请求结束时按未读预取结算，这些行的键由按行补齐自己拉取。原来输出也等它：它对所有键失败时把特征记为失败，返回的行已经填好，或者返回的行是预取发出之后才追加的、连接器从没被问到它们的键，请求都会失败。有一行命中就等待，和原来一样：预取失败时补齐失败，缺的键不再拉；预取成功时只补拉缺的键。判断按键不按行，因为键相同的追加行本来就由预取的回填填上。键检查不逐行分配（第一次读还没建的填充位图时会租一次缓冲）。`limit` 为 0 时跳过的只是候选特征：只有输出读的上下文特征仍在请求开始时随上下文预取发出。预取在选行之前、与召回并发，正是为了不让输出多等一次往返；为返回零行的请求把输出的上下文依赖单独拆出、推迟到知道行数之后，会让每个非空请求变慢，省下的只是零行请求的一次请求级调用。没有选“按行记录失败”：要给每个特征加逐行失败位图，所有读取方都要改，而“失败不重试”本来就是请求内的规则（避免每个读取方再等一次超时）。代价有两个，都是这条规则本身的：返回的行上所有键都失败时特征失败，而为全部行拉取时可能只是降级；更早的节点在整表补齐中记下的失败（节点 `on_failure: skip`）在输出时仍然生效，即使失败的行没有返回。
- **分批取最少的批数，各批一样大**（2026-11-20 用户建议）。特征拉取的分批、缓存分布式层的分块读取和模型调用（`ModelScorer@1`、`PairwiseRanker@1`）都按上限分成最少的批数 k，每批 ⌈N/k⌉ 个，最后一批是剩下的（`Batching.Size`）：9 个键、`max_batch` 4 分成 3、3、3，原来是 4、4、1；1,001 行、`batch_size` 1,000 分成 501、500，原来是 1,000、1。同一次调用的各批并发发出，最大的一批决定等多久，后端也拿到均匀的负载。批数不变，不多一次调用，每批也不超过上限：⌈N/k⌉ 正是分成 k 批时最大一批能有的最小值。没有选“前几批各多一个”的完全均分（10 个分成 4、3、3，这里是 4、4、2）：最大一批一样，而批大小固定时，各调用点仍按“第 c 批从 c × 批大小开始”计算，暂存区和从键找批的计算都不用改。回放：改动之前的录制按旧的边界分批，在新的边界下对不上：成对模型的调用不带行键、只能整次匹配，一次超时记在它那一批上，重新分批后成功变成缺口、超时变成成功。所以录制格式升为 `2026-11-20.2`，旧录制被拒绝，要重新录制；不保留按旧规则分批的读取路径（持久化格式不保留旧读取器）。格式在每个读取、解释或执行录制的入口检查，不只在读文件时（`Serialize`/`Save` 只是归档，原样写出对象的格式，写出的旧格式文件读回时被拒绝）：宿主从自己的存储反序列化出录制对象、直接交给 `ReplayAsync`、`Aborted` 或命令行为录制找引擎的 `ReplayEngines.ForAsync` 也一样被拒绝（检查是公开的 `ReplayBundleFile.CheckFormat`，宿主读出录制时也可以先调用），录制的 JSON Schema 也把 `format` 固定为当前版本（布局没变，反序列化成功不能说明版本对）。同一格式下用改了 `max_batch` 或 `batch_size` 的配置回放，成功的特征调用按键、带行键的模型调用按行重组；重组后仍对不上的（成对模型的调用只能整次匹配）照旧报为缺口。
一次拉取按 `max_batch` 拆成多个分批，每个分批是一次连接器调用。示例请求 5,000 候选时有两百多个分批，原来每个分批约 420 B，占请求分配的四分之三。下面几条让连接器同步返回的分批不再分配（按分批数翻倍的测试锁定为 0 B）。
- **召回源可以带查询值，每一路只等自己的查询读的特征**（2026-11-20 用户提问：双塔召回服务要用户特征作为输入）。原来 ICandidateSource 只收到原始请求输入（CandidateQuery.Inputs），拿不到特征目录里的任何东西：双塔召回要的用户嵌入只能由召回服务自己再查一次，绕开了拉取、缓存、录制和回放，实验也改不了它。`MultiSourceRecall@1` 加了 `queries`：给每个源声明一组值名，各对应一个请求级表达式，在调用时求值，经 CandidateQuery.Values 交给源。值按名字排序，类型是表达式的类型：上下文值在表达式里是提升后的类型，所以 float32 列表是 float64 列表，元素就是原来的 float32（IO 第 2 步复核后改为声明的类型，见“外部依赖”）。
  - **按源等待。** 查询读的上下文特征仍然算节点的读取（在 `CompiledNode.ReadFeatures` 里），预取、数据流检查、实验足迹和探针都不用改。但它们不在 `FilledFeatures` 里，节点开始前不补齐。算子用 `OperatorCompileContext.CompileAwaitedExpression` 编译查询，运行时调用 `OperatorContext.WhenEachReadyAsync`，传入每一路的等待读取和一个回调。它在算子自己的执行流上一轮一轮地做：先对预取的就绪任务观察一次（每个任务只看一次是否完成），再按源的顺序处理这次观察能确定结果的每一路（特征都存好了，或其中一个已经失败），对每一路调用回调发出或拒绝；最后等这次观察里任意一个还在途的任务。没有查询的源立即发出：示例里 popular 不等用户特征，录制里它因此排在 two_tower 前面。查询在算子自己的执行流上逐个求值。最初的实现每一路各自异步等待，评审找出它的四个问题，根子都在这里：
    - 等待原来由节点的取消令牌结束。召回客户端也在这个令牌上注册回调，令牌取消时回调在取消的线程上从新到旧执行，一个晚于等待注册、执行很久的客户端回调能把等待拖过截止时间。现在等待和外部调用（`BoundedCall`）一样，用截止时间本身和调用方的令牌约束，不经过节点的令牌。
    - 节点提前结束（预算到期）时，被丢下的等待之后还会读请求内存里的就绪数组，而那时数组可能已经归还。现在算子只在自己的执行流上取预取的就绪任务（`FeatureFetcher.ContextStoredTask`）和特征状态（`ContextStoredState`），放弃等待之后不再读请求的任何东西；被丢下的只是对预取任务的等待，预取自己持有请求内存，到它的全部任务结束才释放。
    - 几路的特征同时存好时，各自的等待竞争谁先发出（Codex 跑 24 次，two_tower 先发 1 次）。现在每一轮按 `source_order` 处理，录制顺序稳定。
    - 一路读的特征有一个已经失败，它仍等其他特征，可能一直等到预算到期，整个节点超时。现在一个失败就立即拒绝这一路。
    - **评审又改了一次。** 第一次改法（评审之后）是每一路各问一次“好了没有”、再收集没完成的任务来等，评审又找出三个问题，所以改成每轮只观察一次：两次检查之间完成的任务被收集时滤掉，这一路要等到另一个特征存好才发（例如地区特征存好了，two_tower 却要等 region_store 应答）；同一个任务在检查前一路和后一路之间完成，后一路先发；只剩一个任务时直接等它，它自己抛出的 `TimeoutException` 被当成了节点超时。现在等的是这次观察里没完成的任务（`Task.WhenAny`，本身不会抛出），观察之后完成的会立即开始下一轮；预取的故障由下一轮读状态时原样抛出。
  - **一起改的两条。** 查询读的上下文衍生特征原来要等整个预取结束才算出，现在和被键读的衍生特征一样在输入存好时就算（`FeatureRuntimeInfo.ComputedEarly`，原名 ReadByKey：`PlanBuilder` 收集各节点的等待读取，交给 `FeaturePlan.Create`），有一个输入失败就立即记为失败，不再等其余输入（直接读这些输入的查询立即被拒绝，读它们的衍生特征的查询却等到节点超时）；发出的调用原来只有取消异常时还等其余调用，现在不管抛出什么都先等全部调用结束，每次调用都录制完，节点才出结果。代价：特征还在途时，每轮等待分配一个 `Task.WhenAny`（观察用的三个列表在循环外分配、逐轮复用），按请求计，不按行。截止时间在每轮开始、读每一项的状态之前、调用算子的代码（取它列表里的一项、调用它的回调）之前都检查，不只靠等待本身：前一个回调运行到截止时间之后，下一轮观察到的已完成任务会让 `Task.WhenAny` 立即完成，带时限的等待也就不会超时，迟到的读取会在截止时间之后被结算；读状态之前要检查，是因为读状态会原样抛出预取的故障，它不能顶替先到的截止时间或调用方取消；回调之前也要检查，因为判定一项要遍历它的特征，读的特征多时也要时间。算子传入的读取列表只在开头按顺序过一遍，每项取一次，之后不再索引：列表是算子自己的，取一项可能就慢，原来每轮都按下标取，检查与它保护的操作之间夹着算子的代码，截止时间一过回调照样执行，已故障的预取也会顶替超时或取消；过这一遍时每取一项之前也检查，截止时间过了就不再取后面的项。无需等待的项在这一遍里当场结算，其余的项连同它的特征记进等待表，不另外复制列表：什么都不等的算子不分配。等待表每项 16 B（下标和特征），比原来只记下标的 4 B 多：内置召回有要等的查询时，每个请求多 8–24 B（评审实测，250 候选的示例约 18 KB）。不改：成本按读取组计（至多 64 组），不按候选；为它租请求的临时缓冲，每个退出路径都要归还，换几十字节不值得。列表的 `Count` 也是算子的代码，读它之前同样检查。检查只能看到检查那一刻：最后一次检查之后才到的取消，回调仍会运行，由回调自己的令牌看到。
  - **否决的做法：**
    - 把整个请求上下文交给源。源会读到没有声明的特征，计划不知道要预取哪些，实验足迹看不到，录制也无从比较。
    - 节点级等待，即把查询读的特征当作普通读取、在节点开始前补齐。这最简单，但一个慢的用户特征会推迟所有召回源，包括不需要它的；召回正是要和上下文预取并发的那一段（见下一条）。
    - 在绑定里声明查询。查询读什么属于流水线（实验要能改），绑定只描述物理连接。
  - **失败语义。** 查询读的特征失败时，这一路不发出，按失败的召回源计：其余源照常，节点降级；全部失败时节点失败。特征降级时照常发出，节点降级。值缺失时按缺失发送，不变成 0。
  - **等待计入节点预算。** 预算到期时整个节点被截断，和在途的调用一样。只想让这一路失败，就给特征源设一个比节点预算短的 `timeout_ms`。不另设“等待超时”：它和特征源的超时重复，而特征源的超时从请求开始就在计时。节点开始前的补齐不计入预算，这一点和查询不同：查询的等待和其他源的调用重叠，从节点开始计时才能约束整个召回。
  - **录制与回放。** 每次调用的查询值连同类型都录制（ReplayCandidateCall.Query）。回放时如果值不同（配置改了查询，或它读的特征回放出了不同的值），这次调用仍按录制回答（录制的是失败就仍失败），因为回放包里没有对新查询的答案，同时报告 query_changed 缺口。录制里没有这个节点的调用时（配置新增的节点），原来借用这个源返回最长列表的那次调用、不比较查询；现在优先借用查询值相同的成功调用，只有没有时才借最长的，并报告 query_changed。值按“类型 + JSON 值”比较，所以加载回放包时就校验每个查询值的类型、值和定长，错误指向 回放包里这个查询值的 type 或 `/value`，并把它改写成录制写出的形式再比较：原来类型写错、值是对象、列表长度和定长不符也能加载，回放时报成查询变了；同一个值的其他写法（类型 `" bool "`、值 `1` 表示真）解码相同，却按原文比较成不同。超出类型范围的数（`1e400`，float32 的 `1e39`）不是这个类型的值，同样在 `/value` 处拒绝：原来 `1e400` 解码成无穷，改写后成了合法的 `"Infinity"`，和真正的无穷查询匹配，借到了它的答案；float32 的 `1e39` 存进去就是无穷；非有限值按格式写成名字（`"Infinity"`）。日志读取用同一个解码（`LogBatchJson.TryReadValue`），一样拒绝。回放包格式升到 `2026-11-20.1`，没有旧读取器。第 2 步之后不再录制查询值，也没有 query_changed：召回的调用和其他没有逐项键的服务调用一样按输入摘要回放（见“外部依赖”）。
  - **开发用的 `memory_vectors@1`。** 一个内存向量索引：按点积打分，平分时按 id，可以用 `min_score` 过滤，查询向量缺失时不返回候选，没有物品时也一样；扫描用的临时数组从共享池租用。查询值的类型先于值检查：类型不是浮点数列表、或定长与物品向量不同时，调用失败，值缺失也一样，原来缺失值直接返回空，配置错误要等某个请求有值时才暴露。点积不是有限数时调用失败并给出提示：乘积溢出得到 NaN 或无穷，排序和 `min_score` 都会由它决定（原来 NaN 被当作低于 `min_score`，丢掉了本该排第一的物品）。示例的 `two_tower` 改用它：用户嵌入是单位向量，1001 和 1002 各占一个轴，冷启动的默认值占第三个轴；物品向量取原来按用户列出的分数，所以示例结果和原来逐项相同。
  - 目前只有 `MultiSourceRecall@1` 用这套机制，自定义算子同样可以用 `CompileAwaitedExpression` 和 `WhenEachReadyAsync`；只等一组读取的算子传一个元素。轮次、观察和有界等待都在这一个方法里，算子只写回调，不用自己写容易出错的循环。
- **上下文特征按数据源就绪，读者只等自己读的源**（审计 B6）。原来上下文预取是一个任务：所有上下文数据源的调用并发发出，但结果按发出顺序逐个等待和写入，任何读上下文特征的节点都等整个任务结束。读用户向量做 ANN 召回的节点因此要等一个它不读的、更慢的用户特征源，召回在关键路径上晚开始，p99 取决于所有上下文源里最慢的尾部。现在每个远程上下文分组在自己的源应答时写入，各有一个完成任务（`StartContextFetch` 返回前就登记好），读者按自己闭包里的特征逐个等待对应分组。本地读取（`local`、`cache`）的上下文分组后来也各有完成任务，被键或召回查询读到的上下文衍生特征在输入就绪时算出、各有完成任务（链式上下文键需要按分组等待，见“键可以读上下文特征”；查询见“召回源可以带查询值”）；其他上下文衍生特征仍在整个预取的最后算出，读它们的等整个任务。分组并发完成时只写各自特征的槽位，计数是原子的；不管是等待时有分组抛出异常，还是发送某个分组时就抛出异常（录制钩子出错等），都先等所有已发出的分组、等键的链式分组和作为键的衍生特征都完成，再释放请求内存：它们还要读暂存区、写上下文数组（发送阶段的异常原来直接释放，先发出的分组之后从已归还的暂存区读到毒化值）。代价：异步完成的分组各多一个状态机对象（每个约一百字节），同步完成的（键缺失、未发送、内存连接器）没有。
- **连接器用写入器的 `Intern`/`InternUtf8` 去重字符串，作用域是一次调用**（审计 B5）。原来 `IFeatureBatchWriter` 只有 `SetString(string)`：存储返回的是字节，连接器先为每个键解码出一个字符串，5,000 个候选的 3 个类别特征就是约 15,000 个字符串、几百 KB，而这些值大多重复。B5 先做成按字段类型自动去重（`string` 字段去重、`text` 不去重）；去掉 `text` 之后引擎分不出字段的基数，自动去重会在标题这类几乎不重复的字段上白建一张表，所以改成显式：知道字段会重复的连接器调用 `Intern`/`InternUtf8` 取得字符串，再 `SetString`/`SetStringList`（标量和列表元素都能用）。取舍：
  - 表随写入器，一次连接器调用只有一个线程在写，不加锁；最多 4,096 个不同的值，超过的照常各生成一个，误用在高基数字段上的代价有上限。查找经 `GetAlternateLookup<ReadOnlySpan<char>>`，命中不分配；UTF-8 不超过 256 字节在栈上解码，更长的用租来的缓冲，非法字节按 `Encoding.UTF8` 换成 U+FFFD。5,000 和 50,000 个键分配相同（测试比较两者，不用绝对字节数：原来 2 KB 的阈值在并发运行时偶尔超出）。
  - 不做进程级的字符串池。候选规模的字符串主要来自本地表和缓存的进程内层，它们存表内字典的码，回填 0 分配；字典恰好装着表里的值，不用猜基数，压实时清掉死值。剩下的是没有缓存的远程连接器，一次调用内去重已经把 5,000 个值降到几十个，全局池只能再省这几十个（几 KB），代价却是每次查找加锁、更新 LRU 顺序、写共享内存（多核下缓存行来回同步），不知道基数时标题、id 这类值进池只会白算哈希、挤掉有用的值，还多一个要用户理解的容量配置。需要跨请求复用的连接器或候选源实例是长期存活的，自己持有按自己数据定容量的池（例如 CommunityToolkit.HighPerformance 的 `StringPool`）；宿主示例的连接器加载时解码一次，每次取数传同一个实例。
  - 禁用 `string.Intern`、`string.IsInterned`（`BannedSymbols.txt`）：驻留的字符串在进程里永不释放，用在数据值上就是泄漏。
  - 缓存的分布式层命中、回源和过期降级从记录字节解码时用同一个去重（每次读取一个），同一次读取里重复的类别只解码出一个字符串；随后写进进程内层，下次命中不再解码。
- **一次拉取的所有分批共用一个暂存区**。分批在连接器线程上并发写入，超时被放弃的分批还可能在请求返回之后继续写，同时别的分批正在被回填读取。所以布局保证任何两个分批都不写同一块内存：定长值和字符串每个字段一个数组，按拉取内的键序号排列，每个分批只写自己那一段；每个分批的“已写入”位从 64 位字的边界开始，因为两个线程同时写一个字会丢位；列表字段每个分批一个缓冲区，因为列表的数据区会增长、搬移。字符串按引用暂存，回填只复制引用。连接器拿到的 writer 是分批的视图：连接器同步返回后，同一个视图对象接着指向下一个分批，它的 `Intern` 表随之清空，下一次调用不继承上一次调用的值和 4,096 的额度；异步返回的调用独占自己的视图，直到连接器真正结束。没有选的做法：每个分批一套缓冲区（原做法：暂存对象、列数组、每字段一个列对象和一个字符串字典，再加每字段一次租借）；在请求内复用分批的暂存对象（被放弃的分批还在写，复用要等它真正结束，省下的只是对象本身，列和字典照样要建）；用原子操作写位图（每写一个值多一条带锁指令）。代价：分批很小时位图有浪费（`max_batch` 为 25 时每 25 个键占一个 64 位字）；写过列表的分批仍各有一个列表缓冲区；连接器不能保留 writer，`IStagedFeatureValues` 也只在 `Record` 调用期间有效；`SetString` 收到 null 直接让这次调用失败，否则要到后面（写回缓存时编码，或读这一列时）才出错，离出错的连接器很远。
- **一次拉取共用一个取消源和一个时间预算**。拉取开始时算一次预算，同时定下拉取的截止时刻（开始时刻加预算）；有分批要发出时，创建一个关联调用方令牌、到预算时取消的取消源，所有分批的连接器拿同一个令牌。原来每个分批一个关联取消源和一个定时器，等待时再建一个定时器。取消源按引用计数：拉取本身持有一份，直到所有分批发出；每个发出的分批持有一份，直到它的连接器真正结束；最后一份释放时才 Dispose，所以不理会取消、迟迟才结束的连接器手里的令牌一直有效。等待连接器不依赖这个取消源：异步返回的调用用 `WaitAsync(剩余时间, 调用方令牌)` 等待，剩余时间是截止时刻减当前时刻，最少为零，所以后发出的分批不会重新拿到完整预算。原因：取消源触发时，注册在上面的回调在触发它的线程上同步、逐个执行；连接器可以注册自己的回调（释放网络资源、等清理锁），其中一个阻塞，挂在同一个令牌上、排在它后面的等待就一直收不到取消，整个 `Ensure` 跟着卡住，源超时和请求截止时间都失去上界。分类不变：调用方令牌已取消算 `cancelled`；等待超时（`TimeoutException`），或连接器响应共用令牌抛出取消，算超时，失败文字相同。局限：调用方的取消通过关联令牌同步传到连接器的回调，阻塞的回调仍会拖住调用方自己的 `Cancel()` 调用，框架无法阻止。代价：每个异步返回的调用一个定时器（同步返回的调用不等待，仍然不分配）；后发出的分批实际等待略少于预算，少的是发出前面分批所用的时间（微秒级）。连接器的同步部分在发出它的线程上执行、没有上界（接口文档写明了），所以每个分批发出之前看一次截止时刻和调用方令牌，判断规则与“晚到的回答”是同一个（`CutOff`）：时间到了或调用方取消了，剩下的分批不再发出，按超时或取消失败，录成“未发送”，回放照录制结果失败，不访问连接器，也不用回放时的时钟重新判断。原来照样一个个发出，每个都拿着已取消的令牌、跑一遍自己的同步部分，延迟随剩余分批数增长（50 个分批、第一个同步部分用完预算，49 个白白发出，约 1.1 s）。缓存回源的分批同样处理（它们不逐个录制）；分布式层的读取本来就这样做。上下文特征的各个源也是一个接一个发出的，同样在发出前判断：前一个源的同步部分里调用方取消了，后面的源不再发出。
- **同步完成的调用不分配**。拉取内部的调用返回 `ValueTask<FetchStatus>`：连接器同步返回时，记录调用、释放请求内存都在调用点当场完成，不建租约，也不建状态机；只有连接器真正异步时才分配等待要用的对象（租约、续体、状态机、限时等待和它的定时器）。内存规则不变：每个仍在运行的外部调用持有一次请求内存，直到连接器结束并且调用点记录完毕，`stratarec.io.abandoned` 仍然是每个仍在运行的调用计一次。没有用 `PoolingAsyncValueTaskMethodBuilder`：没人等待的预取永远不会把池化的状态机还回去。
- **`EntityKeyBatch` 是只读结构体**（1.0 之前的不兼容改动）。每次连接器调用一个批对象，分批多时是可测量的分配。连接器的 `FetchAsync` 仍按值接收（异步方法不能有 `in` 参数），`IFeatureCallHook.Begin` 和 `Replay` 改为 `in`。自定义连接器和钩子要重新编译；拿批对象的引用做键或判断是否同一批的代码不再成立。
- **删掉 `"lookup": "context"` 和 KeyShape.ContextMap**。初稿为按用户组织的稀疏交叉特征设计了一种形态：只用上下文键发一次请求，响应自带候选键。引擎从来没有按这种形态发起拉取：绑定里可以写 `lookup`，它不起任何作用，连接器也不会收到 ContextMap；本地表拒绝交叉实体时，提示还让用户去写它。现在这两种需要都有现成的写法：只关心有没有交互，存成上下文实体的列表特征（例如 user 实体的一个 `list<int64>` 特征，读 col.entity_id in ctx.user.engaged_items）；每个交互带值时用组合键 `["ctx.request.user_id", "col.entity_id"]`，用户 ID 作为共享部分每批只发一次。真有只能按上下文键读的存储时，再按真实需要设计。
- **只有一部分分批失败时，节点是 `degraded`，失败分批的键按缺失处理**。审计指出这让结果取决于 `max_batch`：500 个键、`max_batch` 1000 时一次失败就是整体失败，节点 `Failed`；`max_batch` 100 时同样的故障只让一个分批失败，节点 `Degraded`，那 100 个键取默认值。保留这个语义：整体失败时没有任何数据，部分失败时一部分键有值，两者本来就不同；一个分批超时就让整个节点失败（再走 `on_failure`），会让大请求的可用性随分批数下降。部分失败不是静默的：节点结果、`stratarec.source.*` 指标和日志里的节点结果都显示 `degraded`。特征不带默认值时，表达式可以用 `??` 显式处理缺失，但这不提供“任一键失败就让节点失败”的保证：没有这种严格模式，等真有需要再加。
- **回填时每行的拉取键在一次拉取里只查一次**。原来一次拉取的每个特征各自遍历存活行，每行重新读键列、在键索引里查一次，还各租一块记录复制行号的缓冲。现在同一次拉取的特征共用一份按名次排列的键下标（第一次需要时查出，`BackfillScratch`）和一块行号缓冲。审计按每次查找 14 ns 估计 30 个特征、5,000 行要 2 ms；实测（`FeatureSupplyBenchmarks`，fetch，8 个物品特征加作者特征，int64 键）5,000 候选从 1,742.8 µs 到 1,722.8 µs，500 候选从 194.9 µs 到 193.1 µs，约 1%：int64 键的字典查找本来就快。保留它是因为改动小、每个请求少租一块“特征数 × 行数”的缓冲（这里约 160 KB），字符串键的每次查找都要算字符串哈希，收益更大。逐特征的复制仍走虚调用（`ColumnBuffer.CopyFrom`），按类型的批量复制等测到瓶颈再做。
- **实体只声明 `key`，类别和键的类型由它推导**。初稿让实体同时写 `scope`、`key` 和 `key_type`，三者可以互相矛盾，其中一种矛盾没有任何检查：`col.entity_id` 的 `key_type` 从不和流水线的 `entity_key_type` 比较，`"key_type": "int64"` 的实体放进字符串 id 的流水线，本地表按 int64 编码键，每次查找都落空，特征全部取默认值，不报错。键的类型其实都有唯一的来源：请求输入在 `request_schema` 里有类型，`col.entity_id` 是 `entity_key_type`，外键是键特征的类型；类别也由键的写法决定。现在只写 `key`，其余推导出来，键不是 `int64` 或 `string` 时报 `ENTITY_BAD_KEY`，指向那个键。后来键改成 1–8 个部分的元组（见“实体键是有序元组”），范围由部分是否全是 `ctx.*` 推导，同样不用另写。代价：目录读起来少了一眼能看到的键类型（要看流水线或键特征）；同一份目录放进不同 `entity_key_type` 的流水线时，候选实体的本地表按各自的键类型建，不共用，这本来就是对的。旧写法的 `scope`、`key_type` 是未知成员，报错指向它们（1.0 之前不兼容）。
- **缓存的记录里没人读的字符串列表不解码**。记录里有来源的每个字段，一次读取只填节点读的那些；字符串列表原来不管有没有目标都租数组、逐个解码和驻留，1,000 条各带 24 个标签的记录只读一个数值要分配 1.9 MB，现在和没有列表的记录一样。判断的是“这一行还有没有目标要它”，所以目标已经填过时也跳过；标量字符串本来就是这样做的。
- **特征源的共享缓存键里有“值从哪来”**。分布式层的键原来只有来源名和实体，记录的指纹只管键类型和字段布局：把同一个来源绑到另一份数据（换连接器、换 `data_file`）之后，新计划从共享层读到旧数据，布局相同所以被当成新鲜的，直到过期。现在键的前缀带连接器及其设置的摘要（`CacheKeyspace.Prefix`，存储不用改）；`timeout_ms`、`max_batch`、`max_bytes`、`cache` 不算在内，它们决定值什么时候到、留多久，不决定值是什么，只调这些的发布继续命中。和服务缓存的“答案身份”是同一条规则，也有同一个边界：身份是绑定的配置，一个相对于部署目录的设置（`data_file: fixtures/items.json`）在两个目录里是同一个身份。两套数据不同的部署共用一个缓存存储时，用不同的 `key_prefix` 分开；没有让连接器再报一个“数据版本”，那是为夹具用的文件连接器给所有连接器加契约。放进键而不是指纹，是因为两个版本并存时各自保留自己的热数据。升级之后原有的共享缓存条目读不到，等于冷启动一次。
