# 计划工具

- **工作区的问题在读取时报告，所有入口共用**（预发布评估 2026-11-18）。`ConfigWorkspace.Load` 是 `validate`、`build`、`run`、`explain-plan` 和以工作区启动的宿主共同的入口，下面三项都在这里报，没有哪个入口会看到不同的结果：同一个产物两个文件（`ARTIFACT_DUPLICATE`，原来后读的静默覆盖先读的，编辑的文件可能根本没进入发布）；`pipelines/` 下没有流水线（`WORKSPACE_NO_PIPELINE`，原来空目录校验通过、宿主启动后健康检查 503）；值不能按 RFC 8785 规范化（`ARTIFACT_NOT_CANONICAL`，带文件和值的指针，原来 `validate --format json` 输出空、只有异常堆栈）。代价是 `run` 等命令对空目录也报错，而它们本来也没有东西可跑。`policy.json` 和其他产物一样可以用 `.json`，原来只读 `policy.jsonc`，单独的 `policy.json` 被静默忽略。
- **一种写法指定配置（ref），按语法先判断 manifest id，再看文件系统**。`sha256:<64 位小写十六进制>` 是 store 里的 manifest；否则已存在的目录是工作区，已存在的文件是 manifest 文件（它的产物也在 `--store` 里）。没有引入 `kind:` 这类前缀：id 本身没有歧义，不发明新语法。`-c` 保持原义（工作区），`--manifest` 是和它互斥的另一种选择，`compare --baseline` 和 `diff --from/--to` 接受任何一种 ref。manifest 文件的 id 和 `build` 一样由 manifest 模型的 RFC 8785 规范形式算出，不按文件字节：重新排版或加注释的文件 id 不变，和 store 里的 blob 对得上。
- **回放结果的差异按条目比较，不按名次**。原来逐个名次比较两边，同一名次上是两个不同的条目时，把它们的列值并排列出，对哪一个都说明不了什么。现在每个条目和它自己比较：在两边各排第几（只在一边的写 `absent`），以及它自己变了的列值；报告还给出两边共有的条目数（`in_both`）。这是 `replay --format json` 中 `changes` 的不兼容改动：原来是 {rank, recorded_id, replayed_id, columns}，现在是 `{id, recorded_rank, replayed_rank, columns}`。
- **命令行解析不了的命令退出 2**，和各命令自己发现的用法错误一样：未知选项、选项缺值都是用法错误。System.CommandLine 默认退出 1，而 1 表示配置有错误，`diff` 的 1 表示有差异，脚本不能把一个拼写错误读成这些。出错时只打印错误、拼写建议和一行 `See 'stratarec run --help' for the usage.`：System.CommandLine 默认在错误后面打印整页帮助（`run` 有 25 行），错误被埋在上面。没有给命令时仍打印帮助，那时命令列表正是要看的。命令的校验器按 token 判断参数有没有给，不读值：`-b` 缺值时读它的值会抛异常，原来让进程崩溃。
- **回放包可以直接作为参数**：`stratarec replay -c feed b.json`，也可以给多个文件（shell 通配）或目录；`-b` 仍然可用。`run --record` 打印可以照抄的回放命令，路径按 shell 引用，以 `-` 开头的相对路径写成 `./-b`，否则会被读成选项。`run --format text` 给出可读的结果（每行一个条目、trace、候选解释）；默认仍输出服务返回的 JSON 文档。
- **回放时，请求跑过的每条流水线都要有配置**。回放包的 `runs` 记着请求跑过的流水线：主流水线，失败后转去的后备流水线，各自带录制时的 manifest。少了后备流水线的配置，主流水线一失败回放就停在失败上，看起来像配置改出了差异，其实是没加载。所以 CLI 为每个包按 `runs` 准备引擎，配置的来源按命令行定：只给 `--store` 时，每条流水线都用它录制时的 manifest，调试线上请求不需要先找到当时的 git 提交；`--manifest` 只替换它那条流水线（必须是包自己的流水线），后备流水线仍用录制时的 manifest，“换一份主流水线的配置看效果”不会顺带换掉后备；`-c` 的工作区提供所有流水线。主流水线总在其中：没有主运行的包（被裁剪过）用包顶层的 manifest 回放主流水线，外部调用都是缺口，和在工作区上一样。`compare` 的两边按同样的规则准备。缺了哪条流水线的配置（store 里没有那个 manifest、工作区没有那条流水线，或者在工作区上录制的包，它的 id 是 `workspace:<流水线>/<环境>` 这样的标签，store 里找不到），这个包就计为 `unresolved`，说明是哪条流水线、哪个 manifest、怎么回放，不挡住其他包。引擎按“流水线 → 配置来源”的组合缓存：同一版本的包共用一个引擎，后备流水线换过版本的请求各用各的。直接调用 `RecEngine.ReplayAsync` 的宿主，引擎没加载录制里跑过的后备流水线时，回放报告的 notes 会写明。
- **manifest 没有配置根，绑定里的相对路径按当前目录解析**，和不设基准目录的宿主一样。只读 manifest 的命令里只影响样例和开发用的内存夹具：`memory@1`、`memory_list@1` 在创建实例时就读 `data_file`（见“绑定的实例”），不加载的编译也要找得到它们；线上的绑定指向外部服务。`run --manifest` 像节点一样加载全部绑定（本地表的快照、模型文件），所以在节点的工作目录里运行。读 manifest 的命令（`run`、`explain-plan`、`diff`、`replay`、`compare`）报的错误里出现当前目录下的路径时，多打印一行，说明相对路径是按哪个目录解析的，否则读者只看到一个意外的绝对路径；只在错误里真有这样的路径时才打印，`--format json` 时不打印。`run` 原来只接受工作区，发布之前或之后想试一个 manifest，只能回放录制过的请求；现在任意请求文件都能在 manifest 上跑，录制的包按打印出的命令从 store 回放（以文件给出的 manifest 不一定在 store 里，命令里带上 `--manifest <文件>`）。请求的 `pipeline_id` 不是 manifest 发布的那条流水线时，在加载之前就报 `REQUEST_INVALID`，退出码 2：这是请求文件的错，和请求的其他错误一样。只加载这个 manifest 的流水线：计划有后备流水线时打印警告，这次运行里请求失败不会转去后备（要试后备，在工作区上跑，或者回放线上录制的包，回放按 `runs` 加载每条流水线录制时的 manifest）。没有加 `--root` 选项，也没有把夹具改成加载时读文件（那要推翻已记录的取舍），等真有需要再做。
- **某个桶组合的有效计划从编译好的统一计划里取，按请求选择变体的同一个方法选，不重新合并补丁**（`EffectivePlan`）。显示的就是实际执行的，编译器的缺陷会在这里暴露，而不是被第二套合并实现重复一遍。`explain-plan --arms` 打印它，`diff` 比较两份它的文档形式，两者不会不一致。只因某个臂才存在的节点、参数、探针，只出现在包含这个臂的组合里。输出统一用 RFC 8785 规范形式：store 里存的是规范字节，成员顺序和工作区不同，不统一的话同一份配置会打印成两样。
- **`diff` 默认比较基线和每个臂单独生效的组合，两个臂同时生效的组合只用 `--arms` 指定**。组合对的数量随臂数平方增长，而且编译时已经逐个校验过；基线上的改动会在每个组合里重复出现，按组合看正是要的结果。只在一侧存在的臂，它的组合标成 `missing_on`，不比较，也不替它编造计划，否则臂的全部内容都会被报成改动；实验换了层，只在实验这一条上报告。比较的是节点、配置、参数、探针、漏斗组和输出，不比较绑定、目录、请求结构和 policy：这些改动在 `diff` 里看不到。退出码按 diff(1)：0 无差异，1 有差异，2 出错。两侧都先编译完再报告，诊断的产物前面加 `--from ` 或 `--to `，一侧坏了不挡另一侧。
- **JSON 差异逐叶比较**（`JsonDiff`）：只在一侧的成员算一条改动，带整个值；数组整体比较，因为元素没有稳定的标识；JSON `null` 和成员不存在不同；改动按指针的序数顺序输出。
- **编辑器支持来自工作区里提交的 JSON Schema**。每类文件在顶层写 `"$schema"` 指向 `schemas/<kind>.schema.json`，编辑器据此补全、悬停、报错，不需要插件。
  - Schema 由服务这个工作区的二进制写出（`stratarec schema --out`，`init` 也写），所以包含宿主自己的算子：宿主示例的 Schema 是用宿主自己的二进制写出的，里面有 `CategoryBoost@1`。没有在仓库根放一份公共的 Schema：同一个框架版本，不同的宿主有不同的算子。
  - `$schema` 不计入内容 ID：读文件时先去掉它，再绑定、哈希、存储，所以 `build` 上传的字节、manifest 和 `diff` 都不受它影响。内容 ID 标识部署的东西，`$schema` 只给编辑器用；它的值是相对路径，换个目录布局就会变；给仓库里所有文件批量加上 `$schema` 也不该产生新发布，或者让大表重新下载。只认顶层的字符串：其他类型的值是 `ARTIFACT_SCHEMA /$schema`，hint 给出这个文件该写的路径；嵌套在别处的 `$schema` 仍按未知键报错。`run` 的请求文件也一样。
  - 流水线按节点的 `op` 校验 `config`，每个算子一组 `if {op: const} then {config: …}`。没有用 `oneOf`：它只报“最接近的那一支”的错误，未知的 op 会显示成误导人的类型错误。`op` 是枚举，带 VS Code 的 `enumDescriptions`。只有算子的配置有必填成员时才要求写 `config`，否则允许 `null`，和引擎把缺失或 `null` 的配置读成 `{}` 一致。
  - 实验臂的 Schema 是流水线可修改视图的合并补丁形式：去掉所有 `required`，每个值都可以是 `null`（删除）；封闭对象里未知的键只能是 `null`：切换节点的 `op` 时要删除旧算子独有的配置成员，新算子的 Schema 里没有它们，删除不存在的成员也不改变什么，带值的未知键照样报错（原来保留 `additionalProperties: false`，合法的切换会被标红）；臂的顶层（分区清单）仍然封闭，分区既不能删除也不能拼错；数组整体替换所以 `items` 不变，`if` 不变（补丁里写了 `op`，`config` 仍按那个算子检查），分区本身不能为 `null`（引擎拒绝删除整个分区）。一个条目是新增（必须完整）还是修改，取决于基线，按类型生成的 Schema 看不到基线，所以它从不拒绝合法的补丁，这一部分留给 `validate`。可修改的分区只有一份清单（`PatchableView.Sections` 由 `ExperimentArtifact` 的分区拼出），Schema 和补丁校验用的是同一份。
  - 描述先取 `[Description]`，没有就取 XML 文档注释的摘要（`MemberDocs`），所以悬停能看到字段说明。代价是 Schema 的字节取决于二进制旁边有没有 XML 文档：生成和检查要用同一个二进制，单文件发布、不带 XML 文档的二进制写出的 Schema 没有描述。
  - 过期检查是 `validate` 的警告 `SCHEMAS_STALE`，不另做 `--check` 命令：CI 本来就跑 `validate`，加 `--warnings-as-errors` 就会失败，开发者本地也看得到。是警告不是错误，因为它不影响部署。只在 `schemas/` 存在时检查，忽略 CRLF 差异，不管目录里的其他文件。`--out` 只改写内容变了的文件。
  - fixtures 不加 `$schema`：它们是连接器的数据，`$schema` 会被当成一个 ID。宿主示例里给 curl 用的请求体也不加：服务的端点是严格的，未知成员是 400。
  - Schema 用了 VS Code 的非标准关键字 `allowComments`、`allowTrailingCommas`、`enumDescriptions`。2020-12 把未知关键字当注解；ajv 的 strict 模式会报错，要关掉。
- **`stratarec init` 生成最小可运行的工作区**。新流水线从一份能跑的小工作区开始，而不是从删减过的示例开始：示例演示全部功能，删的时候不知道哪些能删。生成的工作区包含用户要改的每一种文件（目录、`local` 绑定、一条从召回到 top-k 的流水线、一个改权重的实验、发布文件、夹具和一个带分配的请求），生成后 `validate` 零错误零警告，`run` 离线就能跑；init 最后打印接下来可以照抄的命令。测试按生成的文件跑这几条命令，模板改坏了测试会失败。模板是一个 C# 文件里的原始字符串，没有用嵌入资源或 `dotnet new` 模板：唯一的替换（流水线 ID）由编译器检查，文件、说明和打印的命令用到的名字（实验、臂、请求文件）放在一处。流水线 ID 先按标识符校验再替换，不需要 JSON 转义；实验 ID 固定为 `exp_freshness`，不随流水线变。每个文件（夹具和请求也是）都是 JSONC，开头的注释说明它是什么、先改哪里。参数只有目录、`--pipeline` 和 `--force`，不做交互式提问，其余在生成的文件里改。目录里有可见的条目时不写，并指出挡住的是哪个文件：输错的目录不应被撒满工作区文件；隐藏条目不算（先 `git init` 再生成是常见做法，init 也不写隐藏文件，不会覆盖它们）。`--force` 只覆盖同名文件，从不删除，也不经过工作区里的符号链接写入：链接会把写入带到工作区外，覆盖别处的文件；用户指定的根目录本身是链接没关系，那是用户选的位置。所有检查在写任何文件之前做完，读不了目录也是带提示的诊断。打印的命令按 POSIX shell 的规则引用（必要时用单引号），目录名里有空格、`$`、反引号、引号或反斜线也能照抄。
