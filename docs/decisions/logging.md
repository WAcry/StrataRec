# 日志

- **日志管道的消费循环不因诊断异常退出，队列深度先加后减**。宿主的日志器或指标监听器抛出的异常只丢掉那条记录；每次取出的批次在 `finally` 里恰好结算一次，写入因 sink 以外的原因抛出时计为丢弃（事件 3006），循环继续。原来消费任务直接结束：待处理数、字节预算和队列深度不再下降，`FlushAsync` 永不返回，队列继续接收没人读的批次。队列深度的 +1 在批次对消费者可见之前发布，−1 在待处理数减少之前发布，所以对收到每次增量的监听器，序列不会低于零，`FlushAsync` 返回时深度已经归零。一个监听器在测量回调里抛出时，.NET 不再调用排在它后面的监听器，它们漏收这次增量，累加出的深度可能低于零、不再归零；管道只保证自己的结算不受影响，不能替被跳过的监听器补发。选项的范围按计时器定：排空时限加上关闭的 500 ms 宽限要放得进一次 `WaitAsync`，最长重试间隔至少 1 ms（1 tick 等于不等，持续失败的 sink 会被忙循环重试）。关闭时的事件 3003、3004 和最后一个窗口的汇总 2001 同样隔离，不让 `DisposeAsync` 抛出，也不跳过后面的清理。sink 部分拒绝时，先定下这次写的结果，再通知汇总和 `Rejected` 回调：回调抛出（连异常的 `Message` 都抛出）原来会把已投递的批次记成丢弃。
- **写持久日志和返回批次是两个开关，改变服务内容的调试请求不写持久日志**（预发布评估 2026-11-18）。原来只有 `CaptureLogs` 和配置覆盖会隔离，单独 `ForceArms` 的请求在配了日志管道时把人为指定的臂写进 `$experiments` 和探针，执行器的注释却说强制臂不能进实验数据。现在执行器的请求分开 `CaptureLogs`（返回给调用方，返回的批次绝不同时写出）和 `WriteLogs`（允许写日志管道，默认不写），引擎只给没有强制臂、配置覆盖和捕获的请求设 `WriteLogs`，后备流水线为这样的请求服务时也一样。界线是“是否改变服务内容”：trace、解释候选和录制只观察，请求和正常流量一样服务，照常记录；记录它们正好让调试过的请求在日志里可查。强制臂或配置覆盖而没要求捕获的请求不采样也不捕获，录制里日志去向是 `none`。
- **没有消费者时不采样、不捕获**。批次既不写出（没有日志管道，或请求不允许写）也不返回（没有 `CaptureLogs`，不是回放）时，所有批次都会被丢弃，白白消耗 CPU 和内存。
- **漏斗组的 key 只能读请求输入，且必须是标量**。组决定在请求开始时做出；key 若要等一次拉取，每个请求都会在召回之前阻塞在日志采样上。
- **探针对上下文特征同样是被动的**。只被探针读取的上下文特征不进入预取，否则每个请求都多一次拉取，无论是否被采样。
- **durable 投递以返回值和钩子表达，不内置磁盘缓冲**。`Submit` 返回 Queued/Spilled/Dropped/Closed；内存队列满时调用 `DurableOverflow` 钩子，由宿主决定是否落盘；sink 用 `LogBatchRejectedException` 声明永久不可写的批次，避免一个坏批次堵住整个 durable 流。`DisposeAsync` 的等待有上限，不依赖 sink 配合取消；到时还没写出的批次计为丢弃。
- **关闭时卡住不返回的 sink 不做结算**（一次外部审阅，评估后不改）。`DisposeAsync` 的等待有上界，sink 忽略取消、永远不返回时照样返回；排在卡住的那次写之后的批次要等那次写返回，才由后台循环记为丢弃，在那之前 `FlushAsync` 等不到、队列深度不归零。不改：只有“忽略取消并且永不返回”的 sink 才会这样，此时进程通常正在退出；丢失的 durable 批次本来就靠序号缺口发现，关闭时也写了日志（`LogSinkStuck`，带待处理数）。要结算就得让关闭和卡住的循环同时读队列（现在是单读者），还要标记在途批次、防止晚到的结果重复计数，复杂度和这个场景不相称。
- **浮点列表（包括 embedding）只要有一个非有限元素就整体记为缺失**，部分列表对训练没有意义。
- **不做个人数据过滤**。推荐需要这些数据，内部记录和调试查看是正常用法；不暴露给外部系统由运行环境和数据权限负责。曾经实现过敏感级别、`purpose` 声明和缓冲区清零，已按此决定全部移除。
- **日志队列按字节设上限，不按批次数**。原来 `durable` 队列最多 65,536 个批次、`best_effort` 4,096 个：sink 卡住时，宽的候选探针（几千行、带列表）每批可能上 MB，65,536 批就是几十 GB，进程先被内存耗尽，而不是按预期丢批次。现在按批次占用的内存估算（`LogBatch.ApproximateBytes`：数组、每个值 24 B 和它指向的字符串、列表、向量，信封里的臂列表和节点结果等映射按条目计，第一次入队时算一次）设上限，默认 `durable` 256 MiB、`best_effort` 64 MiB；批次写出或放弃时归还。超过上限的单个批次在队列为空时仍然入队，免得一个大批次永远发不出去。估算不精确，但两个方向的量级都要对：同一个字符串对象在一个批次里只算一次，否则字典编码的列或常量让每行都指向同一个字符串，1,024 行共用一个 4 KB 字符串被高估 158 倍，放得下的 `durable` 批次被丢弃；判断“同一个”用按对象身份直接映射的 256 格小表，两个字符串落在同一格时会重复计算，只会高估。计划里的字符串（探针、节点、臂、列名）所有请求共用，不计；一个请求的各批次共用信封的映射，每批各计一次，高估的倍数是每个请求的探针数，有界。原来信封固定按 256 B 算，有 100 个节点结果、零行的 `$experiments` 批次被低估约 13 倍。
- **出口交付声明的类型：日志、结果和回放包里的类型**（2026-11-21 用户要求；1.0 之前的不兼容改动）。用户的场景：特征存储返回 int32 的特征，特征日志也要 int32；原来日志列沿用表达式结果的类型，int32 特征记成 int64，float32 记成 float64，使用者自己的日志系统要再转回去。原则见 `development.md` 第 6 节，和模型张量同一条（见“模型张量的元素类型就是声明的类型”）。
  - 规则只有一处：`PlanSchema.DeclaredType(expression)`。表达式只是一个引用（列、特征、`@node` 版本、`ctx.*`、参数）时，是这个名字声明的类型，含可空性；上下文字段用 `ContextField.DeclaredType`，因为符号上是提升后的类型。有运算的表达式没有声明，是它提升后的结果类型。日志的列和上下文字段、结果列、回放包的 `column_types`、模型输入的张量和召回的查询值都用它。要把计算出的值以窄类型交出去，声明一个那种类型的衍生特征再引用它：转换只有一处定义，训练和服务共用。
  - “只是一个引用”按写出来的语法判断：表达式是一个名字，带不带括号都算；不看绑定或优化之后的 IR（两轮）。`col.item.clicks * 1` 被优化器、`double(col.item.ctr)` 和 `max(col.item.clicks)` 被绑定器化简成了这一列，它们仍是运算，按提升后的类型交出（int64、float64）。按 IR 判断，出口的类型和日志的 schema id 就取决于化简规则，加一条规则会悄悄改变使用者看到的类型。模型输入“只能是一个引用”用的是同一条判断（`CompiledExpression.Reference`）。
  - 日志列的值是声明类型的存储（int32 是 `int[]`，float32 是 `float[]`，`list<float32,64>` 每行 64 个 float）。`col.*` 的引用不再求值，按选中的行直接从列的存储复制；`ctx.*` 和参数的引用广播到每行，写进声明类型的缓冲时收窄。实测（5,000 个候选，宽探针 3,284 行：6 个标量列和一个 embedding，BenchmarkDotNet，`TapCaptureBenchmarks`）：采集的开销在 D=4 时少了约 156 µs、122 KB，D=64 时少了约 0.38 ms、0.89 MB（相对原来按表达式求值、记成 float64 的采集）；不采集时不变。当时的基准两组读结果的方式不同（不采集的一组读了 `Items`，多建了每行的字典），绝对值里混着这部分，所以只记两版之差，它不受影响；基准后来改成两组都只读列。
  - 直接从存储复制时按有效位判断缺失，不管类型是否可空：没写过的行记为缺失，不记那一格碰巧留下的值（表达式读非可空列时不看有效位，这里有意不同：日志记录实际有什么）。长度不是记录类型的 N 的列表行（自定义算子能写进存储，存储也可能是任意长度的列表）也记为缺失，和表达式读到它时一样；按日志声明的类型判断，不按存储的类型，直接给值的 `LogColumn.FromValues` 也一样。本次请求里没有节点产出的列记为整列缺失；原来求值时抛异常，让请求失败，而探针不应该让请求失败。读这样一个非可空列的运算也记为整列缺失（求值会抛异常）；读可空列的运算照常求值，它读到缺失，`col.x ?? 7` 记 7。运算读到的非可空列在某行无效时（丢弃行的探针能看到节点没写、或标成缺失的行），这一行记为缺失：表达式读非可空列不看有效位，那一格是池里留下的值。
  - 上下文字段的值仍是 `ScalarValue`（提升后保存）：一个请求一个值，不值得做定型数组。批次的 `Context[i]` 与 `Schema.Context[i]` 对齐，接收方按 schema 的类型收窄：`ScalarValue.AsInt32` 对 int32 字段的值精确，越界时抛出异常，不回绕；`AsFloat32` 取最近的 float，对 float32 字段的值精确（它们本来就是 float）。JSON 编码检查对齐，不对齐时拒收批次。
  - JSON 编码：int32 写成整数；float32 的列和上下文字段写成 float 的最短文本（`0.1`，不是 `0.10000000149011612`），按声明类型判断，不看值上的标记；float64 写 double。读回日志时 float32 直接按 float 解析，范围也按这个 float 判断，不先读成 double 再舍入：两次舍入可能落到另一个相邻的 float，或者越过 `float.MaxValue` 而被当成越界。回放包的编码不变，写精确的 double、按类型读回：它要如实保留请求看到的值，包括宿主给的、还没舍入的输入。
  - 结果：`ResultColumns.Types` 给每列的声明类型，输出按声明类型的存储求值。值仍是 `ScalarValue`，宿主按类型用 `AsInt32`、`AsFloat32` 精确地取到窄类型。考虑过像日志那样按列给定型数组：结果只有返回的 k 行，远少于候选数，逐值的 `ScalarValue` 不是瓶颈，宿主也通常逐行读，所以没有做。`ResultColumns.FromItems` 要显式给出每列的类型，不从值推断：全是缺失的列推不出类型，int32 会被推成 int64；它也拒绝不属于列类型的值和重复的列名；行的键按输出的列名逐字比较，不用调用方字典的比较规则（不区分大小写的字典会让 `x`、`X` 两列都取到同一个值；评审）。
  - 回放包的 `column_types` 改记声明类型（int32 等），值的编码不变。回放对比把同名输出列的类型变化也算作差异（`ResultDiff.RetypedColumns`，`--expect-identical` 因此失败；评审）：值相等时，float32 和 float64 的同一个 double 在结果的 JSON 里是 `0.1` 和 `0.10000000149011612`，宿主读到的也不一样。增减的列也按声明的列算，不只看行里的值：没有行的结果仍有输出的列，改名不会被当成相同；失败的结果没有列（录制里仍有计划的类型，用来解码，在线的失败结果没有），不比较。探针的 schema id 包含类型，受影响的探针换了 id，接收端按新 id 再发布一次 schema。
  - 提示词里 float32 的上下文特征按 float 渲染（原来按 double）：它的 `DeclaredType` 现在是声明的 float32。
- **转换到 float32 类型的值舍入成 float**（2026-11-21）。请求输入和默认值转换到 float32（或 `list<float32>` 的元素）时，取最近的 float，和写进 float32 列时一样（`ScalarValue.TryConvert`；参数和查表的值没有 float32 类型）。整数经过它的 double 再舍入，和整数写进 float32 列一样（先提升，再收窄），也和回放把录下的整数读成 double 再转换一样；直接从 long 转 float 在中点附近会落到另一个 float，在线和回放就不一致。元素已经都是 float 的列表不复制，只加上 float32 的标记：请求先检查输入、再绑定，两次都要转换。上下文特征的值发布成 float32 时也经过 double（`ColumnValues.AsStored`），和同一个特征的候选列一样。原来只检查范围，值保留给定的 double：float32 请求输入给 0.1，表达式按 0.1 计算，模型输入、日志和结果拿到的却是 0.1f，同一个字段在引擎里外是两个数；float32 的特征则一直是 float。现在一个 float32 字段的值在任何地方都是同一个 float，提升后再收窄得到原值（`development.md` 第 6 节）。回放包记录宿主给的原值，回放时同样转换。原值按它自己的（提升后的）类型记，不按主流水线声明的类型：后备流水线可能把同一个输入声明成别的类型，主流水线 float32、后备 int64 时，按 float32 记下的整数丢了末几位，回放的后备拿到的是另一个数。代价：float32 请求输入在表达式里的值变了（0.1 变成 0.10000000149011612），依赖它的分数在最后几位和原来不同；需要精确的 double 时，把输入声明成 float64。
- **行采样时请求 id 的哈希每个探针算一次**。原来在按行算优先级的循环里每行重新对请求 id 做 UTF-8 编码和哈希；只影响行采样率小于 1 或超过 `max_rows` 的探针。
- **输出列读某个节点的版本（`col.x@node`）时，结果的血缘里它的产出者是那个节点**，和探针一样：表达式只读一个列时这个列的产出者就是它的产出者，旁边读了参数或请求级的值不影响（`col.x@node * param.k`）；原来只列读当前版本的裸引用。
