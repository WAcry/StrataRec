# 范围：不做的和暂时不做的

一项能力带来的复杂度超过它对核心目标（[`../development.md`](../development.md) 第 1 节）的贡献时，就简化、推迟或不做。这里记不做的、暂时不做的，和理由；被拒绝过的方向再次提出时，先看这里。

- **不做一张表下面再挂一张表；两层的结果按组和成员的关系分两种做法**。没有选的做法是用偏移数组把两张候选表关联起来：那样做的难点（上层过滤之后下层怎么办、下层截断之后上层的汇总过期、表达式怎么区分两张表的列）会散落在执行器、拉取、后备恢复、日志和回放里，一致性只能靠两张表一起改；物品在组之间移动（混排、广告插进某一行）还要重建偏移数组。一条流水线只有一张候选表，一个键一行，两种情况都用它表达。
  - **组由成员决定**（按商家分组的搜索结果）：行是成员，组键是一个列（例如 col.item.merchant_id），组的特征照常按键去重拉取；组的统计和组内名次由 `GroupAggregate@1` 算出、写回组内每一行，每组保留前几项用组内名次加过滤；分组展示由宿主按组键排列结果。
  - **组先于成员存在**（多行首页：先提名候选行、用行级模型过滤，再按每一行自己的来源和数量取内容；物品可以出现在多行里；版面规则作用在行上）：行是组，成员是这一行的列表。页面是一条流水线，它的候选就是这些行，每一行的内容是它调用一条流水线得到的列表（`PipelineColumns@1`，2026-11-26，见“流水线调用”），版面规则是使用方的算子；所以页面的结构在配置里，实验用补丁改它。框架没有“行”“栏目”这样的概念。已知代价：一个实验的臂只能改一条流水线，同时改页面和成员流水线的实验要拆成两个，由实验平台把它们分给同一组用户；把变化放在页面那一条流水线里时不需要拆（“流水线调用”里有这一条的判断）。
  - **这之外不预先定结构。** 早先在这里记过一个“将来原生支持”的方向（一个请求里几张用键列关联的表），现在不再当作方向：它要给节点、日志的行标识、回放和结果都加上“哪一张表”，而它要表达的两种情况上面已经能表达。内容放在列表里有两个边界：页面层要对所有行的物品一起拉特征、过模型时，列式的节点用不上，做法是再调用一条以这些 id 为输入的流水线；一个物品要带的属性多到并排的列表难用时（两到四个没有问题），展示用的属性由宿主按 id 取。这两种做法在真实业务里不够用时，再按那时的需求设计，不按现在的猜想。
- **`fetch_missing` 不做**。这是响应之后的后台拉取：探针缓冲区和请求内存要活过请求本身，拉取还要有自己的超时、并发上限和失败计数，而它只满足“离线训练要的特征比线上用的多”这一种需求。训练用的额外特征，可以离线按键和时间点关联，或者加进线上的拉取。
- **本地磁盘缓冲不在框架里做**。落盘和重启后补发取决于部署环境（磁盘、容器生命周期），由宿主通过 `DurableOverflow` 钩子实现。
- **节点本地的磁盘快照不在框架里做**（即定期把表写到本地磁盘、重启时从磁盘恢复）。它只让同一个节点上的重启更快，数据仍在远端快照和更新流里；常见的部署里 Pod 重建后本地盘是空的，用不上。表的二进制转储会成为一种要兼容的格式：记录布局一变就要有版本和迁移，还要处理写了一半、校验失败、磁盘满和模式变了的文件。实测 `snapshot_files@1` 单线程加载 100 万条记录（168 MB 的 JSON Lines，7 个字段含一个 4 维向量）用 1.6 s，约 64 万条/秒，中等规模的表启动不慢。真要加快启动，该改的是加载快照本身：多个分片文件并行解析，或者换二进制的快照格式，这对每次启动都有效，包括新节点。
- **不做日志量的静态预算，`policy.jsonc` 没有 `log_bytes_per_request_budget`**。原来的打算是 CI 按“采样率 × 最大行数 × 每行字节数”估算每个请求的日志量，与策略里的预算比较。这个字段原来能写、进了 Schema，却没有任何代码读它，设成 0 也照样通过校验，让人以为日志量受了保护。估算本身也站不住：探针的行数取决于请求的候选数，字符串、列表的宽度只能猜，估出来的数既挡不住真实的大请求，也会误伤。删掉字段（之后写它按未知键报错）；实际的保护是有界队列（`best_effort` 满了丢弃并计数，`durable` 溢出计数），观测用逐探针的批次数（送达或丢弃）和队列深度的指标。以后有了可靠的估算规则再加回来。
- **不统计每个探针的字节数和池中保留的字节数**。前者要在 sink 序列化之前估算字节数，后者要池暴露内部状态，调试价值抵不上成本。“池够不够用”实测影响是每请求几 KB（见 observability.md 的“方法内用完的临时缓冲用完就还”一条），也不单独统计。
- **核心不内置模型推理运行时；ONNX、流式、分页现在都不做，但不排除以后以扩展包的形式做**。服务是分布式的，模型由独立的推理服务提供；框架虽然用 C# 实现，不应把模型限定在 ONNX 这类某一种运行时或格式，所以核心里不做 local_onnx@1。重点是编排；扩展包可以有，前提是核心不依赖它、它本身不过度复杂：`StrataRec.Llm` 就是这样一个包，也是写扩展算子的示例，使用方完全可以不用它、自己写大模型算子。流式输出（ExecuteStreamingAsync）和分页现在不做，以后需要时再按扩展的方式加，接口不为它们预留。模型经 `IServiceClient` 接入，推理服务的协议客户端（KServe v2、TF Serving 或公司内部的协议）由使用方按自己的服务实现，注册后由绑定按类型名引用。框架内置静态、确定性的示例客户端，供测试、样例和本地开发：`linear@1`（线性打分）、`random@1`（随机打分的替身，见下一条）、`memory_list@1`（固定列表召回）、`memory@1`（内存特征）。
- **`random@1` 是绑定层的替身，分数只由模型能看到的那部分输入决定**。开发、测试环境把真实模型的逻辑名绑定到它，设置声明它模仿的签名，算子加载时的签名检查照常通过，流水线和实验不改。设置有两种写法：名字数组（每个张量都是 float32 `[-1]`，逐点模型最常见的样子），或者名字到 `{ "type", "shape" }`，照抄真实模型的签名；成对和列表级模型用后一种（输入 `[-1, 2]`、`[1, -1]` 等）。一条规则覆盖所有形状：对每个输出，声明形状以输出形状开头的输入是“逐元素”的，其余是共享的；输出每个元素的分数取（模型逻辑名与输出名的哈希、种子、按名字序数排列的各输入：逐元素的取这个元素的切片，共享的取整个输入）规范编码的 `StableHash` 的高 24 位，乘 2^-24。所以一行的分数只看这一行（和共享输入），一对的偏好只看这两行及其先后，列表里一行的分数只看它在列表中的那一片：与位置、分批和其他元素无关，换请求种子就换分数，离线可以复算；24 位在 float32 里精确且小于 1。名字、类型和形状不进哈希，两种写法对同样的值给同样的分数。每个输出至少要有一个逐元素输入，否则配置错误：输出的大小和变化只能来自它们。浮点（float32、float64）按 float64 规范编码，−0.0 与 0.0、各种 NaN 不区分，同 `hash01`；整数（int32、int64）和 bool（0、1）按 int64 编码；字符串按字符串编码。所以同一个值换一种宽度得到同样的分数，模仿的签名把 float32 改成 float64 不改变分数。输入可以是任何张量类型，因为真实模型可以要任何类型（见“模型张量的元素类型就是声明的类型”）；输出是 float32 或 float64（默认 float32），两种宽度装的是同一个 24 位的值。它只产生分数，其他类型的输出是绑定错误。种子取绑定的 `seed`（各请求同一组分数），否则取调用的种子（模型算子都传 `ctx.request.seed`）；都没有时调用失败，不默认成常数：缺失不静默变成值，要固定只需在绑定里写 `seed`。完整写法的输入必须写 `type`，不设默认值。代价：输入相同的元素同分（真实模型也如此，平分按 `entity_id`）；不接受没有输入的签名；与真实模型不同，一对和它反过来的一对是两次独立的抽样，不是 p 与 1 − p，所以成对重排的结果取决于进入时的顺序（成对算子每对只发一次，排名高的在前）；列表里一行的分数不看列表中的其他行，所以列表级重排的结果只取决于窗口里有哪些行；列表级模型的上下文向量要声明成 `[1, N]`，写成 `[1, -1]` 就成了逐元素输入。
- **常用、复杂、值得框架优化的场景由框架做，其余接入由使用方实现**。本地特征表继续开发（见 local-tables.md）；缓存先做进程内和 Redis 两层。召回服务没有通用协议，请求字段（用户向量、过滤条件、分页）和返回结构各家不同，所以不内置召回客户端（grpc_ann@1、grpc_retrieval@1），由使用方实现 `IServiceClient`。读 Redis 等特征存储的连接器同理（键和值的格式各家不同），由使用方实现；框架内置的 Redis 只是缓存的分布式层（`redis@1`），由引擎写入，不是特征的来源。更新流（Kafka）和对象存储（`s3://`）的快照暂不内置，凭据、SDK 和部署方式取决于环境，宿主可以实现 `IFeatureUpdateSource`；内置的 `snapshot_files@1` 只读本地文件。
- **不负责流量分配，臂由外部实验平台分配**。哪些用户进入哪个实验、比例、扩量、长期对照和分流单元都属于实验平台：分配要和平台的用户口径与分析一致，引擎再算一次，同一个用户在两边的分组可能不同。所以删掉内置分流（TrafficAssigner：域、各层的盐和分流单元、桶范围），manifest 和发布文件里不再有 `assignment` 和桶范围。`allocation/` 改名 `releases/`，只写本环境的目录、绑定、表和在线实验所在的层；分配和桶范围的字段按未知键报错（原来对旧目录和旧字段有专门的迁移提示，1.0 之前没有要迁移的使用者，删了）。引擎这边保留层：层是一组互斥的实验，校验据此判断哪些臂可能同时命中。分配由请求带入（`RecRequest.Assignment`，网关已经问过平台），或者由宿主实现的 `IAssignmentProvider` 查询：它拿到流水线、请求 ID、请求输入（用户 ID 等）和计划的层、实验与臂，与请求共用截止时间；两者都没有时只跑基线。空列表也是平台的回答（没有臂），不再去问 provider。provider 拿到的上下文是只读结构体，计划的层、实验和臂是每个计划建一次的只读视图，查询不为它分配；以后加字段用可选的 init 属性，已有实现不用改。平台 ID 和引擎 ID 的对应由实现负责，框架不保存映射配置，因为各平台的 ID 格式不同。收到的分配怎么映射只在一处：不在计划里的臂记为未知并忽略（实验不在这个 manifest 里、拼错、平台先于发布开始分配）；重复的臂算一次；同一层出现两个不同的臂时这一层按基线执行，两个都记为层冲突。没有选“取第一个”：平台返回的顺序不是约定，结果会随它变化，也不能运行没校验过的组合。被忽略的臂和原因写进实验记录（`ExperimentRecord.Ignored`，按 ID 排序，没有时是空数组、不分配）、回放包（格式改变，旧的包直接拒绝并提示重新录制，不做迁移）和指标（`stratarec.request.arms.ignored`，按 `outcome` 区分 `unknown` 和 `layer_conflict`，不带臂的 ID，因为未知的 ID 来自平台、取值没有上界）。只为分流检查存在的计划加载结果 `rejected`（事件 1003）随之删除。`force_arms` 仍然严格，未知或同层冲突让请求失败；空列表强制只跑基线，请求文件里的 `force_arms: []` 也一样（CLI 原来把空列表当作没写）。provider 的等待就是外部调用共用的有界等待（`BoundedCall`，“外部依赖”第 4 步），守同样的不变量（3）：令牌在截止时或随调用方取消，回调在线程池上运行，取消源等 provider 真正结束才释放；原来随方法返回就释放，计时器停掉，或者调用方取消时还没轮到的注册被删掉，只靠令牌结束的 provider 就永远挂着。取消回调抛出的异常和其他令牌的一样计数，进入请求事件的汇总。分配之前被拒的请求（未知流水线、非法 `force_arms`、provider 超过截止时间）实验记录为空；分配之后、执行之前预算用完的请求带上生效的臂、被忽略的臂和 manifest，与已经计入的指标一致。两者都没有回放包。域也删掉了：平台的长期对照就是不带分配的请求，平台保证互斥的实验可以放进同一层。代价：校验假定不同层的臂都可能同时命中，平台放在不同域、实际不会相遇的两个实验，修改重叠时也要放进同一层；本地运行实验要在请求文件里写 `assignment`，或者用 `--arms`。
- **发布的信任根是指针的写权限，引擎不验证 manifest 的签名**（没有选的做法：manifest 带签名、节点只接受可信签名）。节点按指针给出的 `sha256:` 读 manifest，再按每个产物的哈希读产物，所以指针一旦确定，内容就无法被替换；能决定节点服务什么的只有写指针的人。签名要证明的也正是“这个指针是谁写的”，而它离不开密钥的分发、轮换和吊销，这些属于部署环境的身份体系（KMS、对象存储的 ACL、CI 的发布身份），与“不做个人数据过滤”一样交给环境。需要发布者身份独立于存储权限的部署，实现一个验证签名指针的 `IManifestSource`（指针里带对“流水线、环境、manifest ID、序号”的签名，验证不过就抛异常，节点照常记录并稍后重试），不需要引擎新增接口；产物存储本身只需要保证按哈希读到的内容不被改写。信任边界的两处要部署补上：
  - 内容寻址只在读取时校验才成立。内置的两个存储对返回的字节算 sha256 并比较，自定义的 `IArtifactStore` 必须同样校验（`ContentHash.Matches`）。宿主直接传入的 manifest 对象、绑定引用的数据文件和快照不在这条哈希链上，它们的可信度由提供它们的环境负责。
  - 节点只在进程内拒绝不比当前更新的序号，重启后不记得自己服务过什么。要跨重启防回滚，部署在一个不随指针回退的可信存储里，按流水线和环境保存已接受的最高序号和对应的 ID，在 `IManifestSource` 里拒绝更低的序号、以及同序号但不同 ID 的 manifest（同序号同 ID 照常重新加载）；恢复旧配置要作为序号更高的新发布来批准。引擎不内置这个水位：它要的正是一个不随指针回退的存储，这和签名一样属于部署环境。
- **草稿预览、实时回放推后**。两者都依赖控制面；本地已经可以用 CLI 运行工作区、录制和回放请求。
## 暂时不做，没有排除

| 内容 |
| :--- |
| 变长列表作为模型输入（定长列表 `list<E,N>` 已经支持，送 `[rows, N]`）。变长列表要送进张量，需要先决定填充、截断和长度上限，或者拆成值和偏移两个输入（像 `EmbeddingBag`）；这是要和模型签名一起设计的接口，等有真实模型需要时再定 |
| 草稿预览；实时模式和从请求输入日志采样（见上文） |
| 报告工作区里没有流水线读取的特征；从目录生成可浏览的特征文档 |
