# 工程

- **只支持 .NET 10，CI 只用 Linux**。宿主都在 .NET 10 及以上，所以目标框架是 net10.0、C# 14，CI 用 SDK 10 构建，测试跑在 .NET 10 运行时上。原来以 net8.0 为目标，CI 用 SDK 8 和 SDK 10 各构建一次，测试却都跑在没有人部署的 .NET 8 运行时上；为了 SDK 8 的编译器（Roslyn 4.11），banned-API 分析器停在 3.3.4，语言停在 C# 12。现在分析器用 5.x，框架自带的 System.Text.Json 和 System.Diagnostics.DiagnosticSource 不再显式引用。换运行时之后：每请求的分配逐字节不变（`PipelineBenchmarks`、`FeatureSupplyBenchmarks`），耗时少 10%–25%；`TensorPrimitives` 在 net10.0 上改用运行时的向量数学，`exp`、`log` 等的末位可能和 .NET 8 不同（本机 `log(1.5)` 差 1 ulp，差多少取决于运行时和硬件），同一个二进制里标量和逐行的结果仍然逐位一致。
- **依赖跟着目标框架的版本线，其余用最新稳定版**。与运行时同一版本线发布的包（`Microsoft.Extensions.*`、`System.Numerics.Tensors`、`System.IO.Hashing`，测试用的 `Microsoft.AspNetCore.Mvc.Testing`）停在 10.0 的最新补丁，不升到 11.0：库的目标是 net10.0，依赖 11.0 的 `Microsoft.Extensions.*` 会让 .NET 10 的宿主越过共享框架自带的版本，把整套依赖抬到 11.0；`Mvc.Testing` 要和 ASP.NET Core 共享框架同一个主版本。目标框架改到下一个版本时一起升。其他依赖用最新稳定版：`JsonSchema.Net` 9.7、`System.CommandLine` 3.0（它也以 net10.0 为目标，升级没有改代码）、`xunit.v3`、`StackExchange.Redis`、`BenchmarkDotNet`、分析器；CI 的 actions 同样用最新的大版本。
- **锁仍是 `object`，暂不换成 `System.Threading.Lock`**（2026-11-21）。试过把全部锁换成 `Lock`，后来整体撤回。在 .NET 10、16 个逻辑核的 Linux 上用 BenchmarkDotNet 实测，不争用时两者一样快（16.1 ns 对 16.9 ns）；争用时 `Lock` 更慢，按 `HealthWindow.Add` 的临界区测，2 到 16 个线程时耗时是 Monitor 的 1.14 到 2.30 倍。一个 `Lock` 40 B，`object` 24 B。换掉以后只是类型名更清楚，没有实际好处。锁 `this` 或私有集合的地方照旧：它们不分配，外面的代码也拿不到。
- **测试用 xUnit.net v3，跑在 Microsoft Testing Platform 上**。xUnit 2 只做安全维护。v3 的测试项目是可执行程序；`dotnet test` 按 global.json 的 `test.runner` 走 MTP，不再带 VSTest（`Microsoft.NET.Test.Sdk`、`xunit.runner.visualstudio`）：只有一种运行方式，`dotnet test` 和直接运行测试程序的选项相同（筛选用 `--filter-class`、`--filter-method`，不是 VSTest 的 `--filter`）。接受 `CancellationToken` 的调用都传 `TestContext.Current.CancellationToken`（分析器 xUnit1051 要求），测试超时或被取消时，等待和请求随之停下，不用等到各自的超时。集成测试程序集保留自己的入口：子进程测试用它跑会让进程退出的场景，其他参数交给 xUnit 的 MTP 入口。CI 的 TRX 报告按项目命名（`-p:TestReports=true`），默认的文件名是时间戳，同时结束的程序集会写到同一个文件。一个测试原来用测试 SDK 带来、没人加载的程序集作“能按名字加载、但没有加载”的样本，SDK 去掉后改用单元测试从不加载的 `System.CommandLine`。
- **内存分配预算是估算**。“每请求 ≤ 2 KB”不是硬指标，允许一定偏差。当前示例流水线（`PipelineBenchmarks.Baseline`）每请求：5,000 候选约 35.6 KB，500 候选约 19.7 KB，只有 Gen0（原来分别约 227 KB 和 45 KB；`author_store` 改成本地表之前是 36 KB 和 20 KB）。按键和按分批的工作都不再分配，连接器同步返回的分批是 0 B（原来约 420 B，见“特征拉取”）。5,000 候选时其中约 17 KB 是 `memory@1` 解码字符串：`JsonElement.GetString` 为每个值新建一个字符串，约 500 行读到 `item.category`；这属于单独计量的字符串解码，引擎这边的字符串可以忽略。其余约 18–19 KB 与候选数无关，按 500 候选的抽样：返回给宿主的结果约 4.5 KB（不计入这个预算）；节点预算和拉取的取消源、定时器约 2.5 KB；每次拉取的对象（键索引、暂存区、待完成记录、字段子集）约 0.5 KB，示例请求约 6 次；候选表、表中字符串列的字典、请求状态和节点上下文约 6 KB；算子、模型和召回调用约 1.2 KB。
- **不做请求状态池**。请求级的对象随请求数增长，不随候选数增长，交给 GC 足够；值得优化的是随候选数和特征数增长的部分（列缓冲、位图，已经从请求内存租借）。能放进池的部分（`RequestState`、`CandidateTable`、`RowSelection`、`OutputBindings`、`FeatureFetcher`、表中字符串列的字典、节点上下文）合计约 6 KB，约占剩余分配的三分之一。池化要为每个对象写重置逻辑，漏掉一处就会把上一个请求的数据带进下一个请求；请求返回后，被放弃的 I/O 还持有请求内存，状态只能在最后一次 `Release` 时归还，可能在连接器线程上。每请求 20–40 KB 的 Gen0 分配在每秒数千请求时是每秒几十到一百多 MB，Gen0 回收的成本与存活对象成正比，而回收时这些对象大多已经死亡。更划算的是先做局部的：节点预算复用一个取消源（TryReset），按计划缓存拉取的字段子集，表中字符串列的字典按计划预设容量。原来写的是“压测显示 GC 暂停或分配速率与请求状态有关时再做”，现在定为不做（2026-11-14）：池化是为一个不随候选增长的量增加一整套重置约定。
- **性能上的取舍**（2026-11-14）。原则：随候选数、特征数增长的开销值得在一处内聚地优化，请求级的固定对象交给 GC；不为不是瓶颈的收益增加使用者要理解的约定。做了：`SlidingWindowQuota@1` 的重复扫描（见“执行与宿主”）；结果不再先建 K×C 的中间矩阵；向量输入的 shape 一次建成（每个输入每批少一个数组）；召回来源的字典码每个来源查一次而不是每行一次；字符串主键追加时一次预留字典容量（5,000 个键 583 KB → 约 204 KB）。分批追加时每次至少翻倍、但不超过表还能追加的行数：只按每批的需要预留会让字典每批都重新分配，5,000 个键每批 500 个反而比逐个 `Add` 多分配（866 KB 对 583 KB；只翻倍时最后一批会扩到表的两倍）；`memory@1` 的 `list<int64>` 用租借的缓冲解码。没有做：表达式后端换成手写 SIMD（融合公式 5,000 行约 37 µs、零分配，不是瓶颈）；字符串的请求级驻留池（列本来就是字典编码，缓存命中时分配不随候选数增长）；结果或请求对象池；录制时逐值 JSON 的优化（只在录制时发生）；采样上限很小时的阈值选择（只在采中的请求上，按实际负载再定）；`memory@1` 按行查 JSON 属性（只用于本地和测试，本地表是生产路径）。
- **结构上的取舍**（2026-11-14）。做了：`replay` 的结果项与服务结果共用一个写法（原来另写一份，把输出列平铺进结果项，列名为 `id`、`rank` 时写出重复成员）；扩展算子解析并登记读取是一步（`TryResolveRead`，原来先 `Scope.TryResolve` 再记得 `RecordSymbol`，漏掉第二步时特征不会被预取；`RecordSymbol` 不再公开）；依赖调用结束方式的翻译列出全部取值（新增一种结束方式时编译失败，而不是落进默认分支）；内置模型客户端共用名字列表的读取和未知设置的诊断（`random@1`、`fixed_text@1` 也给出相近的名字）。没有做、留待公开 API 定型时一起定：已发布计划的只读检查视图（现在 `TryGetPipeline` 给出可变的 `ExecutionPlan`）；模型签名“已知、延后、未检查、失败”的显式结果（现在后三者都是 null）；本地表记录引用携带所属版本。数据流规则与它的作用域放进同一个协作者、补丁视图的贯通护栏、最小编译夹具，在下次改动那些规则时一起做。
- **基于示例的测试默认不计时，测预算的测试显式选择原始预算**。示例保留真实的预算（`ctr_ranker` 给模型 50 ms，超时回退到 `ctr_backup`），用来演示预算和回退。晚到的结果一律按超时处理，冷启动的模型调用在繁忙的 CI 上会超过 50 ms，比较两次实时运行的测试就会一次回退、一次没有，结果对不上。所以测试默认用示例的一份副本：其中每个 `timeout_ms`（节点及其实验补丁、特征源、模型、召回源）和请求文件的 `deadline_ms` 都提高到一分钟，`on_failure` 不变，测试自己构造的请求也用一分钟的截止时间；测预算本身的测试选择 `SampleTiming.AsWritten`，由门控的客户端决定调用何时返回，不和时钟赛跑。放宽只有一处（`tests/Shared/SampleBudgets.cs`），基准测试也用它：基准度量的是流水线的工作量，冷启动碰到预算就成了度量回退。放宽只替换文本里的数字，注释和格式不变，测试照常按文本修改副本；遇到不认识的 `*_ms` 设置、一处都没放宽，或编译出的计划里仍有低于一分钟的节点预算或拉取预算（没写 `timeout_ms` 的拉取源用框架默认的 50 ms）时直接报错，不会悄悄失效。比较两次实时运行的测试先逐个节点比较结果（`LiveRunAssert`），时间因素再混进来时，失败信息会指出哪个节点、为什么回退。没有沿用逐个测试改超时字符串的做法：同一条规则散在多处，示例一改就悄悄失效。代价：默认的测试不覆盖示例真实预算下的行为，这部分只由选择 `AsWritten` 的测试覆盖；挂住的调用要等一分钟才让测试失败。
- **测试里的预算只切断测试想切断的调用**。一个预算由一次拉取的所有分批共用（节点预算、请求截止时间同理）：短预算切断的是截止时刻之前没被观察到的所有调用，不只是测试想挂住的那个。CI 上实测过：正常回答的分批 90 ms 内就做完了，但同时运行的其他测试占满了线程池（4 核、5 个线程、几十个工作项排队，GC 暂停只有一百多毫秒），完成的回调 1.4–2.9 s 后才执行，晚于 1.5 s 的预算，有的分批被判为超时；同一时段，等待排空 20 ms 的日志管道关闭用了 3–4 s。所以：单元测试的特征测试台（`FeatureTestRig`）默认的源预算和请求截止时间都是一分钟，与示例测试的“不计时”一致；需要一部分调用正常回答、另一部分被切断时，由测试自己切断：等调用钩子显示其余调用都已判定，再取消调用方令牌（同步回答的调用在 `EnsureAsync` 返回之前就已判定）；集成测试要在某个调用进行中取消请求时，从这个调用发出时计时（`CancelOnceCallStarts`，看调用的 span），不从请求开始时计时，被切断的调用要一分钟才回答。只防止测试挂住的上界（等一个永不自己结束的调用、一个要一分钟的调用）放宽到 30 s。超时的分类和预算的上界由“所有调用都挂住”的测试覆盖，这时预算只可能切断测试想切断的调用。代价：结果有成有败的测试里，失败一方是 `cancelled` 而不是 `timeout`，两者走同一段失败处理（分批标记失败、暂存不被读取），分类另有测试。仍然依赖时钟的有两类：测请求截止时间本身的端到端测试，截止时间之前的节点要在截止时间内跑完；选择 `SampleTiming.AsWritten` 的测试，不测的预算也按原样。
- **真实依赖下的负载和故障演练不在本仓库的 CI 里**。尾延迟、GC、超时后仍在运行的调用占住的请求内存、日志积压、发布传播时间，这些数取决于部署环境（特征存储、模型服务、机器规格、并发），在 CI 的共享机器上测出来的数既不稳定也不能代表线上，做成门禁只会误报。仓库里有的是与环境无关的保证：分配预算测试（按候选数）、BenchmarkDotNet 基准（CI 只试跑）、Redis 的真实容器测试、每个外部依赖的超时和放弃路径的确定性测试（放弃的调用持有请求内存直到真正结束、后台上报不拖住发布等）。上线前由使用方在自己的环境里用 `StrataRec.Samples.Host` 或自己的宿主接真实依赖压测，并在压测中注入延迟和故障；固定环境的基线和性能门禁等有了这样的环境再定。
- **缓冲区毒化是运行期开关，测试一律打开**。原来是 `#if` 条件编译，只在 Debug 构建生效；CI 测的是 Release 构建，这道防线在 CI 里从来没有运行过。现在是 `AppContext` 开关 `StrataRec.PoisonReturnedBuffers`，每个测试项目经 `Directory.Build.targets` 打开，读进一个 `static readonly` 字段，关闭时 JIT 把判断整个去掉，生产的开销为零。基准测试不打开，测的是生产的行为。
- **考虑过、没有做的，和原因**：
  - 发布指针读取超时后仍等到来源返回：`IManifestSource` 的契约是遵守取消令牌；为不遵守令牌的来源再加一层放弃和后台观察，是为违反契约的实现加机制。
  - 抛异常的指标监听器让请求失败：.NET 的 `Meter` 本来就把监听器的异常抛给打点的代码，每个用它的库都是这样；只隔离请求级的那几个点也不完整。
  - 组合检查里只改参数值的臂去重（加载时的分配从 430 MiB 降到 190 MiB）：只影响有上百个臂的发布的加载时间，改的是最容易出错的那段检查；等真有这样规模的发布再做。
  - 离线对比的 Kendall τ 是 O(n²)：返回几十条时没有影响，两万条的返回集不是我们要优化的情形。
- **不保留描述实现的设计文档**（2026-11-26）。最初的设计草稿有 2,500 行，代码在很多地方已经和它不同，代码注释却有一千多处按章节号指向它，有些还出现在使用者在编辑器里看到的 Schema 描述里。读的人要同时读草稿和代码，再自己判断哪个是对的。现在“系统怎么做”只有代码和测试；需要拼很多文件才看得出的东西（请求的路径、项目的依赖方向、全局不变量）在 `docs/architecture.md`，一页，里面的名字由门禁核对。没有选择修订草稿：修订一次之后它仍然没有任何东西保证和代码一致。代价是新来的人没有一份从头讲到尾的叙述，要从 `docs/architecture.md`、示例和代码进入。
- **文档里反引号包着的名字由门禁核对**。决策文件里有上千个对类型、成员、配置键和错误码的引用，代码改名或删除后它们不会报错；第一次运行就查出 77 处已经不存在的名字。规则是：反引号里像标识符的词（两个以上驼峰、全大写带下划线、小写带下划线）必须出现在某个非文档文件里，路径必须存在；已经删掉的名字去掉反引号。代价：举例用的、仓库里没有的名字不能加反引号；属于 .NET 而仓库没有用到的名字要加进 `scripts/gate.py` 的 `EXTERNAL`。单个驼峰的词不查，误报太多。
- **门禁是一个不依赖构建的 Python 脚本**（`scripts/gate.py`），不是分析器或测试项目。它检查的是文件和提交（体量、指针、分层表、术语、提交的组成），不需要语义模型；不到一秒，构建之前就能跑，CI 里排在还原之前。需要语义的规则（禁用的 API）仍然用分析器（`BannedSymbols.txt`）。项目的分层从 `docs/architecture.md` 的表读，表和检查因此不会各说各的。
- **规则文件和代码不在同一个提交里改**。门禁拦住一个改动时，最省事的做法是顺手放宽门禁；分开提交让每一次放宽都单独出现在历史里，带着自己的理由。按提交而不是按推送检查，因为这个仓库直接推主干、一次推送常有几个提交。代价是调低一个存量上限也要单独提交。
- **单个测试超过 8 秒让检查失败**（CI 的共享机器上是 20 秒）。三个各等了 24 到 30 秒的测试曾经让全部测试多花 70 秒，原因都是在等一个不会来的东西（一个之后才打开的门、宿主 10 秒的关闭超时、嵌套深度上平方时间的解析）；8 秒在最慢的正常测试（约 3 秒）之上、10 秒的超时之下。按耗时判断在慢机器上可能误报，所以 CI 的上限更宽，只拦真正的离群值。
- **变异测试按需跑，不进 `scripts/check.sh` 和 CI**（`scripts/mutate.sh`：Stryker.NET，版本钉在 `dotnet-tools.json`）。它回答别的检查回答不了的一个问题：改过的代码被改坏时，有没有测试会发现。对 `ListColumn.cs` 跑一次：45 个变异体，3 分半，其中 2 分多花在让每个测试单独跑一遍以取得覆盖关系上；存活的里有真的缺口（越界检查的 `>=` 换成 `>` 没有测试发现），也有不值得测的（错误信息的文字，所以字符串的变异关掉了）。因此只对改动过的文件跑，由改了容易错得隐蔽的逻辑的人自己跑；不设分数门槛，存活的变异体逐个判断：补一个断言那个行为的测试，或者判断它无关紧要而放过。不进 CI 和交付前的检查：一个项目几分钟，结果又要人判断，放进每次提交只会被跳过。第一次试用时工具在初次运行里和测试进程断开，原因在我们自己的一个测试：它留下了没人等待的失败任务，异常的 `Message` 会抛出，会报告未观察异常的测试宿主在终结器线程上读它，进程就结束了（平时的运行器不报告，所以一直没露出来）。修的是那个测试，不是绕开工具。
- **仓库里没有工作队列和待办文件**。任务从对话和评审来，做完就在代码和提交里；放一份待办清单在仓库里，它会和实际状态脱节，还会被每个读仓库的 agent 读进去。不做和暂时不做的事连同原因记在 `scope.md`，这是唯一需要留下来的部分：防止同一个方向被反复提出、反复论证。
- **决策文件是从一个 21 万字的文件按领域拆出来的，没有逐条重写**。很多条目仍然带着“原来怎样、后来怎样”的叙述，其中一部分已经可以由代码说明。逐条重写要对照代码核实一千多个事实，出错的代价（把一条仍然有效的理由改错或删掉）比留着它们高；所以只修了指向已删除的东西的引用，其余在改到对应领域时顺手精简（`.agents/skills/hygiene-sweep` 第 4 步），每个文件有体量上限防止它继续变长。
