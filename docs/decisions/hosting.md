# 宿主、发布与请求结果

- **计划发布按序号，组装出错整体放弃**。后台编译可能乱序完成，较旧的结果不覆盖较新的计划；`fallback_pipeline` 解析失败时主流水线也不发布。
- **宿主示例 `samples/StrataRec.Samples.Host` 是嵌入引擎和写扩展的指南，用代码写**。一个 ASP.NET Core 服务：`AddStrataRec` 加载它自己的工作区，`POST /recommend/{pipeline}` 把 HTTP 请求转成 `RecRequest`；三个扩展点（特征连接器、外部服务、算子）有几个小实现（最初六个：服务的召回、模型和过滤三种用法，过滤的那个是自定义算子经 `OperatorContext.CallAsync` 调用业务服务：使用方的过滤和业务逻辑要能自然接入，示例里给出这样一段，比再加一种绑定更能帮到第一次接入的人），和内置组件注册在同一个 `PlanEnvironment` 里，工作区按类型名引用。每个组件的注释写契约的规则（取消、预算、不按行分配、缺失值怎么报）和这样写的理由，算子的配置类同时是它的 JSON Schema。测试用 `WebApplicationFactory` 在进程内启动服务，放在单独的 `tests/StrataRec.Samples.Host.Tests`，不放进集成测试项目：引用 Web 项目的测试项目会带上 ASP.NET Core 共享框架，共享框架里也有的包（`Microsoft.Extensions.Logging.Abstractions` 等）就不再复制到输出目录；集成测试在子进程里从自己的输出目录启动 `stratarec.dll`，CLI 的依赖必须在那里。合在一起时 CI 的干净构建就失败了，本地因为输出目录里留着旧的 dll 没有发现。
  - 带自定义组件的工作区由宿主自己的二进制检查和运行（`dotnet run -- stratarec validate -c config`，`run`、`explain-plan`、`schema` 等全部命令同样可用，见下面的 `StrataRec.CommandLine`）：官方 CLI 只认内置组件和随它发布的可选包，不认识的类型名是加载错误。宿主的二进制用 CLI 同一套命令和服务同一个 `PlanEnvironment`，校验通过的就是服务接受的；CI 里原来跑 `stratarec validate` 的地方改跑它。没有选让 CLI 按路径加载插件程序集：版本和依赖要和宿主一致，加载失败的方式也多一种，而宿主的二进制本来就有这些组件。
  - 截止时间由服务定（示例默认 1000 ms），不由调用方传：冷进程第一个请求要 JIT，所以示例放得宽；生产服务按延迟目标设，预热之后再报告就绪。
  - 写示例时暴露出宿主要自己做的几件事：把 JSON 转成 `RequestInputs` 并按 `request_schema` 先校验一遍，才能区分调用方的错（400）和引擎的错（500）；把结果写成 JSON；启动时主动解析一次引擎，配置有错才会在启动时失败；加载的警告没有出口；带自定义组件就用不了 CLI。这些都放进了框架（下面三条），示例的端点只剩传输。
- **失败的请求带类别，调用方的错在分配实验之前按引擎的规则查出**。`RecResult.ErrorKind` 是 `UnknownPipeline`、`InvalidRequest`、`DeadlineExceeded`、`Failed` 之一，宿主不解析错误文本就能回答 404、400、504、500；输入错误另带 `ErrorPointer`（`/inputs/user_id`）。
  - 输入在分配实验之前检查：跑不了的请求不该去问实验平台，后备流水线是给失败的流水线准备的，不接手调用方写错的请求。强制的臂未知或冲突也是 `InvalidRequest`，不带指针（它是调试选项，不在请求体里）。
  - 规则只有一份（`RequestSchema`，在 Pipeline）：执行器绑定输入、宿主读 JSON 请求体、CLI 读请求文件都用它，措辞是配置错误那一套 JSON 说法。宿主读输入用的是读的那一刻的计划，引擎执行时按它实际运行的计划再查一次，以引擎为准：中间换了发布、新计划多了一个必填输入，结果仍是带指针的 `InvalidRequest`，不是 500。合法的输入检查时不分配，只有元素要转换的列表例外（整数列表转成浮点列表，不全是 float 的 double 列表转成 `list<float32>`）：检查和绑定各转换一次，为了省掉一次而把检查的结果带到绑定，要让两处共享状态，不值得。回放也先检查：`ReplayAsync` 解码录制的输入之后、解析臂之前，按回放的计划检查一次，不合法就是带指针的 `InvalidRequest`，不运行后备，和线上对同一个请求的回答一致。原来回放跳过这一步，新发布多了一个必填输入时，没有后备的回放是 `Failed`，有后备的竟由后备“成功”服务，离线比较会把线上会拒绝的请求当成一次正常的降级。后备自己要求的输入请求里没有，仍是 `Failed`，回放和线上一样。
  - `DeadlineExceeded` 只表示流水线开始之前截止时间就用完了（分配实验用掉了），什么都没执行；流水线执行中超时属于 `Failed`，因为那时节点的预算、跳过和后备都已经按截止时间做过决定。
  - 后备流水线只拿到它自己声明的输入（输入都已声明时直接用原对象，不分配）：后备通常用更少的信号（热门列表不需要用户），不必为它不读的输入改 schema。它要求的输入请求里没有，或类型不同，是配置的错，请求以 `Failed` 结束，错误里两条流水线的原因都有。这种不兼容在加载和 `validate` 时就给出警告，报在主流水线的 `/fallback_pipeline`：后备要求主流水线没有声明的输入（`FALLBACK_INPUT_UNDECLARED`）、主流水线里可选而后备里必填（`FALLBACK_INPUT_OPTIONAL`）、主流水线接受的值转换不到后备声明的类型（`FALLBACK_INPUT_TYPE`）。类型兼容按后备绑定输入时实际做的转换判断（`ScalarValue.TryConvert`）：int32→int64、float32→float64、整数→浮点、列表元素同理、定长列表→任意长度或同长度的列表，每个值都能转换，不警告（原来要求类型相同，int32 的主流水线配 int64 的后备也报警告，实际却能服务）。整数→浮点算兼容：超过 2^53 的整数取最近的 double，和任何浮点输入接收整数时一样。反方向、浮点→整数、其他长度、其他种类会让部分或全部值失败，警告说明哪些值失败。可空性单独检查，两者都不满足时各报一条。节点在后台加载一条计划后，也检查以它为后备、正在服务的流水线（事件 1003），和启动时一样；原来只检查它自己的后备，后备单独热更新后新增的必填输入要等主流水线第一次兜底才暴露。是警告不是错误：主流水线照常服务，只是失败时接不住；严格的 CI 用 `--warnings-as-errors`。`validate -p` 也编译它的后备流水线并报告未知的后备，与加载用同一段代码（`ConfigWorkspace.WithFallbacks`），原来未知的后备要到加载时才发现。
  - JSON 请求体用 `JsonDocument` 读，再用 `StrictJson` 查重复的成员和不成对的代理转义，报在第二次出现的位置；没有用 `JsonDocumentOptions.AllowDuplicateProperties = false`：它只抛 `JsonException`，说不出位置，也查不出代理转义。`JsonObject` 不能用来读请求体：它在第一次枚举成员时才对重复的名字抛 `ArgumentException`，越过宿主的 400 路径成了空体的 500。`JsonDocument` 也收下原文不是 UTF-8 的字符串和成员名（一个原始的 `0xFF`、截断的多字节序列），读它们时才抛异常，所以 `StrictJson` 也用 `Utf8.IsValid` 查每个字符串和成员名的原始字节：字符串报在它自己的指针，成员名写不出指针，报在所在的对象，说是第几个成员；消息不引用这些字节，提示让调用方按 UTF-8 发送。ASCII 和合法的非 ASCII 文本都不分配。
  - 结果只有一种 JSON 文档（`RecResultJson`），服务和 `stratarec run` 都输出它：输出列放在每一项的 `columns` 里，int64 的 ID 是 JSON 数字（原来 `run` 写成字符串），缺失和非有限的浮点是 `null`，另有 `request_id`、`error_kind`、`error_pointer`、`elapsed_ms`。这是 `run` 输出格式的不兼容改动。
  - float32 列的值按 float32 的最短往返形式输出（`0.08`，不是它扩展成的 double `0.07999999821186066`），结果的 JSON、`run --format text`、候选解释和回放报告都一样；float64 列仍是 double 的最短往返形式。值在 `ScalarValue` 里仍然是扩展后的 double，只是记住它来自 float32 存储（`FromFloat32`），相等和哈希只看 double，所以比较不受来源影响。输出列是表达式，表达式里的浮点都是 float64，所以只有正好是一个引用的输出列（`"score": "col.score.final"`，最常见的写法；`ctx.*` 和参数的引用也一样）保留声明的类型，float32 时按 float32 显示，回放包也记它为 float32；有运算的输出列是 float64 的值，照 double 显示（见“出口交付声明的类型”）。没有在输出时按“这个 double 恰好是某个 float32”来判断：float64 列里同样的数会被写成另一个 double，回放报告里两个不同的值可能显示得一样。回放包的编码不变（float32 列仍写精确的 double，按类型读回），它给程序读；日志后来改成按声明的类型写（见“出口交付声明的类型”）。CLI 报告原来把浮点四舍五入到 6 位小数，比 1e-6 小的分数显示成 0，回放差异里两个不同的值也可能一样，现在都按上面的规则精确输出。组合打分的说明按输出列的精度书写，float32 列时算式的结果就是列里的值；各项是 float64，只在 float32 表示得了时（有限、不被冲成 0、不是次正规数）按 float32 写，否则按 double 写，不然 `1e100 × 1e-100` 会写成 `Infinity × 0 = 1`；精确的各项在 `terms` 里。代价：服务返回的 float32 值读成 double 时是 `0.08`，不再是存储的那个 double，调用方要精确的值时转回 float32。
  - int32 输入越界时，提示改成 int64 并保留可空性（`int32?` 提示 `int64?`）：照抄 `int64` 会把一个可选输入变成必填。
- **`AddStrataRec` 在宿主开始监听之前加载工作区**。加载在一个托管服务的 `IHostedLifecycleService.StartingAsync` 里做：通用主机先等所有服务的 `StartingAsync` 完成，再调用各服务的 `StartAsync`，ASP.NET Core 的服务器在自己的 `StartAsync` 里开始监听，所以服务一能应答，每个计划都已加载。没有放在 `StartAsync` 里依靠注册顺序：宿主打开 `HostOptions.ServicesStartConcurrently` 后，各服务的 `StartAsync` 并发运行，后注册的服务和服务器会在加载完成之前开始。代价：别的服务的 `StartingAsync` 不能指望计划已经加载。配置有错误时抛出列出全部错误的 `ConfigException`，服务启动不了；警告写进宿主的日志（事件 1003）。原来在第一次解析引擎时同步加载，宿主要记得在启动时解析一次，警告也被丢掉。相对的 `ConfigRoot` 从宿主的内容根目录算，`PlanEnvironment` 没有 `BaseDirectory` 时用配置根目录，绑定里的相对路径不再取决于进程的当前目录。没有加健康检查包：能应答就是就绪的，存活和就绪的区分、预热由宿主决定。不是通用主机的宿主（只有一个 `ServiceProvider`）自己调用 `LoadWorkspaceAsync`。
- **节点按 manifest 上线，不兼容、撤销和过期都是状态，不是异常**。`RecEngine.LoadManifestAsync` 依次：不比正在服务的新（同一个 manifest 也算）是 `Stale`；`requires` 不是二进制能力的子集是 `Incompatible`，列出缺少的能力。这两种都不下载、不编译。读不到产物、编译失败、绑定加载失败是 `Rejected`，只有它重试可能成功。原来不兼容的 manifest 只会在编译时报“未知算子”，分不出是二进制缺能力还是配置写错，而发布控制器要的正是这个区别。能力检查只在 `ManifestBuilder.CheckCapabilities` 一处，引擎和 CLI 报同一个 `MANIFEST_INCOMPATIBLE`（指向 `/requires`）。
  - 节点检查指针指向的 manifest 属于自己的流水线和环境，指错了不会加载成另一条流水线。
  - **计划的只读是公开面上的，不防强转**。`ExecutionPlan` 和它引出的类型没有公开的 setter，集合都声明成只读接口、`ImmutableArray` 或 `FrozenDictionary`（`PlanImmutabilityTests` 按声明类型检查，新加的成员也在内）。其中十几个成员背后是数组、List 或 Dictionary，宿主把它强转回去就能改，之后的请求读到改过的计划。不为此把它们都换成冻结的集合或再包一层：宿主是同一个进程里受信任的代码，要改的话反射一样做得到；只读接口挡住的是无意的修改（排序、追加都要先复制），这才是会发生的事。重新考虑的条件：计划要交给不受信任的代码（脚本、插件沙箱）。
- **撤销是一次普通的新发布，去掉 min_accepted_seq**。原来撤销的 manifest 把 min_accepted_seq 设成自己的 `seq`，节点记下见过的最大值、拒绝低于它的 manifest，为的是重启的节点不会从本地 LKG 把被撤销的实验带回来。可框架不在磁盘上保存 LKG，节点记下的下限也只在进程内：重启之后就没了，恰好保护不了它要保护的情形。进程内它只多管一种情况：撤销本身加载失败，又有更旧的 manifest 晚到。为此要有 `Revoked` 状态、加载完成那一刻的二次检查、一个日志事件、`publish` 的 PUBLISH_REVOKED，以及 `build` 沿用下限的规则。`seq` 单调已经保证节点不会退回更旧的发布：撤销比被撤销的新，晚到的旧版本是 `Stale`。所以去掉它，状态只剩 `Applied`、`Stale`、`Incompatible`、`Rejected`，日志事件 1007 停用。宿主自己组合 LKG 时，LKG 是节点最后应用的 manifest，应用过撤销就是撤销本身。
  - `AddStrataRec` 设置 `Releases` 时服务 manifest 而不是工作区：启动时每条流水线都必须应用成功，否则宿主不启动，异常列出每条流水线的状态和原因；只服务一部分流水线，或者后备流水线从未加载，请求都会悄悄失败，所以后备流水线也必须在 `Pipelines` 里。之后每条流水线各有一个任务按间隔轮询自己的指针，只有新的 id 才加载（见下一条）。`Applied`、`Stale`、`Incompatible` 对同一个 id 是最终结果，不再尝试；`Rejected` 和读不到指针或 manifest 按倍增的间隔重试，上限 `MaxRetryInterval`（默认 5 分钟）。编译失败本来是确定的，但要把它和暂时的失败（存储还没一致、表的来源宕机）分开需要更多状态，上限已经限住了重编译的成本。指针消失时继续服务当前计划。每次尝试的结果交给可选的 `IReleaseStatusReporter`，它抛出的异常只记日志。时钟是 `ReleaseOptions.TimeProvider`，不从 DI 取，应用里注册的时钟不会悄悄改变轮询。
  - **每条流水线单独轮询，状态上报不在等待链上**。原来一个任务依次处理所有流水线，并原地等待每次上报：卡住流水线 A 的上报，B 已发布的新版本过了 25 个轮询周期还没应用，紧急撤销的时效取决于最慢的那条流水线和上报方。现在：每条流水线一个轮询任务，一次加载、一次挂起的指针读取只推迟它自己；不同流水线可能同时编译（引擎的加载本来线程安全），代价是 CPU 和内存的峰值。后台的结果进一个有界队列（每条流水线 4 个、至少 16 个），由一个任务按尝试的顺序逐个上报，上报方从不被并发调用；队列满了丢最旧的（事件 1014），新的结果更能说明节点的状态。上报的令牌在 `ReportTimeout`（默认 30 秒）后取消（事件 1015），下一个上报仍等这次调用返回：不理会令牌的上报方只拖住上报，不拖住发布。启动时仍然逐条上报完再加载下一条，宿主启动失败之前，控制器已经知道原因。上报晚于尝试，所以结果带上尝试开始的时刻（`ManifestLoadResult.AttemptedAt`，按轮询的时钟）。读指针的令牌在 `PointerTimeout`（默认 30 秒）后取消，按读取失败退避重试；manifest 和产物的读取属于加载，不设超时（大表的加载本来就慢）。两种超时用系统时钟，测试推进的手动时钟只管轮询和重试。停止宿主时先由框架直接取消每个进行中的调用、再取消轮询，所以等的回调包括这些调用令牌上的（调用的令牌嵌套在轮询的令牌下，只经链接取消时，停止不会等它们的回调，容器会在源清理到一半时释放它）。超时取消之后，调用可能先返回、令牌上的清理回调还在跑，所以调用返回后仍留在登记里，直到回调跑完，停止照样等它（原来调用一返回就移除，停止 3.5 ms 就结束，容器在清理之前释放了源）；不在调用返回处等回调，那样会卡住轮询。启动时读指针同样受 `PointerTimeout` 限制，读不到就以 `RELEASE_POINTER_UNREADABLE` 让启动失败，并说明是超时（原来启动时没有超时，宿主的启动令牌默认不会取消，一次挂起的读取就让服务一直起不来）
  - 控制面的扩展（`IManifestSource`、`IArtifactStore`、`IReleaseStatusReporter`）和其他扩展一样，拿到的是框架的 `ObservedCancellationSource` 的令牌（站点 `release`；manifest 的下载属于引擎的加载，站点 `plan_load`），取消时回调在线程池上运行、抛出的异常被计数，不会从宿主或调用方的计时器线程抛出、终止正在服务旧计划的进程。下载算作加载的一部分：先登记再下载，释放引擎也会取消它，和等待表加载时一样。停止宿主等轮询结束，也等这次取消的回调跑完，都以宿主的停止期限为界：容器随后释放扩展，回调做清理时不能发现它们已被释放（一度完全不等回调，停止期限还很充裕，容器就在清理进行到一半时释放了 manifest 源）；期限到了就不再等；此后轮询里出现的异常属于正在停止的宿主，安静地结束，不再作为未观察的异常出现。只等回调结束，不再抛出回调的异常：它由取消源观察，重新抛出的任务没人观察。日志器或指标监听器抛出的异常只丢掉那条记录，不改变重试、上报和轮询：原来读指针失败时写日志抛出，后台任务就永久结束，节点看起来正常、却再也不接收新的发布。每条流水线的轮询外面还有最后一层防护（事件 1013），缺陷也不会让后台任务结束；被它打断的尝试按被拒绝处理，退避后重试。指针换到新的 manifest 时，上一个的结果（最终与否、重试时刻）全部清掉（一次尝试在记下结果之前抛出——描述异常时读 `Message` 本身抛出——新 id 就沿用上一个的“最终”，轮询还活着，却再也不加载它）；描述扩展的异常一律用不会抛出的 `ExceptionText.Of`。计划加载的遥测（事件 1001–1008、`stratarec.plan.loads`）同样不抛出：原来日志器在计划上线之后抛出，加载会把已经上线的计划报成异常。
  - 不在本地磁盘保存 last-known-good。落盘的 manifest 和产物是又一种要兼容的格式，还要处理写了一半的文件，理由同“节点本地的磁盘快照不在框架里做”；控制面不可用时的启动由宿主组合 `IManifestSource` 解决，例如先问控制面，失败时读镜像里内置的基线指针。
  - `stratarec publish -s <store> <manifest>` 是最小的发布控制器（紧急停止是 `stratarec revoke`，见下文；没有分批推进）。指针是 store 下的 `pointers/<环境>/<流水线>.json`，内容 `{ "manifest": "sha256:…" }`；流水线 ID 和环境名不能以 `.` 开头：列出指针时跳过以点开头的临时和隐藏文件，这样的名字原来写得进去却列不出来（`status` 成功但什么都不报），现在写、读、列出用同一条规则拒绝（旧版本以这种名字发布过的环境：换一个没人用过的环境名，把 `releases/<流水线>.<旧名>.jsonc` 复制成新名并改掉其中的 `environment`，准备好新环境的绑定，从中去掉旧发布撤销的实验，再 build 和 publish，然后让宿主指向新名。撤销了哪些实验直接读 store 里的文件：`pointers/<旧名>/<流水线>.json` 给出 manifest 的 `sha256:<hex>`，`blobs/sha256/<hex>` 就是这份 manifest（JSON），列在 `revoked` 下且不在 `experiments` 下的就是撤销的实验。哪个版本的 `status` 都读不到这种名字的指针（旧版本列指针时跳过点开头的名字，显式给出环境也一样；新版本拒绝这个名字）；按 id 读 manifest 的 `explain-plan`、`diff` 要编译它，需要在当前目录下找得到绑定，而且只显示发布的实验，不显示撤销。只改目录名不够，manifest 里记着它的环境；只改 `build -e` 也不够，build 按新环境的发布文件取实验（三个实验会变成零个），也不知道旧名下的撤销（撤销过的实验会回来）。宿主启动时读不到这种名字的指针，`RELEASE_POINTER_UNREADABLE` 给出同样的提示）；节点忽略不认识的成员，控制器以后加字段不影响旧节点。发布前按节点的方式把产物读一遍，指针永远不指向节点读不到的 manifest；`seq` 必须比当前指向的大，回滚也要一个新的 `seq`。指针已经指向同一个 manifest 时什么都不写、成功退出，所以 CI 里的发布步骤可以重跑。
  - `build` 不给 `--seq` 时构建“下一个发布”：读 store 里这条流水线、这个环境的指针，`seq` 取它指向的 manifest 加一，并把它写进 `previous`，于是 `diff --to <新 manifest>` 不用 `--from` 就比较这次发布改了什么；还没有发布过时是 1。原来默认总是 1，每次发布都要使用者自己查当前的 `seq`，第二次发布必然先撞上 `PUBLISH_NOT_NEWER`；`previous` 字段原来有，`build` 却从来不写。配置和已发布的一样（只差 `seq`、`previous`、`revoked` 这几个发布字段）时不产生新发布：`build` 输出已发布的那个 manifest，`publish` 随后报“已经发布”，所以 CI 里 build 加 publish 整个重跑也不会多出一个内容相同的发布。指针或它指向的 manifest 读不到时报错，提示修好或显式给 `--seq`：猜一个序号，`publish` 也会因为同样的原因失败。指针指向别的流水线或环境的 manifest（手工复制或改过的指针）时同样报错（`POINTER_MANIFEST_FOREIGN`），`publish` 也一样：那个 `seq` 说明不了这条流水线发布到哪里，拿它编号或比较新旧，要么平白跳号，要么把正确的发布当作“不比已发布的新”拒绝。“配置没变”是和 `build` 自己写出的形式比较：别的工具写的 manifest 省略了取默认值的字段时，内容 id 不同，会多出一个内容相同的发布；这只多一个序号，不会错发，所以没有为它改 manifest 的身份定义。`build` 生成的 `seq` 最大到 2^53 − 1，即最大安全整数：manifest 是 RFC 8785 规范化的 JSON，整数按双精度写，到它为止的整数都能精确写出，超过它的就不一定。`--seq` 超出范围是用法错误（转换不了的值仍是解析器自己的用法错误：原来范围检查读取转换失败的值时抛出，进程以 134 退出，`--deadline-ms` 原来也是这样），已发布的到了最大值时报 `SEQ_EXHAUSTED`。别的工具写的 manifest 文件里有写不准的整数时，它没有内容 id，报 `MANIFEST_NOT_CANONICAL`（原来是未处理的异常）；store 里的 manifest 存进去时已经规范化过，读取不受这个上限限制。显式给 `--seq` 时不读指针，留给自己编号的发布控制器。代价：`build` 的输出取决于 store 当时的指针，同一份配置在两个 store 里构建出的 manifest 可能不同；两次构建同时进行会算出同一个 `seq`，后发布的一个被 `PUBLISH_NOT_NEWER` 拒绝，不会错发。不检查能力：发布用的二进制不一定是服务的那个，缺能力的节点自己报 `incompatible`。同一台机器上的两次发布由锁文件互斥，后来的一次报 `PUBLISH_BUSY`、提示稍后重试；跨机器的条件写入要靠对象存储，不在这里做。构建成功时也打印警告：原来只在失败时和错误一起打印，`validate` 报过的警告到了发布这一步反而看不到。
  - `stratarec revoke -s <store> -p <流水线> [-e <环境>] <实验>...` 是紧急停止：把指针当前指向的 manifest 去掉这些实验，`seq` 加一，把它们连同产物哈希记进 `revoked`（之前撤销、仍未带回的照样保留），`previous` 指向原来那个，写进 store 并立即移动指针。不编译、不校验：去掉实验不会让有效的发布变得无效，所以停止只需要节点的轮询间隔加一次编译，不需要仓库和 CI。产物按节点的方式读一遍。`requires` 不重新计算：基线的照抄，被撤销实验自己的 `requires` 随条目一起去掉，所以二进制回滚之后，去掉依赖新能力的实验得到的 manifest 恰好能被旧二进制接受，前一次停止去掉的也不会在下一次回来。读指针和写指针都在指针的锁里，和 `publish` 互斥，中间插不进别的发布。重复执行什么都不改、成功退出（实验已经在已发布的 `revoked` 里时说明是哪个 `seq` 停止的），停止可以放心重试；有一个实验名不认识就报错（提示相近的名字或列出已发布的实验），什么都不撤销。
  - 停止要持续下去。没有选的做法是在控制器的状态里标记为已停止；这里不另存状态，而是记在已发布的 manifest 里：`revoked` 列出被停止的实验和当时的产物哈希；`build` 原样发布其中某个实验时报 `EXPERIMENT_REVOKED`，位置是发布文件里这个实验的条目，提示先从发布文件里去掉，或者用 `--restore` 原样恢复。没有这个检查，停止之后 CI 的下一次例行发布就会把出问题的实验原样带回来。产物变了（owner 的修复）照常发布；一次普通发布的 manifest 不带 `revoked`：它没带上的是有意去掉的，带上的是有意恢复的。从发布文件里去掉这个实验之后，构建结果和撤销本身一样（`revoked` 算发布字段），`build` 报“未变化”，停止继续有效。已发布的 manifest 又带上了被停止的实验（别的控制器把它恢复了），它就不算被停止，下一次撤销也不再列出它。原来停止状态从撤销链推出：撤销的 manifest 以 min_accepted_seq 等于 `seq` 为标记，沿 `previous` 往回读，历史中间读不到时还要警告；min_accepted_seq 去掉之后（见“撤销是一次普通的新发布”），这个标记没有了，直接把列表随撤销带下去更简单：不读历史，没有读不到的情况。没有在 `publish` 检查：发布文件是做这个决定的地方，`publish` 只移动指针（和它不查能力同理）；用 `--seq` 自己编号的控制器自己保存停止状态。
  - `stratarec status -s <store>` 列出 store 发布的内容：每个指针指向的 manifest、`seq`、发布的实验，以及正在生效的停止（`revoked` 列出、当前发布里又没有的实验，`build` 会把它们挡在外面；当前发布又发布了的是被恢复了，控制器保留了旧记录也不算。是否生效只由 `ReleaseManifest.TryGetStop` 判断，`build`、`revoke`、`status` 共用）。原来要看线上是什么，只能自己读指针文件再去 blob 目录里找 manifest；紧急停止之后更需要一眼看到“停了什么、谁停的”。只读 store，节点实际应用了什么由节点上报，这里不猜。一个指针读不到就报错（退出码 1），其余照常列出，不让一个坏指针挡住全部：内容不是合法字符串、文件名不能是指针、目录读不了都算读不到（它们原来让整个命令以未处理的异常结束），`-e` 只列那个环境的目录；目录是枚举出来的，不先问它是否存在：进不去的目录在 `Directory.Exists` 看来不存在，会被当成“没有发布”；位置上是普通文件时系统报的也是“找不到”（ENOTDIR），所以再看路径上有没有文件，有就是读不到；store 目录不存在是用法错误，多半是 `-s` 写错了。
  - 命令写不了的东西报诊断，不抛异常（原来只打印异常和堆栈，退出码 1 又是“配置有错”，使用者会去查已经通过校验的配置）。`build`、`publish`、`revoke` 写不了 store 时报 `STORE_UNWRITABLE`，位置是 `--store`，消息是系统给的、带着路径；`build --manifest` 和 `run --record` 写不了文件时报 `OUTPUT_UNWRITABLE`，位置是那个选项；退出码都是 1。输出文件的目录不存在就创建，和 `init`、`schema --out`、`run --record` 一致（`build --manifest` 原来不建）。`run --record` 写不了时照样打印结果，请求已经执行了。读不到的东西仍在读的地方报（`ARTIFACT_UNAVAILABLE`、`POINTER_UNREADABLE`），所以命令外层只把剩下的 I/O 错误归给 store。
- **`stratarec` 的命令是一个库（`StrataRec.CommandLine`），工具只是调用它**。宿主的二进制用自己的 `PlanEnvironment` 调用 `StrataRecCommandLine.InvokeAsync`，得到全部命令，选项、输出和退出码与官方工具相同，`schema`、`operators` 也列出它自己的算子。单独成库是因为打包成工具（PackAsTool）的项目不能被项目引用。每个命令用 `with { BaseDirectory = … }` 把环境放进它读的工作区，所以 `PlanEnvironment` 改成了 record。官方的 `stratarec` 只剩一个环境：内置组件、`StrataRec.Llm` 和 `redis@1`。
- **配置里写 `null` 的地方，模型说不能为空就是绑定错误**。所有产物、算子配置和请求文件都经过 `ArtifactSerializer`：成员由 System.Text.Json 的 `RespectNullableAnnotations` 检查，集合的元素（`"outputs": { "x": null }`、`"source_order": ["a", null]`）由 `NullElements` 按成员的可空注解检查（序列化器不查元素）。错误在值的指针上，用 “must be …, got null.” 的说法，同其他绑定错误。原来只有回放包有自己的遍历，算子配置里的 null 一路传到读它的代码，变成没有位置的异常（流水线的列、请求输入、模型输出、召回的来源顺序和 `GroupAggregate@1` 的输出都会）。遍历的是文档，不是绑定出的对象，由序列化器自己的 `JsonTypeInfo` 引导（成员的 JSON 名字、集合和字典的元素类型、多态类型按鉴别字段）：位置就是 null 写在文档里的位置。先后试过遍历绑定出的对象：会执行只读的计算属性（返回 `this` 的无限递归），位置要从对象重建，而 enum 键、`"01"` 这样的数字键、带小数秒的日期键读回来拼法变了，`HashSet`、`SortedSet`、`Stack` 去重、重排或倒序，指针指向别的值或不存在，键专用的转换器还会让诊断本身抛异常。根是集合时也走它的元素（实验补丁的段是字典），但根的元素可空性未知，元素为 null 时放过（补丁里的 null 是删除）；有自己转换器的成员和序列化器不当作对象、列表或字典读的类型不往里走；扩展数据的项在对象本身的层级。只查序列化器真正读的成员：有 setter、经构造参数或按 populate 填写的；忽略的（`[JsonIgnore]`）和只有 getter 的计算属性，序列化器跳过文档里的值，检查也跳过，原来照样检查，合法的输入被拒。忽略的成员连同同名的构造参数都不读；类型或选项上的 populate 只是偏好，结构体、数组、不可变或只读的集合退回替换，没有 setter 就不读，只有成员上明写的 populate 一定生效（序列化器不能填写时拒绝这份契约）；扩展数据成员不被填写时，归它的成员也不查。能不能填写由序列化器的转换器决定，它没有公开：能创建的集合（`JsonTypeInfo.CreateObject`）算能填写，此外还有序列化器能往里加元素、但不能创建的集合（只有带参数构造函数、派生自 `List<T>` 或 `Dictionary<K, V>` 的类型，只实现 `ICollection<T>` 的类型），按转换器填写的形状认（列表、集合、字典、队列、栈），数组和 `System.Collections.Immutable` 的集合除外。原来只看能不能创建，前一种被当成不填写，其中的 null 漏查。测试逐个类型和序列化器的实际行为对照。经构造参数填写的成员按参数的注解检查：文档读进的是参数，构造函数可以接收 null 再滤掉，属性的注解说的是滤过之后。有值的 `Nullable<T>` 按 `T` 走（它自己的类型信息是不透明的，原来里面的 null 元素漏掉了）。文档里没有任何 null 时不遍历（字符串入口的严格检查顺带记下有没有 null，树入口先扫一遍；树里的 `JsonValue` 可以包着 CLR 的数组或对象，按它写出的 JSON 种类算，同样的 JSON 不因树的建法不同而漏查），每个类型的成员只查一次，只在绑定时运行。`DataFile` 按字节读：先按文本读时非法字节被替换成 U+FFFD，被替换的 id 成了另一个 id；数据文件因此和工作区的其他 JSON 一样只能是 UTF-8（可以带 BOM），UTF-16 的文件报错并提示转存为 UTF-8。可空性只能来自注解：新的模型成员或配置成员按需要写成 `T?`，绑定就按它检查，不用另外登记。
- **结果按列构造，逐行的 `Items` 在第一次读取时才生成**。`RecResult` 持有 `Columns`（`ResultColumns`：按名次排列的 id 数组，每个输出列一个 `ScalarValue[]`），`Items` 是由它生成的逐行字典，只生成一次：第一次读取时在锁里生成，之后不加锁读取（原来用比较交换发布，多个线程同时第一次读取时各自生成一份，只留一份）。返回的行通常远少于召回的行，逐行字典最好用；少数宿主返回大量行再处理，按列读不必为每行建字典（5,000 行 8 列：列约 1 MB，逐行约 3.4 MB）。`RecResultJson` 和 `stratarec replay` 都按列写，所以只把结果写成 JSON 的宿主也不再建逐行字典。每列带着声明的类型（`ResultColumns.Types`，见“出口交付声明的类型”）。没有选“请求里选结果形式”的开关：使用者要先知道有两种形式、在请求时选对，而按列构造、逐行按需生成，两种读法都不多付成本。手工构造结果（测试替身）用 `ResultColumns.FromItems`，要给出每列的名字和类型。
- **请求文档由引擎读，和结果文档对称**。原来引擎只提供读输入的 `RequestSchema.TryRead`，请求文档其余的规则（顶层必须是对象、`request_id` 非空、`assignment` 是字符串数组、未知成员报错并提示最接近的名字、重复成员和坏的转义）由示例宿主手写了约 100 行，另一个宿主得再写一遍，写法还会不一样。现在 `RecRequestJson.TryRead` 读出 `RecRequestDocument`（输入、请求 id、分配），宿主只补截止时间和它授权的调试选项。调试成员（强制的臂、配置覆盖、固定的时间和种子）不在文档里：谁能用它们是宿主的决定。CLI 的请求文件仍是自己的格式：它带 `pipeline_id` 和这些调试成员，按 JSON Schema 绑定。
- **`stratarec run` 的截止时间可以覆盖：`--deadline-ms`**。CLI 每次只跑一个请求，进程是冷的，第一个请求还要 JIT 编译它执行的代码：示例请求的 200 ms 是给预热好的服务的，在慢机器或繁忙的 CI 上会用完（CI 曾因此失败，节点都成功、请求截止时间到了，错误是 “no time left before the request deadline”）。请求失败并且用掉了截止时间（不少于九成）时，CLI 在标准错误上提示原因和这个选项。只覆盖请求的截止时间，节点和数据源的预算不变：那些是被演示的配置。没有选预热：先跑一遍同样的请求，会让真实连接器的调用、日志和录制都发生两次。也没有改示例的 200 ms：示例演示真实预算。CI 运行示例时用 `--deadline-ms 10000`。
- **输出列是一个列时直接读列的存储**。原来每个输出列都按表的容量租一块缓冲、求值、再取返回的那几行：4,096 行里返回 1 行的 128 维 embedding 列要租 2 MB。纯列引用现在按返回的行从列里读，和探针的做法一样，读某个节点的版本（`col.x@node`）也是；计算出来的输出列不变。
