# 绑定的实例

模型客户端、召回源和特征连接器是绑定的实例，可能是内置的，也可能是使用方写的。持有连接、要先读文件或询问远程服务的实现需要知道框架什么时候创建、共用、调用和释放它们，才能放心接入。

- **契约从实现方的角度写，只写在一处**：`BindingContext` 的文档（工厂接口 `IBindingFactory<T>` 和 `ILoadable` 都指向它），内置的和使用方写的实例、各种绑定的实例都是同一套规则。框架保证：
  - `Create` 只在计划编译、还没有这个身份的可用实例时调用：引擎加载第一个用到它的计划时，前一个实例加载失败之后，以及每一次不服务的编译（`validate`、`build`、`explain-plan`），后者的实例从不加载、调用或释放；两个计划同时加载可能各建一个，多出来的不加载、不调用就释放。
  - 同一身份一个实例，引擎的所有计划和它们的并发请求共用；绑定不变的计划切换接手已经加载的实例，设置变了就建新的，在新计划服务之前加载好。
  - `LoadAsync` 最多一次，在线程池上，有上界、可取消，完成之前不用它服务任何计划；请求路径上不等任何本可以在加载时做的 I/O。
  - 请求的调用和签名查询都在加载完成之后。调用超时时引擎不再等它、取消令牌，但实例活到调用真正返回。
  - Dispose 恰好一次，在线程池上：不再有服务中的计划用它，也没有请求、被放弃的调用或签名查询还在它里面，加载（如果开始了）已经返回；开始 Dispose 之后不再有调用。可能没有加载就 Dispose（不加载的回放引擎、多出来的实例），也可能在加载失败之后。加载或调用一直不返回的实例一直不 Dispose，关闭时报告。

  实现方要做的：`Create` 只读、检查设置，不做 I/O，不占用需要释放的东西（不服务的编译从不释放实例），可能被并发调用；I/O、连接和秘密解析放在 `LoadAsync`；实例线程安全；遵守取消令牌（不遵守只会推迟释放）；Dispose 释放到目前为止拿到的一切；设置错误抛 `BindingException`，带设置的指针和 hint；秘密值不放进消息、异常和日志。内置的 `memory@1`、`memory_list@1` 不守“`Create` 不做 I/O”：它们是样例和测试用的固定数据，在 `Create` 里读一个小的本地文件，换来不需要加载，单元测试可以直接用工厂建出来调用；代价是 `validate` 也要有这些文件。生命周期测试用计数的替身包住它们（以及一个要加载的模型客户端、一个要问模型服务才知道签名的客户端），不依赖真实的推理或存储。
- **一个计划一个绑定租约，表和实例都在里面**。`LocalTableHost` 改名 `BindingHost`、`LocalTableLease` 改名 `BindingLease`：计划编译时向自己的租约取表和实例（`IPlanBindings`），身份相同就拿已有的，切换计划时接手已经加载的实例，不重建。生命周期的规则只在两处：`BindingHost` 管共享、加载、释放和关闭，`BindingLease` 管一个计划持有什么、什么时候归还；`RecEngine` 只开租约、发布、退役，加载、发布和释放的排序不变（见“本地特征表”）。没有为实例另开一种租约：两种租约要分别和发布排序，归还的时机也是两套，出错的地方翻倍。
- **实例的身份**是 RFC 8785 规范化的 {段（`services`、`sources`）、逻辑名、类型、绑定自己的全部设置、基准目录（绝对路径）}，并且只在同一个工厂对象之间共享，两个注册表不同的引擎不会共用实例。框架自己解释的设置（`client`、`timeout_ms`、`max_batch`）不在里面，改超时不会重新加载模型。设置整体放进身份，理由和 `LocalTableSpec.Identity` 相同。逻辑名也在身份里，因为工厂拿到它（错误和日志用它称呼实例）；代价：两个名字绑定同一个模型文件或服务、同样的设置时是两个实例，各加载一次。凭据只以引用出现，所以身份里没有秘密值，秘密轮换不换实例。
- **表在计划退役时释放，实例要等计划的最后一个用户离开**。两条规则不同，因为表的读取钉住了版本：请求读自己钉住的版本，停掉来源不影响它；实例没有版本可钉，还在运行的请求、它在超时时放弃的调用都还会用它。所以租约有一个计数：请求进入（`TryEnter`）到请求结束；请求的每次运行加入（`Join`），在它的请求内存最后一次 `Release` 时离开（`IRequestEndObserver`）。被放弃的调用持有请求内存直到客户端真正返回（见“执行与宿主”），所以这一刻之后请求的任何部分都不会再调用实例，不需要第二套计数。签名查询也是这个计数里的用户，从发出到客户端返回：租约退役时取消查询，但客户端还在 `DescribeAsync` 里时不释放它（只等加载返回的话，加载超时或被拒绝的计划会在查询中途释放客户端，有回归测试）；取消查询本身也是一个用户，直到客户端注册在查询令牌上的回调都运行完，租约退役和调用方放弃走同一个取消入口。租约退役并且计数归零时，实例还给宿主；宿主在线程池上等实例的加载返回，再 Dispose（`IAsyncDisposable` 优先，否则 `IDisposable`），不在请求或客户端的线程上执行实例的代码。退役后进入失败的请求重新读当前计划；引擎释放之后请求抛 `ObjectDisposedException`，包括它从没服务过的流水线；释放时还在运行的请求照常完成，实例在它们结束之后释放。后备流水线进入自己的租约，主流水线运行之后引擎被释放的话，请求返回主流水线的结果，和没有后备一样。回放也进入租约：回放不调用客户端，但一条规则管所有运行，比依赖“这次运行不会调用”更不容易出错。代价：每个请求多几次原子操作。
- **实例在计划服务之前加载，不在请求路径上**（`ILoadable`）。引擎等计划的表完成首次加载时，也等它的实例加载完，任一失败就停止等待。加载在线程池上运行，有上界（`BindingHostOptions.LoadTimeout`，默认 2 分钟）；失败或超时的计划被拒绝，`BINDING_LOAD_FAILED` 指向绑定，实例抛 `BindingException` 时指向那个设置并带它的 hint，例如 `bindings:prod /services/ctr_model/credentials`。失败的实例不再交给任何计划，同一个绑定再加载时建新实例、真正重试，与表的首次加载失败一样，后台不自动重试。实例不会在加载还在运行时被 Dispose：释放先取消加载，等加载和这次取消的回调都返回再 Dispose（回调可能先结束加载、再用实例做清理，与表的来源停止相同；关闭和释放谁先取消，都等第一次取消的回调）；加载或取消回调一直不返回的实例一直不 Dispose，关闭时报告。关闭在同一个 `ShutdownTimeout` 里等所有表的来源停止、所有实例 Dispose，超时写日志（事件 1210：还有请求或被放弃的调用在用的实例，或者加载、Dispose 没有返回的实例）；日志或 Dispose 抛出的异常只记录，不结束也不跳过任何等待（与表的停止相同）。
- **模型签名改成异步，在加载时取得；需要等待时计划编译两次**（1.0 之前的不兼容改动）。`IModelClient.GetSignature` 改成 `GetSignatureAsync(model, version, CancellationToken)`（第 2 步起是 `IServiceClient.DescribeAsync`）：真实客户端的签名要等它读完模型文件，或者问模型服务。SPI 只改这一处，检查的位置不变，仍在 `ModelScorer` 编译时：编译向租约要签名，已有答案的直接检查；还要等的是 `Pending`，这次编译跳过；`BindingLease.CompileAsync` 编译一次之后，同时等所有未完成的查询（每个先等它的客户端加载完再问），上界是 `LoadTimeout`，再用答案编译一次，只有第二次的结果算数，到时没有答案的查询在第二次里是 `SERVICE_SIGNATURE` 错误，hint 说明调大 `LoadTimeout` 或检查服务。要不要第二次编译，看第一次编译里有没有哪次检查被答了 `Pending`，不看编译结束时还有没有未完成的查询：查询可能在基线那一遍之后、某个臂那一遍之前回来，这样的编译只检查了一部分臂组合。原来按后者判断，这种时序下计划只编译一次，错误归到某个臂上，归属随时序变化；所有检查都是 `Pending`、查询又恰好在编译结束前回来时，签名完全没有检查（单元测试确定地复现这个时序，集成测试原来偶发失败）。每个（客户端、模型、版本）只问一次，两次编译和各个验证阶段共用答案；客户端加载失败时签名不检查，错误是那次加载失败，只报一次。没有选的做法：把检查推迟到编译之后（检查要知道节点、配置键和臂组合，`UnifiedCompilation` 的归属和去重要另做一遍）；在编译里同步阻塞地等（模型多时串行，且占着加载线程）；在请求路径上第一次调用时检查（违背加载时检查）。客户端的签名方法整个在线程池上运行，包括第一次 await 之前的同步部分：原来在编译线程上直接调用，方法在返回任务之前同步阻塞（同步询问元数据）时，编译连 `Pending` 都拿不到，`LoadTimeout` 和调用方的取消都不起作用，超过上界之后同步返回的答案还被当作已知。代价：引擎加载检查模型签名的计划通常编译两次，原来立即回答的客户端（`linear@1`）只编译一次；只有检查时每个答案都已经回来，才只编译一次，这时每项检查都做了，所以测试不能假定一定编译两次；计划加载不在请求路径上，这个代价只在发布时付。没有选“先在编译线程上试一次、未完成才放到线程池”：同步部分正是会阻塞的部分。查询等客户端加载时随计划取消：查询占着租约，租约要等最后一个用户离开才归还客户端，客户端没有人持有才取消加载，原来计划被取消后，这三者要到 `LoadTimeout` 才放开（外部评审）；另一个计划持有同一个客户端时加载照常进行，已经在客户端方法里的查询照旧等它返回。
- **静态编译不加载实例，需要加载才能回答的签名不检查**。`validate`、`build`、`explain-plan` 用 `UnloadedBindings`：实例照常创建，设置的错误照样报告，但不加载；签名只在客户端不需要加载并且立即回答时检查（`linear@1`），其余留给引擎加载时检查。所以静态检查不需要模型文件、网络和秘密；代价：版本名写错、模型输入名不符这类错误要到引擎加载时才发现。回放用的引擎（`Load = false`）同样不加载实例。
- **凭据只以引用出现**（`"credentials": "secret://<名字>"`）。工厂创建实例时用 `BindingContext.SecretReference` 读出引用：不是 `secret://` 就是指向那个设置的配置错误，消息不引用写错的值，因为它可能就是误贴进来的凭据。实例加载时用宿主的 `ISecretResolver` 解析（DI 容器里注册的，或 `BindingHostOptions.Secrets`）；没有这个秘密、宿主没有秘密存储，都是 `BINDING_LOAD_FAILED`，指向那个设置并带 hint。解析出的值是 `Secret`，`ToString()` 是 `[secret]`，只有 `Reveal()` 读得到；框架不持有值，值从存储直接交给实例，诊断、日志、trace 和回放包里只有引用。不做缓存和轮换：实例每次加载解析一次，要轮换的实例自己再解析。测试确认值不出现在诊断、日志、trace 和回放包里，误写成值的凭据也不出现在诊断和日志里。
- **本地文件设置只有一条规则：`LocalPaths`**。基准目录在 `BindingContext.PinBaseDirectory` 固定成绝对路径（原来在 `LocalTableSpec`，理由见“本地特征表”），文件设置可以是相对于配置根目录的路径、绝对路径或 `file://` URI，别的 scheme 不是本地路径。本地表和 `snapshot_files@1` 用它，读本地文件的其他实现也应该用：`BindingContext.LocalFile` 把错误转成指向设置的 `BindingException`，各处接受同样的写法、拒绝同样的错误。
- **工厂接口改成 `Create(BindingContext)`**（1.0 之前的不兼容改动）。模型、召回源、连接器的工厂原来各自接收名字、设置和基准目录；`BindingContext` 还带着秘密存储，以后再加东西不用改工厂接口。工厂只读设置、不做 I/O：实例由多个计划共享，I/O 放在 `LoadAsync`，只在引擎加载时做。`RecEngine` 的构造参数相应是 `bindings`（外部的 `BindingHost`，由调用方释放）或 `bindingOptions`（引擎自建宿主的选项：秘密存储、加载和关闭的上界），只能给一个。
- **绑定工厂的设置是类型**。原来每个工厂手工解析 `IReadOnlyDictionary<string, JsonElement>`：`linear@1` 一百多行，未知键、类型错误、缺必填的报错措辞和严格程度各不相同，绑定的 Schema 只能接受任意成员，编辑器标不出写错的设置。现在工厂接口有 `SettingsType`，基类 `BindingFactory<TInstance, TSettings>` 把设置类型写在类型参数里，只写一次，绑定、报错和 Schema 都由它生成，不会不一致；接口不以设置类型为参数，因为注册表按名字混放工厂、测试的装饰器要转发，不想用基类的自定义工厂直接调用 `BindingSettings.Bind<T>`。报错用算子配置的同一套措辞（`JsonBindingErrors`），缺必填成员时指针是它所在的对象，和算子配置一致。`LocalFile`、`SecretReference` 的转换器需要绑定上下文和指针，System.Text.Json 不给转换器传调用状态、每次新建 options 又会丢掉元数据缓存，所以用线程静态的作用域（同步绑定，嵌套时保存并恢复），指针由值在被绑定字节里的偏移算出；只在编译时运行，不在请求路径上。多种写法的设置（`random@1` 的输入输出、`memory_list@1` 的列表项）声明为 `JsonElement`，确定写法后再绑定，不引入多态转换器，Schema 里只有描述。可选设置写 `null` 等于不写。代码构造的设置可能含重复的键或超出 double 范围的数，绑定时在具体指针处报错，不静默取后一个值或绑定成无穷大。实例身份仍是绑定自己写下的全部设置。更新来源的上下文暂时没有密钥存储（没有需要的来源）。
