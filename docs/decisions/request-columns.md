# 请求列

- **节点算出的请求级信息是请求列 `req.*`，不是可写的 `ctx.*`，也不是只给调用方的旁路**（2026-11-22）。需要它的有三方：后面的节点（表达式和 `when`，例如候选太少时不打散、按最高分的比例设阈值）、探针（`context`）和调用方（`output.values`）。原来算子只能写候选列，请求级的值只能写成每行一样的一列，调用方拿不到，`when` 也读不了。不并进 `ctx.*`：`ctx` 是请求开始时就确定的输入和特征，在区段开始前就能求值、预取；混进节点写的值，读者就分不清一个名字是一直有值，还是到某个位置才有。单独的前缀让读者一眼看出它由节点写、按位置有值；`ctx.x` 写成了请求列（或者反过来）时，错误提示另一个名字空间。存储复用请求的上下文数组，表达式引擎不用改，每次求值读当时的值。
  - 声明和列共用一份定义和一套规则（`request_columns`，`ColumnSpec`）：非空的请求列在读取者之前要有不会被跳过的产出者，同一路径上只有一个产出者（`flow` 除外），浮点和 `int32` 的非空请求列要有 `default`，存不下的值（NaN、±∞、超出 `int32`）被替换并计数（`stratarec.column.nonfinite` 的 `column` 是 `req.<名字>`），float32 的值和默认值都按 float32 保存。一套规则用户不用学两次，数据流检查也照样覆盖每一种实验组合。只认显式声明，不像候选列那样允许写者隐式声明：候选列的隐式输出多是算子自己的中间结果（`recall.*`、组内名次），请求列多半是给后面的节点、探针和调用方的约定，类型、可空和默认值应该写在一处，而不是由先写它的节点决定。没有声明时，错误直接给出要加的那条声明（`RequestAggregate@1` 按它写出的类型），多写这一行几乎没有成本。
  - 节点写的值先暂存在这次尝试里，节点提交时才发布；节点失败、回滚、超时之后才到的写都不发布，和候选列的槽位一样，后备节点看到的是主节点之前的值。暂存数组只在写了请求列的尝试里分配，每列一项。节点什么都没写时，它之后这个请求列是缺失（流动列也一样：节点的写就是新版本），非空的就让节点失败。没有选“没写就保留上一个版本”：那样流动列的版本取决于算子走了哪条代码路径，读者无从知道。
  - 算子在编译时用 `TryWriteRequestColumn` 取得要写的请求列（必须声明，描述符要有 `RequestWriter`），运行时用 `SetRequestValue` 暂存值。值的类别不对（例如给 `int64?` 写字符串）、字符串列表里有 null，抛 `ArgumentException`，这是算子的缺陷，不是数据问题，按节点失败处理；整数可以写进浮点请求列。值按节点编译时取得的声明检查，不按算子传来的句柄：句柄只是“第几个请求列”，改了它的类型也写不进别的类别（原来按句柄的类型检查，错误的值被提交，到输出求值时才抛异常，越过了节点的失败处理）。
- **读请求列的 `when` 在节点的位置求值，不在区段开始前**。区段开始时它要读的值还没写。代价是这个节点的候选特征照常随区段预取，`when` 最后为假时这次拉取白做了；不改成到节点的位置再拉取，因为它为真时，那样会失去和前面节点的重叠，而它多半为真（这类条件通常是“候选够多才执行”）。
- **触发条件可以读请求列，触发仍然对所有桶对称**。站点条件是“还没被触发的实验”在这个位置上各桶条件的“或”。一个实验在被触发之前对请求没有任何作用：它改动的每个位置都是它的站点，到达站点时只要有一个桶会执行改动就已经触发了。所以条件读到的请求列，在这个实验的每个桶里都是同一个值。条件读的请求列只由某个桶的节点写时也一样：那个节点的位置是更早的站点，实验在那里已经触发，后面的条件不再求值。运行时对“非空的请求列还没写”的检查（节点跳过为 `skipped_input`，条件不成立）因此只是防御，和候选列没有产出时跳过节点一样。
- **漏斗组的键和目录的衍生特征不能读请求列**。漏斗组的键在请求开始时决定是否采样，那时请求列还没有值；衍生特征是请求级的特征，在任何节点之前计算。探针在它的挂载点读，`context` 记录到那里为止写过的值。
- **输出的列也可以读请求列，规则和 `values` 一样**。每个条目读同一个请求级的值是正当的用法（例如按最高分归一化）；原来只检查了 `values` 读的非空请求列有没有产出者，`columns` 读一个没有产出者的，计划照样通过，构建结果时抛异常。
- **调用方经 `output.values` 拿到请求级的值**（`RecResult.Values`，JSON 的 `values`）。它们是请求级的表达式，可以读 `ctx`、`param` 和 `req`，按名字返回，带声明的类型。没有放进每个条目的列：一个请求一份的值重复写在每一行上，调用方还得自己判断各行是否一致。后备流水线接手的请求返回后备流水线的值，和它的条目一样（原来合并结果时漏掉了，录制里有、实时和回放的结果里没有）。回放包记录它们和它们的类型，格式升到 `2026-11-22.1`；回放比较的结果包括它们，值或类型不同、只有一边有，按名字报告（`value_changes`）。
- **内置 `RequestAggregate@1` 只做 count、sum、mean、min、max 加 `where`**。缺失值像 SQL 的聚合一样不参加，没有可聚合的值时，除了 count 都是缺失，所以这些请求列要声明为可空（编译时检查）。整数的 sum 和 mean 用 `Int128` 精确累加到最后：sum 只在最终结果超出 int64 时让节点失败（不回绕，也不悄悄改成浮点），不取决于行的顺序；mean 在和的绝对值不超过 2^53 时是精确的和除以个数，一次除法，正确舍入；更大时先把和舍入成 double 会丢掉信息，改为精确的商加上余数除以个数，误差不超过一个 ULP，每行相同时得到那个值（按 double 舍入）。超过 2^53 的和在推荐的统计里几乎不会出现，为它做正确舍入要多一套有理数比较，不值得（原来逐步检查溢出，`[MaxValue, 1, -1]` 失败而换个顺序就成功；mean 逐项转成 double，`[MaxValue, MinValue]` 得 0）。浮点的 sum 仍按行的顺序逐项相加，中间值可能先溢出成 ±∞（然后按非有限值替换）；精确的浮点和要补偿求和或更宽的类型，为这种极端输入不值得。一个节点的各个值共用求值的缓冲区，每种至多一份，不按值各租一份、持有到请求结束。不扩展 `GroupAggregate@1`：它给每一行写一列（组内的值），这里是一个值，两种输出放进一个算子，配置就得说明写到哪里。分位数、标准差等等有需要时再加。
- **实验可以新增请求列，不能修改或删除基线声明的**。和 `columns` 一样是只能新增的集合，理由也一样：一个名字在所有组合里只有一个意思，节点的编译不受别的层的补丁影响。实验之间的交互检查也包括请求列（两个臂新增的节点写同一个流动请求列，一个臂新增的节点读另一个臂新增的节点写的请求列），`reviewed_interactions` 里写成 `req.<名字>`，和同名的候选列区分。只有一种情况仍会撞上：候选列自己就叫 `req.<名字>`（读作 `col.req.<名字>`），又有一个叫 `<名字>` 的请求列，两者的审阅共用一个键。这只影响交互警告和让渡报告里列出的原因（两条原因按字符串合成一条），而这样起名本来就让人分不清，不为它给候选列的键加前缀、改掉已有的审阅。臂声明的请求列只在这个臂被分配的组合里存在：别的层的节点或探针读它、而这个臂不在场时，统一计划报 `NAME_NOT_DECLARED`，和那个组合单独编译的结果一致；按作用域检查组合时，探针绑定的、只由臂声明的请求列也决定它在哪些组合里检查，和候选列一样，包括被优化器删掉的分支里的名字。在那个组合里也没有产出者时，节点读非空的请求列报 `COLUMN_NO_PRODUCER`，探针读请求列（可空的也一样）报 `TAP_COLUMN_NOT_PRODUCED`，同一处不再另报未声明：只补声明不够，还得有节点写它。`output` 不在可补丁视图里，所以臂新增的请求列给本臂的节点和探针用，不能加进 `output.values`。
- **请求列不支持 `req.x@node` 版本引用**。候选列的版本引用依赖每个产出者有自己的槽位；请求列只保留当前值，要读前面的值，可以把它写到另一个请求列。实际需要很少，不为它给每个版本多存一份。
