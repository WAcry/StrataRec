# 实验与计划编译

- **组合校验超限是错误，不是警告**。组合空间不超过 `MaxCombinationsChecked`（4096）时全量枚举。超过时按作用域枚举：数据流的每条规则只取决于少数节点和探针（`PlanBuilder.DataFlowScopes`：一列的产出者、读取方和行源，同一 `order` 上的两个节点，节点和它的后备，探针和它读取的列、特征、固定版本），逐个枚举能改变这些节点和探针的层的组合，与全量枚举一样完整；某个作用域自己超过上限时报 `COMBINATION_CHECK_LIMIT`（说明规则对象、涉及的层和组合数），计划不发布。设计假设涉及的层很少，但层数一多组合会指数增长；只给警告就等于在没有证明安全的情况下发布。原来超限后只按列检查非可空列有没有产出者，可空列整个跳过：只在三个桶同时生效时才出现的第二个产出者没有被检查，默认上限下就能发布并运行。可空只豁免“读取方需要产出者”这一条。约束：新增数据流规则必须在 `DataFlowScopes` 里给出它的作用域，否则超限时三层及以上的组合不检查它。成本边界：上限约束的是全空间和单个作用域，不是一次编译的总工作量；同样的层集合和组合只检查一次，作用域枚举的部分最多是（不同作用域的层集合数）×上限。此外，超限时基线、每个单臂和跨层的每对臂总是先检查，与作用域无关，这部分随臂数平方增长：100 个独立层各一个臂是 1 + 100 + C(100,2) = 5051 次。Codex 测过的最坏配置是 13 个互相重叠、各 4096 种组合的作用域：8191 次检查，182 ms，162 MiB。不设总量上限：编译不在请求路径上，硬上限会把慢但正确的编译变成难以处理的拒绝；成了问题时先让每次检查更便宜。单个节点的组合数先判断再相乘，超出就饱和，报 `NODE_TOO_MANY_COMBINATIONS`；原来先乘后截断，层多、桶多时溢出，绕过上限并抛 `OverflowException`。
- **schema 段始终只增**。`columns`、`param_schema`、`features`、`derived_features`、`funnel_groups` 实验都只能新增。实验修改或删除基线 schema，会让其他实验和基线的类型检查失效。
- **实验能改什么是引擎的规则，`policy.jsonc` 只剩 owner**。原来 `experiment_patchable`、experiment_add_only 两个前缀列表声明可修改范围，但只能比引擎的规则更窄：放宽到视图之外的路径照样报错，把 schema 段写成可修改也照样只增（上一条），而且列表和引擎的硬编码规则各报一种错，措辞不同。为了节点按同一份列表重新校验，manifest 还要带上 policy，改一下 owner 就是一次新发布。没有见到需要收窄的场景：要保护的节点由 owner 评审。所以删掉两个列表，可修改范围固定为视图（参数、节点、探针可改，schema 段只增，其他不能改），报错和提示只有一种；policy 只有 `owners`，键是 JSON 指针（写错是加载错误，不再是一个永远匹配不上的前缀），只供 `explain-plan` 列出每个臂的 owner，不进 manifest、不影响编译。`init` 不再生成 policy。旧文件里的两个列表是未知键。
- **基线必须能单独编译**。实验新增的特征或列不能“修好”基线中的引用，否则实验下线后基线就坏了。只要有实验，就把裸基线单独编译一遍（不建计划）。原来只在实验新增 schema 条目或参数叶子时才编，漏了实验新增的节点隐式声明的列：统一 schema 里有它，基线读它（可空，`??` 给默认值）照样通过；撤销不重新编译，发布出去的计划没有节点能加载，节点继续服务带着这个实验的旧计划（外部评审）。不再列举实验声明名字的方式，代价是每次编译多编一遍基线。统一计划的检查已经在同一处报过同一个错误时（组合检查说得更具体），不再重复。
- **校验假定不同层的臂都可能同时生效**。原来不同域的臂组合直接跳过；分配交给实验平台之后没有域了（见“范围调整”），所有跨层的组合都要校验。例外是下一条的让出。
- **跨层冲突用实验级的“让出”解决，不引入优先级**（2026-11-20 用户提问：流量不够、不能把冲突的实验放进同一层时，能否允许低优先级实验被稀释，让高优先级的覆盖）。发布文件的实验条目可以写 `yields_to`：请求同时分到 A 和 A 让给的实验 B 时，A 的所有臂都不生效，记为 `ignored: yielded`；A 和 B 因此永远不同时生效，编译把它们当作同一层。
  - **收益在哪里**：一个实验只能属于一层，它在那一层里还要和别的实验互斥。两层之间有一对冲突时，原来唯一合法的做法是把两层合成一层，所有实验的流量都要减少；让出只让 A 损失 B 的份额。
  - **为什么不用优先级（按路径取高优先级的值）**：A 在重叠流量上会运行“去掉被覆盖部分的 A”，测出来是两种处理的混合；B 的处理组里 A 的改动被盖掉，对照组里却还在，B 的比较也有偏差；两者都无法从记录里修正。全局的层或臂优先级还会把以后新出现的冲突悄悄变成稀释，而不是报错。联合计划的前提（同时生效的臂不改同一处，所以合并与顺序无关）也会被打破。请求级配置覆盖按路径覆盖不受这些影响：它只用于调试，不写持久日志、不进入分析。
  - **为什么按实验、不按臂**：只让给 B 的处理臂时，B 的处理组没有 A、对照组有，B 有偏差；A 的对照臂不一起让出时，A 的两组不可比。按实验让出，B 的两组里 A 都不生效；A 让出的请求在两组之间对称，触发分析自然排除它们；在 A 的分组与 B 的分配（及其依赖的用户特征）共同独立时，只看没分到 B 的用户，A 的估计在这部分用户上没有偏差。
  - **判定只看分配，不看最终生效**：A 让给 B、B 让给 C，三者都分到时只有 C 生效（B 虽然自己也让出，A 仍然让给它）。这样是否让出只取决于别的实验的分配，不需要排序或求不动点，可同时生效的关系也只由成对的声明决定。代价是链条上的稀释略多，这种三方重叠很少。
  - **声明放在发布文件，由让出的一方写**：让出决定的是流量结构，和层写在一起；写在 A 的条目上，评审时由要损失流量的 A 的 owner 确认。没有数值优先级，也不需要排序。
  - **声明本身就是确认，不是警告**：有了 `yields_to`，这一对的 `PATCH_CONFLICT` 和交互都不再报，`explain-plan` 列出它隔开了什么。做成警告的话，CI 用 `--warnings-as-errors` 时还要再加一层确认。声明自身的检查：让给自己或成环是错误（`YIELD_SELF`、`YIELD_CYCLE`）；同一层的让出没有意义，是警告（`YIELD_SAME_LAYER`）；两者既不冲突也不交互时是警告（`YIELD_UNUSED`），因为过时的让出只会白白损失流量，还会掩盖下一个冲突。发布文件里让给本次发布没有的实验是错误（`YIELD_UNKNOWN`，带拼写建议）；manifest 里则不起作用、不报错：紧急撤销被让给的实验不经过校验，撤销时顺便去掉指向它的条目。`YIELD_UNUSED` 只看成对的冲突和交互，看不到“三个实验一起才出问题”的组合缺口；为它再枚举组合不值得，这种情况下删掉让出，组合检查照样会报出来。
  - **`ADD_CONFLICT` 照旧是错误**：新增的名字在任何地方只有一种含义，同一层的两个实验也一样，让出不改变这一点。
  - **组合校验的上限按会生效的组合计数**。原来按各层选择的乘积计数，枚举之后才去掉让出的组合：13 层互相让出时只有 14 种组合会运行，却因为乘积 8,192 超过 4,096 被拒绝。让出就是这一对实验“有条件的同一层”：这一对实验的桶同时出现的组合不会运行，计数也不该算它们，否则会因为根本不会运行的组合超限。两层各只有这一个实验时就等于合并两层；一层还有别的实验时，那些实验和另一层的组合照样要查，所以比合并两层多。现在枚举直接跳过含有让出两端的组合（按层顺序剪枝，访问顺序和原来的里程表相同）；有让出时计数也用这个枚举，数到上限加一为止，所以代价不超过一次上限内的枚举，同一组层的计数只做一次；没有让出时仍用乘积。枚举是迭代的：递归的深度随层数增长，层数很多的发布会耗尽线程栈。节点变体的密集索引（`NODE_TOO_MANY_COMBINATIONS`）不变：它按修改这个节点的各层的乘积分配槽位，是存储的上限而不是校验的额度；一个节点被十一层修改、而且两两让出，这种配置不值得为它换成稀疏索引。
  - **回放按回放的计划重新解析录制的分配**。平台的分配（来源 `external`、`provider`）录制的是平台发来的全部 ID：生效的和因任何原因被忽略的。回放把它们按平台的规则重新解析（`ExternalArms.Resolve`：未知和层冲突是忽略，不是错误），再解析让出，被忽略列表全部由这次解析得出，和请求现在的分配方式相同。原来只把录制里生效的桶送进新计划：让出关系被删除或反转后，原来让出的臂不参加解析，回放结果和录制一样却和线上不同，报告还说一致；两个臂在新计划里同层时，回放报无效请求，线上却是层冲突、按基线执行。强制的桶和传给回放的桶是严格的：同一层的两个臂拒绝回放，和请求里的强制桶一样；不存在的臂去掉并写说明，这一点比请求宽（请求会拒绝），因为回放的配置本来就可能少了录制时的实验（已有约定）。回放的输入是请求的分配记录，主运行记下的臂只用于报告的对比：引擎写的包里两者一致，手改了分配的包按改后的分配回放，报告里录制和回放的臂不同。生效情况和录制不同的臂各写一条说明（录制里运行、回放里被忽略的，录制里被忽略、回放里运行的）。
  - **工具**：`diff` 把让出关系的增删列为结构变化（反转是一删一增），因为默认比较的基线和单个桶不受它影响；显式比较 `--arms a,b` 时，只有一边让出的组合报为那一边不存在（`missing_on`），两边都让出才报错。`EffectivePlan.Create` 先解析让出，给出请求在这些桶里实际运行的计划，`ArmIds` 是生效的桶；`explain-plan` 仍然先拒绝永远不会同时运行的组合，因为用户点名的组合不存在比静默改写更该说明。
  - **回放包格式升到 `2026-11-20.3`**：新增的原因 `yielded` 是旧构建读不了的取值，按格式版本的规则（布局或含义变了就升级）升级，旧构建在 `/format` 给出重新录制的提示，而不是在原因上报一个它不认识的取值。
  - **持久的触发记录不写被忽略的分配**。`$experiments` 批次只有生效的桶和被触发的实验。被忽略的桶连同原因由平台的分配和当时的发布唯一确定（未知、层冲突、让出都是分配的函数），分析只需要知道它没有生效：把平台的分配和触发记录按请求 ID 关联即可。原因用于排查，逐请求的结果、回放包和指标都有。所以改设计不改实现：不为每个请求的持久日志多写一个字段，也不升级日志格式。
  - **让出的请求仍预取 A 读的上下文特征**。整份计划的上下文特征都预取（见下文“键可以读上下文特征”），没分到 A 的请求本来就会多拉 A 读的特征；让出的请求和它一样，不单独处理。节点的选择和语义与单独编译这个组合一致，但预取的范围、耗时和遥测不同：多拉的字段可能让一次调用变慢、超时或整体失败，连带本请求要读的字段（实测过超时），派生特征的越界计数也包括它们。这对没分到 A 的请求同样成立，由整份计划的预取决定，不因让出另做处理。
  - **一处判定，编译期和运行时共用**（`ArmYields`）：编译器在每个收集组合里的臂的地方先去掉让出的臂（变体定义、组合校验、日志点变体），含有让出两端的组合定义为去掉之后的组合，不另外编译；运行时在分配之后、选择变体之前统一解析，平台分配、分配服务和强制臂都经过这里；执行器入口再做一次（没有让出时只是判空），直接调用执行器的测试和工具得到同样的结果。`CompileMerged`（配置覆盖和差分测试的参照）按同一规则去掉让出的臂。`explain-plan` 和计划对比遇到永远不会同时运行的臂组合时报错，不静默展示解析后的组合；回放时录制里一起运行、在回放的计划里却让出的臂，按回放的计划去掉并写一条说明。
  - **成本**：没有让出关系时只有一次判空，零分配。有让出时，宿主在分配之后对每个分到的臂查一次它让给的实验，执行器入口对生效的臂再查一次；真的让出时分配被忽略列表（列表、底层数组和最终数组）并复制一次每层的臂数组，实测约 168 B，和层冲突的路径一样。编译期只会少编译组合。manifest 里没有让出时不写 `yields_to`，已有 manifest 的内容 ID 不变；带 `yields_to` 的 manifest 旧构建在该字段上拒绝（`MANIFEST_SCHEMA`），所以先升级节点，再发布带让出的 manifest。
- **统一计划接受的组合，必须和单独编译这个组合时完全一致**。原来有几项检查在最终 `Build` 里对所有变体取并集：固定版本引用（`col.x@node`）只要任何一个变体是行源就报 `VERSION_REF_ROW_SOURCE`，互斥的合法臂被误拒；被固定的节点只在三个桶同时生效时不再写这一列，单独编译会拒绝，统一计划却接受了。现在固定版本在每个组合里判断：被固定的节点要在这个组合里存在并写这一列（否则 `VERSION_REF_UNKNOWN`），不能是行源（`VERSION_REF_ROW_SOURCE`），错误指向读取方（节点、日志点、输出）并带 hint；作用域是读取方加被固定的节点。运行时的规则不变：被固定的节点在这个请求里没有运行（跳过、失败），读到缺失。行为变化：固定一个在某些组合里被删除的节点，原来能通过，现在报错。日志点同理：挂载点（`TAP_UNKNOWN_NODE`）和它记录的上下文特征（`TAP_FEATURE_NOT_FETCHED`）原来对所有变体取并集，基线日志点挂在只由某个臂增加的节点后面也能通过，不带这个臂的请求里静默不记录；现在在每个组合里检查，日志点和它挂载的节点由同一个臂一起增加照样通过（外部评审）。判断一个组合在挂载点之前拉取了哪些特征时，节点读到的特征沿衍生特征的输入和实体键展开，上下文键和候选范围的键都算：节点的补齐会先把键特征写进表。后备读到的特征只算上下文特征及其所需（衍生输入、上下文键），上下文预取不管谁运行都会存下它们；后备读到的候选特征和它们的键，只在后备运行时由它自己的补齐写进候选表，为后备发出的预取不回填。原来特征计划在这些检查之后才把键特征挂成依赖，记录 `ctx.country.region`（只被召回查询读到的 `ctx.region.boost` 的键）的探针被拒绝，而预取每个请求都会拉它；原来后备读到的候选特征也算已拉取，节点之后记录 `col.creator.pop`（只有这个节点未运行的后备才读它）或它的键 `col.item.base` 的探针能通过检查，被采样时请求在读这列时抛异常。被 `when` 或 `min_remaining_ms` 跳过的节点不补齐，它的后备也不运行：它读到的候选特征只在挂在它之后的探针里算（这个探针只在节点或后备运行之后才触发），更晚的挂载点（后面的节点、输出）不算；它读到的上下文特征照算，预取不管谁运行都会存下它们。原来都算，节点被跳过时，挂在输出或更晚节点之后的探针被采样，请求在读这列时抛异常。补齐只写它运行时存活的行，探针又从不补齐：一个位置可能追加行（节点或它的后备是行源）时，之前补齐的候选特征对追加的行没有值，这个位置上节点自己读到的也一样，直到后面的节点读它、为所有存活的行重新补齐，才又算已拉取；上下文特征不受影响（主节点读了 `col.item.base` 后失败，行源后备追加了候选 2，挂在节点之后的探针把候选 2 那一格从没写过的存储当有效值记了下来，旧版本同样如此）。追加的行只出现在这个位置的存活行和之后的挂载点：挂在这个位置、记录 `entered` 或 `dropped` 的探针记的是节点开始前存活的行，补齐时它们都在，节点读到的照算（原来一律不算，只记原有行的探针被拒，改挂到后面又会改变记录的行）。按作用域检查组合时，探针记录的候选特征除了由探针、挂载节点和读它的节点决定，还和每个行源（连同它的后备关系）组成一个作用域（原来行源不在其中，三个独立层分别跳过后面的读取者、在两个读取者之间加行源、让输出探针记录这个特征，超过组合上限后统一编译照样接受，执行时记下追加行的垃圾值）；只算可能在探针触发之前追加行的行源：它作为行源的变体的 order（后备取指向它的节点各变体的 order；没有节点指向的后备不会运行，不算）不晚于记录这个特征的探针变体的挂载点（挂在输出的算全部）。之后才运行的行源追加的行探针记不到，原来也算进来，作用域多了它的层，超过组合上限时一个每个组合都合法的计划被拒（最大的 order 被当成没有 order、算作最早，没有节点指向的后备也一样，不是行源的变体和不记录这个特征的探针变体也参与取值）。order 和挂载点在各变体上分别取极值，不按组合配对：同一个臂同时移动挂载点和行源，或一个后备同时被较早和较晚的节点指向时，仍按可能在前算。配对要逐个组合推理，这正是作用域要省掉的枚举；多算只会多拒（`COMBINATION_CHECK_LIMIT`，hint 说明把哪些实验并到一层），不会漏查，这样的配置也少见。代价是作用域的数目多了“候选特征数 × 之前的行源数”，每个作用域只有几个节点。常量为假的 `when` 也算可能运行：检查从不求值 `when`，别的规则也一样；臂要关掉一个行源，用合并补丁的 `null` 删掉节点。运行时不另加兜底（把没写过的候选特征当缺失记录）：合法的计划走不到那里，测不到，还会把这项检查的缺陷藏起来；节点的补齐在节点预算之前、只受请求取消约束，补齐失败的特征是 `Failed`，探针已经按缺失记录。拒绝的 hint 指出可以记录的位置：挂载点之后第一个读它、且对记录存活行的探针来说这个位置不追加行的节点（原来是第一个读它的节点，这个位置追加行时改挂过去又被拒）；输出读它时挂在输出，只对记录存活行的探针这样说，输出只接受这个范围（原来只找节点；评审：`entered`、`dropped` 的探针照做会被 `TAP_BAD_SCOPE` 拒绝）；挂载点之前读它的节点之后有位置追加了行时，指出这两个节点；记录 `entered`、`dropped` 的探针，读它的节点自己的位置追加行时，指出这个节点，挂在那里记录的行补齐时都在（原来让它找更晚的读取者）；挂载点之前读它的最后一个节点可能被跳过、位置不追加时，指出这个节点和原因（原来先去找追加行的后续读取者）；之后读它的位置都追加行时，指出最后一个，要在它之后读（原来只说“挂在读它的节点之后”，照做的唯一读取者又被拒）；hint 只为缺的这个特征找位置：改挂到较早的位置时，探针别的字段在那里可能还没产出，下一次编译按那个字段报错和提示，不在每个候选位置重做整套检查（保留）；都没有时，说明只有后备读它。探针记录的上下文特征仍按整个组合检查，后备读到的也算。
- **每个组合里，节点绑定的名字都要先声明**。统一计划每个节点只编译一次，用的 schema 是所有臂声明的并集；合并成普通配置单独编译时，一个名字只有在这个组合里声明过才认得。所以每个带臂的组合都检查：节点、fallback、日志点和输出绑定的每个名字（列、参数、特征），在这个组合里编译到它之前必须已经声明，否则报 `NAME_NOT_DECLARED`，hint 建议在基线或读它的臂里声明。声明只有三个来源：基线；这个组合里被分配的臂新增的条目；对列来说，还有先于它编译、写这一列时自带类型（隐式输出，`CompiledNode.Declares`）的节点。编译顺序和统一编译相同：先 order 后 id，fallback 排在时间线之后按 id，日志点和输出最后。这条规则之前是几条各管一种情形的检查，逐个暴露出缺口：一个臂删掉或移走写者、另一层的臂新增读者（生成式差分测试）；节点先读后写自己的输出；评审又找到三处。其一，一个臂在 `columns` 里声明了基线写者隐式写出的列，并集 schema 里这一列就不再算隐式列，另一个臂删掉写者、第三个臂读它，没有声明臂的组合被放行；撤销声明臂后发布的新清单没有节点能加载。其二，死分支和未使用的 `let`：绑定时名字必须存在，优化后的读取（`Reads`）里却没有它。现在表达式同时保留两份：`Names` 是绑定解析过的全部名字，用于这条规则；`Reads` 是优化后的读取，用于取数，死分支不会多取特征。其三，`TryWriteColumn` 不带类型的写需要已有声明，不能当作它自己声明了这一列。节点内部的先后也要记录：节点读自己写过的列，若写在前且自带类型，这次读不再要求别处的声明（`GroupAggregate@1` 按名字先写 `a`、再拿 `a` 算 `b` 合法），否则要求。不带臂的组合不查名字：裸基线会单独编译（见“基线必须能单独编译”），在表达式的确切位置报错，同一个原因不报两次。只有声明会随组合变化的名字（隐式列、臂新增的名字）才登记作用域，否则每个读基线参数的节点都会成为作用域，按作用域检查很快超出上限。没有选择让统一计划接受这些情况、把名字当作缺失：那样有的组合在统一计划上能跑，合并成普通配置却编译不了，16.2 的等价关系不再成立。同一个组合里，其他检查已经在这个读者（或它下面的位置）报过错时，名字规则不再报：日志点读的列在挂载点之前没有产出者时，`TAP_COLUMN_NOT_PRODUCED` 已经说明了原因。
- **实验只给配额就能新增召回源，这个源在没有这个臂的请求里不占位**。map 参数的叶子是基线的加上所有臂新增的键；`MapParam` 返回全部，没有某个臂的请求里，只有这个臂新增的键是缺失的，而这个组合单独编译时根本没有它。所以算子在运行时把缺失的叶子当作没有这一项，也不能从叶子的集合推出位置、个数这类东西。`MultiSourceRecall@1` 原来按来源在全部来源中的位置分配 `recall.sources_mask` 的位：未分配的臂新增的源排在前面时，基线的源的位整体后移，按掩码过滤的基线节点留下了和自己单独编译不同的行。现在第 i 位是这个请求有配额（包括 0）的来源中按合并顺序的第 i 个，和这个组合单独编译时一致。`source_order` 不再要求列出每个源：列出的在前，其余按名字排在后面。原来流水线写了 `source_order`（示例就写了）时，实验无法只靠配额新增源，臂单独编译报“没有列出”；臂同时改 `source_order`，统一计划里基线的变体又因为看到这个新源而报同样的错。列出的源按名字绑定它的配额叶子，臂列出只有另一层的臂新增的源时报 `NAME_NOT_DECLARED`；同一个源列两次是错误（原来会调用两次、占两位）。没有选择把 map 的成员集合记成节点的依赖、逐组合比较：只靠配额新增源正是实验的用法，没有这个臂的组合都会不同，都会被拒。代价：64 个源的上限按所有臂给过配额的源合计，单个请求可能用不了这么多。
- **写已声明的列和声明未声明的列，写者都给出自己的类型**。`TryWriteColumn` 带类型时，未声明的列按这个类型声明；已声明的列保持声明的类型，由调用方检查自己能不能写（`GroupAggregate@1` 接受 int32、可空的声明）。原来 `GroupAggregate@1`、ModelRanker 系列、`LlmAnnotator@1`、`GenerativeRetriever@1` 先查 schema：声明过就不带类型，没声明才带。统一 schema 里另一个臂的声明会让这次写看起来需要声明，而在没有那个臂的组合里，同一个节点会自己声明这一列。`MultiSourceRecall@1` 的 `recall.*` 列只能是固定的类型，改为自己检查。
- **写者声明的列要和臂声明的一致**。一个臂声明的列只在这个臂被分配的组合里存在；其他组合里，写这一列时自带类型的节点声明它。统一计划只有一个 schema，里面是臂的声明，所以在没有这个臂的组合里（包括裸基线），每个这样的写必须声明出同一列：类型相同，没有默认值，不是流动列，否则报 `COLUMN_TYPE_MISMATCH`，hint 建议在基线里声明。生成式差分测试找到了它：同一层互斥的两个臂，一个把 `stat.b` 声明为 `int64?`，另一个用不分组的计数写出 `int64` 并直接读它，统一计划以“可能缺失”拒绝了读者，而那个臂单独编译时这一列从不缺失，错误信息也看不出原因。读者的编译错误可能正来自这里，所以组合里有变体编译失败时，这一项仍然检查。同一个臂既声明又写，声明在写存在的地方都存在，不受影响。
- **生成式差分测试**。`GeneratedExperimentTests` 在示例基线上随机生成实验（多数 1～3 个，四分之一的种子 4～5 个，见下）：有时两个实验共用一层，有时没有对照臂，有时基线多一个读者。每个臂由几个原子改动组成：改参数、新增 `GroupAggregate@1` 写者（可空或不可空）、写者加读者、把基线节点移到新写者之后并改读它、删节点、移节点、加打分节点、加日志点。对每份配置比较统一编译和逐组合的合并编译。统一计划接受的，每个组合都要接受，并且执行结果一致（逐项输出和节点结果）。每个组合都接受、统一计划却拒绝的，只能是跨组合的规则（路径冲突、一列一种类型等）。生成时单独无效的臂大多会重新生成，否则一个无效臂就让整份配置被拒，差分无从比较。实验在代码里直接构造，不经过 JSON 文本，补丁里的数字是 CLR 数值，像宿主构造的那样。它找到了一个臂删掉写者、另一层的臂新增读者的缺陷（见“每个组合里，节点绑定的名字都要先声明”）；只认解析出的 `order` 的缺陷它也能发现。回退外部评审的 P1、P2（按定义编译的顺序）或那个缺陷的修复，它都会失败；其中 P1 要跑到 3000 个种子才稳定出现，另有专门的回归测试覆盖。有时关掉每个臂的单独编译（同时更多地留下单独无效的臂），只靠组合检查拒绝；有时把 `MaxCombinationsChecked` 调到很小，走按作用域的检查；还会生成读自己输出的节点（先写后读的合法形状和先读后写的非法形状，后者让评审的自读豁免失败）。评审指出，层数最多 3、上限不是很小就是 4096，三层的作用域要么全量穷举、要么超出上限，按作用域枚举再检查的路径从没走到；现在四分之一的种子有 4～5 层、多数每层一个处理臂，上限取 8、12 或 16，整个空间超出上限而三层的作用域放得下。但随机生成的配置几乎不会只在三层同时生效时才出错，省掉按作用域的检查照样全绿，所以其中一半植入一条这样的规则：基线有一个写 `stat.a` 的节点排在 `author_cap` 之前，一个臂让 `author_cap` 读它，一个把 `author_cap` 移到 513，一个把写者移到 514，任意一个或两个都合法。省掉检查后 300 个种子里有 2 个失败。原子改动里加了臂的 `columns` 声明和死分支读者，由此找到了“写者声明的列要和臂声明的一致”那一条的缺陷；评审的其他几处由 `DeclarationTests` 逐条覆盖。它的局限：两边共用编译代码，共同的误收误拒发现不了；没有生成后备节点、行源、固定版本和输出读取的变化，这些由专门的测试覆盖。默认 300 个种子，约 25 秒；设置 `STRATAREC_GENERATED_SEEDS` 可以跑更多。
- **`columns_from` 跟随模型变体**。探针展开的是当前臂组合下实际生效的模型节点；修改该模型的层也参与探针的变体划分；探针 schema id 包含每列解析后的表达式。训练日志必须记录服务时真正的输入。
- **节点按时间线顺序编译，不按 id**。一个节点在编译时声明它写的、没有在 `columns` 里声明的列（隐式输出：`recall.*`、`GroupAggregate@1` 的输出、成对和列表重排写的分数列），之后编译的节点才能读到。原来按 id 的字典序编译，读的节点 id 排在写的节点前面（`author_cap` 在 `author_rank` 前面；任何排在 `recall` 前面的节点读 `col.recall.*`）就报“未知名字”，而且看不出原因。现在先合并出每个节点在各组合下的定义，每个不同的定义按它自己的 `order` 编译，后备节点（没有 `order`）排在时间线之后，相同时按 id。原来一个节点的所有定义按其中最小的 `order` 一起编译：实验把读的节点挪到写的节点之后，它的新定义仍在写的节点之前编译，统一计划拒绝了这个组合单独编译能通过的配置（外部评审）。合法的配置里，每个组合中写的节点都在读的节点之前运行，所以写的定义在读的定义之前编译；读的节点排在写的节点之前时，诊断仍是“未知名字”，不是“它的产出者运行得更晚”，这一点没有为它再做一遍。`order` 按绑定时的语义读：只要是整数 JSON 数字，不管树里存的是哪种 CLR 类型。宿主在代码里构造的补丁存的是 `int`，原来只认解析出来的 JSON 元素和 `long`，被移动的写节点因此被当作没有 `order`、排到最后编译，同一份 JSON 程序构造时被拒，解析时通过。没有选“算子先声明再编译”的两阶段接口：多一个所有算子都要实现的扩展点，只为了这个顺序；按定义排序之后，每个读已经在它所有可能的写之后编译。统一 schema 里有别的组合才声明的列，这一点由逐组合的数据流检查和每个臂单独编译把关。
- **节点 id 只能是标识符**（字母、数字、`_`）。版本引用 `col.x@node` 要能写出每个节点；含 `.` 或 `-` 会被解析成字段访问或减法。这是在扩展语法和收紧 id 之间选了后者。
- **行源节点不能被版本引用**（`VERSION_REF_ROW_SOURCE`）。所有行源向同一个槽位追加行，没有“某个节点的版本”可读。
- **行源和它们共用的列版本在编译时检查**。所有行源把自己追加的行写进每一列的同一个共享版本，而一行没写就是缺失（见“执行与宿主”），所以在一条路径上：写不可空列的第一个行源之前，每个行源也要写这一列（`ROW_SOURCE_BEFORE_COLUMN`，指向没写的那个行源，提示同时写这一列，或者声明为可空，例如 `"recall.best_score": { "type": "float64?" }`，再用 `??` 处理缺失）；之后的行源也要写（原有的 `ROW_SOURCE_AFTER_COLUMN`；列由行源以外的节点产出时，提示改为把行源移到那个节点之前，因为这时写这一列也没用）；别的节点已经写出这一列自己的版本之后，行源把自己追加的行写进这个当前版本（见“排序之后注入的行写进当前版本”）。这两种情况运行时会让每个同时运行两个节点的请求在提交时失败，放在编译期，错误指向造成问题的节点。行为变化：自定义行源在 `MultiSourceRecall` 之前、自己不写 `recall.*` 的配置现在编译失败（原来能运行，前一个行源的行读到旧数据），按提示把 `recall.*` 声明为可空即可。后备按它所替代节点的位置检查：主节点失败后已经回滚，不是后备的前驱，所以两者都对照这个位置之前的状态检查；这个位置之后的状态是两者都可能留下的，即可能追加了行、可能写了自己的版本。两者的效果可以不同。后备的输出列和主节点完全相同，同一种效果的检查只取决于之前的状态和这些列，所以每种效果检查一次，错误指向有这种效果的节点（两者都有时指向主节点），不重复报告。原来行源检查只看时间线上的主节点，后备只核对输出列和必需的输入：给写列的节点配一个行源后备，就绕过了上面三项检查，后备追加的行在不可空列里线上读到池里的旧数据、回放读到 0；给行源配一个写列的后备，则绕过了 `COLUMN_MULTIPLE_PRODUCERS`。这样的配置现在编译失败。没有选“主节点和后备的效果必须相同”：满足这些检查的混合配置能正确运行，检查本来就按效果做。
- **实验的过期日期只在 `validate` 和 `build` 检查，到期前 14 天警告**。原来宿主启动、`run`、`explain-plan`、`replay`、`compare` 都拿当天的日期编译：一个实验过了 `expires_at`，正在服务的进程重启就加载失败，过期之前却没有任何提示，调试和回放上周的请求也一起失败。过期是发布流程的规则，不是运行的规则：现在只有决定发布的两个命令检查，`EXPERIMENT_EXPIRING` 警告（CI 可以用 `validate --warnings-as-errors` 拒绝），过期是 `EXPERIMENT_EXPIRED` 错误。宿主不看日期，已经发布的 manifest 照常加载。
- **删掉 ORDER_COLLISION**。初稿规定可能同时生效的两个臂不能在同一个 `order` 上放节点。这条规则比要保护的东西更严：同一 `order` 的节点之间有数据依赖时，逐组合的数据流检查本来就会拒绝（`ORDER_DEPENDENCY`）；没有依赖时，两者谁先执行结果都一样。它只会拒绝每个组合单独编译都能通过的配置，作者只能去协调另一个实验的编号。删掉之后，随机生成的 1,500 份实验配置上，统一计划和逐组合编译的结论仍然一致。
- **行源之后，只有还会被依赖的不可空列需要它写**。初稿的规则是：一个不可空列产出之后，任何追加行的行源都必须写它。规则要防的是读到没有值的行，但它不看之后有没有谁读：生成召回放在多路召回之后，就要为召回的四个归属列（`recall.*`）写值，而这些列描述的是召回找到的行，之后没有谁再读；测试和示例只好把它们声明为可空，注入类的实验也写不出来。现在数据流检查先从后往前走一遍（`ReadsAfterRowSources`），找出每个行源之后还依赖这一列每一行的地方：读它的节点或后备、记录它的日志点、读它的输出，以及之后写这一列的行源（它写进当前版本，提交时检查所有存活行）。在这之前有一个不会被跳过、又不是行源的节点重写了这一列时，重写覆盖所有存活行，之后的读取方不受影响。错误信息指出依赖它的是谁。`ROW_SOURCE_BEFORE_COLUMN` 不放宽：第一个写不可空列的行源提交时检查所有存活行，前面行源的行没有值就会失败。超过组合上限时按作用域检查，这条规则的作用域加上了读这一列的节点、记录它的日志点和它们挂接的节点。
- **读取已弃用的特征是警告，报在特征的声明处，每条流水线一次**。`deprecated` 原来只被接受、从不读取。警告放在声明处而不是读取处：同一个特征可能在很多表达式、臂和组合里被读，按读取处报会在每个变体里重复；声明处一条就说清楚哪个特征、哪条流水线，读取的位置由 `explain-plan` 列出。判断依据是计划实际读到的名字，不是注册了什么：`cache` 数据源整表注册的成员没人读就不警告；读一个外键实体的特征也读它的键（先拉取键），键已弃用时警告。设计初稿里的“报告没有被引用的特征”和“生成可浏览的目录文档”没有做，列在“尚未实现”里：一份目录被多个工作区共用时，一个工作区没读不等于没人用。
- **每个实验在 manifest 里记录自己在基线之外需要的能力，能力从编译结果算出**。原来 manifest 只有一个扁平的 `requires`，撤销时按名字推断去掉哪些：被撤销实验写过、保留的配置没写的模型和召回源绑定才去掉。这条启发式改了四轮，仍有已知的漏洞：算子按配置默认值用到的绑定看不到名字；只被被撤销实验读取的特征数据源，连接器和存储类型撤销后仍然要求，旧二进制接不了这次撤销。现在 `build` 先单独编译基线，再分别编译基线加每个实验（不建计划、不加载任何东西），基线编译用到的算子、模型和召回源客户端、所读特征数据源的连接器、引导来源和分布式存储记在 `requires`，每个实验多用到的记在 `experiments.<id>.requires`；撤销只是删掉条目，不编译也是精确的。组合可能需要单独编译时都不需要的能力（一个实验让召回改读配额 `q2`，另一层的实验往 `q2` 里加一个新客户端类型的源），一个实验单独需要的能力也可能另有一对实验组合起来需要（只记在那一个实验上，撤掉它之后剩下的一对少要求了）。所以基线之外的每项能力这样归属：先记到单独就需要它的实验（集合 O）；再编译一次去掉 O 的其余实验，仍需要它时，其余实验中“去掉它其余的就不再需要”的每一个也记上（各编译一次）；一个也没有的（去掉哪一个都还需要）留在基线。编译更多的实验只会需要更多（每个臂的变体都和基线的变体并存），所以任何撤销后剩下的实验集合：如果需要这项能力，要么含有 O 中的实验，要么是其余实验的子集，从而含有其余实验中记上它的每一个，要么能力在基线里；只会多要求，不会少要求。每个不同的 O 多编译一次，组合真的另有需要时再多若干次，都发生在构建时，有缓存。回滚二进制的控制器撤掉所有列出缺失能力的实验即可。能力取自编译时实际绑定的东西（算子工厂、解析过的客户端名、注册了的特征），所以默认值用到的模型照样计入，没人用的绑定不计入。新字段让更早构建的二进制拒绝新的 manifest；1.0 之前持久化格式没有旧读者，接受。expr_functions@1 删掉了：函数集合的版本从来没人改，改了反而让每个新 manifest 都不被旧二进制接受，不管它用没用新函数；缺函数的二进制在加载时编译失败，错误带表达式位置，节点保留当前计划，和缺算子的结局一样，只是发现得晚一步。
- **字符串主键和其他字符串列一样存在 `StringColumn` 里**。主键先于其他字符串列改成不做字典编码：主键每行各不相同，字典编码只是把每个键在字典和反查表里各存一次，和候选表的键索引重复；字典不从请求内存租借，5,000 个键每个请求约 200 KB（逐个加入是 583 KB，评审为此加的预留也一并删掉）。后来所有字符串列都不做字典编码了（见“只有一种字符串类型”），主键不再是特例。按列名直接读列的分组算子（`GroupAggregate@1`、`SlidingWindowQuota@1`）按字符串相等分组、按首次出现编号，经一个临时的键索引，不为每个请求建字典（主键改存 `text` 时按 `entity_id` 分组的合法配置曾被拒）。
- **交互警告只看新增的节点，评审过的交互记在实验里**。初稿的列足迹包括臂修改过的已有节点：两个不同层的实验各改 `fusion` 的一个乘子，因为 `fusion` 写流动列 `score.final` 就报一次 `INTERACTION_FLOW_COLUMN`，6 个这样的实验两两组合报 15 次；同样的改动通过参数做却一次也不报，同一件事是否警告取决于写法。改已有节点的设置和调参数一样，沿用流水线的结构，所以列足迹只算结构的变化：新增节点的全部列，以及被改的节点比基线版本多写、多读的列（把过滤节点换成写 `score.final` 的打分节点，再被另一个实验新增的节点读取，原来不警告）。读只算读当前版本的：固定版本（`col.x@node`）看不到别的实验新增的写入者，不计；从固定版本改成读当前版本是新的依赖，计入。节点失败时走到的后备节点也算这个节点的读：臂打开后备（`skip` 改成 `fallback`）或换一个后备时，新后备读的列和基线节点能走到的（它自己和它原来的后备）比较，多出来的计入，警告说明是经哪个后备读到的；基线已经能走到的后备不重复计，没有节点会走到的后备不计，免得误报。后备写的列不另算：后备替代的是主节点的输出，主节点的写已经计入。初稿还把评审结论只留在 PR 记录里，警告在每次 validate、build、加载时都重复出现，示例工作区永远带着一条警告，`--warnings-as-errors` 用不了。现在评审者在其中一个实验里写 `reviewed_interactions: { 另一个实验: [列] }`，这一对在这些列上不再警告；新的列照样警告。记录放在实验里而不是发布文件里，因为 manifest 带着实验产物，节点加载时也认得；它只影响警告，不影响编译，实验仍然只依赖基线。记录了却没有交互需要它时报 `INTERACTION_REVIEW_UNUSED`，免得过时的记录悄悄压住以后的警告；记录里的实验不在这次发布里时不检查（可能是别的环境的发布）；配置有错误时整个不检查，交互算不出来（节点配置写错时，有效的记录被报成没用到，提示还让删掉它）。
- **计划只含它读到的目录特征**。原来定义 schema 时把目录的每个特征都注册进计划，候选表的槽位和填充位、上下文值、拉取器的逐特征状态、输出绑定都按目录大小分配：home_feed 示例加 2,000 个不读的特征，每请求从 18.6 KB 到 76.5 KB、71 µs 到 112 µs；目录里只有别的环境才绑定的数据源，也让计划以 `SOURCE_UNBOUND` 失败。现在名字第一次解析到目录特征时才注册（`CatalogFeatures`，挂在 `PlanSchema` 的查找上），所有引用路径自动覆盖，计划建好后断开；同样的 2,000 个特征下每请求 18.6 KB、72 µs，和没有它们时一样，编译时间不变。没有选“编译一遍、收集读到的闭包、再编译一遍”：那要把节点、探针和所有臂的变体都编译两遍；按引用注册只多编译一次被读到的衍生特征。目录内容仍整体检查：另建一个只有请求字段的 schema 把整份目录注册一遍（每个衍生特征编译一次，原来的重试循环去掉了），失败的在计划的 schema 里标记为不可用。代价：特征编号和槽位按引用顺序分配，确定但没有含义（`explain-plan` 和 explain 按名字列出读的列）；`cache` 数据源读到一个特征就把整张表注册进来（未命中写回的记录必须完整，否则字段集指纹不同的计划会在分布式层互相覆盖），这些未读的特征仍有每请求约 25 B 的开销，要去掉得让拉取组带只暂存、不回填的成员，以后再做；`local` 表的布局取目录中这个数据源和实体的全部物理特征，表的身份和共享不随流水线变化。发布也只看读到的数据源：manifest 只要求编译时注册了特征的数据源的连接器、引导来源和分布式层类型（目录里另一条流水线才用的数据源，连接器不在这个程序里，工作区能校验、构建、运行，manifest 却被同一个程序拒绝），按基线和每个实验分开记录，见 manifest 的能力一条。
- **衍生特征的依赖环报 `FEATURE_CYCLE`，只报一次**。原来按重试循环编译，环上的特征都以“未知名字”报错，`FeaturePlan` 里的环检查走不到；现在注册时遇到正在注册的特征，就在环上第一个衍生特征处报一次，带上路径（`item.a → item.b → item.a`），环上和依赖它的特征不再各报一个错。经过键的环（键读的衍生特征从它自己的实体、或从以它作键的实体计算，候选和上下文都一样）在计划编译时报 `ENTITY_KEY_CYCLE`，指向读下一个特征的那个键部分并带上路径：环是键造成的，修复要改键或改衍生特征（原来候选侧报 `FEATURE_CYCLE`，指向衍生特征）。只由键组成的环由目录报告，编译时不重复报。读一个有错误的衍生特征也不再报第二个错，和其他声明有错的名字一致。上下文特征和请求输入同名（实体叫 `request`）原来会抛异常，现在是 `FEATURE_DUPLICATE`。
- **日志列按 Arrow 的方式存成定型数组，批次带着自己的 schema 记录**。原来每个值是一个 `ScalarValue`（24 字节），列表每行再复制一个数组，行概率是每行一个、其实全相同的 `double[]`；schema id 算了哈希，记录却从未发布，JSON 读者不知道列的类型。现在 `LogColumn` 是一个定型数组（声明类型的存储：`bool[]`、`int[]`、`long[]`、`float[]`、`double[]`、`string[]`，列表是全部元素加偏移；见“出口交付声明的类型”）和一个有效位图，1,000 行 10 个数值列从 240 KB 降到 80 KB，列表每列一个数组；`RowProbability` 是一个数（协调采样下同一批次每行概率相同）。非有限值在采集时就是缺失。`LogSchema`（列和上下文字段的名字、类型、表达式）在编译时建好、所有批次共用，接收端按 id 发布一次，引擎自己不发布任何东西；id 是记录本身（去掉 id）的 sha256，记录写了什么 id 就随什么变（原来哈希探针定义和列的类型，上下文字段换了类型 id 不变，按 id 缓存的读者用旧类型读），只改采样率或过滤条件、记录不变时 id 也不变；不记录“定义它的实验桶”，因为同一个定义在多个臂组合间共用编译结果，生效的臂在批次的 `assigned_arms` 里。
- **探针绑定的每一种“只有臂声明”的名字都决定它的检查范围**。按作用域检查时，探针的作用域原来只为输出列和请求列登记条件声明，漏了参数（和臂新增的特征）：一个探针经 `columns_from` 读到只有另一层的臂声明的参数，组合数超过上限时计划能加载，分到那几个臂、探针捕获时抛异常。现在凡是完整检查里要看“分配了哪些臂”才知道有没有声明的名字（`Conditional`），都让探针在它的臂所在的组合里检查。
- **数据流规则和它的作用域暂不合并成一个对象**。每条规则写在两处：`PlanBuilder.ValidateDataFlow` 里怎么检查，`DataFlowScopes` 里由哪些节点决定；后者只在组合数超过上限、按作用域检查时用，新增规则忘了登记作用域，小配置的测试照样全绿。合并成“每条规则一个对象，同时给出检查和作用域”是正确的方向，但这是约一千行、最难的一段代码，刚经过多轮评审稳定下来，现在重写的风险大于收益：新增规则时才真正出现遗漏的风险。现在的护栏：生成式差分测试的多层模式（4–5 层、上限 8–16，组合空间超过上限）逐组合对照合并后的普通编译，一条没有作用域的规则会在某个组合上放行而被它抓到；植入的三层规则保证去掉按作用域的检查就失败；另有作用域的专门测试。约定：给 `ValidateDataFlow` 加规则时，在同一个改动里给 `DataFlowScopes` 加作用域，并在生成器里加能触发它的原子；下一次加数据流规则时先做这次合并。
- **组合的作用域是保守的超集**（第二次评审）。一条规则的作用域列出可能影响它的全部节点，不按顺序细分：例如探针读一个列时，它的作用域包括这个列的所有写者，也包括挂载点之后才写的；非空的列已经有一个不会被跳过的固定写者时，可选的写者仍在作用域里。细分就要在作用域里推理节点的先后，而实验可以移动节点，这正是规则本身做的事。代价只在组合数超过上限、按作用域检查时出现：组合数是作用域里各层选项数（层里的臂数加上“不分配”）的乘积，每层一个臂时要 13 层、每层两个臂时 8 层才超过默认的 4,096，这时报 `COMBINATION_CHECK_LIMIT`，指出是哪些层，可以合并层。例外是请求列：流动请求列的写者只在它非空、又被输出读的时候才一起检查（输出要它一定有值），其他时候没有规则需要它们一起；探针只是绑定一个只由臂声明的请求列（名字在被删掉的分支里）时，只和决定探针的臂一起检查声明，不带上这一列的写者。候选列没有照此改：它的写者还决定行源要不要写这一列、版本写在哪里，判断哪些情况可以省掉，比请求列复杂得多。
