# StrataRec 开发规范：理念、取舍与规则

本文写给在 StrataRec 上开发的任何人和 AI agent：判断一个方案好不好的标准、常见的取舍怎么做、哪些规则必须守以及为什么。读代码就能知道的东西（类型怎么组织、某个函数做什么）不写在这里。

文档的分工：

- 本文：开发理念、取舍标准和规则，适用于每一次改动。
- [`decisions.md`](decisions.md)：每个具体决定、取舍和理由，包括刻意不做的事。
- [`design.md`](design.md)：最初的设计草稿，描述整体架构。
- [`AGENTS.md`](../AGENTS.md)：构建、测试、项目结构等操作上的约定。

优先级：`design.md` 是草稿，优先级最低；`decisions.md` 高于 `design.md`，两者冲突时以 `decisions.md` 和代码为准。两者都不是定论：有更好的方案就改，并在 `decisions.md` 写下新的理由。不要因为“设计是这么写的”而照做。

## 1. 核心目标

StrataRec 要成为一个整体性能好、分配低、好用、容易开发调试和测试的推荐执行框架。判断任何方案只看三条：

1. **易用好用**：配置和接口容易写对；错误信息说明位置和修法；排查有工具（trace、解释、回放、计划对比）。使用者写直观的代码就能得到高性能，不需要学习框架的内部约定。
2. **易于开发和维护**：容易出错的逻辑集中在一处；改动的影响局部、可以推断；代码不被逐步侵蚀（第 2 节）。
3. **性能好、分配低**：随候选数和特征数增长的开销决定扩展性，热路径不按行分配（第 4 节）。

可维护性和性能需要权衡：复杂度只换来很小的性能提升时，选更简单的方案。

做一项功能之前先问：它对这三条的收益，值得它带来的复杂度吗？不值得就简化、推迟或不做，并在 `decisions.md` 记下决定和理由，不必为了贴合设计而实现。

## 2. 可演进性

根本目标是代码库在持续迭代中始终容易修改：下一次变更仍然容易理解、定位、实现和验证。高内聚、低耦合、深模块、封装、类型约束、重构都是手段，不是目标。这条标准贯穿方案和实现的每一步，不只在评审时检查。

- **变化局部化。** 一起变化的知识、数据、行为和不变量有唯一的权威所有者；模块之间通过小而稳定的接口协作。
- **一条规则只有一个实现。** 同一条规则不在两处各写一遍，即使一处在编译期、一处在运行期。例如校验哪些实验组合可能同时生效的代码，和请求期决定哪些实验生效的代码，调用同一个判定，所以“校验过的就是运行的”。同一种错误在每个入口都是同一句话；同一份文档从哪个入口读都是同一个结论。
- **影响可推理。** 不依赖记住隐含的依赖。漏改要显式暴露：编译错误（例如对枚举的全部取值做穷举，新增一个取值时编译失败，而不是落进默认分支）、校验或测试，而不是悄悄破坏别的功能。
- **结构不被侵蚀。** 不为当前方便堆特例、重复知识和跨模块耦合；特例隔离在合适的边界；必要时先做局部重构再改。
- **警惕这些信号**：重复的规则、散弹式修改、循环或双向依赖、隐式约定、职责混杂，以及不必要的特例、抽象和扩展点。
- **看未来的改动。** 评估当前写法会不会迫使以后散弹式修改；有让以后更容易守住标准的写法就用它。但只依据已经显现的变化方向，不为猜测的需求加抽象或预留接口。
- **复杂、易错的逻辑内聚。** 难写对的逻辑（无锁发布、unsafe 循环、缓冲增长、超时与放弃、预算核算、组合枚举）收拢到一个类型或函数里，其他地方调用它而不是复制；并给它写针对不变量和边界的回归测试。这一条来自实际的教训：同一类缺陷总是出在被分散到多处、各自重复实现的地方。
- **声明的契约就要强制。** 算子声明的效果、节点声明的类型，都在编译期或运行期检查；从来没有实现或从来没有被读取的声明直接删掉，它只会让人误以为有这个功能。
- **契约只写在一处，从实现方的角度写。** 扩展点的规则写在一个地方，其他地方指向它。

## 3. 找更简单的方案

- **从真实目标出发，而不是照字面需求做。** 先弄清要解决的问题（Why），再找达成它的更简单的方案，主动考虑放弃某些低价值需求能否大幅降低复杂度或风险。例如“可撤销编辑”可以是每分钟自动保存一个版本；“撤回已发的邮件”可以是延迟发送；“文件保存”要先确认是否真的需要原子写入和并发冲突处理。
- **先简单，再优化。** 默认选最简单的正确方案；更复杂的优化需要基准数据支撑。
- **评审意见和缺陷报告逐条判断，不逐条打补丁。** 对每一条先问三个问题：
  1. 这段逻辑或限制必要吗？不必要就简化或删掉。一个缺陷常常说明逻辑太复杂。
  2. 是必要功能的真实缺陷吗？修，并带回归测试。
  3. 是罕见场景，处理成本远大于收益吗？不改，在 `decisions.md` 记下判断和理由。

  逐条打补丁会让逻辑越来越复杂。修的时候，优先加约束或换一个更简单的规则，而不是为每个反例加特例。
- **宁可显式声明的局部例外，也不要隐式的全局规则。** 例如两个实验冲突时，由要让出流量的一方显式声明“让给谁”，而不是引入全局的优先级：全局优先级会把以后新出现的冲突悄悄变成别的行为，而不是报错。
- **声明本身就是确认。** 用户已经明确声明的意图不再报警告。反过来，过时的声明（不再起作用的豁免、让出、评审记录）要报警告，否则它会掩盖下一个真正的问题。

## 4. 性能与分配

- **重要的是随候选数和特征数增长的开销。** 按行、按特征的工作和分配值得在一处内聚地优化，可以为此增加一些复杂度。
- **请求级的固定对象交给 GC。** 它们随请求数增长，不随候选数增长，.NET 的 GC 处理得很好。不做请求状态池：池化要为每个对象写重置逻辑，漏掉一处就会把上一个请求的数据带进下一个请求，换来的却是一个不随候选增长的量。
- **热路径不按行分配。** 请求生命周期内的缓冲从 `RequestMemory` 租借（`Rent`），算子不自己归还，随请求一起归还；在一个方法里用完、之后没有任何引用的临时缓冲（行列表、掩码、选择）用 `RentScratch` 租、用完立即 `ReturnScratch`。
- **`src/` 中不用 LINQ。** 请求可能携带大量候选，引擎采用列式存储正是为了减少分配；LINQ 会分配枚举器、闭包和中间集合。用显式循环、数组、`List<T>`、`Dictionary`/`HashSet` 和带序数比较器的 `Array.Sort`/`List.Sort`。构建会强制这一条；测试和基准可以用 LINQ。
- **分配预算是估算，看趋势，不是门禁。** 设计里“每请求约 2 KB”之类的数字允许偏差，目标是持续压低随候选增长的部分。
- **不为不是瓶颈的收益增加约定。** 便宜、不增加复杂度的优化随手做；伤害可维护性或使用体验、收益又小或不在瓶颈上的优化不做。做之前问：它随候选或特征增长吗？能内聚在一处并被测试吗？框架的使用者需要知道它吗？
- **不为防住写错的实现让所有请求付出代价。** 例如扩展点在请求线程上直接调用，只约束它返回之后的异步等待；没有每次都切到线程池，那会给每个请求增加调度延迟和分配，只为防住阻塞的实现。框架保证的是不采用迟到的结果。
- **能在加载期做的事不放到请求期。** 名字解析、类型检查、依赖分析和实验合并都在加载期完成，编译一次、执行多次；请求期不解析 JSON，不按名字查找。
- **共享的编译结果不可变。** 一个计划被所有并发请求共用，又交给宿主查看，所以从它可达的公开面都是只读的；宿主顺手改一下就会改到所有请求在跑的东西，而且不会报错。

## 5. 语义：缺失、失败与确定性

- **缺失是显式的。** 用可空类型、`??` 和 `has()` 表达；绝不把缺失静默变成 0。除数为 0 的取模得到缺失；非有限值、越界值同样不静默替换成一个看似合法的数。
- **配置错误、依赖失败和合法缺失分三层处理。** 配置错误在加载期拒绝；依赖失败按节点的失败策略降级或回退，并留下记录；合法缺失是值的一部分，在表达式里显式处理。
- **失败的尝试不留下痕迹。** 失败的节点尝试让候选表回到尝试之前；超时后才到的结果不采用；被放弃的调用只写租借的缓冲区。
- **确定性。** 计划、请求输入、时间、外部响应和执行决定都相同时，排序、分数、选中的变体和采样决定都相同。平分时按 `entity_id` 升序；随机性只来自 `hash01` / `StableHash`（以请求的 seed 为输入）。耗时、序号等运行元数据不在保证内。
- **校验不完整时拒绝，不放行。** 检查因为规模超限而无法做完时是错误，不是警告：不能发布一个某些分配下会运行未校验组合的计划。
- **编译期接受的，运行时就能执行。** 统一编译接受的每一种组合，都要和单独编译这个组合的结果一致；运行期保护只作为防御，不作为正确性的依据。

## 6. 配置与使用体验

- **只用被广泛使用的标准，不发明 DSL。** JSON(C)、RFC 7396 合并补丁、RFC 6901 指针、RFC 8785 规范化、JSON Schema 2020-12、CEL 风格的表达式、Mustache。理由：熟悉世界知识的 AI agent 和工程师已经懂这些标准，可以直接生成、修改和审查配置，不需要先学一套私有语法。只借用标准的语法、不照搬它的语义时（例如 CEL 的逐行求值、错误值与本项目按列求值、缺失显式的要求冲突），把差异写清楚，不支持的写法在编译期报错。
- **声明与实现分离。** 配置描述“做什么”，二进制实现“怎么做”；配置语言保持有限，新能力通过新增算子获得。
- **配置错误必须说明位置和修法。** 位置是 JSON 指针或表达式里的偏移；修法是一句 hint（拼错时给 did you mean）。工具把位置换算成文件的行列，编辑器能直接跳转。
- **宁可笼统，也不给错误的具体结论。** 找不到确切位置时退到最近的祖先，不猜一个行号，不指向另一个文件。
- **一个错误只报一次。** 出错的声明标为不可用，引用它的地方不再连带报错。
- **严格绑定。** 未知的键、类型不对的值都是带位置的错误；重复的键被拒绝。宽松的读法只会让拼错的配置悄悄不生效。
- **默认值让常见情况正确。** 示例工作区开箱可运行，内置静态、确定性的示例客户端（固定列表召回、内存特征、按哈希随机打分），供测试、样例和本地开发。
- **调试工具和服务走同一条路径。** 解释、计划对比、回放读的是请求实际执行的编译结果，不另写一份合并逻辑：工具展示的就是运行的，编译器的缺陷会在工具里显现，而不是被第二份实现重复。

## 7. 兼容与版本

- **1.0 之前公开 API 可以直接不兼容地改。** 只以 NuGet 包发布，宿主升级时重新编译，所以不考虑只替换 DLL 的二进制兼容。改 API 时在同一个改动里更新所有调用方、示例和测试；不保留旧重载，不加 `[Obsolete]` 过渡，改动在编译时暴露给使用者。
- **持久化格式的版本是日期加当日序号**（`2026-11-14.1`；二进制头写成 `2026111401`），不用 v1、v2。日期说明布局是什么时候定的，同一天再改是 `.2`，按文本也能排序。
- **布局或含义一变就升版本。** 新增一个旧读取器读不懂的取值、记录的含义改变（布局不变）也要升，否则旧数据会被按新含义读错。读取器只读当前版本，其他版本在版本字段处拒绝，并提示用当前构建重新生成；1.0 之前不保留读旧版本的代码。
- **算子和客户端的类型版本是序号**（`TopK@1`、`memory@1`），只在破坏性地改配置时加一。
- **只面向 .NET 10 及以上。** 放心使用新运行时的 API，不为旧运行时写兼容代码或 polyfill。与运行时同一版本线发布的依赖跟着目标框架的版本线，其余依赖用最新稳定版。CI 只用 Linux。

## 8. 范围：做什么，不做什么

- **重点是编排。** 配置、编译好的执行计划、容易配置和测试的多层实验、预算与回退、回放与诊断。
- **常用、复杂、值得框架统一优化的场景由框架做，其余接入由使用方实现。** 本地特征表和两层缓存（进程内 + 分布式）属于前者。召回服务、特征存储、推理服务各家的协议和数据格式不同，由使用方实现扩展接口，框架只提供示例。
- **核心不内置模型推理运行时。** 服务是分布式的，模型由独立的推理服务提供，框架不应把模型限定在某一种运行时或格式。ONNX、流式输出、分页现在都不做，但也不在设计上排除，以后可以作为扩展加入。
- **扩展包是可选的。** 核心不依赖它；它本身保持简单，同时是写扩展的示例。
- **不负责流量分配。** 哪些用户进入哪个实验、比例和扩量属于外部实验平台，引擎只接收分配；引擎再算一次，同一个用户在两边的分组就可能不同。
- **不做个人数据过滤。** 推荐系统内部需要使用、记录和调试个人数据；谁能看到什么由部署环境和数据库权限控制，框架里不做敏感度规则、脱敏或用途限制。同理，发布的信任根是部署环境的写权限，引擎不内置签名体系。
- **依赖部署环境的测量不放进 CI。** 尾延迟、GC、真实依赖下的故障演练取决于部署环境，在共享的 CI 机器上测出的数既不稳定也不代表线上；仓库里放与环境无关的保证（按候选数的分配测试、基准、确定性的故障路径测试）。

## 9. 测试

- **每个缺陷修复都带回归测试，并确认它在修复前的代码上失败。** 不能在旧代码上失败的测试证明不了任何事。
- **针对不变量和边界写测试**，用故障注入覆盖超时、放弃、部分失败和取消路径。
- **复杂的编译逻辑用生成式差分测试。** 随机生成配置，对照两种独立得出的结果（例如统一编译与逐组合的合并编译），断言一个性质而不是逐例枚举；植入只在少见条件下才触发的规则，确认去掉某段检查时测试会失败。也要写清它的局限（两边共用的代码出错时发现不了）。
- **用测试守住结构规则。** 例如一个测试遍历从计划可达的类型，遇到公开 setter、数组或可变集合就失败，新加的成员就不会悄悄退回可变的写法。
- **测试不和时钟赛跑。** 默认放宽时间预算，测预算本身的测试显式选择原始预算，由测试控制调用何时返回；一个短预算会切断截止时刻之前所有未完成的调用，不只是测试想挂住的那个。放宽只写在一处，并在没生效时报错，不会悄悄失效。
- **防御性检查在测试里全部打开**（例如归还缓冲区时的毒化），生产中关闭时零开销。

## 10. 文档

- **文档只记录读代码看不出来的东西**：决定、取舍、理由和整体架构。不复述代码；过时或与代码重复的文档删掉。
- **改变设计或做出取舍时，在 `decisions.md` 写一条。** 写清做了什么、为什么、考虑过而没有选的方案、代价，以及刻意不做的事和不做的理由。罕见场景决定不处理时，也记下判断。
- **文档用中文；代码、标识符和代码注释用英文。**
- **公开类型写 XML 文档注释，说明为什么这样设计**，不复述名字。会序列化的配置成员的注释就是 JSON Schema 里的描述，按使用者能读懂的方式写。
