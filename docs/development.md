# StrataRec 开发理念

本文是在 StrataRec 上开发的指南针，写给任何开发者和 AI agent。它讲三件事：项目要达成什么，用什么标准判断一个方案，取舍时往哪边倾斜、为什么。具体的决定不写在这里，读代码就能知道的东西也不写。

文档的分工：

- 本文：理念、判断标准和取舍的方向，适用于每一次改动。
- [`decisions.md`](decisions.md)：每个具体决定、取舍和理由，包括刻意不做的事。
- [`design.md`](design.md)：最初的设计草稿，描述整体架构。
- [`AGENTS.md`](../AGENTS.md)：构建、测试、项目结构和代码约定。

`design.md` 是草稿，优先级最低。它和 `decisions.md` 冲突时，以 `decisions.md` 和代码为准。两者都不是定论：有更好的方案就改，并在 `decisions.md` 写下新的理由。不要因为“设计是这么写的”就照做。

## 1. 核心目标

StrataRec 要成为一个推荐执行框架：整体性能好、分配低、好用，容易开发、调试和测试。判断任何方案只看三条：

1. **易用好用**：配置和接口容易写对。错误信息说明出错的位置和修法。排查问题有工具。使用者写直观的代码就能得到高性能，不需要学框架的内部约定；接入自己的系统时，看到的是自己声明的东西（第 6 节）。
2. **易于开发和维护**：容易出错的逻辑集中在一处。改动的影响局部、可以推断。代码不被逐步侵蚀。
3. **性能好、分配低**：随候选数和特征数增长的开销决定扩展性。

可维护性和性能需要权衡：复杂度只换来很小的性能提升时，选更简单的方案。

做一项功能之前先问：它在这三条上的收益，值得它带来的复杂度吗？不值得就简化、推迟或不做，并在 `decisions.md` 记下决定和理由。不必为了贴合设计而实现。

## 2. 可演进性

根本目标是代码库在持续迭代中始终容易修改：下一次变更仍然容易理解、定位、实现和验证。高内聚、低耦合、深模块、封装、类型约束、重构都是手段，不是目标。这条标准贯穿方案和实现的每一步，不只在评审时检查。

- **变化局部化。** 一起变化的知识、数据、行为和不变量，只有一个权威的所有者。模块之间通过小而稳定的接口协作。
- **一条规则只有一个实现。** 同一条规则不在两处各写一遍，即使一处在编译期、一处在运行期。校验用的判定和执行用的判定是同一个，校验过的就是运行的。同一种错误在每个入口都是同一句话，同一份文档从哪个入口读都是同一个结论。
- **影响可推理。** 正确性不靠记住隐含的依赖。漏改要显式暴露出来：编译错误、校验或测试，而不是悄悄破坏别的功能。
- **结构不被侵蚀。** 不为当前方便堆特例、重复知识或跨模块耦合。特例隔离在合适的边界里；必要时先做局部重构再改。
- **警惕这些信号**：重复的规则、散弹式修改、循环或双向依赖、隐式约定、职责混杂，以及不必要的特例、抽象和扩展点。
- **看未来的改动。** 评估当前写法会不会迫使以后散弹式修改；有让以后更容易守住标准的写法就用它。但只依据已经显现的变化方向，不为猜测的需求加抽象或预留接口。
- **复杂、易错的逻辑内聚。** 难写对的逻辑收拢到一个类型或函数里，其他地方调用它而不是复制它，并为它的不变量和边界写回归测试。这一条来自实际的教训：同一类缺陷总是出在被分散到多处、各自重复实现的地方。
- **声明的契约就要强制。** 声明了就要检查；从来没有实现或从来没有被读取的声明直接删掉，因为它只会让人误以为有这个功能。
- **契约只写在一处，从实现方的角度写。** 其他地方指向它。

## 3. 找更简单的方案

- **从真实目标出发，不照字面需求做。** 先弄清要解决的问题，再找达成它的更简单的方案。主动考虑：放弃某些低价值的需求，能不能大幅降低复杂度或风险？例如“可撤销编辑”可以是每分钟自动保存一个版本，“撤回已发的邮件”可以是延迟发送，“文件保存”要先确认是否真的需要原子写入和并发冲突处理。
- **先简单，再优化。** 默认选最简单的正确方案；更复杂的优化需要测量数据支撑。
- **评审意见和缺陷报告逐条判断，不逐条打补丁。** 对每一条先问三个问题：
  1. 这段逻辑或限制必要吗？不必要就简化或删掉。一个缺陷常常说明逻辑太复杂。
  2. 是必要功能的真实缺陷吗？修，并带回归测试。
  3. 是罕见场景，处理成本远大于收益吗？不改，在 `decisions.md` 记下判断和理由。

  逐条打补丁会让逻辑越来越复杂。修的时候，优先加约束或换一个更简单的规则，不为每个反例加特例。
- **宁可显式声明的局部例外，也不要隐式的全局规则。** 全局规则会把以后出现的新情况悄悄变成某种行为；局部声明遇到新情况时报错，由人来决定。
- **声明本身就是确认。** 用户明确声明过的意图，不再对它报警告。反过来，过时的声明（不再起作用的豁免、让出、评审记录）要报警告，否则它会掩盖下一个真正的问题。

## 4. 性能与分配

- **重要的是随候选数和特征数增长的开销。** 按行、按特征的工作和分配，值得在一处集中优化，可以为此多一些复杂度。
- **请求级的固定开销交给 GC。** 它随请求数增长，不随候选数增长，.NET 的 GC 处理得很好。不池化请求状态：池化要为每个对象写重置逻辑，漏掉一处就会把上一个请求的数据带进下一个请求，换来的却是一个不随候选增长的量。
- **热路径不按行分配，也不藏分配。** 按行的缓冲随请求租借、随请求归还。生产代码不用 LINQ 这类会悄悄分配枚举器、闭包和中间集合的便利写法：引擎用列式存储，本来就是为了减少分配。
- **分配预算是估算，看趋势，不是门禁。** 目标是持续压低随候选增长的部分。
- **不为不是瓶颈的收益增加约定。** 便宜、不增加复杂度的优化随手做。伤害可维护性或使用体验、收益又小、又不在瓶颈上的优化不做。做之前问：它随候选或特征增长吗？能集中在一处并被测试吗？框架的使用者需要知道它吗？
- **不为防住写错的实现，让所有请求付出代价。** 框架保证的是正确的实现得到正确、快速的结果，并且不采用迟到的结果；它不为每个请求加调度或拷贝，只为防住阻塞或越界的扩展。
- **能在加载期做的事，不放到请求期。** 名字解析、类型检查、依赖分析和实验合并都在加载期完成，编译一次、执行多次。请求期不解析配置，也不按名字查找。
- **共享的编译结果不可变。** 一个计划被所有并发请求共用，又交给宿主查看。宿主顺手改一下，就会改到所有请求正在用的东西，而且不会报错。

## 5. 缺失、失败与确定性

- **缺失是显式的。** 绝不把缺失静默变成 0。非有限值、越界值同样不静默替换成一个看似合法的数。
- **配置错误、依赖失败和合法缺失，分三层处理。** 配置错误在加载期拒绝。依赖失败按节点的策略降级或回退，并留下记录。合法缺失是值的一部分，由表达式显式处理。
- **失败的尝试不留下痕迹。** 失败的节点让候选表回到尝试之前。超时后才到的结果不采用。
- **确定性。** 计划、请求输入、时间、外部响应和执行决定都相同时，排序、分数、选中的变体和采样决定都相同。平分有确定的次序；随机性只来自以请求种子为输入的稳定哈希。耗时、序号等运行元数据不在保证之内。
- **校验不完整时拒绝，不放行。** 检查因为规模超限而做不完时，是错误不是警告：不能发布一个在某些情况下会运行未经校验的组合的计划。
- **编译期接受的，运行时就能执行。** 运行期的保护只是防御，不是正确性的依据。

## 6. 类型：内部按提升的类型计算，边界交付声明的类型

- **内部计算用提升后的类型。** 表达式把整数当 int64、浮点当 float64 来算，一套运算规则覆盖所有宽度，结果按声明的类型写回。这是实现方式，不是对外的契约。提升不丢信息（int32 到 int64、float32 到 float64 都是精确的），所以提升之后再收窄回声明的类型，得到的就是原值。
- **每个边界交付声明的类型，宽度不变。** 连接器、本地表、模型客户端、日志接收方、宿主拿到的结果，看到的都是使用者声明的类型：声明 int32 就是 int32，float32 就是 float32，bool 就是 bool，string 就是 string。理由：使用者有自己的特征存储、模型服务和日志系统，它们按自己的类型工作。从特征存储拿到 int32 的特征，模型要 int32，特征日志也记 int32；框架如果在中间把它变成 int64 或 float64，使用者就要在每个边界上转回去，训练和服务看到的值还可能不一样（float64 舍入成 float32，超过 2^24 的整数送成 float32 时也被舍入）。
- **框架不在类型之间做隐式转换。** bool 不变成 0/1，整数不变成浮点，float64 不舍入成 float32。类型对不上时，在加载期报错，并说明怎么改：改对方的声明，或声明一个所需类型的衍生特征。转换于是只有一处定义，训练和服务共用。使用者自己写的算子或客户端怎么转换，由它们自己决定，与框架无关。
- **没有声明的值，用它自己的类型。** 表达式的结果没有使用者声明的类型，它的类型就是表达式的结果类型。

## 7. 配置与使用体验

- **只用被广泛使用的标准，不发明 DSL。** JSON、合并补丁、JSON 指针、JSON Schema、CEL 风格的表达式、Mustache 这类标准，熟悉世界知识的工程师和 AI agent 已经懂，可以直接生成、修改和审查配置，不用先学一套私有语法。只借用标准的语法、不照搬它的语义时，把差异写清楚，不支持的写法在编译期报错。
- **声明与实现分离。** 配置描述做什么，二进制实现怎么做。配置语言保持有限，新能力通过新的算子获得。
- **配置错误必须说明位置和修法。** 位置要精确到配置里的那个值或表达式里的那个字符。修法是一句提示；名字拼错时，给出可能想写的名字。
- **宁可笼统，也不给错误的具体结论。** 找不到确切位置时，退到最近的上层位置，不去猜。
- **一个错误只报一次。** 出错的声明标为不可用，引用它的地方不再连带报错。
- **严格绑定。** 未知的键、类型不对的值都是错误；宽松的读法只会让拼错的配置悄悄不生效。
- **默认值让常见情况正确。** 示例开箱可运行；内置静态、确定性的示例组件，供测试、样例和本地开发使用。
- **调试工具和服务走同一条路径。** 解释、计划对比、回放读的是请求实际执行的编译结果，不另写一份逻辑：工具展示的就是实际运行的，编译器的缺陷会在工具里显现，而不是被第二份实现掩盖。

## 8. 兼容与版本

- **1.0 之前，公开 API 可以直接做不兼容的修改。** 改 API 时，在同一个改动里更新所有调用方、示例和测试；不保留旧重载，也不加过渡期，改动在编译时就暴露给使用者。
- **持久化的数据，布局或含义一变就升版本。** 布局不变、含义变了也要升，否则旧数据会被按新含义读错。读取器只读当前版本，其他版本在版本字段处就拒绝，并提示重新生成；1.0 之前不保留读取旧版本的代码。
- **跟着新的运行时走。** 放心使用目标运行时的新 API，不为更旧的运行时写兼容代码。

## 9. 范围：做什么，不做什么

- **重点是编排。** 配置、编译好的执行计划、容易配置和测试的多层实验、预算与回退、回放与诊断。
- **常用、复杂、值得统一优化的由框架做，其余由使用方接入。** 召回服务、特征存储、推理服务、日志系统，各家的协议和数据格式不同，由使用方实现扩展接口；框架让这种接入自然（第 6 节），并提供示例。
- **核心不把模型限定在某一种运行时或格式。** 模型由独立的推理服务提供；暂时不做的能力，不在设计上排除。
- **扩展包是可选的。** 核心不依赖它们；它们本身保持简单，同时是写扩展的示例。
- **不负责流量分配。** 哪些用户进入哪个实验，属于外部实验平台；引擎只接收分配结果。引擎自己再算一次，同一个用户在两边的分组就可能不同。
- **不做个人数据保护。** 推荐系统内部需要使用、记录和调试个人数据；谁能看到什么，由部署环境和存储的权限控制。
- **依赖部署环境的测量，不放进 CI。** 尾延迟、GC、真实依赖下的故障取决于部署环境，在共享的 CI 机器上测出的数既不稳定，也不代表线上。仓库里只放与环境无关的保证。

## 10. 测试

- **每个缺陷修复都带回归测试，并确认它在修复前的代码上失败。** 在旧代码上也能通过的测试，证明不了任何事。
- **针对不变量和边界写测试。** 用故障注入覆盖超时、放弃、部分失败和取消。
- **复杂的编译逻辑，用生成式的差分测试。** 随机生成输入，对照两种独立得出的结果，断言一个性质，而不是逐例枚举；同时写清它的局限。
- **用测试守住结构规则。** 新增的代码就不会悄悄退回被禁止的写法。
- **测试不和时钟赛跑。** 测试控制调用何时返回，不靠短超时碰运气。
- **防御性检查在测试里全部打开**，在生产中关闭时零开销。

## 11. 文档

- **文档只记录读代码看不出来的东西**：决定、取舍、理由和整体架构。不复述代码；过时或与代码重复的文档删掉。
- **改变设计或做出取舍时，在 `decisions.md` 写一条。** 写清做了什么、为什么、考虑过而没选的方案、代价，以及刻意不做的事和理由。决定不处理某个罕见场景时，也记下判断。
- **文档用中文；代码、标识符和代码注释用英文。**
- **公开类型写 XML 文档注释，说明为什么这样设计**，不复述名字。会序列化的配置成员，注释就是 JSON Schema 里的描述，按使用者能读懂的方式写。
