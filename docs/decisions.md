# 决策记录

`design.md` 描述整体设计。本文只记录实现过程中做出的、读代码看不出来的决定和理由：对设计的调整、取舍，以及刻意没有做的事。两者冲突时以本文和代码为准。括号中的“评审 N”指 Codex 第 N 轮评审发现的问题。

## 实验与计划编译

- **组合校验超限是错误，不是警告**（设计 11.5、12.3）。组合空间不超过 `MaxCombinationsChecked`（4096）时全量枚举；超过时退回到单个实验、成对组合和按列枚举，同时报 `COMBINATION_CHECK_LIMIT`。设计假设涉及的层很少，但层数一多组合会指数增长；只给警告就等于在没有证明安全的情况下发布（评审 3）。
- **schema 段始终只增**（设计 11.4）。`columns`、`param_schema`、`features`、`derived_features`、`funnel_groups` 无论 policy 怎么写，实验都只能新增。实验修改或删除基线 schema，会让其他实验和基线的类型检查失效。
- **基线必须能单独编译**（设计 11.5）。实验新增的特征或列不能“修好”基线中的引用，否则实验下线后基线就坏了（评审 3）。
- **跨域的臂组合直接跳过**（设计 11.1）。不同域的臂不可能同时分配，编译它们只会产生误报（评审 3）。
- **`columns_from` 跟随模型变体**（设计 8.3、6.9）。探针展开的是当前臂组合下实际生效的模型节点；修改该模型的层也参与探针的变体划分；探针 schema id 包含每列解析后的表达式。训练日志必须记录服务时真正的输入（评审 4）。
- **节点 id 只能是标识符**（字母、数字、`_`）。版本引用 `col.x@node` 要能写出每个节点；含 `.` 或 `-` 会被解析成字段访问或减法。这是在扩展语法和收紧 id 之间选了后者（评审 4）。
- **行源节点不能被版本引用**（`VERSION_REF_ROW_SOURCE`）。所有行源向同一个槽位追加行，没有“某个节点的版本”可读（评审 5）。
- **行源和它们共用的列版本在编译时检查**（设计 4.6）。所有行源把自己追加的行写进每一列的同一个共享版本，而一行没写就是缺失（见“执行与宿主”），所以在一条路径上：写不可空列的第一个行源之前，每个行源也要写这一列（`ROW_SOURCE_BEFORE_COLUMN`，指向没写的那个行源，提示同时写这一列，或者声明为可空，例如 `"recall.best_score": { "type": "float64?" }`，再用 `??` 处理缺失）；之后的行源也要写（原有的 `ROW_SOURCE_AFTER_COLUMN`；列由行源以外的节点产出时，提示改为把行源移到那个节点之前，因为这时写这一列也没用）；行源不能写一个别的节点已经写过自己版本的列，不论是否可空（`ROW_SOURCE_SHADOWS_VERSION`）：提交会让读取方切到共享版本，那里没有那个节点写的任何值，原来不报错，那些值静默消失。前两种情况运行时会让每个同时运行两个节点的请求在提交时失败，放在编译期，错误指向造成问题的节点。行为变化：自定义行源在 `MultiSourceRecall` 之前、自己不写 `recall.*` 的配置现在编译失败（原来能运行，前一个行源的行读到旧数据），按提示把 `recall.*` 声明为可空即可。已知限制：打分之后再追加行（例如插入广告）并写同一个分数列不支持，要么把追加放在打分之前，要么写到另一列、在之后的节点里合并。没有改成让行源写进当前版本的槽位：那要在节点之间共享或复制槽位，回滚和版本引用都会跟着变复杂，等有真实需求再做。后备按它所替代节点的位置检查（评审 13）：主节点失败后已经回滚，不是后备的前驱，所以两者都对照这个位置之前的状态检查；这个位置之后的状态是两者都可能留下的，即可能追加了行、可能写了自己的版本。两者的效果可以不同。后备的输出列和主节点完全相同，同一种效果的检查只取决于之前的状态和这些列，所以每种效果检查一次，错误指向有这种效果的节点（两者都有时指向主节点），不重复报告。原来行源检查只看时间线上的主节点，后备只核对输出列和必需的输入：给写列的节点配一个行源后备，就绕过了上面三项检查，后备追加的行在不可空列里线上读到池里的旧数据、回放读到 0；给行源配一个写列的后备，则绕过了 `COLUMN_MULTIPLE_PRODUCERS`。这样的配置现在编译失败。没有选“主节点和后备的效果必须相同”：满足这些检查的混合配置能正确运行，检查本来就按效果做。

## 执行与宿主

- **参数触发在调用算子之前记录**（设计 12.6）。节点之后失败也算触发；按结果决定是否触发会让失败的请求从实验组里消失（评审 3）。
- **取消或中止的请求仍然发布 `$experiments` 记录和已捕获的探针**。慢请求更容易被取消，而慢往往与臂相关（评审 4）。例外：设置了 `CaptureLogs` 的请求（调试、预览）在任何情况下都不写持久日志（评审 5）。
- **后备流水线只用剩余时间**（设计 5.6）。设计只说“宿主可以选择返回它的结果”；实现统一为自动执行、不带实验、不重新计时，外部分配服务也受同一个截止时间约束（评审 3、4）。
- **计划发布按序号，组装出错整体放弃**（设计 10.3）。后台编译可能乱序完成，较旧的结果不覆盖较新的计划；`fallback_pipeline` 解析失败时主流水线也不发布（评审 3、4）。
- **衍生特征表达式抛异常只让该特征失败**（设计 6.7）。表达式后端对数据错误返回缺失值，抛异常只可能是缺陷；按数据源失败处理，不影响同一请求的其他特征。
- **召回源和模型调用的等待有自己的上界，不依赖客户端响应取消**（设计 4.8、5.6；评审 10、11）。节点尝试开始时定下绝对截止时刻，`OperatorContext.RetrieveAsync` 和 `InvokeModelAsync` 都经过 `BoundedCall`：等待在调用自己的 `timeout_ms`、节点截止时刻（取较早者）或调用方取消时结束，用 `WaitAsync(剩余时间, 调用方令牌)`，从不等客户端手里的令牌（令牌的回调同步执行，一个阻塞就卡住等待）。结果只有被框架在上界之内观察到完成才采用，谁先到只判一次：真正装上了的等待看等待本身的结局；没装上的（同步返回，或者在装上等待之前就完成、`WaitAsync` 原样返回）在框架看到它的那一刻按时钟、令牌和调用方判断。取舍：按时完成、只因抢占晚被看到的调用也算超时；框架只认它观察到的事实，按客户端声称的完成时刻判就给不出上界。等不到的调用被放弃，不取消也不再等：客户端的令牌一直有效，请求内存持有到它真正结束并且调用点记录完毕（`stratarec.io.abandoned` 计一次），召回缓冲区当场关闭，算子和录制都读不到被放弃的数据。分类与特征拉取一致，每次调用只完成、录制一次。调用自己的超时返回失败状态，由算子按失败处理（模型节点因此走后备）；预算用完或调用方取消抛 `OperationCanceledException`。1.0 之前的不兼容改动：`InvokeModelAsync` 的令牌参数换成 `int? timeoutMs`。代价：与节点共用预算的同步调用不分配；自身超时更短的调用在发出前建一个关联取消源和定时器（约 160 B），取消源必须在发出前建好，客户端拿到的令牌才带着自己的超时，所以不推迟、不复用；被放弃的客户端占用的线程和内存要等它自己结束，框架只计数。
- **召回源、模型和特征拉取各有一份等待实现，守同一组不变量**。`BoundedCall` 管单次调用，`FeatureFetcher` 管一次拉取的几百个分批：所有分批共用一个取消源和截止时刻，同步返回的分批在调用点当场完成、不分配，分批写共用暂存区的视图，分类多一个 `partial`。两边真正相同的只有十几行；合成一个原语要把这些差异做成参数，并改动已被分配测试锁定的热路径，风险大于收益。改一份时对照另一份：（1）等待以绝对截止时刻和调用方令牌为界，不等客户端的令牌；（2）每个外部调用从发出前到客户端真正结束、调用点记录完毕，持有一次请求内存；（3）客户端的令牌在它结束之前一直有效；（4）调用方取消算 `cancelled`，超时（包括预算用完、`TimeoutException`）算 `timeout`，其余算 `error`；（5）在调用点完成并录制恰好一次，完成本身抛异常（例如录制钩子出错）时也不再从失败路径完成第二次；（6）被放弃的调用写入的数据不被读取，录制里也没有；（7）同步返回、不需要自己的取消源的调用不分配；（8）结果只在框架于上界之内观察到它时才算：装上了的等待由等待的结局决定，其余（同步完成、`WaitAsync` 的快捷路径）在框架看到它的那一刻判断，两边各由一个 `Observed` 函数负责。两边的测试逐条覆盖这些不变量，并用故障注入确认违反任何一条都会失败。行为变化：同步连接器冷启动时（JIT、忙碌的机器）超过数据源超时，这次调用就超时；示例的内存数据源因此写明 `timeout_ms: 1000`。两边的等待都由 `WaitAsync` 计时，它把剩余时间截断到整毫秒：等待最多比截止时刻早约 1 ms 结束，剩余不足 1 ms 时立即超时。不向上取整：那样等待会在截止时刻之后结束，截止之后才完成的结果会被采用。
- **算子在预算用完之后才返回，按超时处理，不论它返回什么**（设计 5.6）。规则只在 `AttemptBudget.RanOut` 一处：调用方没有取消，并且截止时刻已过或预算的定时器已经取消了节点令牌（定时器可能比时钟早一点触发，两者任一即算）。成立时不提交输出，候选表回到尝试之前（见下一条），按 `on_failure` 处理，说明是 “timed out after N ms”。原来只有算子抛出取消才算超时，没看令牌、在预算之后才成功返回的算子照样提交，负载高时请求会拿到超出预算的结果，节点预算就不再是上界。执行器不放弃算子本身，仍然等它返回：算子在请求线程上改候选表和行选择，放弃它就会有两方同时写请求状态。所以 CPU 密集的算子超出预算时，节点照样晚于截止时刻结束，只是结果不用；自定义算子如果自己做 I/O（不经 `RetrieveAsync` / `InvokeModelAsync`），要自己用 `CancellationToken` 或 `BudgetRemaining` 限时，并持有请求内存直到调用结束。代价：原来勉强在预算之后完成的节点现在走后备。
- **失败的节点尝试让候选表回到尝试之前**（设计 4.6、4.8、5.6；评审 10）。规则只在 `CandidateTable`：执行器在每次尝试前取 `Checkpoint()`，任何失败（异常、`Fail`、超时、晚成功、提交校验失败）都 `Rollback`：恢复行选择；释放尝试期间追加的物理行（行数和剩余可追加数退回，这些行在每个槽位里缺失、未填充，实体索引里不再有它们的键）；丢弃尝试期间建立的槽位（见下一条）。原来只恢复行选择：后备召回按 `FindRow` 去重时把失败主节点留下的死行当成已有候选，而回放跳过失败的主节点，同一份录制回放出不同的结果。检查点之前已有的行保持原状，包括被过滤掉的行，后面的行源仍不能把它们召回来，所以 `FindRow` 的去重不变。`RowSelection.Restore` 改为内部方法，表以外只能整体回滚。回滚不能跨过 `Compact`（只在节点成功后做）。其余按行的状态已核对：`OutputBindings` 只在成功时提交；特征回填和预取按键匹配存活行，不按物理行号；被放弃的 I/O 只写租借的缓冲区。约束：后备会复用释放的物理行，所以尝试结束之后任何东西都不能再写候选表；框架的 I/O 边界从不写表，自定义算子不能让后台工作直接写表。
- **失败尝试建立的槽位在回滚时丢弃，之后读起来和从未写过一样**（设计 4.6、13.4）。规则也只在 `CandidateTable` 一处：表记下槽位建立的顺序，检查点记下当时建立了几个，回滚把之后建立的槽位（失败节点自己的输出，或者它第一个写的共享行源槽位）连同填充位图一起丢掉，数组留到请求结束时归还。所以执行器对每次尝试都取检查点，不再只对有行效果的节点。原来这些槽位留着，理由是失败节点的输出不提交、没有人读；但 `col.x@node` 这种固定版本引用直接读该节点自己的槽位，不经过输出绑定：节点写了 99 之后超时并被跳过，线上读到 99，回放跳过录制为超时的尝试、从没建立这个槽位，读到缺失（评审 11）。丢弃之后两边都是“槽位不存在”，任何读取路径（当前版本、固定版本、算子的 `Read`、日志、输出）都读到缺失，读取方不用改。没有选在读取时检查“这个版本提交过没有”：标量后端、向量后端和 `OperatorContext.Read` 各要一份，新加的读取路径还得记得。尝试之前就存在的共享行源槽位不丢，只释放尝试追加的行，之前成功的行源写的行保持原值。代价：没有行效果的节点每次尝试多复制一次行顺序（5,000 行约 20 KB，从请求内存租借，不产生托管分配；与只对有行效果的节点取检查点相比，测得的延迟差别在噪声之内）。约束：节点只写自己的输出槽位，行源只写自己追加的行；回滚撤销不了写进已有槽位里其他行的内容，框架内置算子都遵守，自定义算子由作者保证，框架不检查。
- **一行在一个槽位里，没有被写过就是缺失**（设计 4.4、4.6）。规则只在 `CandidateTable`：新建的槽位里每一行都是缺失、未填充，包括槽位建立之前就已追加的行；追加的行和回滚释放的行在每个已有槽位里同样。写入方用 `Set`，或批量写值之后用 `SetValid`，标记自己写的行；忘了标记的行是缺失而不是错的值，不可空列会在提交时失败（见下一条）。原来没有有效位图的列算作全部有效：一个行源第一个写某列时，之前行源的行读到池里的旧数据，并且算作有效。两个行源写同一列时共用一个版本，各自只写自己追加的行。算子直接创建的临时列缓冲仍是“没有位图就全部有效”，它们只在写过的行上被读。所以写入方要对照真实的表槽位测试（测试中的 `TableWrites`）：写进临时缓冲区，漏标测不出来（评审 13：表达式写 bool 列时不标记，原有测试全部通过）。没有选的做法：列缓冲默认全部缺失（规则不再只属于表，所有临时缓冲区都要改）；用“前 N 行未写”之类的第二种表示省掉标记（每个读取方都要认识它）；让密集写入方声明“写了全部存活行”（多一个用错就静默出错的接口）。代价：表中每个槽位从建立起就带有效位图（5,000 行 632 B），整列写入多一次按行置位，同一个字的位先在寄存器里攒齐再写；示例流水线每请求多分配 8 B（候选表多了记录槽位建立顺序的字段），延迟约 +2%。
- **提交时不可空列在每个存活行上都要有值，`default` 不补缺失**（设计 4.3、4.6）。提交先按非有限值规则替换（有 `default` 用默认值，否则缺失），再按 64 行一个字比较存活位图和有效位图，有一行缺失就让节点失败，说明是 “left non-nullable column 'x' without a value on N of M live rows”。原来位图为空就当作全部有效、不检查；有位图时缺失的行用 `default` 填上，没写的行于是会悄悄变成默认值，与设计 4.6“`default` 不会填充一个没有产出者的列”相反。现在 `default` 只替换存不下的值：非有限值在提交时，超出 int32 范围的值在写入时。“一行都没写”和“写了缺失”合成一个检查、一条说明（原来分别是 “did not write non-nullable column” 和 “wrote a missing value into non-nullable column”）。行为变化：自定义算子把缺失写进带 `default` 的不可空列，或者没写全存活行，原来得到默认值或旧数据，现在节点失败，按 `on_failure` 处理。
- **行源后备的表容量按主节点和后备中较大的预留**（设计 4.8、5.6）。候选表的容量在请求开始时按各行源节点的行数上限确定；配置了 `fallback:` 的位置，取主节点和这次臂组合下所选后备节点上限中较大的一个。失败的主节点追加的行由回滚收回、后备复用，同一位置留下的只有一方的行。原来失败不撤销追加的行，曾按两者之和预留（提交 4e32cd9，否则主节点配额 1、后备配额 3 时后备只剩 1 行）；有了回滚就不再多预留。
- **`ModelScorer@1` 在加载时检查每个可能用到的模型版本**（设计 6.9）。每个版本：签名里的每个输入都必须在 `inputs` 里有映射，用到的每个输入和输出都必须是 float32、形状 `[-1]`（每行一个值，批维度动态）；否则加载失败，错误指向 `/inputs/<名字>`、`/outputs/<名字>`，缺少输入时指向 `/model`，提示说明打分算子支持什么。原来只核对名字，类型或形状不符、少给输入的版本也能加载，然后每个请求都失败或走后备。签名里有、`inputs` 没给的输入是错误，因为模型签名没有“可选输入”的约定。设计 6.9 的 `[batch, dim]` 输入暂不支持：`ModelScorer` 只按行构建一维张量，需要其他张量的模型用自己的算子调用。规则只在 `ScorerSignature` 一处。
- **`TopK@1` 按精确的排序键比较**（设计 5.7）。原来分数都转成 double 比较，超过 2^53 的不同 int64（例如按 `entity_id` 排序时的大 id）会相等，再按 id 升序平分，于是升序和降序给出同样的顺序。现在 int64、int32 用翻转符号位后的无符号 64 位键，float64、float32 用 IEEE 754 全序键（−0.0 当作 +0.0），降序取反；缺失和 NaN 仍排在最后，平分仍按 `entity_id` 升序，不按行分配。排序键只在 `RowRanking.TryGetSortKey` 一处。`MmrDiversifier` 例外：它对分数做浮点运算（相关性减去相似度惩罚），仍按 float64 读取，超过 2^53 的 int64 分数会丢精度。

## 特征拉取

一次拉取按 `max_batch` 拆成多个分批，每个分批是一次连接器调用。示例请求 5,000 候选时有两百多个分批，原来每个分批约 420 B，占请求分配的四分之三。下面几条让连接器同步返回的分批不再分配（按分批数翻倍的测试锁定为 0 B）。

- **一次拉取的所有分批共用一个暂存区**（设计 4.5、6.5）。分批在连接器线程上并发写入，超时被放弃的分批还可能在请求返回之后继续写，同时别的分批正在被回填读取。所以布局保证任何两个分批都不写同一块内存：定长值、向量、`string` 和 `text` 每个字段一个数组，按拉取内的键序号排列，每个分批只写自己那一段；每个分批的“已写入”位从 64 位字的边界开始，因为两个线程同时写一个字会丢位；列表字段每个分批一个缓冲区，因为列表的数据区会增长、搬移。`string` 先按引用暂存，回填时才做字典编码，因为字典也不能并发写。连接器拿到的 writer 是分批的视图：连接器同步返回后，同一个视图对象接着指向下一个分批；异步返回的调用独占自己的视图，直到连接器真正结束。没有选的做法：每个分批一套缓冲区（原做法：暂存对象、列数组、每字段一个列对象和一个字符串字典，再加每字段一次租借）；在请求内复用分批的暂存对象（被放弃的分批还在写，复用要等它真正结束，省下的只是对象本身，列和字典照样要建）；用原子操作写位图（每写一个值多一条带锁指令）。代价：分批很小时位图有浪费（`max_batch` 为 25 时每 25 个键占一个 64 位字）；写过列表的分批仍各有一个列表缓冲区；连接器不能保留 writer，`IStagedFeatureValues` 也只在 `Record` 调用期间有效；`SetString` 收到 null 直接让这次调用失败，否则要到回填编码时才在请求线程上出错。
- **一次拉取共用一个取消源和一个时间预算**（设计 4.8、5.4）。拉取开始时算一次预算，同时定下拉取的截止时刻（开始时刻加预算）；有分批要发出时，创建一个关联调用方令牌、到预算时取消的取消源，所有分批的连接器拿同一个令牌。原来每个分批一个关联取消源和一个定时器，等待时再建一个定时器。取消源按引用计数：拉取本身持有一份，直到所有分批发出；每个发出的分批持有一份，直到它的连接器真正结束；最后一份释放时才 Dispose，所以不理会取消、迟迟才结束的连接器手里的令牌一直有效。等待连接器不依赖这个取消源：异步返回的调用用 `WaitAsync(剩余时间, 调用方令牌)` 等待，剩余时间是截止时刻减当前时刻，最少为零，所以后发出的分批不会重新拿到完整预算。原因：取消源触发时，注册在上面的回调在触发它的线程上同步、逐个执行；连接器可以注册自己的回调（释放网络资源、等清理锁），其中一个阻塞，挂在同一个令牌上、排在它后面的等待就一直收不到取消，整个 `Ensure` 跟着卡住，源超时和请求截止时间都失去上界（Codex review 8）。分类不变：调用方令牌已取消算 `cancelled`；等待超时（`TimeoutException`），或连接器响应共用令牌抛出取消，算超时，失败文字相同。局限：调用方的取消通过关联令牌同步传到连接器的回调，阻塞的回调仍会拖住调用方自己的 `Cancel()` 调用，框架无法阻止。代价：每个异步返回的调用一个定时器（同步返回的调用不等待，仍然不分配）；后发出的分批实际等待略少于预算，少的是发出前面分批所用的时间（微秒级）。
- **同步完成的调用不分配**（设计 4.8、15）。拉取内部的调用返回 `ValueTask<FetchStatus>`：连接器同步返回时，记录调用、释放请求内存都在调用点当场完成，不建租约，也不建状态机；只有连接器真正异步时才分配等待要用的对象（租约、续体、状态机、限时等待和它的定时器）。内存规则不变：每个仍在运行的外部调用持有一次请求内存，直到连接器结束并且调用点记录完毕，`stratarec.io.abandoned` 仍然是每个仍在运行的调用计一次。没有用 `PoolingAsyncValueTaskMethodBuilder`：没人等待的预取永远不会把池化的状态机还回去。
- **`EntityKeyBatch` 是只读结构体**（1.0 之前的不兼容改动）。每次连接器调用一个批对象，分批多时是可测量的分配。连接器的 `FetchAsync` 仍按值接收（异步方法不能有 `in` 参数），`IFeatureCallHook.Begin` 和 `Replay` 改为 `in`。自定义连接器和钩子要重新编译；拿批对象的引用做键或判断是否同一批的代码不再成立。

## 本地特征表

第一阶段做了存储引擎（`src/StrataRec.Features/Local/`）：表、写入器、读取 API、更新来源的契约、`snapshot_files@1`，以及测试用的 `memory_updates@1`。第二阶段接入了 `local` 供给方式：绑定、宿主里的表生命周期、请求读取路径、回放和指标（本节后半）。`cache` 方式和 Kafka 来源不内置（见“范围调整”）；节点本地磁盘快照没有做。

- **单写线程、读取无锁：读者能碰到的东西要么发布后不再改，要么整体替换**（设计 6.6 第 3、4 条）。记录先写进页末尾的空闲区，再用一次 release 写把位置发布到索引槽；索引、页目录和字符串字典增长时复制到新数组、填完整之后再发布引用，旧数组不再写；读者用 acquire 读到位置之后才读键、页和记录，页号或字符串码超出手里的目录或字典时重新加载一次。完整规则写在 `LocalFeatureTable` 的注释里。没有选的做法：读写锁或 seqlock（读者在按行的路径上要重试，写得频繁时读者会被饿死）；每条记录一个对象（几百万个对象都要被垃圾回收器扫描）。x64 是 TSO，普通读写本来就有 acquire/release 语义，`Volatile` 只是不让 JIT 重排，所以压力测试（一个写线程、三个读线程，专用线程、固定工作量，`taskset -c 0,1` 下也通过）在 x64 上证明不了硬件重排类的错误。故障注入改的是程序顺序：先发布位置再写记录、读者不重新加载页目录、索引或字典在复制完成前发布，都能被测试抓到；字典那一项要把不同字符串的数量提高到百万级才稳定复现。CI 没有 ARM64，ARM64 上的内存序没有经过测试。
- **索引是一个键和位置交错的 `long[]`**（设计写的是 `IndexKeys`、`IndexPositions` 两个数组）。一次探测只碰一个缓存行，两个数组要碰两个。位置是 `(页号 + 1) << 32 | 页内偏移`，0 表示空槽，新数组不用初始化。装载率不超过一半；条目从不删除（删除是墓碑记录），读者的探测序列不会断开。int64 键分块查找：先读一块键的初始槽，再完成探测、解析记录，让一块键的缓存未命中同时进行，而不是一个键一个键地等。
- **字符串键用 XXH3-64（种子 0）对 UTF-16 码元求哈希，键和 `text` 都存 UTF-16**。`TextColumn` 存的是 .NET 字符串，查找时直接比较 `ReadOnlySpan<char>`，读写都不用转码。代价：以 ASCII 为主的数据多占一倍空间。哈希相同的键靠记录里的原键区分。
- **记录头带整条记录的长度，变长数据和定长部分在同一页里相邻**。记录是一段自包含的字节，压实时整段复制，只需要把字符串码重新编码。`list<string>` 的元素也存成表内字典的码。
- **字符串字典属于版本，压实时重建**。压实把记录复制到新版本时，字符串码重新编码进新版本的字典，不再使用的字符串随之丢弃。没有选全表共用一个只增不减的字典：高基数的 `string` 字段会让字典无限增长。
- **压实按字节触发，墓碑一直保留到 reload**（设计 6.6 第 4 条）。被替代的记录超过记录总字节数的一半、并且不少于 `CompactionMinBytes`（默认 1 MiB）时压实。按字节而不按条数，是因为变长记录大小不一；有下限是为了不让小表每几次更新就重建一次。压实在写线程上同步进行，期间更新等待，读者不受影响。压实按记录原来的页序复制，每个新页只开到装下剩余记录所需的大小（不超过 `PageSize`），通常不比原表大；按索引槽的顺序复制会把大小不一的记录混在一起，每页末尾空得更多，副本常常比原表还大。按页序复制也不保证不变大：新开的页按剩余字节开满一页，下一条记录比这页剩下的空间大时只能另开一页，开好的页就几乎空着。例如 `PageSize` 64 KiB，键 1 是空文本、键 2 是 4 万字符的文本：原表是一个小页加一个装键 2 的页，84,632 B；副本先开一个 64 KiB 的页放键 1，键 2 放不进，再开一页，146,072 B（评审 11）。墓碑在压实时保留，否则晚到的旧更新会让已删除的键复活；reload 从空表开始，快照就是那个位置上的全集，所以 reload 之后墓碑不再保留。
- **`max_bytes` 计当前版本的页、索引、页目录和字典，按字节精确执行**（评审 9、11）。写入之前算出它实际会增加的字节：新页、索引增长、字典里还没有的每个不同字符串（同一记录里重复的只算一次），以及加入它们时经过的每一次字典扩容。一次写入会超出、又有被替代的记录时，在旁边建一个不发布的压实副本，按副本重新计算；副本加上这次写入放得下才换上，否则丢弃副本并抛 `LocalTableFullException`，表完全不变（版本、字节数、generation）。自动压实和显式 `Compact` 用同一个构建过程，副本单独放得下才换上：自动压实放不下就静默放弃，被替代的字节翻倍之前不再尝试；显式 `Compact` 放不下就抛异常。副本可能比原表大（压实时页按剩余字节开满，下一条大记录放不进就要再开一页），所以这两处检查都会走到，各有回归测试。试算用的副本不能被写入器留住：提交内复用的字符串查找结果只在一次 `Commit` 里有效，由同一个 `finally` 清掉。代价：副本的最后一页正好装满，表离上限不到一页、又没有被替代的记录时，写入会失败，直到调大 `max_bytes`；上限通常比页大几个数量级，不为此缩小新页。空表本身超过 `max_bytes` 时建表就失败。压实和 reload 期间新旧两个版本同时存在，进程短时间需要约两倍的内存，`max_bytes` 不算这部分。
- **读取是一次查找加按块填充**（设计 6.6“读取路径”）。`Lookup` 为每个键给出一个记录引用，同一张表的所有特征共用；多字段 `Fill` 把行按 128 行分块，先把每块记录要用到的缓存行都读一遍，让未命中同时进行，再逐个字段填这一块，记录在 L1 里被所有字段复用。按行的循环不做边界检查，安全靠每次调用开头的一次检查，检查的是副本：行、记录引用和读取说明先复制进从 `ArrayPool` 租来的数组，检查副本，循环只读副本。只检查调用方的 span 不够：行可以就是某个目标列自己的数组，写进第一个值就改了还没用到的行，下一行就落到列外（评审 9 的例子）；行也可以和非有限值计数重叠，或者在检查之后被别的线程改写。复制的代价在 500 行时每次调用约 1 μs，约占 30 个特征热缓存填充的 3%。缺失时填缺失的列在循环开始前就建好有效位图，即使最后没有缺失的行：循环里只要有一次调用，JIT 就把循环的状态放到栈上。填充位由调用方处理：每一行的每个字段都会被填，同一张行位图 OR 进每个槽位即可。`float32`/`float64` 的 NaN 和 ±∞ 原样存储，读取时按缺失处理并计数，向量分量原样返回，与暂存区回填（设计 4.3）一致。`text` 读取时要新建字符串，等文本列改存 UTF-8 之后才能不分配（设计 4.4）。
- **读取测量没有达到设计估计的 20 μs**。`LocalFeatureTableBenchmarks`：100 万条记录、每条 30 个特征（25 个 `float32`、2 个 `int64`、1 个 `bool`、1 个 `string`、1 个 64 维向量，约 400 B），一成的键不在表中，0 B 分配。在开发机（Xeon 6975P-C，KVM 虚拟机，.NET 8）上：同一组键反复读（数据都在缓存里）500 键 34 μs、5,000 键 490–505 μs；每次换一组随机键 500 键 51 μs、5,000 键 830–860 μs，其中查找本身 10 μs 和 120 μs。每个字段单独调用一次 `Fill` 时，500 键慢一倍多，5,000 键慢两倍（每个字段都把全部记录再走一遍，还要各复制一次行和记录引用）。热缓存时一个 `float32` 值约 1.5 ns，按列的循环每个值二十来条指令，已经到了这种做法的下限；换键之后多出来的部分主要是 TLB 未命中：4 KB 页随机访问 400 MB，虚拟机里还要走两级页表。要再快，可以试大页（.NET 的 GC 堆默认不用透明大页），或者为连续的同类型字段写按行读取的内核，等接入请求路径、有真实的特征组合之后再决定。
- **快照是 JSON Lines 数据文件加一个 manifest**（`snapshot_files@1`）。设计提到 Arrow 等列式格式；第一阶段选 JSON Lines：标准格式、能手写，错误能指到“文件:行”和 JSON 指针，也不引入 Arrow 依赖。快照覆盖的更新流位置写在 manifest（`snapshot.json` 的 `position`）里，不写在数据文件头：数据文件可以由多个任务并行写，最后写入 manifest（先写临时文件再 rename），读者不会看到半个快照。每次加载都是一次 reload：在读者看不到的新版本里构建，完整之后整体替换；失败就放弃新版本，读者继续用旧的。manifest 内容没变就不重新加载；第一次运行时，如果表的位置已经等于 manifest 的位置也跳过（从本地磁盘恢复之后接着跑）。`reload` 写 ISO 8601 时长（`PT1H`），设计里写的是 `1h`：配置只用标准语法。超出 `float32` 范围的数读成 ±∞，与 `memory@1` 一致（两者都用 System.Text.Json），之后按非有限值处理。加载吞吐（`LocalFeatureTableLoadBenchmarks`，10 万条上面那样的记录，每行约 1 KB）：经 `RecordBuilder` 直接写约 240 万条/秒，解析 JSON Lines 约 20 万条/秒，`RecordBuilder` 只占其中不到十分之一，其余是 JSON 解码（每行约 90 个数）。一行先写 `key` 和 `version` 时字段只扫描一遍，否则先跳过 `fields`、读完整行之后再解码它。
- **写入器的接口比设计多了几样**（设计 6.6 末尾的 `IFeatureTableWriter`）。`Begin` 和 `Delete` 另有 int64 键和 `ReadOnlySpan<char>` 键的重载，解码器不用为每条消息建 `EntityKey` 或字符串。`RecordBuilder` 是值类型句柄，要显式 `Commit`：解码到一半出错的消息不提交就是放弃，下一次 `Begin` 会丢弃它。`Delete` 返回是否因版本过旧被忽略。`BeginReload`、`CompleteReload`、`AbortReload` 对应设计中“建好新版本后整体替换”；reload 期间不能 `Checkpoint`，位置只随完整的 reload 前进。
- **交叉特征（cross 实体）不能放进本地表**。`LocalTableSchema.FromCatalog` 直接拒绝并提示用 `fetch`：交叉特征的键空间没有上限，正是设计表中 `fetch` 适用的情形。
- **绑定写成 `"mode": "local"`，`max_bytes` 和 `bootstrap` 与 `mode` 平级**（设计 6.4 把 `max_bytes`、`max_lag_ms` 放在嵌套的 `local` 对象里）。每个设置只属于一种模式，写了另一种模式的设置是错误，指针指到那个设置，提示删掉它或者改模式：从 `fetch` 改成 `local` 的绑定不会留下一个静默失效的 `timeout_ms`。平级之后每个设置只有一个位置，错误指针也短。设置和模式的对应关系只写在 `FeatureSourceResolver.ModeSettings` 一处，测试用反射核对它覆盖绑定类型的每个属性：以后加的设置忘了归属，测试就失败，而不是被另一种模式默默接受。连接器自己的设置（绑定里没有声明的成员）只属于 `fetch`；来源自己的设置写在 `bootstrap` 里面。`max_bytes` 写整数加 IEC 单位（`16MiB`），JSON Schema 的 `pattern` 和解析器接受同样的写法。`max_lag_ms` 和 `updates` 随 Kafka 来源再加：现在没有更新流，加了也没有地方生效。绑定的每个问题一次报完（另一种模式的设置、缺少的 `max_bytes` 或 `bootstrap`、未注册的来源类型、来源设置的错误），`stratarec validate` 不加载表，所以不需要快照文件。同一个数据源的每个实体一张表，每张表一个来源实例：来源可以有状态（流消费者），不能在两张表之间共用。
- **表的身份只有一条规则，在 `LocalTableSpec.Identity`**。身份是 RFC 8785 规范化的 {数据源、实体、键类型、物理字段和它们的存储类型（按字段名排序）、整个绑定、相对路径的基准目录（绝对路径）}。身份相同的计划共用一张表，切换计划时直接接手已经加载的表，不重新加载；改特征名、默认值、声明顺序、其他数据源、流水线和实验都不改变身份。绑定整体放进身份，而不是挑选几个设置：以后加的设置自动成为身份的一部分，不会因为漏加，让设置不同的两个计划共用一张表。代价是绑定的任何改动都会重新加载一次（例如只改 `reload` 周期）。快照的内容不在身份里：同一个绑定的新快照由来源按 `reload` 自己发现，不靠重新发布配置。
- **基准目录在创建 spec 时固定成绝对路径，来源和身份用同一个值**。`LocalTableSpec.Create` 把基准目录按当时的当前目录变成绝对路径（为空就是当时的当前目录），用它创建来源，也把它写进身份；来源自己也把 manifest 路径在创建时变成绝对路径，直接用工厂创建的来源同样不会留着相对路径。原来身份里存的是传入的原值：为空或是相对路径时，相对的 `uri` 实际按读取时的当前目录解析，身份却一样，宿主会让指向两个目录的计划共用一张表，静默地服务另一个目录的数据；编译之后、后台开始加载之前改变当前目录，读的位置也跟着变（评审 12）。没有选“相对 `uri` 必须配绝对基准目录”：公开 API 本来就接受空的基准目录，固定下来就够了，不用给调用方加一条规则。spec 的构造函数改成私有，创建来源和计算身份只有这一个入口。
- **`uri` 的语法错误是配置错误，在 `/uri`**。`snapshot_files@1` 的工厂解析 `uri` 时，把预期的格式错误（`UriFormatException`，以及路径里的非法字符等 `ArgumentException`）转成 `FeatureUpdateException`，指针 `/uri`，hint 说明接受本地路径或合法的 `file://` URI；解析器统一映射到 `bindings:<环境>` 的 `/sources/<数据源>/bootstrap/uri`。原来 `file://%` 这样的值让 `new Uri` 直接抛异常，越过诊断流程，`validate --format json` 没有任何 JSON 输出（评审 12）。转换放在工厂的解析边界，不在解析器里捕获所有异常：解析器不知道哪些异常是配置错误。测试在单独的进程里运行真正的 `stratarec validate --format json`，快照目录删掉，确认输出是带指针和 hint 的 JSON，且不读快照文件。
- **就绪按计划判断，表的生命周期只在 `BindingHost`**（设计 6.6 第 6 条写的是节点就绪；原名 `LocalTableHost`，现在也管绑定的实例，见“绑定的实例”）。引擎加载计划时开一个 `BindingLease`，编译时向它取表（身份相同就取已有的），然后等这个计划的所有表完成首次加载，才把它设为当前计划；在此之前旧计划照常服务。按节点判断就绪的话，一个新计划的表还在加载时，节点要么停止服务，要么用还没有数据的表服务新计划，两者都不对。表的创建、共享、后台运行、重启、释放和停止都在 `BindingHost` 里，计划和请求只通过租约拿表，`Features` 只依赖 `ILocalTableProvider` 这个接口。
- **引擎的加载、发布和释放由一把锁排序**（`RecEngine` 的 `_publishGate`）。加载开始时在锁里登记自己和自己的租约，发布也在锁里；释放在锁里把引擎标成已释放，并取走所有登记中的加载和已发布的计划。于是：释放之后不会再有发布（发布前在锁里检查）；释放会取消还在进行的加载，它们抛 `ObjectDisposedException`；每个租约只由当时的所有者归还一次：发布之前属于加载，没有发布就在加载唯一的 `finally` 里归还，发布之后属于服务中的计划，计划被替换时或引擎释放时归还。释放会先归还在途加载的租约，不等它们自己结束，这样卡在编译里的加载也不会让表一直运行；之后加载的 `finally` 再归还一次是空操作。原来释放只遍历已发布的计划：等表加载的那个租约不在里面，发布时也不检查是否已释放，使用外部宿主时，加载完成后照样发布，释放过的引擎重新开始服务，这张表和它的来源永远不会被释放（评审 12）。外部传入的宿主仍然不由引擎关闭：它可能同时服务别的引擎，引擎只归还自己的引用，测试用两个共享一个宿主的引擎验证。
- **取消加载：开始时、等表时、发布前在锁里各检查一次**。`LoadAsync` 一开始就检查令牌；`WaitLoadedAsync` 在没有表、宿主不加载表、表已经就绪时也检查（原来只在等待循环里检查，这几种情况直接成功）；发布锁里在修改当前计划之前再检查一次。取消的加载抛 `OperationCanceledException`，当前计划不变，没有发布的租约在 `finally` 里归还，共享的表只少一个引用，别的计划照常用它的来源。原来表已经就绪或没有表时，取消的加载仍然返回 `Applied = true` 并替换当前计划，结果取决于表需不需要等（评审 12）。为了让测试确定地把取消和释放放进“等完表、发布之前”这个窗口，`RecEngine` 有一个内部的 `Publishing` 回调，只给测试用。
- **首次加载失败：计划不生效，下一次加载才重试**。诊断是 `LOCAL_TABLE_LOAD_FAILED`，位置是绑定（`bindings:<环境>` 加 `/sources/<数据源>`），消息里有数据文件和行号，hint 来自来源。设计说表超出 `max_bytes` 时“按数据源不可用处理”，这里改成拒绝计划：从没加载成功的表会让每个请求读它的特征都失败，在加载时拒绝，错误出现得更早、更清楚，旧计划也不受影响。失败的表不再交给任何计划，同一个配置再加载时建新表，真正重新读一遍；后台不自动重试首次加载：配置或数据有错时，自动重试只会不停地写日志，重新发布（或者修好数据后再加载）是更明确的重试时机。还没有服务过任何计划的引擎，这条流水线就一直没有计划，宿主看加载结果决定是否就绪。没有 `max_lag_ms`：现在只有快照来源，首次加载完成就是就绪。
- **首次加载之后来源失败：表继续用已有的数据服务，来源从 `Position` 重启，间隔加倍**（从 `RestartDelay` 1 s 开始，最长 `MaxRestartDelay` 5 min）。一次运行有进展（完成过一次 reload 或 checkpoint）就把间隔重置。进展看表的完成次数（`LocalFeatureTable.Completions`），不看位置：没有更新流的快照来源每次 reload 都停在空位置，按位置判断会永远认为没有进展。失败写日志（事件 1203，带位置、间隔和连续失败次数），计入 `stratarec.local.load.failures`；数据有多旧看 `time() - stratarec_local_load_last_success`，来源一直失败时这个值一直增长。
- **释放和关闭**。计划被替换后，它持有而新计划不共用的表停止来源；还在旧计划上执行的请求读自己钉住的版本，停止来源不用等请求结束。宿主关闭时取消所有来源，最多等 `ShutdownTimeout`（10 s），超时写日志。来源在单独的长期线程上启动：`snapshot_files@1` 在第一次 await 之前同步读完整个快照，不能占用调用方的线程或线程池。
- **停止来源不在调用方线程上运行来源的代码**。取消用 `CancellationTokenSource.CancelAsync()`：令牌立即进入取消状态，来源注册在令牌上的回调在线程池上执行。原来用 `Cancel()`，回调在释放租约或关闭宿主的线程上同步执行：回调阻塞时，关闭要等它返回之后才开始计时，`ShutdownTimeout` 不起作用；计划替换释放旧表也走这条路，新计划已经发布，`LoadAsync` 却可能一直不返回（评审 12）。一张表的“已停止”是来源的运行和取消回调都结束（`TableEntry.Completion`），关闭在同一个 `ShutdownTimeout` 里等所有表，包括之前被释放、还没停完的表；超时之后条目和它的 `CancellationTokenSource`（从不释放）留到两者都结束，表才离开宿主的集合。回调抛出的异常写日志（事件 1206），不抛给释放或关闭的调用方，也不会成为未观察的任务异常。测试覆盖阻塞和抛异常的回调，分别经过租约释放（计划替换）和宿主关闭两条路径，引擎层面另测一次计划替换。
- **请求读取路径集中在 `FeatureFetcher.Local.cs`**（设计 6.6“读取路径”）。一个节点需要某张表的特征时：取存活行中还缺这些特征的行，键去重之后 `Lookup` 一次，每行从这次查找里取自己键的记录，多字段 `Fill` 一次，再把行位图 OR 进各个槽位的填充位。不预取、不受拉取屏障约束、不经过暂存区：读取是同步的内存访问，预取只会提前占用请求内存，读到之后可能被过滤掉的行。同一个 wave 里先发出拉取，再做本地读取，本地读取和拉取的 I/O 重叠。每个请求每张表 `Pin` 一次，所以 reload 和压实不会让一个请求的几次读取看到不同的版本；更新流逐条写入的记录在同一个版本里可见（以后有 Kafka 时，同一个请求先后两次读取可能读到同一个键的新旧两条记录，每条记录本身是完整的）。已经部分填充的特征（行追加之后再读）只填没填过的行，节点读到的值在请求内不变。读取不分配（`text` 除外），测试和同一请求的第二次 `Ensure` 比较字节数，抵消 Debug 构建里异步状态机的分配；去重用的 `EntityKeyIndex` 由 `FeatureFetcher` 在构造时建一个，每次读取 `Reset`。
- **一次本地读取是一个批次，填充和录制都只用这一批记录**（`LocalReadBatch`）。批次是：要填的行、它们去重后的键（首次出现的顺序）、这些键一次 `Lookup` 得到的记录引用、每行的记录。`Pin` 固定的是版本对象，写入器在同一个版本里原地更新时会把索引槽改指新记录，同一个键查两次可能得到两条记录。原来录制时按键再 `Find` 一次，更新落在填充和录制之间时，请求用的是旧记录，回放包里却是新记录，回放和线上不一致（评审 12）；原来也不去重，共用一个外键的几行在一次 `Lookup` 里分别查找，可能拿到不同的记录。现在每个键只查一次，共用键的行拿到同一条记录，录制直接用这批记录引用，不再查索引。回归测试在 `stratarec.local.keys` 的 `MeterListener` 回调里更新 author 表（这个计数正好在填充之后、录制之前），再回放同一份录制，要求逐项相同。命中率按去重后的键计数，和拉取的 `stratarec.source.keys` 一样。
- **缺失和默认值只有一个定义：`FeatureDefinition.Absent`**（有默认值取默认值，否则缺失）。拉取的回填、非有限值替换、上下文特征和本地读取都用它，原来散在 `FeatureFetcher` 里的 `DefaultOrMissing` 去掉了。键不在表中、记录没有这个字段、外键或上下文键缺失、非有限值，都得到 `Absent`；外键失败时读它的本地特征失败，外键降级时它们降级，与拉取相同。测试把同一批记录分别通过 `local` 和 `memory@1` 读出来逐值比较，示例流水线两种绑定的结果和回放记录也逐项相同。
- **表没有加载就读：特征失败，不当作缺失**。空表会把每个键都答成“没有值”，结果看起来正常但全是默认值。只有不经引擎加载的计划会遇到（`validate`、`build`、`explain` 用 `UnloadedLocalTables` 编译），错误文字说明这一点。
- **回放：本地读取记成特征调用，回放包格式不变**（设计 13.4）。录制时每次读取记一次调用：键是读取的行的键，按存活行顺序去重，值是这次读取用的记录里存的值，没有记录就是缺失；回放时本地组和拉取组一样由录制回答，走暂存和回填，不读表。格式没变，旧的回放包和工具照常可用；回放专用的引擎（`stratarec replay`、`compare`）用 `Load = false` 的宿主（表和实例都不加载），不需要快照文件，表变了也照样逐项复现。同一配置上录制和回放取的是同一批行，键完全一致。录制时额外分配（键列表、记录数组），只有录制的请求付这个代价。
- **表的指标**（设计 13.1）：字节数和记录数（gauge，每次 reload 或 checkpoint 时记录）、压实次数、加载耗时（直方图）、加载失败次数、最近一次成功的时间（gauge，Unix 秒），读取命中率用 `stratarec.local.keys` 的 `outcome = hit | miss` 两个计数相除。最近成功写时间戳而不是年龄：年龄要有人定时刷新，时间戳只在成功时写一次，告警规则自己算 `time() - x`。标签（`stratarec.source`、`stratarec.entity`）建表时缓存，记录时不分配。计划加载的结果多了 `bindings_failed`（原名 `tables_failed`，现在也包括实例的加载失败）。
- **`stratarec schema bindings` 的两处修正**。原来带扩展字段的类型（连接器设置、来源设置）也生成 `additionalProperties: false`，合法的绑定会被编辑器标成错误；现在去掉。`mode` 的 `enum`、`max_bytes` 的 `pattern` 由代码里的 `AllowedValues`、`RegularExpression` 特性生成，不手写第二份。
- **组的供给方式只有一个描述：`GroupSupply`**。`FeatureSourceResolver.Group` 为每个组生成它：模式，以及这个模式持有的东西（`fetch` 是连接器、超时和分批，`local` 是表）。组直接存这个描述，计划构建、读取路径和拉取路径都按 `Mode` 判断。原来组只存连接器和表，模式由“表是不是空”推出来，`FeaturePlan.Create` 自己再按模式分支：加一种同时有表和连接器的模式时，这样推出来的模式就错了，而且没有任何地方会报错。现在按模式的判断都是列出每个取值、没有默认分支的 switch 表达式（解析器 4 处、`FeatureFetcher` 2 处）；全局关闭了 CS8524（没有覆盖未命名的枚举值），所以加一个模式时，每个要处理它的地方都编译不过（CS8509，警告视为错误）。编译器看不到的是绑定里模式的拼写和 JSON Schema 的 `enum`，由测试核对：每个模式的名字都能解析回它自己，`AllowedValues` 正好是这些名字。
- **`local` 与 `memory@1` 的请求耗时**（`FeatureSupplyBenchmarks`：示例流水线、无实验，`item_store` 每个候选 8 个特征、`author_store` 经外键每个候选 1 个，两种方式用同一批记录，拉取方式每个数据源每次只调用一次）。开发机（Xeon 6975P-C，.NET 8）上，500 候选：拉取 213 μs、19.5 KB，本地 86 μs、14.9 KB；5,000 候选：拉取 1,933 μs、35.3 KB，本地 640 μs、15.7 KB。本地方式的分配基本不随候选数增长。差距主要是 `memory@1` 自己的成本（每个值从 `JsonElement` 解码，`string` 值每次新建），再加上暂存和回填；真实的远程连接器还要加上网络往返，所以这个比例只说明请求路径本身的开销，不是两种部署的对比。

## 绑定的实例

模型客户端、召回源和特征连接器是绑定的实例（设计 6.4），可能是内置的，也可能是使用方写的。原来每次编译都新建，从不释放；持有连接、要先读文件或询问远程服务的实现需要知道框架什么时候创建、共用、调用和释放它们，才能放心接入。

- **契约从实现方的角度写，只写在一处**：`BindingContext` 的文档（三个工厂接口和 `ILoadable` 都指向它），内置的和使用方写的实例、三种实例都是同一套规则。框架保证：
  - `Create` 只在计划编译、还没有这个身份的可用实例时调用：引擎加载第一个用到它的计划时，前一个实例加载失败之后，以及每一次不服务的编译（`validate`、`build`、`explain-plan`），后者的实例从不加载、调用或释放；两个计划同时加载可能各建一个，多出来的不加载、不调用就释放。
  - 同一身份一个实例，引擎的所有计划和它们的并发请求共用；绑定不变的计划切换接手已经加载的实例，设置变了就建新的，在新计划服务之前加载好。
  - `LoadAsync` 最多一次，在线程池上，有上界、可取消，完成之前不用它服务任何计划；请求路径上不等任何本可以在加载时做的 I/O。
  - 请求的调用和签名查询都在加载完成之后。调用超时时引擎不再等它、取消令牌，但实例活到调用真正返回。
  - Dispose 恰好一次，在线程池上：不再有服务中的计划用它，也没有请求、被放弃的调用或签名查询还在它里面，加载（如果开始了）已经返回；开始 Dispose 之后不再有调用。可能没有加载就 Dispose（不加载的回放引擎、多出来的实例），也可能在加载失败之后。加载或调用一直不返回的实例一直不 Dispose，关闭时报告。

  实现方要做的：`Create` 只读、检查设置，不做 I/O，不占用需要释放的东西（不服务的编译从不释放实例），可能被并发调用；I/O、连接和秘密解析放在 `LoadAsync`；实例线程安全；遵守取消令牌（不遵守只会推迟释放）；Dispose 释放到目前为止拿到的一切；设置错误抛 `BindingException`，带设置的指针和 hint；秘密值不放进消息、异常和日志。没有分别写在三个工厂接口上：同一套规则抄三份，改一处就会漏两处。

- **一个计划一个绑定租约，表和实例都在里面**。`LocalTableHost` 改名 `BindingHost`、`LocalTableLease` 改名 `BindingLease`：计划编译时向自己的租约取表和实例（`IPlanBindings`），身份相同就拿已有的，切换计划时接手已经加载的实例，不重建。生命周期的规则只在两处：`BindingHost` 管共享、加载、释放和关闭，`BindingLease` 管一个计划持有什么、什么时候归还；`RecEngine` 只开租约、发布、退役，加载、发布和释放的排序不变（见“本地特征表”）。没有为实例另开一种租约：两种租约要分别和发布排序，归还的时机也是两套，出错的地方翻倍。
- **实例的身份**是 RFC 8785 规范化的 {段（`models`、`candidate_sources`、`sources`）、逻辑名、类型、绑定自己的全部设置、基准目录（绝对路径）}，并且只在同一个工厂对象之间共享，两个注册表不同的引擎不会共用实例。框架自己解释的设置（`client`、`timeout_ms`、`max_batch`）不在里面，改超时不会重新加载模型。设置整体放进身份，理由和 `LocalTableSpec.Identity` 相同。逻辑名也在身份里，因为工厂拿到它（错误和日志用它称呼实例）；代价：两个名字绑定同一个模型文件或服务、同样的设置时是两个实例，各加载一次。凭据只以引用出现，所以身份里没有秘密值，秘密轮换不换实例。
- **表在计划退役时释放，实例要等计划的最后一个用户离开**。两条规则不同，因为表的读取钉住了版本：请求读自己钉住的版本，停掉来源不影响它；实例没有版本可钉，还在运行的请求、它在超时时放弃的调用都还会用它。所以租约有一个计数：请求进入（`TryEnter`）到请求结束；请求的每次运行加入（`Join`），在它的请求内存最后一次 `Release` 时离开（`IRequestEndObserver`）。被放弃的调用持有请求内存直到客户端真正返回（见“执行与宿主”），所以这一刻之后请求的任何部分都不会再调用实例，不需要第二套计数。签名查询也是这个计数里的用户，从发出到客户端返回：租约退役时取消查询，但客户端还在 `GetSignatureAsync` 里时不释放它（只等加载返回的话，加载超时或被拒绝的计划会在查询中途释放客户端，有回归测试）。租约退役并且计数归零时，实例还给宿主；宿主在线程池上等实例的加载返回，再 Dispose（`IAsyncDisposable` 优先，否则 `IDisposable`），不在请求或客户端的线程上执行实例的代码。退役后进入失败的请求重新读当前计划；引擎释放之后请求抛 `ObjectDisposedException`，包括它从没服务过的流水线；释放时还在运行的请求照常完成，实例在它们结束之后释放。后备流水线进入自己的租约，主流水线运行之后引擎被释放的话，请求返回主流水线的结果，和没有后备一样。回放也进入租约：回放不调用客户端，但一条规则管所有运行，比依赖“这次运行不会调用”更不容易出错。代价：每个请求多几次原子操作。
- **实例在计划服务之前加载，不在请求路径上**（`ILoadable`）。引擎等计划的表完成首次加载时，也等它的实例加载完，任一失败就停止等待。加载在线程池上运行，有上界（`BindingHostOptions.LoadTimeout`，默认 2 分钟）；失败或超时的计划被拒绝，`BINDING_LOAD_FAILED` 指向绑定，实例抛 `BindingException` 时指向那个设置并带它的 hint，例如 `bindings:prod /models/ctr_model/credentials`。失败的实例不再交给任何计划，同一个绑定再加载时建新实例、真正重试，与表的首次加载失败一样，后台不自动重试。实例不会在加载还在运行时被 Dispose：释放先取消加载，等它返回再 Dispose；加载一直不返回的实例一直不 Dispose，关闭时报告。关闭在同一个 `ShutdownTimeout` 里等所有表的来源停止、所有实例 Dispose，超时写日志（事件 1210：还有请求或被放弃的调用在用的实例，或者加载、Dispose 没有返回的实例）；日志或 Dispose 抛出的异常只记录，不结束也不跳过任何等待（与表的停止相同）。
- **模型签名改成异步，在加载时取得；需要等待时计划编译两次**（设计 6.9；1.0 之前的不兼容改动）。`IModelClient.GetSignature` 改成 `GetSignatureAsync(model, version, CancellationToken)`：真实客户端的签名要等它读完模型文件，或者问模型服务。SPI 只改这一处，检查的位置不变，仍在 `ModelScorer` 编译时：编译向租约要签名，已有答案的直接检查；还要等的是 `Pending`，这次编译跳过；`BindingLease.CompileAsync` 编译一次之后，同时等所有未完成的查询（每个先等它的客户端加载完再问），上界是 `LoadTimeout`，再用答案编译一次，只有第二次的结果算数，到时没有答案的查询在第二次里是 `MODEL_SIGNATURE` 错误，hint 说明调大 `LoadTimeout` 或检查模型服务。每个（客户端、模型、版本）只问一次，两次编译和各个验证阶段共用答案；客户端加载失败时签名不检查，错误是那次加载失败，只报一次。没有选的做法：把检查推迟到编译之后（检查要知道节点、配置键和臂组合，`UnifiedCompilation` 的归属和去重要另做一遍）；在编译里同步阻塞地等（模型多时串行，且占着加载线程）；在请求路径上第一次调用时检查（违背加载时检查）。代价：需要加载或 I/O 才能回答签名的计划，第一次加载时在引擎里编译两次；之后的计划拿到已加载的客户端，只编译一次。
- **静态编译不加载实例，需要加载才能回答的签名不检查**。`validate`、`build`、`explain-plan` 用 `UnloadedBindings`：实例照常创建，设置的错误照样报告，但不加载；签名只在客户端不需要加载并且立即回答时检查（`linear@1`），其余留给引擎加载时检查。所以静态检查不需要模型文件、网络和秘密；代价：版本名写错、模型输入名不符这类错误要到引擎加载时才发现。回放用的引擎（`Load = false`）同样不加载实例。
- **凭据只以引用出现**（`"credentials": "secret://<名字>"`，设计 6.4 第 4 条）。工厂创建实例时用 `BindingContext.SecretReference` 读出引用：不是 `secret://` 就是指向那个设置的配置错误，消息不引用写错的值，因为它可能就是误贴进来的凭据。实例加载时用宿主的 `ISecretResolver` 解析（DI 容器里注册的，或 `BindingHostOptions.Secrets`）；没有这个秘密、宿主没有秘密存储，都是 `BINDING_LOAD_FAILED`，指向那个设置并带 hint。解析出的值是 `Secret`，`ToString()` 是 `[secret]`，只有 `Reveal()` 读得到；框架不持有值，值从存储直接交给实例，诊断、日志、trace 和回放包里只有引用。不做缓存和轮换：实例每次加载解析一次，要轮换的实例自己再解析。测试确认值不出现在诊断、日志、trace 和回放包里，误写成值的凭据也不出现在诊断和日志里。
- **本地文件设置只有一条规则：`LocalPaths`**。基准目录在 `BindingContext.PinBaseDirectory` 固定成绝对路径（原来在 `LocalTableSpec`，理由见“本地特征表”），文件设置可以是相对于配置根目录的路径、绝对路径或 `file://` URI，别的 scheme 不是本地路径。本地表、`snapshot_files@1`、`memory@1`、`memory_list@1` 都用它，使用方读本地文件的实现也可以用：`BindingContext.LocalFile` 把错误转成指向设置的 `BindingException`，各处接受同样的写法、拒绝同样的错误。
- **工厂接口改成 `Create(BindingContext)`**（1.0 之前的不兼容改动）。模型、召回源、连接器的工厂原来各自接收名字、设置和基准目录；`BindingContext` 还带着秘密存储，以后再加东西不用改三个接口。工厂只读设置、不做 I/O：实例由多个计划共享，I/O 放在 `LoadAsync`，只在引擎加载时做。`RecEngine` 的构造参数相应是 `bindings`（外部的 `BindingHost`，由调用方释放）或 `bindingOptions`（引擎自建宿主的选项：秘密存储、加载和关闭的上界），只能给一个。

## 日志

- **没有消费者时不采样、不捕获**。没有日志管道且请求没有 `CaptureLogs` 时，所有批次都会被丢弃，白白消耗 CPU 和内存。
- **漏斗组的 key 只能读请求输入，且必须是标量**（设计 8.2）。组决定在请求开始时做出；key 若要等一次拉取，每个请求都会在召回之前阻塞在日志采样上（评审 4、5）。
- **探针对上下文特征同样是被动的**（设计 8.5）。只被探针读取的上下文特征不进入预取，否则每个请求都多一次拉取，无论是否被采样（评审 4）。
- **durable 投递以返回值和钩子表达，不内置磁盘缓冲**（设计 8.6）。`Submit` 返回 Queued/Spilled/Dropped/Closed；内存队列满时调用 `DurableOverflow` 钩子，由宿主决定是否落盘；sink 用 `LogBatchRejectedException` 声明永久不可写的批次，避免一个坏批次堵住整个 durable 流（评审 4）。`DisposeAsync` 的等待有上限，不依赖 sink 配合取消（评审 5）；到时还没写出的批次计为丢弃（评审 6）。
- **非有限向量记为缺失**。一个分量是 NaN 的向量整体记为缺失，部分向量对训练没有意义。
- **不做个人数据过滤**（设计 8.9）。推荐需要这些数据，内部记录和调试查看是正常用法；不暴露给外部系统由运行环境和数据权限负责。曾经实现过敏感级别、`purpose` 声明和缓冲区清零，已按此决定全部移除。

## 表达式

- **哈希的规范编码**（设计 5.7）。`float64` 中 −0.0 按 0.0、所有 NaN 按 `0x7FF8000000000000` 编码。IEEE 754 不规定定义域错误产生的 NaN 的符号和载荷，优化器和 SIMD 重写都可能改变它，`hash01` 结果不能随之变化。离线复算哈希也要这样规范化（评审 4）。
- **`hash01` 有两份编码实现**。表达式后端用栈上缓冲区写编码，标量路径不经过数组池；与 `StableHash.Builder` 的一致性由测试锁定。
- **int32 越界的派生特征，不可空又没有默认值时整个特征失败**（设计 4.3、4.6；评审 6）。和节点输出、非有限值是同一条规则：不可空的列装不下替换出来的“缺失”，读取方按不可空编译、不检查有效位。没有选择让类型推断因为“可能越界”而变成可空：那样所有 int32 派生特征的读取方都得写 `??`，而越界在实践中很少见。失败的特征对所有读取方都一样：节点按 `on_failure` 处理；输出读到它时请求失败（之后由后备流水线兜底）；探针不让请求失败，读到它的列记为缺失，过滤条件视为 false。
- **`lookup(table, key, default)` 在 key 缺失时返回 `default`**（设计 7.4 的例外）。第三个参数本身就是调用方给出的缺失处理；改成缺失会让现有打分表达式变成可空类型而无法编译。

## 可观测性

指标名称、单位和标签写在 `StrataRecMetrics`（`src/StrataRec.Core/Diagnostics`）的文档注释里，这里只记取舍。

- **显式引用 System.Diagnostics.DiagnosticSource 10.x**（设计 13.1）。net8 自带的 8.0 版没有 `InstrumentAdvice` 和同步的 `Gauge<T>`；`Microsoft.Extensions.Logging.Abstractions` 10.x 在 net8 上本来就依赖同一版本，所以 Core 显式引用不会给部署增加任何程序集。建议边界：耗时按 √2 递增（0.1 ms 到约 13 s，35 个边界，每桶宽约 41%），行数、键数、字节数按 2 递增。导出为指数直方图时宿主会忽略这些建议。
- **请求级指标和请求 span 由 `RecEngine` 记录**。一次请求就是一次 `IRecEngine.ExecuteAsync`，包含分配、主流水线和后备流水线：由后备流水线返回的结果计为降级，不计为错误（设计 5.6）；被调用方取消的请求计为错误，因为慢请求更容易被取消，而慢往往与臂相关。直接调用 `PipelineExecutor` 只得到节点、数据源、模型、列和内存指标。
- **执行器不自己补建请求 span**。它只在当前 span 是已记录的 StrataRec span 时创建节点和 I/O 子 span。如果 `RecEngine` 的 span 被采样掉之后执行器再试一次，对根请求来说每次都会生成新的 trace id，按 trace id 采样的采样器第二次可能放行，等于把采样率翻倍。直接用执行器的宿主可以用 `StrataRecTracing.StartRequest` 包住调用。
- **按臂的请求指标用单独的名字**（`stratarec.arm.request.*`）。一个请求在每个分配到臂的层各记一次；如果和请求级指标同名、只靠 `arm` 标签区分，按流水线求和就会把多层请求重复计算。
- **标签键都带 `stratarec.` 前缀**。采集链路会自己加标签（例如 Kubernetes 的 `node`），短名字会冲突。
- **数据源健康按窗口判断**（设计 13.2）。一个窗口（10 秒）内至少一半调用失败就判为失败，判断翻转时才写一条日志；没有调用的窗口不改变判断。按连续失败次数判断在低流量下会来回翻转。部分成功（`partial`）算健康。
- **汇总日志由定时器刷新，定时器只弱引用日志对象**。被丢弃的执行器不会被自己的定时器留住；窗口内最后的计数在进程退出时可能丢失，精确计数看指标。
- **日志 sink 失败按状态变化记录**：开始失败时写一条（带异常），恢复时写一条（带失败次数）。宿主钩子（`DurableOverflow`、`Rejected`）抛异常和被 sink 永久拒绝的批次按窗口汇总。
- **调用方取消不算依赖超时**。外部调用（特征源、召回源、模型）被调用方取消时，不记耗时、不记错误、不进健康判断，否则客户端断开会被当成依赖变慢。算子拿到的节点令牌同时受节点预算控制，分不清两者，所以请求状态另外保留调用方的令牌。请求本身仍计为错误（见上）。
- **越界计数只按流水线记录**（`stratarec.column.out_of_range`；设计 13.1 写的是 `{node,column}`）。int32 窄化发生在表达式后端和上下文特征写入处，计入每请求共享的计数器，那里不知道列；按列归属要在每个写入点传标签。int32 列通常很少，按流水线报警之后再查具体列。
- **被调用方中止的节点记为 `aborted`**，耗时和行数照记（评审 6）。否则节点延迟分布恰好漏掉调用方等不及而放弃的慢尝试。
- **每请求多约 60 B**。为了携带事件日志、span、调用方令牌和当前位置的状态，请求状态和特征拉取器多了几个字段。记录指标本身不分配：挂上 `MeterListener` 时和不挂时分配的字节数相同；被采样掉的请求多一个未记录的 `Activity`（约 0.4 KB）；被记录的请求为每个节点和每次外部调用各建一个 span。

## 回放

回放包的结构见 `stratarec schema replay_bundle`（`src/StrataRec.Artifacts/Model/ReplayBundle.cs`），这里只记取舍。

- **回放包的布局一变就升格式版本，读取时先看版本再解析结构**。不在同一个版本号下原地修改布局，哪怕那个版本只在主干上出现过：已经录下的包无从分辨自己是哪种布局。读取器只读当前版本；其他版本在 `/format` 处拒绝并提示用当前构建重新录制，不把旧布局当作当前版本的结构错误报告。没有选择兼容读取旧版本：回放包是调试用的短期产物，重新录制的代价小于维护多套读取逻辑。

- **在框架的调用点录制和回放，不在连接器里**（设计 13.4）。特征拉取由 `FeatureFetcher` 的调用点经 `IFeatureCallHook` 录制（读连接器解码后的暂存缓冲区，按键记录值），召回源和模型调用经 `OperatorContext.RetrieveAsync` / `InvokeModelAsync`。宿主注册的连接器、模型客户端和算子不用实现任何东西就能录制和回放。没有选择包装 `IFeatureSourceConnector` / `IModelClient`：包装层看不到超时、跳过等执行决定，回放时也要重写按键匹配。代价：自定义算子如果绕过这两个方法直接调用客户端，不会被录制，回放时会真的调用外部服务。
- **录制按请求开启，关闭时只多几个字段**。`DebugOptions.Record` / `PipelineRequest.Record` 默认关闭；关闭时每次外部调用多一次空检查，每请求多约 40 B（请求状态和拉取器上的字段），不做任何按行的工作。开启时分配与请求拉取的数据量成正比，示例请求约 95 KB、多约 0.4 ms，不适合全量常开；按比例常开录制以后再做。
- **计时决定取自录制，回放不计时**（设计 13.4、10.8）。回放的截止时间是 1 小时，不设节点超时：节点的 `min_remaining_ms` 比较用录制时该节点的剩余时间，每次尝试按录制的结果（`ran`、`deadline_exceeded`、`timed_out`）处理，外部调用按录制的状态返回。没有用录制的耗时驱动虚拟时钟：配置一改，调用的顺序和并发就变了，模拟出来的决定在线上从未发生过。代价：修改后的配置里新增的节点没有录制的时间，视为时间充足，永远不会因时间被跳过或超时。
- **数据先按调用精确匹配，再按值合成**。同一数据源、同样的键和顺序、并且包含全部所需字段的调用原样重放，包括超时和失败。只覆盖部分字段的调用不算精确匹配：否则其余字段会被报成缺口，而录制里别的调用其实取到过它们。配置改变了键、字段或分批时，按（数据源、实体、键、字段）从录制中成功的调用取值；取不到的值是缺失，并按原因计入缺口报告（`not_recorded`、`type_changed`、`limit_exceeds_recording`、`inputs_changed`）。录制的值换成新类型时有损（例如超出 float32 范围）也算 `type_changed`，精确匹配和合成用同一条规则，不让溢出变成 ±∞ 混进结果。合成的调用状态是 `ok`：录制中超时的分批不会映射到新的分批上，那些键的值只是缺失。失败调用的数据从不使用。召回源按节点匹配：节点重放并占用自己录制的调用；录制里没有调用的节点（例如配置新加的）复制该数据源返回过的最长列表，不占用任何调用，所以节点的执行顺序变了也不会抢走别的节点的录制；要的数量超过录制、而录制当时已到上限时，报 `limit_exceeds_recording`。
- **模型输出按实体和输入摘要匹配**。每行输出按实体 id 和该行全部输入的 XXH3 摘要记录，只在输入没变时使用；输入变了算缺口（`inputs_changed`），输出缺失。没有选择忽略输入直接复用：那会在特征改动后静默地显示旧分数。哪些输入按行切分只看张量约定：首维等于 `batch_size` 的输入每行取自己的切片，其余输入（共享的用户向量、文本）整体计入每一行的摘要，不按长度能否整除来猜。摘要包含每个输入的元素类型和形状，按行切分的输入不计批维度，所以换一种分批仍然匹配，而同样的数值换一种形状不会。同一实体可能以不同输入被打分多次，合成时按（实体、摘要）查找。回放也不调用模型客户端（设计 5.9、10.8）。因此修改模型绑定（例如线性模型的权重）不改变回放结果；评估模型本身的改动要用实时模式或草稿预览。
- **回放抛出录制时的异常类型**。模型客户端抛出的异常连同类型身份录制（`error_type`）。回放时 `TimeoutException` 仍是 `TimeoutException`，取消仍是 `OperationCanceledException`；其他类型如果回放进程已经加载、派生自 `Exception` 并有 `(string message)` 构造函数，就用录制的消息重新创建，否则抛出带原类型名的 `ReplayedCallException`。这样经 `InvokeModelAsync` 处理特定客户端异常的算子在回放时走同一条路，节点失败的说明也不变。没有选择统一成一种回放异常：那会改变按约定使用调用接口的算子的控制流。代价：需要更多构造参数的类型、回放进程没有加载的类型，算子看到的是 `ReplayedCallException`。
- **异常类型按身份查找，只在已加载的程序集里找**。身份是类型（封闭泛型取泛型定义）的完整名、定义它的程序集的简单名，以及各类型参数的身份。回放只看已加载、简单名相同的程序集，在它们定义的类型里找完整名相同的那一个；泛型的定义和每个参数分别这样找，再组合。没有选择只记完整名：两个程序集可以定义同名类型，按名字挑第一个会让算子接住另一种异常。也没有选择交给 `Type.GetType` / `Assembly.GetType` 解析：它们会跟随类型转发、加载新的程序集，回放包不应该让回放进程加载代码。找不到或找到不止一个（同名程序集加载了两次）都不猜，回退到 `ReplayedCallException`。`TimeoutException` 和 `OperationCanceledException` 也按身份判断，只有核心库的这两个类型才走超时、取消的路径；别的程序集里的同名类型是它自己。代价：数组等构造类型作为类型参数时回退；枚举一个程序集的类型时，运行时可能为解析基类型加载它的依赖。
- **回放用录制的臂，不重新分流**。分流配置变了，同一请求在线上会进入别的臂，但回放要比较的是同一处理下配置的差别。`--arms` 可以指定别的臂；回放计划里没有的臂和请求输入会被去掉，并写进报告的说明。
- **回放不是流量**。回放不记指标、事件日志和 span，不写持久日志（探针捕获到结果里）。否则回放录制下来的失败（例如特征源报错）会把一个健康的依赖判为失败，CI 的批量回放也会混进延迟分布。没有选择加 `replay` 标签区分：所有看板和告警都得过滤它。录制则不改变任何观测：被录制的请求照常计入。
- **后备流水线是包里单独的一次运行**（`role: fallback_pipeline`）。回放时主流水线失败，就用这份录制回放后备流水线；录制中主流水线失败却没有运行后备流水线（时间已用完，设计 5.6），回放也不运行。
- **中止的请求也交付回放包，内容是中止那一刻的快照**。被调用方取消或因缺陷中止的请求没有结果，`RecResult.Recording` 带不出回放包，所以录制经回调交付：`DebugOptions.OnRecording` 收到整个请求的回放包，`PipelineRequest.OnRecording` 收到一次运行的录制。返回和中止都会调用回调；回调抛出的异常只记日志，不改变请求的结果，取消照常传给调用方。中止时立即构建录制，不等任何调用。召回源和模型调用的等待在调用方取消时就结束，调用点把它记为 `cancelled`，这正是请求看到的；快照时调用点还没有记录的调用（例如算子发出后没有等待的调用）记为 `outstanding`，它的键和模型输入摘要在调用开始时就已记下；之后才完成的调用的数据不在包里。回放中止的包时，引擎复现录制里每个已完成位置的决定，在录制没有完成的第一个位置停下（录制中正在执行的节点再记一次 `aborted`），报告这次运行被中止，不给出结果。两边都中止的对比算相同；对比报告里中止计入错误率，和线上指标一致。没有选择等在途调用完成再交付：不理会取消的连接器会让取消迟迟到不了调用方。也没有选择把录制挂在异常上（`Exception.Data` 或专用异常类型）：调用方得改写 catch 才拿得到，取消的异常类型也会变。代价：快照之后才返回的数据丢了，修改后的配置如果用到这些调用，回放按取消处理；在分流阶段就中止的请求还没有运行流水线，没有回放包。
- **被放弃的调用按请求看到的录制**。超时被放弃的召回源和模型调用记为 `timeout`，不带数据（召回源不记返回的 id，模型不记输出），因为请求没有用到它们；客户端之后才返回的东西不进入录制。节点按超时结束、晚到的成功被丢弃时，调用本身照实记为 `ok`，节点尝试记为 `timed_out`，回放按尝试的结果处理，不使用这次调用的输出。回放时这些调用直接按录制的结果返回，不等待。
- **中止位置的实验触发按录制恢复**。中止时正在执行的位置可能已经触发了实验：到达了站点、节点读了臂改过的参数、走了后备。这次曝光已经发生，计入了实验记录。回放在这个位置停下，不重新执行它，因为执行到一半的位置无法复现。所以录制在中止的节点上记下这个位置从开始到中止新触发的实验（`triggered`，只出现在中止的节点上），回放停在这里时按 id 恢复，只恢复回放计划里存在、并且在回放的臂下已分配的实验。这样相同配置上回放的触发集合与录制完全相同。没有选择回放时给中止节点补记它的全部参数触发：取消可能发生在节点读参数之前（例如还在拉特征），那会多出没有发生过的曝光。代价：修改后的配置即使改了这个位置的触发条件，回放也只恢复录制的事实；录制的请求在每个位置开始时多复制一份触发状态，不录制时没有这份开销。
- **值编码复用日志编码，类型写在值旁边，但保留非有限值**。`null` 是缺失；NaN 和 ±∞（包括向量的分量）写成字符串 `"NaN"`、`"Infinity"`、`"-Infinity"`，日志里仍然写成 `null`。回放包必须如实保留请求看到的值：并不是每条路径都会先把非有限值换成缺失或默认值（设计 4.6），暂存的原始向量和直接求值的输出表达式就不会，按缺失录制会让回放走另一条路（`has()` 变成假、结果出现差异）。两者共用同一个编码器，回放包只是打开一个选项，没有另写一套。每个值按旁边记录的类型解码，类型不兼容时报出 JSON 指针。
- **对比指标的定义**（设计 10.8）。Top-K 重合度 = 交集 / 两个 Top-K 中较长者，短列表不会抬高重合度；Kendall τ 只在两边共有的条目上计算，少于两个时为空；分数分布变化用双样本 KS 统计量，另给同一条目的分数差；两者都只用有限的分数，NaN 和 ±∞ 按每一边单独计数报告：它们没有位置可排，混进去会让 KS 失去意义，NaN 还会让排序比较不再自洽。降级率的分母是全部请求，分子只算成功但降级服务的请求；失败的请求只算错误，不算降级。特征缺失率包括数据源本身缺失和回放包里没有的值。录制模式下外部 I/O 立即返回，延迟只反映引擎计算，不能用来评估依赖延迟。配置增删的输出列在差异中单独列出，不逐条重复。
- **`replay` 和 `compare` 只有用上了每个包才算通过**。没有包、包全部读不出来、或者一个都没比较成，以 2 退出；部分包读不出来也以 2 退出，但照常输出报告，JSON 里带 `status`（`ok`、`partial`、`failed`）和读不出来的包数。CI 用退出码判断对比是否通过，只覆盖一部分包（或一个都没覆盖）的指标不能当作干净的结果放行。没有选择部分成功时返回 0 只在报告里标出：CI 步骤通常只看退出码。

## 工程

- **最低 SDK 是 .NET 8，CI 只用 Linux**。CI 分别在固定的 SDK 8 和 SDK 10 上构建测试。banned-API 分析器用 3.3.4：5.x 依赖 Roslyn 4.12，在 SDK 8 的编译器（4.11）上报 CS9057（评审 5）。
- **内存分配预算是估算**（设计 15）。“每请求 ≤ 2 KB”不是硬指标，允许一定偏差。当前示例流水线（`PipelineBenchmarks.Baseline`）每请求：5,000 候选约 35 KB，500 候选约 19 KB，只有 Gen0（原来分别约 227 KB 和 45 KB；`author_store` 改成本地表之前是 36 KB 和 20 KB）。按键和按分批的工作都不再分配，连接器同步返回的分批是 0 B（原来约 420 B，见“特征拉取”）。5,000 候选时其中约 17 KB 是 `memory@1` 解码字符串：`JsonElement.GetString` 为每个值新建一个字符串，约 500 行读到 `item.category`；这属于第 15 节单独计量的字符串解码，引擎这边的字符串可以忽略。其余约 18–19 KB 与候选数无关，按 500 候选的抽样：返回给宿主的结果约 4.5 KB（第 15 节不计）；节点预算和拉取的取消源、定时器约 2.5 KB；每次拉取的对象（键索引、暂存区、待完成记录、字段子集）约 0.5 KB，示例请求约 6 次；候选表、表中字符串列的字典、请求状态和节点上下文约 6 KB；算子、模型和召回调用约 1.2 KB。
- **暂不做请求状态池**（设计 4.8 表中第二行）。能放进池的部分（`RequestState`、`CandidateTable`、`RowSelection`、`OutputBindings`、`FeatureFetcher`、表中字符串列的字典、节点上下文）合计约 6 KB，约占剩余分配的三分之一。池化要为每个对象写重置逻辑，漏掉一处就会把上一个请求的数据带进下一个请求；请求返回后，被放弃的 I/O 还持有请求内存，状态只能在最后一次 `Release` 时归还，可能在连接器线程上。每请求 20–40 KB 的 Gen0 分配在每秒数千请求时是每秒几十到一百多 MB，Gen0 回收的成本与存活对象成正比，而回收时这些对象大多已经死亡。更划算的是先做局部的：节点预算复用一个取消源（`TryReset`），按计划缓存拉取的字段子集，表中字符串列的字典按计划预设容量。压测显示 GC 暂停或分配速率与请求状态有关时再做。
- **基于示例的测试默认不计时，测预算的测试显式选择原始预算**。示例保留真实的预算（`ctr_ranker` 给模型 50 ms，超时回退到 `ctr_backup`），用来演示预算和回退。晚到的结果一律按超时处理，冷启动的模型调用在繁忙的 CI 上会超过 50 ms，比较两次实时运行的测试就会一次回退、一次没有，结果对不上。所以测试默认用示例的一份副本：其中每个 `timeout_ms`（节点及其实验补丁、特征源、模型、召回源）和请求文件的 `deadline_ms` 都提高到一分钟，`on_failure` 不变，测试自己构造的请求也用一分钟的截止时间；测预算本身的测试选择 `SampleTiming.AsWritten`，由门控的客户端决定调用何时返回，不和时钟赛跑。放宽只有一处（`tests/Shared/SampleBudgets.cs`），基准测试也用它：基准度量的是流水线的工作量，冷启动碰到预算就成了度量回退。放宽只替换文本里的数字，注释和格式不变，测试照常按文本修改副本；遇到不认识的 `*_ms` 设置、一处都没放宽，或编译出的计划里仍有低于一分钟的节点预算或拉取预算（没写 `timeout_ms` 的拉取源用框架默认的 50 ms）时直接报错，不会悄悄失效。比较两次实时运行的测试先逐个节点比较结果（`LiveRunAssert`），时间因素再混进来时，失败信息会指出哪个节点、为什么回退。没有沿用逐个测试改超时字符串的做法：同一条规则散在多处，示例一改就悄悄失效。代价：默认的测试不覆盖示例真实预算下的行为，这部分只由选择 `AsWritten` 的测试覆盖；挂住的调用要等一分钟才让测试失败。
- **测试里的预算只切断测试想切断的调用**。一个预算由一次拉取的所有分批共用（节点预算、请求截止时间同理）：短预算切断的是截止时刻之前没被观察到的所有调用，不只是测试想挂住的那个。CI 上实测过：正常回答的分批 90 ms 内就做完了，但同时运行的其他测试占满了线程池（4 核、5 个线程、几十个工作项排队，GC 暂停只有一百多毫秒），完成的回调 1.4–2.9 s 后才执行，晚于 1.5 s 的预算，有的分批被判为超时；同一时段，等待排空 20 ms 的日志管道关闭用了 3–4 s。所以：单元测试的特征测试台（`FeatureTestRig`）默认的源预算和请求截止时间都是一分钟，与示例测试的“不计时”一致；需要一部分调用正常回答、另一部分被切断时，由测试自己切断：等调用钩子显示其余调用都已判定，再取消调用方令牌（同步回答的调用在 `EnsureAsync` 返回之前就已判定）；集成测试要在某个调用进行中取消请求时，从这个调用发出时计时（`CancelOnceCallStarts`，看调用的 span），不从请求开始时计时，被切断的调用要一分钟才回答。只防止测试挂住的上界（等一个永不自己结束的调用、一个要一分钟的调用）放宽到 30 s。超时的分类和预算的上界由“所有调用都挂住”的测试覆盖，这时预算只可能切断测试想切断的调用。代价：结果有成有败的测试里，失败一方是 `cancelled` 而不是 `timeout`，两者走同一段失败处理（分批标记失败、暂存不被读取），分类另有测试。仍然依赖时钟的有两类：测请求截止时间本身的端到端测试，截止时间之前的节点要在截止时间内跑完；选择 `SampleTiming.AsWritten` 的测试，不测的预算也按原样。
- **确定性的范围**（设计 5.7）。计划、请求输入、时间、外部响应和执行决定（超时、跳过、后备）都相同时，排序结果、分数、选中的变体和采样决定相同。耗时、`seq`、producer id 等运行元数据不在保证内，回放对比时要排除。

## 范围调整

框架的核心目标是：整体性能好、整体分配低、用户体验好、容易调试、开发和测试。`design.md` 是起点，不是约束；一项设计带来的复杂度超过它对这个目标的贡献时，就简化、推迟或不做。

- **父子层级表（偏移数组嵌套）不做；组按它和成员的关系分两种情况**（设计 4.7）。嵌套表的难点（父表过滤后子表怎么办、子表截断后父表的汇总值过期、表达式怎么区分两张表的列）会散落在执行器、拉取、后备恢复、日志和回放里，一致性只能靠两张表一起改；物品在组之间移动（混排、广告插进某一行）还要重建偏移数组。
  - **组由成员决定**（按商家分组的搜索结果）：一张表，组键是外键实体（例如 `col.item.merchant_id`），组的特征照常按键去重拉取；组的得分和组内名次由分组聚合算出、回填到组内每一行（`sum`、`mean`、`max`、`top_k_mean`、`logsumexp`），每组保留前几项用组内名次加过滤；分组展示由宿主按组键排列结果。分组聚合算子有实际需求时再加。
  - **组先于成员存在**（多行首页：先提名候选行、用行级模型过滤，再按每一行自己的召回源和数量取内容；物品可以出现在多行里；版面规则作用在行上）：框架现在不原生支持，由使用方组合实现，例如宿主先调用排行的流水线，再把选中的行作为请求输入交给排物品的流水线，或者写自定义的行源算子。已知代价：实验按流水线定义，同时改行和物品的实验要拆成两个实验，并让它们共用同一个分流。
  - **将来原生支持时的方向：一个请求几张扁平表，用键列关联，不嵌套。** 子表声明父表，子表的一行由（父键, `entity_id`）标识；节点只写一张目标表，可以读其他表，父表的列按请求内的外键实体读取（父行已淘汰时读到缺失）；跨表汇总用分组聚合；父行淘汰时子行不级联删除，输出时按父表顺序 join，孤儿行不出现，要省掉后续拉取就显式过滤。现在的格式都能按增量扩展（节点加可选的 `table`，缺省就是唯一的表；日志的行标识加表名；回放包有版本号；结果加可选的分组结构），所以不提前定格式。等组合方案的代价（拆实验、宿主胶水）在真实业务里显现时再做。
- **`fetch_missing` 不做**（设计 8.5）。这是响应之后的后台拉取：探针缓冲区和请求内存要活过请求本身，拉取还要有自己的超时、并发上限和失败计数，而它只满足“离线训练要的特征比线上用的多”这一种需求。训练用的额外特征，可以离线按键和时间点关联，或者加进线上的拉取。
- **本地磁盘缓冲不在框架里做**（设计 8.6）。落盘和重启后补发取决于部署环境（磁盘、容器生命周期），由宿主通过 `DurableOverflow` 钩子实现。
- **不统计每个探针的字节数和池中保留的字节数**（设计 13.1）。前者要在 sink 序列化之前估算字节数，后者要池暴露内部状态，调试价值抵不上成本。
- **框架只做编排，不内置推理、存储和召回的接入**（设计 6.4、6.9）。StrataRec 管的是配置、计划、实验、预算与后备、录制回放。推理用 ONNX、Triton 还是公司内部的模型服务，特征存在 Redis 还是别处，召回服务用什么协议，都是使用方的技术选型，往往已经有现成的服务。框架内置一份实现，就要跟着这些技术的版本和部署方式演进，而用得上的只是一部分使用方。所以接入由使用方实现四个接口之一：`IModelClient`（模型）、`IFeatureSourceConnector`（特征拉取）、`ICandidateSource`（召回）、`IFeatureUpdateSource`（本地表的快照和更新），注册后由绑定产物按类型名引用；设计 6.4 示例里的 `grpc_tensor@1`、`redis_hash@1` 这类名字都是使用方自己的类型。框架负责让这些实现可以放心接入：实例的创建、跨计划共享和释放、加载期的 I/O、秘密引用、等待上界、录制回放和诊断。内置的 `memory@1`、`memory_list@1`、`linear@1`、`snapshot_files@1`（只读本地文件）只用于测试、样例和本地开发。所以不做：`local_onnx@1`、`grpc_tensor@1`、`grpc_ann@1`、`grpc_retrieval@1`、`redis_*@1`、Kafka 和对象存储来源。
- **`cache` 供给方式不内置**（设计 6.6）。进程内缓存要定 TTL、过期兜底、未命中合并和后台写入，怎么取舍取决于业务（同一用户的连续请求、热门物品）。需要的使用方在自己的连接器里缓存（包一层装饰器），框架不阻止：同步返回的分批在调用点当场完成、不分配（见“特征拉取”）。保留 `fetch` 和 `local` 两种方式。
- **草稿预览、实时回放推后**（设计 10.7、10.8）。两者都依赖控制面；本地已经可以用 CLI 运行工作区、录制和回放请求。
