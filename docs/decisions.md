# 决策记录

`design.md` 描述整体设计。本文只记录实现过程中做出的、读代码看不出来的决定和理由：对设计的调整、取舍，以及刻意没有做的事。两者冲突时以本文和代码为准。括号中的“评审 N”指 Codex 第 N 轮评审发现的问题。

## 实验与计划编译

- **组合校验超限是错误，不是警告**（设计 11.5、12.3）。组合空间不超过 `MaxCombinationsChecked`（4096）时全量枚举；超过时退回到单个实验、成对组合和按列枚举，同时报 `COMBINATION_CHECK_LIMIT`。设计假设涉及的层很少，但层数一多组合会指数增长；只给警告就等于在没有证明安全的情况下发布（评审 3）。
- **schema 段始终只增**（设计 11.4）。`columns`、`param_schema`、`features`、`derived_features`、`funnel_groups` 无论 policy 怎么写，实验都只能新增。实验修改或删除基线 schema，会让其他实验和基线的类型检查失效。
- **基线必须能单独编译**（设计 11.5）。实验新增的特征或列不能“修好”基线中的引用，否则实验下线后基线就坏了（评审 3）。
- **跨域的臂组合直接跳过**（设计 11.1）。不同域的臂不可能同时分配，编译它们只会产生误报（评审 3）。
- **`columns_from` 跟随模型变体**（设计 8.3、6.9）。探针展开的是当前臂组合下实际生效的模型节点；修改该模型的层也参与探针的变体划分；探针 schema id 包含每列解析后的表达式。训练日志必须记录服务时真正的输入（评审 4）。
- **节点 id 只能是标识符**（字母、数字、`_`）。版本引用 `col.x@node` 要能写出每个节点；含 `.` 或 `-` 会被解析成字段访问或减法。这是在扩展语法和收紧 id 之间选了后者（评审 4）。
- **行源节点不能被版本引用**（`VERSION_REF_ROW_SOURCE`）。所有行源向同一个槽位追加行，没有“某个节点的版本”可读（评审 5）。

## 执行与宿主

- **参数触发在调用算子之前记录**（设计 12.6）。节点之后失败也算触发；按结果决定是否触发会让失败的请求从实验组里消失（评审 3）。
- **取消或中止的请求仍然发布 `$experiments` 记录和已捕获的探针**。慢请求更容易被取消，而慢往往与臂相关（评审 4）。例外：设置了 `CaptureLogs` 的请求（调试、预览）在任何情况下都不写持久日志（评审 5）。
- **后备流水线只用剩余时间**（设计 5.6）。设计只说“宿主可以选择返回它的结果”；实现统一为自动执行、不带实验、不重新计时，外部分配服务也受同一个截止时间约束（评审 3、4）。
- **计划发布按序号，组装出错整体放弃**（设计 10.3）。后台编译可能乱序完成，较旧的结果不覆盖较新的计划；`fallback_pipeline` 解析失败时主流水线也不发布（评审 3、4）。
- **衍生特征表达式抛异常只让该特征失败**（设计 6.7）。表达式后端对数据错误返回缺失值，抛异常只可能是缺陷；按数据源失败处理，不影响同一请求的其他特征。
- **召回源和模型调用的等待有自己的上界，不依赖客户端响应取消**（设计 4.8、5.6）。原来节点超时只是取消令牌，然后一直等算子返回；不理会取消的模型客户端或召回源会让节点、进而整个请求失去时间上界。现在节点尝试开始时定下绝对截止时刻，`OperatorContext.RetrieveAsync` 和 `InvokeModelAsync` 都经过同一个内部机制 `BoundedCall`：等待在调用自己的 `timeout_ms`、节点截止时刻（取较早者）或调用方取消时结束，用 `WaitAsync(剩余时间, 调用方令牌)`，从不等客户端手里的令牌（理由见“特征拉取”中共用取消源一条：令牌的回调同步执行，一个阻塞就卡住等待）。客户端的结果（返回值、异常或它响应的取消）只在上界之内完成时才采用；谁先到在调用结束时定下一次，之后不再按客户端的状态重新推断。异步返回的调用看等待本身的结果：`WaitAsync` 正常完成，是客户端按时回答；以它自己的 `TimeoutException` 结束，是上界先到（客户端自己抛的 `TimeoutException` 靠对象同一性区分，`WaitAsync` 转交的是客户端抛出的那个对象）；被取消并且调用方已取消，是调用方先到；其余是客户端按时以自己的失败或取消结束。同步返回的调用没有等待，完成时刻就是 `Send` 返回的时刻：这时调用方已取消、截止时刻已过，或者限时的定时器已经取消了客户端的令牌（定时器可能比时钟早一点触发），结果同样不用，按取消、预算用完或调用自己的超时处理。原来异步路径在等待结束后再读 `client.IsCompleted`，上界或调用方已经赢了、客户端恰好在分类之前完成，就被当成按时的成功并录制；同步路径不检查上界，自身超时 10 ms、阻塞到令牌取消才返回的客户端，在节点预算还剩很多时照样算成功（评审 10）。行为变化：同步客户端在节点预算之后才返回，调用现在记为 `timeout`，原来记为 `ok`、再由执行器按晚成功判节点超时，节点结果不变。等不到的调用被放弃，不再取消、也不再等：客户端继续运行，它的令牌一直有效；请求内存一直持有到它真正结束并且调用点记录完毕，`stratarec.io.abandoned` 计一次；召回缓冲区当场关闭，此后读出来是空的，晚到的写入被丢弃，所以算子和录制都读不到被放弃的数据。分类和特征拉取一致：调用方取消算 `cancelled`，不记耗时、不进健康判断；调用自己的超时、节点预算用完、客户端抛 `TimeoutException` 算 `timeout`；其余算 `error`；每次调用只完成、录制一次。调用自己的超时返回失败状态（召回源是 `CandidateSourceStatus.Failed`，模型是 `ModelStatus.Failed`，说明都是 “timed out after N ms”），由算子按失败处理：模型节点因此走后备，原来是抛出取消、以节点超时结束。节点预算用完或调用方取消时抛 `OperationCanceledException`，节点按超时或中止处理。`MultiSourceRecall` 等完所有召回调用（每个都有上界）再抛出，保证每个调用在节点结束前都已记录。1.0 之前的不兼容改动：`InvokeModelAsync` 的 `CancellationToken` 参数换成 `int? timeoutMs`，取消只由节点预算和调用方决定，算子不再自建取消源；新增 `OperatorContext.BudgetRemaining`。代价：每次节点尝试多一个预算对象（约 50 B）；异步返回的调用多一个租约、一个续体和限时等待的定时器；同步返回、与节点共用预算的调用不分配（测试锁定为 0 B）；自身超时短于节点预算的调用，不论同步还是异步，在发出前建一个关联取消源和它的定时器，约 160 B（测试锁定上界 256 B）；被放弃的客户端占用的线程和内存要等它自己结束才释放，框架只计数。接受自身超时的这份固定开销，不做复用：取消源必须在发出之前建好，客户端拿到的令牌才带着自己的超时；推迟到 `Send` 返回之后再建，会改变同步客户端看到的令牌（评审 10）。
- **召回源、模型和特征拉取各有一份等待实现**。`BoundedCall` 管单次调用，`FeatureFetcher` 管一次拉取的几百个分批。考虑过把两者合成 `StrataRec.Core` 里的一个原语，没有做：特征拉取要求一次拉取的所有分批共用一个取消源和一个截止时刻，同步返回的分批在调用点当场完成、不分配（按分批数翻倍的测试锁定为 0 B），分批写的是共用暂存区的视图，分类还有 `partial` 和按数据源的说明。两边真正相同的只是十几行等待和租约代码；要共用就得把这些差异做成参数，改动已经被分配测试锁定的热路径，风险大于收益。两份实现必须守同样的不变量，改一份时对照另一份：（1）等待以绝对截止时刻和调用方令牌为界，不等客户端手里的令牌；谁先到由等待本身的结果决定，不按客户端之后的状态重新推断（`FeatureFetcher` 的异步路径直接用 `WaitAsync` 的结果，符合这一条；它的同步路径还没有检查上界，连接器同步阻塞到拉取截止时刻之后才返回时，值仍会回填，改特征拉取时补上）；（2）每个外部调用从发出前到客户端真正结束、并且调用点记录完毕，持有一次请求内存；（3）客户端拿到的令牌在它结束之前一直有效（取消源按引用计数，最后一份释放时才 Dispose）；（4）调用方取消算 `cancelled`，超时（包括预算用完、`TimeoutException`）算 `timeout`，其余算 `error`；（5）在调用点完成并录制恰好一次；（6）被放弃的调用写入的数据不被读取，录制里也没有；（7）同步返回、不需要自己的取消源的调用不分配。`BoundedCallTests` 逐条测试这些规则；故障注入（等待不受截止时刻约束、在调用点就释放内存、调用点结束时就释放令牌、等待结束后按客户端是否已完成判胜者、同步返回时不查上界、把任何 `TimeoutException` 都当成等待自己的）都会让测试失败。
- **算子在预算用完之后才返回，按超时处理，不论它返回什么**（设计 5.6）。规则只在 `AttemptBudget.RanOut` 一处：调用方没有取消，并且截止时刻已过或预算的定时器已经取消了节点令牌（定时器可能比时钟早一点触发，两者任一即算）。成立时不提交输出，候选表回到尝试之前（见下一条），按 `on_failure` 处理，说明是 “timed out after N ms”。原来只有算子抛出取消才算超时，没看令牌、在预算之后才成功返回的算子照样提交，负载高时请求会拿到超出预算的结果，节点预算就不再是上界。执行器不放弃算子本身，仍然等它返回：算子在请求线程上改候选表和行选择，放弃它就会有两方同时写请求状态。所以 CPU 密集的算子超出预算时，节点照样晚于截止时刻结束，只是结果不用；自定义算子如果自己做 I/O（不经 `RetrieveAsync` / `InvokeModelAsync`），要自己用 `CancellationToken` 或 `BudgetRemaining` 限时，并持有请求内存直到调用结束。代价：原来勉强在预算之后完成的节点现在走后备。
- **失败的节点尝试让候选表回到尝试之前**（设计 4.6、4.8、5.6）。规则只在 `CandidateTable` 一处：执行器在有行效果的节点尝试之前取 `Checkpoint()`，尝试不论以哪种方式失败（抛异常、`Fail`、超时、晚成功、提交时校验失败）都调用 `Rollback`。回滚恢复行选择，并释放尝试期间追加的物理行：物理行数和还能追加的行数都退回去；这些行在每个槽位里都是缺失、未填充；实体索引里不再有它们的键（尝试期间建过的索引清空，下次查找时从第 0 行重建）。原来失败只恢复行选择，追加的行和它们的键都留着：后备 `MultiSourceRecall` 按 `FindRow` 去重，和死行同 id 的候选被当成已有而丢掉；回放跳过录制为超时的主节点，没有死行，同一份录制就回放出不同的结果（主节点追加 7 后超时、后备返回 [7, 11, 22] 时，线上是 11、22，回放是 7、11、22；评审 10）。检查点之前已有的行保持原状，包括被之前已提交的节点过滤掉的行，所以后面的行源仍然不能把过滤掉的 id 召回来。没有改 `FindRow` 的去重：它必须继续认得过滤掉的行，问题在于失败尝试的行本不该还在表里。尝试期间分配的槽位不收回：失败节点的输出不提交，没有人读。被释放的行在每个已分配的槽位里，回滚时清空一次，下次追加时再清空一次（追加时的清空原本就有，防的是池里的旧数据），两处是同一个方法。`RowSelection.Restore` 改为内部方法，表以外只能整体回滚，只恢复行选择的写法编译不过。回滚不能跨过 `Compact`（行号已经变了），跨过时抛异常；`Compact` 只在节点成功之后做。也逐项核对了其余按行的状态：`OutputBindings` 只在成功时提交；特征只在请求线程上、节点尝试之外回填，按键匹配当时存活的行，预取只带着发起时存活的行的键，所以后备追加、复用了物理行的候选拿不到预取的值，要另行拉取（集成测试在预取跨过失败尝试时，与只运行后备的结果逐行逐列比对）；被放弃的召回和模型调用写的是租借的缓冲区，不写表。约束：尝试结束之后不能再有任何东西写候选表的行，因为后备会复用失败尝试释放的行；框架自己的 I/O 边界从不写表，自定义算子如果让后台工作直接写表就会写到后备的行上。
- **行源后备的表容量按主节点和后备中较大的预留**（设计 4.8、5.6）。候选表的容量在请求开始时按各行源节点的行数上限确定；配置了 `fallback:` 的位置，取主节点和这次臂组合下所选后备节点上限中较大的一个。失败的主节点追加的行由回滚收回、后备复用，同一位置留下的只有一方的行。原来失败不撤销追加的行，曾按两者之和预留（提交 4e32cd9，否则主节点配额 1、后备配额 3 时后备只剩 1 行）；有了回滚就不再多预留。
- **`ModelScorer@1` 在加载时检查每个可能用到的模型版本**（设计 6.9）。每个版本：签名里的每个输入都必须在 `inputs` 里有映射，用到的每个输入和输出都必须是 float32、形状 `[-1]`（每行一个值，批维度动态）；否则加载失败，错误指向 `/inputs/<名字>`、`/outputs/<名字>`，缺少输入时指向 `/model`，提示说明打分算子支持什么。原来只核对名字，类型或形状不符、少给输入的版本也能加载，然后每个请求都失败或走后备。签名里有、`inputs` 没给的输入是错误，因为模型签名没有“可选输入”的约定。设计 6.9 的 `[batch, dim]` 输入暂不支持：`ModelScorer` 只按行构建一维张量，需要其他张量的模型用自己的算子调用。规则只在 `ScorerSignature` 一处。
- **`TopK@1` 按精确的排序键比较**（设计 5.7）。原来分数都转成 double 比较，超过 2^53 的不同 int64（例如按 `entity_id` 排序时的大 id）会相等，再按 id 升序平分，于是升序和降序给出同样的顺序。现在 int64、int32 用翻转符号位后的无符号 64 位键，float64、float32 用 IEEE 754 全序键（−0.0 当作 +0.0），降序取反；缺失和 NaN 仍排在最后，平分仍按 `entity_id` 升序，不按行分配。排序键只在 `RowRanking.TryGetSortKey` 一处。`MmrDiversifier` 例外：它对分数做浮点运算（相关性减去相似度惩罚），仍按 float64 读取，超过 2^53 的 int64 分数会丢精度。

## 特征拉取

一次拉取按 `max_batch` 拆成多个分批，每个分批是一次连接器调用。示例请求 5,000 候选时有两百多个分批，原来每个分批约 420 B，占请求分配的四分之三。下面几条让连接器同步返回的分批不再分配（按分批数翻倍的测试锁定为 0 B）。

- **一次拉取的所有分批共用一个暂存区**（设计 4.5、6.5）。分批在连接器线程上并发写入，超时被放弃的分批还可能在请求返回之后继续写，同时别的分批正在被回填读取。所以布局保证任何两个分批都不写同一块内存：定长值、向量、`string` 和 `text` 每个字段一个数组，按拉取内的键序号排列，每个分批只写自己那一段；每个分批的“已写入”位从 64 位字的边界开始，因为两个线程同时写一个字会丢位；列表字段每个分批一个缓冲区，因为列表的数据区会增长、搬移。`string` 先按引用暂存，回填时才做字典编码，因为字典也不能并发写。连接器拿到的 writer 是分批的视图：连接器同步返回后，同一个视图对象接着指向下一个分批；异步返回的调用独占自己的视图，直到连接器真正结束。没有选的做法：每个分批一套缓冲区（原做法：暂存对象、列数组、每字段一个列对象和一个字符串字典，再加每字段一次租借）；在请求内复用分批的暂存对象（被放弃的分批还在写，复用要等它真正结束，省下的只是对象本身，列和字典照样要建）；用原子操作写位图（每写一个值多一条带锁指令）。代价：分批很小时位图有浪费（`max_batch` 为 25 时每 25 个键占一个 64 位字）；写过列表的分批仍各有一个列表缓冲区；连接器不能保留 writer，`IStagedFeatureValues` 也只在 `Record` 调用期间有效；`SetString` 收到 null 直接让这次调用失败，否则要到回填编码时才在请求线程上出错。
- **一次拉取共用一个取消源和一个时间预算**（设计 4.8、5.4）。拉取开始时算一次预算，同时定下拉取的截止时刻（开始时刻加预算）；有分批要发出时，创建一个关联调用方令牌、到预算时取消的取消源，所有分批的连接器拿同一个令牌。原来每个分批一个关联取消源和一个定时器，等待时再建一个定时器。取消源按引用计数：拉取本身持有一份，直到所有分批发出；每个发出的分批持有一份，直到它的连接器真正结束；最后一份释放时才 Dispose，所以不理会取消、迟迟才结束的连接器手里的令牌一直有效。等待连接器不依赖这个取消源：异步返回的调用用 `WaitAsync(剩余时间, 调用方令牌)` 等待，剩余时间是截止时刻减当前时刻，最少为零，所以后发出的分批不会重新拿到完整预算。原因：取消源触发时，注册在上面的回调在触发它的线程上同步、逐个执行；连接器可以注册自己的回调（释放网络资源、等清理锁），其中一个阻塞，挂在同一个令牌上、排在它后面的等待就一直收不到取消，整个 `Ensure` 跟着卡住，源超时和请求截止时间都失去上界（Codex review 8）。分类不变：调用方令牌已取消算 `cancelled`；等待超时（`TimeoutException`），或连接器响应共用令牌抛出取消，算超时，失败文字相同。局限：调用方的取消通过关联令牌同步传到连接器的回调，阻塞的回调仍会拖住调用方自己的 `Cancel()` 调用，框架无法阻止。代价：每个异步返回的调用一个定时器（同步返回的调用不等待，仍然不分配）；后发出的分批实际等待略少于预算，少的是发出前面分批所用的时间（微秒级）。
- **同步完成的调用不分配**（设计 4.8、15）。拉取内部的调用返回 `ValueTask<FetchStatus>`：连接器同步返回时，记录调用、释放请求内存都在调用点当场完成，不建租约，也不建状态机；只有连接器真正异步时才分配等待要用的对象（租约、续体、状态机、限时等待和它的定时器）。内存规则不变：每个仍在运行的外部调用持有一次请求内存，直到连接器结束并且调用点记录完毕，`stratarec.io.abandoned` 仍然是每个仍在运行的调用计一次。没有用 `PoolingAsyncValueTaskMethodBuilder`：没人等待的预取永远不会把池化的状态机还回去。
- **`EntityKeyBatch` 是只读结构体**（1.0 之前的不兼容改动）。每次连接器调用一个批对象，分批多时是可测量的分配。连接器的 `FetchAsync` 仍按值接收（异步方法不能有 `in` 参数），`IFeatureCallHook.Begin` 和 `Replay` 改为 `in`。自定义连接器和钩子要重新编译；拿批对象的引用做键或判断是否同一批的代码不再成立。

## 本地特征表

第一阶段只做了存储引擎（`src/StrataRec.Features/Local/`）：表、写入器、读取 API、更新来源的契约、`snapshot_files@1`，以及测试用的 `memory_updates@1`。绑定、请求读取路径和 `cache` 的语义在第二阶段接入（见本节末条）。

- **单写线程、读取无锁：读者能碰到的东西要么发布后不再改，要么整体替换**（设计 6.6 第 3、4 条）。记录先写进页末尾的空闲区，再用一次 release 写把位置发布到索引槽；索引、页目录和字符串字典增长时复制到新数组、填完整之后再发布引用，旧数组不再写；读者用 acquire 读到位置之后才读键、页和记录，页号或字符串码超出手里的目录或字典时重新加载一次。完整规则写在 `LocalFeatureTable` 的注释里。没有选的做法：读写锁或 seqlock（读者在按行的路径上要重试，写得频繁时读者会被饿死）；每条记录一个对象（几百万个对象都要被垃圾回收器扫描）。x64 是 TSO，普通读写本来就有 acquire/release 语义，`Volatile` 只是不让 JIT 重排，所以压力测试（一个写线程、三个读线程，专用线程、固定工作量，`taskset -c 0,1` 下也通过）在 x64 上证明不了硬件重排类的错误。故障注入改的是程序顺序：先发布位置再写记录、读者不重新加载页目录、索引或字典在复制完成前发布，都能被测试抓到；字典那一项要把不同字符串的数量提高到百万级才稳定复现。CI 没有 ARM64，ARM64 上的内存序没有经过测试。
- **索引是一个键和位置交错的 `long[]`**（设计写的是 `IndexKeys`、`IndexPositions` 两个数组）。一次探测只碰一个缓存行，两个数组要碰两个。位置是 `(页号 + 1) << 32 | 页内偏移`，0 表示空槽，新数组不用初始化。装载率不超过一半；条目从不删除（删除是墓碑记录），读者的探测序列不会断开。int64 键分块查找：先读一块键的初始槽，再完成探测、解析记录，让一块键的缓存未命中同时进行，而不是一个键一个键地等。
- **字符串键用 XXH3-64（种子 0）对 UTF-16 码元求哈希，键和 `text` 都存 UTF-16**。`TextColumn` 存的是 .NET 字符串，查找时直接比较 `ReadOnlySpan<char>`，读写都不用转码。代价：以 ASCII 为主的数据多占一倍空间。哈希相同的键靠记录里的原键区分。
- **记录头带整条记录的长度，变长数据和定长部分在同一页里相邻**。记录是一段自包含的字节，压实时整段复制，只需要把字符串码重新编码。`list<string>` 的元素也存成表内字典的码。
- **字符串字典属于版本，压实时重建**。压实把记录复制到新版本时，字符串码重新编码进新版本的字典，不再使用的字符串随之丢弃。没有选全表共用一个只增不减的字典：高基数的 `string` 字段会让字典无限增长。
- **压实按字节触发，墓碑一直保留到 reload**（设计 6.6 第 4 条）。被替代的记录超过记录总字节数的一半、并且不少于 `CompactionMinBytes`（默认 1 MiB）时压实。按字节而不按条数，是因为变长记录大小不一；有下限是为了不让小表每几次更新就重建一次。压实在写线程上同步进行，期间更新等待，读者不受影响。压实按记录原来的页序复制，每个新页只开到装下剩余记录所需的大小（不超过 `PageSize`），副本实际上不比原表大；按索引槽的顺序复制会把大小不一的记录混在一起，每页末尾空得更多，副本可能比原表还大。墓碑在压实时保留，否则晚到的旧更新会让已删除的键复活；reload 从空表开始，快照就是那个位置上的全集，所以 reload 之后墓碑不再保留。
- **`max_bytes` 计当前版本的页、索引、页目录和字典，按字节精确执行**。每次写入之前，先算出它实际会增加的字节：新页、索引增长，以及记录里字典还没有的每个不同字符串（`string` 字段和 `list<string>` 元素，同一记录里重复的只算一次），再加上加入这些字符串时字典数组和码表经过的每一次扩容。一次写入会超出、又有被替代的记录时，在旁边建一个压实后的副本，不发布，按副本的页和字典重新计算这次写入（只被被替代记录用过的字符串在副本里已经丢掉，对这次写入又成了新字符串）。副本加上这次写入放得下，才换上副本、写入；否则丢弃副本，抛 `LocalTableFullException`，这次加载随之失败。失败的写入不改变表：版本对象、字节数和 generation 都和之前一样，被丢弃的副本不占 generation。原来先发布压实结果再检查，失败的写入也会留下一个新版本（评审 9）。自动压实和显式 `Compact` 用同一个构建过程，副本单独放得下才换上：自动压实发生在写入成功之后，放不下就静默放弃，被替代的字节翻倍之前不再尝试，免得每次写入都白建一个副本；显式 `Compact` 放不下就抛 `LocalTableFullException`。副本实际上不比原表大（见上条），这两处检查在测试里走不到，留着守住不变式。副本的最后一页正好装满，之后的第一次写入要开新页（`PageSize` 和 4 KB 中较小的那个）：表离上限不到一页、又没有被替代的记录时，写入会一直失败，直到调大 `max_bytes`。没有在接近上限时把新页缩到只装得下这条记录：上限通常比页大几个数量级，省下的不到一页。原来按每个字符串值估一个上限、字典只算一次扩容：同一个字符串重复写入会被多算而误拒，一条记录带来大量新字符串时又会少算而超限。空表本身（按 `InitialCapacity` 建的索引、页目录、字典）已经超过 `max_bytes` 时，建表就失败并提示调大 `max_bytes` 或调小初始容量。压实和 reload 期间新旧两个版本同时存在，进程短时间需要大约两倍的内存，`max_bytes` 不算这一部分。`cache` 的记录头里的版本就是写入时间，按写入时间淘汰是第二阶段的事，入口是 `Compact(dropWrittenBefore)`。第二阶段要保证：一次未命中拉取写回的记录，版本取拉取发起的时刻，不取完成的时刻。按版本覆盖只保证版本大的留下；版本取完成时刻时，一个发起得早、返回得慢的拉取会盖掉较新的拉取结果。
- **读取是一次查找加按块填充**（设计 6.6“读取路径”）。`Lookup` 为每个键给出一个记录引用，同一张表的所有特征共用；多字段 `Fill` 把行按 128 行分块，先把每块记录要用到的缓存行都读一遍，让未命中同时进行，再逐个字段填这一块，记录在 L1 里被所有字段复用。按行的循环不做边界检查，安全靠每次调用开头的一次检查，检查的是副本：行、记录引用和读取说明先复制进从 `ArrayPool` 租来的数组，检查副本，循环只读副本。只检查调用方的 span 不够：行可以就是某个目标列自己的数组，写进第一个值就改了还没用到的行，下一行就落到列外（评审 9 的例子）；行也可以和非有限值计数重叠，或者在检查之后被别的线程改写。复制的代价在 500 行时每次调用约 1 μs，约占 30 个特征热缓存填充的 3%。缺失时填缺失的列在循环开始前就建好有效位图，即使最后没有缺失的行：循环里只要有一次调用，JIT 就把循环的状态放到栈上。填充位由调用方处理：每一行的每个字段都会被填，同一张行位图 OR 进每个槽位即可。`float32`/`float64` 的 NaN 和 ±∞ 原样存储，读取时按缺失处理并计数，向量分量原样返回，与暂存区回填（设计 4.3）一致。`text` 读取时要新建字符串，等文本列改存 UTF-8 之后才能不分配（设计 4.4）。
- **读取测量没有达到设计估计的 20 μs**。`LocalFeatureTableBenchmarks`：100 万条记录、每条 30 个特征（25 个 `float32`、2 个 `int64`、1 个 `bool`、1 个 `string`、1 个 64 维向量，约 400 B），一成的键不在表中，0 B 分配。在开发机（Xeon 6975P-C，KVM 虚拟机，.NET 8）上：同一组键反复读（数据都在缓存里）500 键 34 μs、5,000 键 490–505 μs；每次换一组随机键 500 键 51 μs、5,000 键 830–860 μs，其中查找本身 10 μs 和 120 μs。每个字段单独调用一次 `Fill` 时，500 键慢一倍多，5,000 键慢两倍（每个字段都把全部记录再走一遍，还要各复制一次行和记录引用）。热缓存时一个 `float32` 值约 1.5 ns，按列的循环每个值二十来条指令，已经到了这种做法的下限；换键之后多出来的部分主要是 TLB 未命中：4 KB 页随机访问 400 MB，虚拟机里还要走两级页表。要再快，可以试大页（.NET 的 GC 堆默认不用透明大页），或者为连续的同类型字段写按行读取的内核，等接入请求路径、有真实的特征组合之后再决定。
- **快照是 JSON Lines 数据文件加一个 manifest**（`snapshot_files@1`）。设计提到 Arrow 等列式格式；第一阶段选 JSON Lines：标准格式、能手写，错误能指到“文件:行”和 JSON 指针，也不引入 Arrow 依赖。快照覆盖的更新流位置写在 manifest（`snapshot.json` 的 `position`）里，不写在数据文件头：数据文件可以由多个任务并行写，最后写入 manifest（先写临时文件再 rename），读者不会看到半个快照。每次加载都是一次 reload：在读者看不到的新版本里构建，完整之后整体替换；失败就放弃新版本，读者继续用旧的。manifest 内容没变就不重新加载；第一次运行时，如果表的位置已经等于 manifest 的位置也跳过（从本地磁盘恢复之后接着跑）。`reload` 写 ISO 8601 时长（`PT1H`），设计里写的是 `1h`：配置只用标准语法。超出 `float32` 范围的数读成 ±∞，与 `memory@1` 一致（两者都用 System.Text.Json），之后按非有限值处理。加载吞吐（`LocalFeatureTableLoadBenchmarks`，10 万条上面那样的记录，每行约 1 KB）：经 `RecordBuilder` 直接写约 240 万条/秒，解析 JSON Lines 约 20 万条/秒，`RecordBuilder` 只占其中不到十分之一，其余是 JSON 解码（每行约 90 个数）。一行先写 `key` 和 `version` 时字段只扫描一遍，否则先跳过 `fields`、读完整行之后再解码它。
- **写入器的接口比设计多了几样**（设计 6.6 末尾的 `IFeatureTableWriter`）。`Begin` 和 `Delete` 另有 int64 键和 `ReadOnlySpan<char>` 键的重载，解码器不用为每条消息建 `EntityKey` 或字符串。`RecordBuilder` 是值类型句柄，要显式 `Commit`：解码到一半出错的消息不提交就是放弃，下一次 `Begin` 会丢弃它。`Delete` 返回是否因版本过旧被忽略。`BeginReload`、`CompleteReload`、`AbortReload` 对应设计中“建好新版本后整体替换”；reload 期间不能 `Checkpoint`，位置只随完整的 reload 前进。
- **交叉特征（cross 实体）不能放进本地表**。`LocalTableSchema.FromCatalog` 直接拒绝并提示用 `fetch`：交叉特征的键空间没有上限，正是设计表中 `fetch` 适用的情形。
- **第二阶段的接入方式**。（1）绑定解析：`mode`、`ttl_ms`、`stale_if_error_ms`、`max_bytes` 和 `bootstrap`/`updates` 的来源设置，变成 `LocalTableSchema.FromCatalog`、`LocalFeatureTableOptions` 和按来源类型注册的 `IFeatureUpdateSourceFactory`（与连接器工厂的注册方式相同）。表的布局在建表时就固定了，绑定的特征集合在新计划中变化时，建新表并重新加载，不迁移旧表。（2）宿主为每个 `local` 绑定建表，在后台运行 `RunAsync(table.Position, table.Writer, …)`，失败后从 `Position` 重新运行；所有 `local` 表完成首次加载并追上 `max_lag_ms` 之后才报告就绪；加载因 `max_bytes` 失败时按数据源不可用处理。（3）读取路径：`FeatureFetcher` 不为 `local` 数据源发拉取；请求为每张表 `Pin` 一次，节点开始前对存活行做一次 `Lookup` 和一次多字段 `Fill`，把行位图 OR 进各槽位的填充位，非有限值计数并入现有指标；不经过暂存区，也不受拉取屏障约束。（4）`cache`：命中且未过期的键直接填充；未命中、过期的键合并成一次 `fetch`，回填之后交给后台写线程（有界队列，满了就丢弃），以拉取发起的时刻为版本写入（理由见 `max_bytes` 那一条末尾）；远程确认没有值的键写一条全部缺失的记录；TTL 按键的哈希浮动 ±10%；`stale_if_error_ms` 读过期记录；容量超出时用 `Compact(dropWrittenBefore)` 丢弃过期记录，再按写入时间丢弃最早的记录。（5）随后是指标和事件日志（表大小、压实、加载耗时、更新延迟、命中率）、回放包里本地读取的记录（按键记下读到的值，回放时不读表）、Kafka 来源和节点本地磁盘快照。

## 日志

- **没有消费者时不采样、不捕获**。没有日志管道且请求没有 `CaptureLogs` 时，所有批次都会被丢弃，白白消耗 CPU 和内存。
- **漏斗组的 key 只能读请求输入，且必须是标量**（设计 8.2）。组决定在请求开始时做出；key 若要等一次拉取，每个请求都会在召回之前阻塞在日志采样上（评审 4、5）。
- **探针对上下文特征同样是被动的**（设计 8.5）。只被探针读取的上下文特征不进入预取，否则每个请求都多一次拉取，无论是否被采样（评审 4）。
- **durable 投递以返回值和钩子表达，不内置磁盘缓冲**（设计 8.6）。`Submit` 返回 Queued/Spilled/Dropped/Closed；内存队列满时调用 `DurableOverflow` 钩子，由宿主决定是否落盘；sink 用 `LogBatchRejectedException` 声明永久不可写的批次，避免一个坏批次堵住整个 durable 流（评审 4）。`DisposeAsync` 的等待有上限，不依赖 sink 配合取消（评审 5）；到时还没写出的批次计为丢弃（评审 6）。
- **非有限向量记为缺失**。一个分量是 NaN 的向量整体记为缺失，部分向量对训练没有意义。
- **不做个人数据过滤**（设计 8.9）。推荐需要这些数据，内部记录和调试查看是正常用法；不暴露给外部系统由运行环境和数据权限负责。曾经实现过敏感级别、`purpose` 声明和缓冲区清零，已按此决定全部移除。

## 表达式

- **哈希的规范编码**（设计 5.7）。`float64` 中 −0.0 按 0.0、所有 NaN 按 `0x7FF8000000000000` 编码。IEEE 754 不规定定义域错误产生的 NaN 的符号和载荷，优化器和 SIMD 重写都可能改变它，`hash01` 结果不能随之变化。离线复算哈希也要这样规范化（评审 4）。
- **`hash01` 有两份编码实现**。表达式后端用栈上缓冲区写编码，标量路径不经过数组池；与 `StableHash.Builder` 的一致性由测试锁定。
- **int32 越界的派生特征，不可空又没有默认值时整个特征失败**（设计 4.3、4.6；评审 6）。和节点输出、非有限值是同一条规则：不可空的列装不下替换出来的“缺失”，读取方按不可空编译、不检查有效位。没有选择让类型推断因为“可能越界”而变成可空：那样所有 int32 派生特征的读取方都得写 `??`，而越界在实践中很少见。失败的特征对所有读取方都一样：节点按 `on_failure` 处理；输出读到它时请求失败（之后由后备流水线兜底）；探针不让请求失败，读到它的列记为缺失，过滤条件视为 false。
- **`lookup(table, key, default)` 在 key 缺失时返回 `default`**（设计 7.4 的例外）。第三个参数本身就是调用方给出的缺失处理；改成缺失会让现有打分表达式变成可空类型而无法编译。

## 可观测性

指标名称、单位和标签写在 `StrataRecMetrics`（`src/StrataRec.Core/Diagnostics`）的文档注释里，这里只记取舍。

- **显式引用 System.Diagnostics.DiagnosticSource 10.x**（设计 13.1）。net8 自带的 8.0 版没有 `InstrumentAdvice` 和同步的 `Gauge<T>`；`Microsoft.Extensions.Logging.Abstractions` 10.x 在 net8 上本来就依赖同一版本，所以 Core 显式引用不会给部署增加任何程序集。建议边界：耗时按 √2 递增（0.1 ms 到约 13 s，35 个边界，每桶宽约 41%），行数、键数、字节数按 2 递增。导出为指数直方图时宿主会忽略这些建议。
- **请求级指标和请求 span 由 `RecEngine` 记录**。一次请求就是一次 `IRecEngine.ExecuteAsync`，包含分配、主流水线和后备流水线：由后备流水线返回的结果计为降级，不计为错误（设计 5.6）；被调用方取消的请求计为错误，因为慢请求更容易被取消，而慢往往与臂相关。直接调用 `PipelineExecutor` 只得到节点、数据源、模型、列和内存指标。
- **执行器不自己补建请求 span**。它只在当前 span 是已记录的 StrataRec span 时创建节点和 I/O 子 span。如果 `RecEngine` 的 span 被采样掉之后执行器再试一次，对根请求来说每次都会生成新的 trace id，按 trace id 采样的采样器第二次可能放行，等于把采样率翻倍。直接用执行器的宿主可以用 `StrataRecTracing.StartRequest` 包住调用。
- **按臂的请求指标用单独的名字**（`stratarec.arm.request.*`）。一个请求在每个分配到臂的层各记一次；如果和请求级指标同名、只靠 `arm` 标签区分，按流水线求和就会把多层请求重复计算。
- **标签键都带 `stratarec.` 前缀**。采集链路会自己加标签（例如 Kubernetes 的 `node`），短名字会冲突。
- **数据源健康按窗口判断**（设计 13.2）。一个窗口（10 秒）内至少一半调用失败就判为失败，判断翻转时才写一条日志；没有调用的窗口不改变判断。按连续失败次数判断在低流量下会来回翻转。部分成功（`partial`）算健康。
- **汇总日志由定时器刷新，定时器只弱引用日志对象**。被丢弃的执行器不会被自己的定时器留住；窗口内最后的计数在进程退出时可能丢失，精确计数看指标。
- **日志 sink 失败按状态变化记录**：开始失败时写一条（带异常），恢复时写一条（带失败次数）。宿主钩子（`DurableOverflow`、`Rejected`）抛异常和被 sink 永久拒绝的批次按窗口汇总。
- **调用方取消不算依赖超时**。外部调用（特征源、召回源、模型）被调用方取消时，不记耗时、不记错误、不进健康判断，否则客户端断开会被当成依赖变慢。算子拿到的节点令牌同时受节点预算控制，分不清两者，所以请求状态另外保留调用方的令牌。请求本身仍计为错误（见上）。
- **越界计数只按流水线记录**（`stratarec.column.out_of_range`；设计 13.1 写的是 `{node,column}`）。int32 窄化发生在表达式后端和上下文特征写入处，计入每请求共享的计数器，那里不知道列；按列归属要在每个写入点传标签。int32 列通常很少，按流水线报警之后再查具体列。
- **被调用方中止的节点记为 `aborted`**，耗时和行数照记（评审 6）。否则节点延迟分布恰好漏掉调用方等不及而放弃的慢尝试。
- **每请求多约 60 B**。为了携带事件日志、span、调用方令牌和当前位置的状态，请求状态和特征拉取器多了几个字段。记录指标本身不分配：挂上 `MeterListener` 时和不挂时分配的字节数相同；被采样掉的请求多一个未记录的 `Activity`（约 0.4 KB）；被记录的请求为每个节点和每次外部调用各建一个 span。

## 回放

回放包的结构见 `stratarec schema replay_bundle`（`src/StrataRec.Artifacts/Model/ReplayBundle.cs`），这里只记取舍。

- **回放包的布局一变就升格式版本，读取时先看版本再解析结构**。不在同一个版本号下原地修改布局，哪怕那个版本只在主干上出现过：已经录下的包无从分辨自己是哪种布局。读取器只读当前版本；其他版本在 `/format` 处拒绝并提示用当前构建重新录制，不把旧布局当作当前版本的结构错误报告。没有选择兼容读取旧版本：回放包是调试用的短期产物，重新录制的代价小于维护多套读取逻辑。

- **在框架的调用点录制和回放，不在连接器里**（设计 13.4）。特征拉取由 `FeatureFetcher` 的调用点经 `IFeatureCallHook` 录制（读连接器解码后的暂存缓冲区，按键记录值），召回源和模型调用经 `OperatorContext.RetrieveAsync` / `InvokeModelAsync`。宿主注册的连接器、模型客户端和算子不用实现任何东西就能录制和回放。没有选择包装 `IFeatureSourceConnector` / `IModelClient`：包装层看不到超时、跳过等执行决定，回放时也要重写按键匹配。代价：自定义算子如果绕过这两个方法直接调用客户端，不会被录制，回放时会真的调用外部服务。
- **录制按请求开启，关闭时只多几个字段**。`DebugOptions.Record` / `PipelineRequest.Record` 默认关闭；关闭时每次外部调用多一次空检查，每请求多约 40 B（请求状态和拉取器上的字段），不做任何按行的工作。开启时分配与请求拉取的数据量成正比，示例请求约 95 KB、多约 0.4 ms，不适合全量常开；按比例常开录制以后再做。
- **计时决定取自录制，回放不计时**（设计 13.4、10.8）。回放的截止时间是 1 小时，不设节点超时：节点的 `min_remaining_ms` 比较用录制时该节点的剩余时间，每次尝试按录制的结果（`ran`、`deadline_exceeded`、`timed_out`）处理，外部调用按录制的状态返回。没有用录制的耗时驱动虚拟时钟：配置一改，调用的顺序和并发就变了，模拟出来的决定在线上从未发生过。代价：修改后的配置里新增的节点没有录制的时间，视为时间充足，永远不会因时间被跳过或超时。
- **数据先按调用精确匹配，再按值合成**。同一数据源、同样的键和顺序、并且包含全部所需字段的调用原样重放，包括超时和失败。只覆盖部分字段的调用不算精确匹配：否则其余字段会被报成缺口，而录制里别的调用其实取到过它们。配置改变了键、字段或分批时，按（数据源、实体、键、字段）从录制中成功的调用取值；取不到的值是缺失，并按原因计入缺口报告（`not_recorded`、`type_changed`、`limit_exceeds_recording`、`inputs_changed`）。录制的值换成新类型时有损（例如超出 float32 范围）也算 `type_changed`，精确匹配和合成用同一条规则，不让溢出变成 ±∞ 混进结果。合成的调用状态是 `ok`：录制中超时的分批不会映射到新的分批上，那些键的值只是缺失。失败调用的数据从不使用。召回源按节点匹配：节点重放并占用自己录制的调用；录制里没有调用的节点（例如配置新加的）复制该数据源返回过的最长列表，不占用任何调用，所以节点的执行顺序变了也不会抢走别的节点的录制；要的数量超过录制、而录制当时已到上限时，报 `limit_exceeds_recording`。
- **模型输出按实体和输入摘要匹配**。每行输出按实体 id 和该行全部输入的 XXH3 摘要记录，只在输入没变时使用；输入变了算缺口（`inputs_changed`），输出缺失。没有选择忽略输入直接复用：那会在特征改动后静默地显示旧分数。哪些输入按行切分只看张量约定：首维等于 `batch_size` 的输入每行取自己的切片，其余输入（共享的用户向量、文本）整体计入每一行的摘要，不按长度能否整除来猜。摘要包含每个输入的元素类型和形状，按行切分的输入不计批维度，所以换一种分批仍然匹配，而同样的数值换一种形状不会。同一实体可能以不同输入被打分多次，合成时按（实体、摘要）查找。回放也不调用模型客户端（设计 5.9、10.8）。因此修改模型绑定（例如线性模型的权重）不改变回放结果；评估模型本身的改动要用实时模式或草稿预览。
- **回放抛出录制时的异常类型**。模型客户端抛出的异常连同类型身份录制（`error_type`）。回放时 `TimeoutException` 仍是 `TimeoutException`，取消仍是 `OperationCanceledException`；其他类型如果回放进程已经加载、派生自 `Exception` 并有 `(string message)` 构造函数，就用录制的消息重新创建，否则抛出带原类型名的 `ReplayedCallException`。这样经 `InvokeModelAsync` 处理特定客户端异常的算子在回放时走同一条路，节点失败的说明也不变。没有选择统一成一种回放异常：那会改变按约定使用调用接口的算子的控制流。代价：需要更多构造参数的类型、回放进程没有加载的类型，算子看到的是 `ReplayedCallException`。
- **异常类型按身份查找，只在已加载的程序集里找**。身份是类型（封闭泛型取泛型定义）的完整名、定义它的程序集的简单名，以及各类型参数的身份。回放只看已加载、简单名相同的程序集，在它们定义的类型里找完整名相同的那一个；泛型的定义和每个参数分别这样找，再组合。没有选择只记完整名：两个程序集可以定义同名类型，按名字挑第一个会让算子接住另一种异常。也没有选择交给 `Type.GetType` / `Assembly.GetType` 解析：它们会跟随类型转发、加载新的程序集，回放包不应该让回放进程加载代码。找不到或找到不止一个（同名程序集加载了两次）都不猜，回退到 `ReplayedCallException`。`TimeoutException` 和 `OperationCanceledException` 也按身份判断，只有核心库的这两个类型才走超时、取消的路径；别的程序集里的同名类型是它自己。代价：数组等构造类型作为类型参数时回退；枚举一个程序集的类型时，运行时可能为解析基类型加载它的依赖。
- **回放用录制的臂，不重新分流**。分流配置变了，同一请求在线上会进入别的臂，但回放要比较的是同一处理下配置的差别。`--arms` 可以指定别的臂；回放计划里没有的臂和请求输入会被去掉，并写进报告的说明。
- **回放不是流量**。回放不记指标、事件日志和 span，不写持久日志（探针捕获到结果里）。否则回放录制下来的失败（例如特征源报错）会把一个健康的依赖判为失败，CI 的批量回放也会混进延迟分布。没有选择加 `replay` 标签区分：所有看板和告警都得过滤它。录制则不改变任何观测：被录制的请求照常计入。
- **后备流水线是包里单独的一次运行**（`role: fallback_pipeline`）。回放时主流水线失败，就用这份录制回放后备流水线；录制中主流水线失败却没有运行后备流水线（时间已用完，设计 5.6），回放也不运行。
- **中止的请求也交付回放包，内容是中止那一刻的快照**。被调用方取消或因缺陷中止的请求没有结果，`RecResult.Recording` 带不出回放包，所以录制经回调交付：`DebugOptions.OnRecording` 收到整个请求的回放包，`PipelineRequest.OnRecording` 收到一次运行的录制。返回和中止都会调用回调；回调抛出的异常只记日志，不改变请求的结果，取消照常传给调用方。中止时立即构建录制，不等任何调用。召回源和模型调用的等待在调用方取消时就结束，调用点把它记为 `cancelled`，这正是请求看到的；快照时调用点还没有记录的调用（例如算子发出后没有等待的调用）记为 `outstanding`，它的键和模型输入摘要在调用开始时就已记下；之后才完成的调用的数据不在包里。回放中止的包时，引擎复现录制里每个已完成位置的决定，在录制没有完成的第一个位置停下（录制中正在执行的节点再记一次 `aborted`），报告这次运行被中止，不给出结果。两边都中止的对比算相同；对比报告里中止计入错误率，和线上指标一致。没有选择等在途调用完成再交付：不理会取消的连接器会让取消迟迟到不了调用方。也没有选择把录制挂在异常上（`Exception.Data` 或专用异常类型）：调用方得改写 catch 才拿得到，取消的异常类型也会变。代价：快照之后才返回的数据丢了，修改后的配置如果用到这些调用，回放按取消处理；在分流阶段就中止的请求还没有运行流水线，没有回放包。
- **被放弃的调用按请求看到的录制**。超时被放弃的召回源和模型调用记为 `timeout`，不带数据（召回源不记返回的 id，模型不记输出），因为请求没有用到它们；客户端之后才返回的东西不进入录制。节点按超时结束、晚到的成功被丢弃时，调用本身照实记为 `ok`，节点尝试记为 `timed_out`，回放按尝试的结果处理，不使用这次调用的输出。回放时这些调用直接按录制的结果返回，不等待。
- **中止位置的实验触发按录制恢复**。中止时正在执行的位置可能已经触发了实验：到达了站点、节点读了臂改过的参数、走了后备。这次曝光已经发生，计入了实验记录。回放在这个位置停下，不重新执行它，因为执行到一半的位置无法复现。所以录制在中止的节点上记下这个位置从开始到中止新触发的实验（`triggered`，只出现在中止的节点上），回放停在这里时按 id 恢复，只恢复回放计划里存在、并且在回放的臂下已分配的实验。这样相同配置上回放的触发集合与录制完全相同。没有选择回放时给中止节点补记它的全部参数触发：取消可能发生在节点读参数之前（例如还在拉特征），那会多出没有发生过的曝光。代价：修改后的配置即使改了这个位置的触发条件，回放也只恢复录制的事实；录制的请求在每个位置开始时多复制一份触发状态，不录制时没有这份开销。
- **值编码复用日志编码，类型写在值旁边，但保留非有限值**。`null` 是缺失；NaN 和 ±∞（包括向量的分量）写成字符串 `"NaN"`、`"Infinity"`、`"-Infinity"`，日志里仍然写成 `null`。回放包必须如实保留请求看到的值：并不是每条路径都会先把非有限值换成缺失或默认值（设计 4.6），暂存的原始向量和直接求值的输出表达式就不会，按缺失录制会让回放走另一条路（`has()` 变成假、结果出现差异）。两者共用同一个编码器，回放包只是打开一个选项，没有另写一套。每个值按旁边记录的类型解码，类型不兼容时报出 JSON 指针。
- **对比指标的定义**（设计 10.8）。Top-K 重合度 = 交集 / 两个 Top-K 中较长者，短列表不会抬高重合度；Kendall τ 只在两边共有的条目上计算，少于两个时为空；分数分布变化用双样本 KS 统计量，另给同一条目的分数差；两者都只用有限的分数，NaN 和 ±∞ 按每一边单独计数报告：它们没有位置可排，混进去会让 KS 失去意义，NaN 还会让排序比较不再自洽。降级率的分母是全部请求，分子只算成功但降级服务的请求；失败的请求只算错误，不算降级。特征缺失率包括数据源本身缺失和回放包里没有的值。录制模式下外部 I/O 立即返回，延迟只反映引擎计算，不能用来评估依赖延迟。配置增删的输出列在差异中单独列出，不逐条重复。
- **`replay` 和 `compare` 只有用上了每个包才算通过**。没有包、包全部读不出来、或者一个都没比较成，以 2 退出；部分包读不出来也以 2 退出，但照常输出报告，JSON 里带 `status`（`ok`、`partial`、`failed`）和读不出来的包数。CI 用退出码判断对比是否通过，只覆盖一部分包（或一个都没覆盖）的指标不能当作干净的结果放行。没有选择部分成功时返回 0 只在报告里标出：CI 步骤通常只看退出码。

## 工程

- **最低 SDK 是 .NET 8，CI 只用 Linux**。CI 分别在固定的 SDK 8 和 SDK 10 上构建测试。banned-API 分析器用 3.3.4：5.x 依赖 Roslyn 4.12，在 SDK 8 的编译器（4.11）上报 CS9057（评审 5）。
- **内存分配预算是估算**（设计 15）。“每请求 ≤ 2 KB”不是硬指标，允许一定偏差。当前示例流水线（`PipelineBenchmarks.Baseline`）每请求：5,000 候选约 36 KB，500 候选约 20 KB，只有 Gen0（原来分别约 227 KB 和 45 KB）。按键和按分批的工作都不再分配，连接器同步返回的分批是 0 B（原来约 420 B，见“特征拉取”）。5,000 候选时其中约 17 KB 是 `memory@1` 解码字符串：`JsonElement.GetString` 为每个值新建一个字符串，约 500 行读到 `item.category`；这属于第 15 节单独计量的字符串解码，引擎这边的字符串可以忽略。其余约 18–19 KB 与候选数无关，按 500 候选的抽样：返回给宿主的结果约 4.5 KB（第 15 节不计）；节点预算和拉取的取消源、定时器约 2.5 KB；每次拉取的对象（键索引、暂存区、待完成记录、字段子集）约 0.5 KB，示例请求约 6 次；候选表、表中字符串列的字典、请求状态和节点上下文约 6 KB；算子、模型和召回调用约 1.2 KB。
- **暂不做请求状态池**（设计 4.8 表中第二行）。能放进池的部分（`RequestState`、`CandidateTable`、`RowSelection`、`OutputBindings`、`FeatureFetcher`、表中字符串列的字典、节点上下文）合计约 6 KB，约占剩余分配的三分之一。池化要为每个对象写重置逻辑，漏掉一处就会把上一个请求的数据带进下一个请求；请求返回后，被放弃的 I/O 还持有请求内存，状态只能在最后一次 `Release` 时归还，可能在连接器线程上。每请求 20–40 KB 的 Gen0 分配在每秒数千请求时是每秒几十到一百多 MB，Gen0 回收的成本与存活对象成正比，而回收时这些对象大多已经死亡。更划算的是先做局部的：节点预算复用一个取消源（`TryReset`），按计划缓存拉取的字段子集，表中字符串列的字典按计划预设容量。压测显示 GC 暂停或分配速率与请求状态有关时再做。
- **确定性的范围**（设计 5.7）。计划、请求输入、时间、外部响应和执行决定（超时、跳过、后备）都相同时，排序结果、分数、选中的变体和采样决定相同。耗时、`seq`、producer id 等运行元数据不在保证内，回放对比时要排除。

## 范围调整

框架的核心目标是：整体性能好、整体分配低、用户体验好、容易调试、开发和测试。`design.md` 是起点，不是约束；一项设计带来的复杂度超过它对这个目标的贡献时，就简化、推迟或不做。

- **父子层级表（偏移数组嵌套）不做；组按它和成员的关系分两种情况**（设计 4.7）。嵌套表的难点（父表过滤后子表怎么办、子表截断后父表的汇总值过期、表达式怎么区分两张表的列）会散落在执行器、拉取、后备恢复、日志和回放里，一致性只能靠两张表一起改；物品在组之间移动（混排、广告插进某一行）还要重建偏移数组。
  - **组由成员决定**（按商家分组的搜索结果）：一张表，组键是外键实体（例如 `col.item.merchant_id`），组的特征照常按键去重拉取；组的得分和组内名次由分组聚合算出、回填到组内每一行（`sum`、`mean`、`max`、`top_k_mean`、`logsumexp`），每组保留前几项用组内名次加过滤；分组展示由宿主按组键排列结果。分组聚合算子有实际需求时再加。
  - **组先于成员存在**（多行首页：先提名候选行、用行级模型过滤，再按每一行自己的召回源和数量取内容；物品可以出现在多行里；版面规则作用在行上）：框架现在不原生支持，由使用方组合实现，例如宿主先调用排行的流水线，再把选中的行作为请求输入交给排物品的流水线，或者写自定义的行源算子。已知代价：实验按流水线定义，同时改行和物品的实验要拆成两个实验，并让它们共用同一个分流。
  - **将来原生支持时的方向：一个请求几张扁平表，用键列关联，不嵌套。** 子表声明父表，子表的一行由（父键, `entity_id`）标识；节点只写一张目标表，可以读其他表，父表的列按请求内的外键实体读取（父行已淘汰时读到缺失）；跨表汇总用分组聚合；父行淘汰时子行不级联删除，输出时按父表顺序 join，孤儿行不出现，要省掉后续拉取就显式过滤。现在的格式都能按增量扩展（节点加可选的 `table`，缺省就是唯一的表；日志的行标识加表名；回放包有版本号；结果加可选的分组结构），所以不提前定格式。等组合方案的代价（拆实验、宿主胶水）在真实业务里显现时再做。
- **`fetch_missing` 不做**（设计 8.5）。这是响应之后的后台拉取：探针缓冲区和请求内存要活过请求本身，拉取还要有自己的超时、并发上限和失败计数，而它只满足“离线训练要的特征比线上用的多”这一种需求。训练用的额外特征，可以离线按键和时间点关联，或者加进线上的拉取。
- **本地磁盘缓冲不在框架里做**（设计 8.6）。落盘和重启后补发取决于部署环境（磁盘、容器生命周期），由宿主通过 `DurableOverflow` 钩子实现。
- **不统计每个探针的字节数和池中保留的字节数**（设计 13.1）。前者要在 sink 序列化之前估算字节数，后者要池暴露内部状态，调试价值抵不上成本。
- **草稿预览、实时回放推后**（设计 10.7、10.8）。两者都依赖控制面；本地已经可以用 CLI 运行工作区、录制和回放请求。
