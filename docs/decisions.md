# 决策记录

`design.md` 描述整体设计。本文只记录实现过程中做出的、读代码看不出来的决定和理由：对设计的调整、取舍，以及刻意没有做的事。两者冲突时以本文和代码为准。括号中的“评审 N”指 Codex 第 N 轮评审发现的问题。

## 实验与计划编译

- **组合校验超限是错误，不是警告**（设计 11.5、12.3）。组合空间不超过 `MaxCombinationsChecked`（4096）时全量枚举。超过时按作用域枚举：数据流的每条规则只取决于少数节点和探针（`PlanBuilder.DataFlowScopes`：一列的产出者、读取方和行源，同一 `order` 上的两个节点，节点和它的后备，探针和它读取的列、特征、固定版本），逐个枚举能改变这些节点和探针的层的组合，与全量枚举一样完整；某个作用域自己超过上限时报 `COMBINATION_CHECK_LIMIT`（说明规则对象、涉及的层和组合数），计划不发布。设计假设涉及的层很少，但层数一多组合会指数增长；只给警告就等于在没有证明安全的情况下发布（评审 3）。原来超限后只按列检查非可空列有没有产出者，可空列整个跳过：只在三个桶同时生效时才出现的第二个产出者没有被检查，默认上限下就能发布并运行（评审 18）。可空只豁免“读取方需要产出者”这一条。约束：新增数据流规则必须在 `DataFlowScopes` 里给出它的作用域，否则超限时三层及以上的组合不检查它。成本边界：上限约束的是全空间和单个作用域，不是一次编译的总工作量；同样的层集合和组合只检查一次，作用域枚举的部分最多是（不同作用域的层集合数）×上限。此外，超限时基线、每个单臂和跨层的每对臂总是先检查，与作用域无关，这部分随臂数平方增长：100 个独立层各一个臂是 1 + 100 + C(100,2) = 5051 次（评审 22）。Codex 测过的最坏配置是 13 个互相重叠、各 4096 种组合的作用域：8191 次检查，182 ms，162 MiB（评审 20）。不设总量上限：编译不在请求路径上，硬上限会把慢但正确的编译变成难以处理的拒绝；成了问题时先让每次检查更便宜。单个节点的组合数先判断再相乘，超出就饱和，报 `NODE_TOO_MANY_COMBINATIONS`；原来先乘后截断，层多、桶多时溢出，绕过上限并抛 `OverflowException`（评审 18）。
- **schema 段始终只增**（设计 11.4）。`columns`、`param_schema`、`features`、`derived_features`、`funnel_groups` 无论 policy 怎么写，实验都只能新增。实验修改或删除基线 schema，会让其他实验和基线的类型检查失效。
- **基线必须能单独编译**（设计 11.5）。实验新增的特征或列不能“修好”基线中的引用，否则实验下线后基线就坏了（评审 3）。只要有实验，就把裸基线单独编译一遍（不建计划）。原来只在实验新增 schema 条目或参数叶子时才编，漏了实验新增的节点隐式声明的列：统一 schema 里有它，基线读它（可空，`??` 给默认值）照样通过；撤销不重新编译，发布出去的计划没有节点能加载，节点继续服务带着这个实验的旧计划（外部评审 P1）。不再列举实验声明名字的方式，代价是每次编译多编一遍基线。统一计划的检查已经在同一处报过同一个错误时（组合检查说得更具体），不再重复。
- **校验假定不同层的臂都可能同时生效**（设计 11.1、11.5）。原来不同域的臂组合直接跳过（评审 3）；分配交给实验平台之后没有域了（见“范围调整”），所有跨层的组合都要校验。
- **统一计划接受的组合，必须和单独编译这个组合时完全一致**（设计 11.5、11.6）。原来有几项检查在最终 `Build` 里对所有变体取并集：固定版本引用（`col.x@node`）只要任何一个变体是行源就报 `VERSION_REF_ROW_SOURCE`，互斥的合法臂被误拒；被固定的节点只在三个桶同时生效时不再写这一列，单独编译会拒绝，统一计划却接受了（评审 20）。现在固定版本在每个组合里判断：被固定的节点要在这个组合里存在并写这一列（否则 `VERSION_REF_UNKNOWN`），不能是行源（`VERSION_REF_ROW_SOURCE`），错误指向读取方（节点、日志点、输出）并带 hint；作用域是读取方加被固定的节点。运行时的规则不变：被固定的节点在这个请求里没有运行（跳过、失败），读到缺失。行为变化：固定一个在某些组合里被删除的节点，原来能通过，现在报错。日志点同理：挂载点（`TAP_UNKNOWN_NODE`）和它记录的上下文特征（`TAP_FEATURE_NOT_FETCHED`）原来对所有变体取并集，基线日志点挂在只由某个臂增加的节点后面也能通过，不带这个臂的请求里静默不记录；现在在每个组合里检查，日志点和它挂载的节点由同一个臂一起增加照样通过（外部评审）。
- **每个组合里，节点绑定的名字都要先声明**（设计 11.5、16.2）。统一计划每个节点只编译一次，用的 schema 是所有臂声明的并集；合并成普通配置单独编译时，一个名字只有在这个组合里声明过才认得。所以每个带臂的组合都检查：节点、fallback、日志点和输出绑定的每个名字（列、参数、特征），在这个组合里编译到它之前必须已经声明，否则报 `NAME_NOT_DECLARED`，hint 建议在基线或读它的臂里声明。声明只有三个来源：基线；这个组合里被分配的臂新增的条目；对列来说，还有先于它编译、写这一列时自带类型（隐式输出，`CompiledNode.Declares`）的节点。编译顺序和统一编译相同：先 order 后 id，fallback 排在时间线之后按 id，日志点和输出最后。这条规则之前是几条各管一种情形的检查，逐个暴露出缺口：一个臂删掉或移走写者、另一层的臂新增读者（生成式差分测试）；节点先读后写自己的输出（评审 50）；评审 51 又找到三处。其一，一个臂在 `columns` 里声明了基线写者隐式写出的列，并集 schema 里这一列就不再算隐式列，另一个臂删掉写者、第三个臂读它，没有声明臂的组合被放行；撤销声明臂后发布的新清单没有节点能加载。其二，死分支和未使用的 `let`：绑定时名字必须存在，优化后的读取（`Reads`）里却没有它。现在表达式同时保留两份：`Names` 是绑定解析过的全部名字，用于这条规则；`Reads` 是优化后的读取，用于取数，死分支不会多取特征。其三，`TryWriteColumn` 不带类型的写需要已有声明，不能当作它自己声明了这一列。节点内部的先后也要记录：节点读自己写过的列，若写在前且自带类型，这次读不再要求别处的声明（`GroupAggregate@1` 按名字先写 `a`、再拿 `a` 算 `b` 合法），否则要求。不带臂的组合不查名字：裸基线会单独编译（见“基线必须能单独编译”），在表达式的确切位置报错，同一个原因不报两次。只有声明会随组合变化的名字（隐式列、臂新增的名字）才登记作用域，否则每个读基线参数的节点都会成为作用域，按作用域检查很快超出上限。没有选择让统一计划接受这些情况、把名字当作缺失：那样有的组合在统一计划上能跑，合并成普通配置却编译不了，16.2 的等价关系不再成立。同一个组合里，其他检查已经在这个读者（或它下面的位置）报过错时，名字规则不再报：日志点读的列在挂载点之前没有产出者时，`TAP_COLUMN_NOT_PRODUCED` 已经说明了原因（评审 52）。
- **实验只给配额就能新增召回源，这个源在没有这个臂的请求里不占位**（设计 11.8、16.2）。map 参数的叶子是基线的加上所有臂新增的键；`MapParam` 返回全部，没有某个臂的请求里，只有这个臂新增的键是缺失的，而这个组合单独编译时根本没有它。所以算子在运行时把缺失的叶子当作没有这一项，也不能从叶子的集合推出位置、个数这类东西。`MultiSourceRecall@1` 原来按来源在全部来源中的位置分配 `recall.sources_mask` 的位：未分配的臂新增的源排在前面时，基线的源的位整体后移，按掩码过滤的基线节点留下了和自己单独编译不同的行（评审 52 P2）。现在第 i 位是这个请求有配额（包括 0）的来源中按合并顺序的第 i 个，和这个组合单独编译时一致。`source_order` 不再要求列出每个源：列出的在前，其余按名字排在后面。原来流水线写了 `source_order`（示例就写了）时，实验无法只靠配额新增源，臂单独编译报“没有列出”；臂同时改 `source_order`，统一计划里基线的变体又因为看到这个新源而报同样的错。列出的源按名字绑定它的配额叶子，臂列出只有另一层的臂新增的源时报 `NAME_NOT_DECLARED`；同一个源列两次是错误（原来会调用两次、占两位）。没有选择把 map 的成员集合记成节点的依赖、逐组合比较：只靠配额新增源正是实验的用法，没有这个臂的组合都会不同，都会被拒。代价：64 个源的上限按所有臂给过配额的源合计，单个请求可能用不了这么多。
- **写已声明的列和声明未声明的列，写者都给出自己的类型**。`TryWriteColumn` 带类型时，未声明的列按这个类型声明；已声明的列保持声明的类型，由调用方检查自己能不能写（`GroupAggregate@1` 接受 int32、可空的声明）。原来 `GroupAggregate@1`、`ModelRanker` 系列、`LlmAnnotator@1`、`GenerativeRetriever@1` 先查 schema：声明过就不带类型，没声明才带。统一 schema 里另一个臂的声明会让这次写看起来需要声明，而在没有那个臂的组合里，同一个节点会自己声明这一列。`MultiSourceRecall@1` 的 `recall.*` 列只能是固定的类型，改为自己检查。
- **写者声明的列要和臂声明的一致**。一个臂声明的列只在这个臂被分配的组合里存在；其他组合里，写这一列时自带类型的节点声明它。统一计划只有一个 schema，里面是臂的声明，所以在没有这个臂的组合里（包括裸基线），每个这样的写必须声明出同一列：类型相同，没有默认值，不是流动列，否则报 `COLUMN_TYPE_MISMATCH`，hint 建议在基线里声明。生成式差分测试找到了它：同一层互斥的两个臂，一个把 `stat.b` 声明为 `int64?`，另一个用不分组的计数写出 `int64` 并直接读它，统一计划以“可能缺失”拒绝了读者，而那个臂单独编译时这一列从不缺失，错误信息也看不出原因。读者的编译错误可能正来自这里，所以组合里有变体编译失败时，这一项仍然检查。同一个臂既声明又写，声明在写存在的地方都存在，不受影响。
- **生成式差分测试**（设计 16.2）。`GeneratedExperimentTests` 在示例基线上随机生成实验（多数 1～3 个，四分之一的种子 4～5 个，见下）：有时两个实验共用一层，有时没有对照臂，有时基线多一个读者。每个臂由几个原子改动组成：改参数、新增 `GroupAggregate@1` 写者（可空或不可空）、写者加读者、把基线节点移到新写者之后并改读它、删节点、移节点、加打分节点、加日志点。对每份配置比较统一编译和逐组合的合并编译。统一计划接受的，每个组合都要接受，并且执行结果一致（逐项输出和节点结果）。每个组合都接受、统一计划却拒绝的，只能是跨组合的规则（路径冲突、同一 order、一列一种类型等）。生成时单独无效的臂大多会重新生成，否则一个无效臂就让整份配置被拒，差分无从比较。实验在代码里直接构造，不经过 JSON 文本，补丁里的数字是 CLR 数值，像宿主构造的那样。它找到了一个臂删掉写者、另一层的臂新增读者的缺陷（见“每个组合里，节点绑定的名字都要先声明”）；只认解析出的 `order` 的缺陷（评审 49）它也能发现。回退外部评审的 P1、P2（按定义编译的顺序）或那个缺陷的修复，它都会失败；其中 P1 要跑到 3000 个种子才稳定出现，另有专门的回归测试覆盖。有时关掉每个臂的单独编译（同时更多地留下单独无效的臂），只靠组合检查拒绝；有时把 `MaxCombinationsChecked` 调到很小，走按作用域的检查；还会生成读自己输出的节点（先写后读的合法形状和先读后写的非法形状，后者让评审 50 的自读豁免失败）。评审 51 指出，层数最多 3、上限不是很小就是 4096，三层的作用域要么全量穷举、要么超出上限，按作用域枚举再检查的路径从没走到；现在四分之一的种子有 4～5 层、多数每层一个处理臂，上限取 8、12 或 16，整个空间超出上限而三层的作用域放得下。但随机生成的配置几乎不会只在三层同时生效时才出错，省掉按作用域的检查照样全绿，所以其中一半植入一条这样的规则：基线有一个写 `stat.a` 的节点排在 `author_cap` 之前，一个臂让 `author_cap` 读它，一个把 `author_cap` 移到 513，一个把写者移到 514，任意一个或两个都合法。省掉检查后 300 个种子里有 2 个失败。原子改动里加了臂的 `columns` 声明和死分支读者，由此找到了“写者声明的列要和臂声明的一致”那一条的缺陷；评审 51 的其他几处由 `DeclarationTests` 逐条覆盖。它的局限：两边共用编译代码，共同的误收误拒发现不了；没有生成后备节点、行源、固定版本和输出读取的变化，这些由专门的测试覆盖。默认 300 个种子，约 25 秒；设置 `STRATAREC_GENERATED_SEEDS` 可以跑更多。
- **`columns_from` 跟随模型变体**（设计 8.3、6.9）。探针展开的是当前臂组合下实际生效的模型节点；修改该模型的层也参与探针的变体划分；探针 schema id 包含每列解析后的表达式。训练日志必须记录服务时真正的输入（评审 4）。
- **节点按时间线顺序编译，不按 id**。一个节点在编译时声明它写的、没有在 `columns` 里声明的列（隐式输出：`recall.*`、`GroupAggregate@1` 的输出、成对和列表重排写的分数列），之后编译的节点才能读到。原来按 id 的字典序编译，读的节点 id 排在写的节点前面（`author_cap` 在 `author_rank` 前面；任何排在 `recall` 前面的节点读 `col.recall.*`）就报“未知名字”，而且看不出原因。现在先合并出每个节点在各组合下的定义，每个不同的定义按它自己的 `order` 编译，后备节点（没有 `order`）排在时间线之后，相同时按 id。原来一个节点的所有定义按其中最小的 `order` 一起编译：实验把读的节点挪到写的节点之后，它的新定义仍在写的节点之前编译，统一计划拒绝了这个组合单独编译能通过的配置（外部评审 P2）。合法的配置里，每个组合中写的节点都在读的节点之前运行，所以写的定义在读的定义之前编译；读的节点排在写的节点之前时，诊断仍是“未知名字”，不是“它的产出者运行得更晚”，这一点没有为它再做一遍。`order` 按绑定时的语义读：只要是整数 JSON 数字，不管树里存的是哪种 CLR 类型。宿主在代码里构造的补丁存的是 `int`，原来只认解析出来的 JSON 元素和 `long`，被移动的写节点因此被当作没有 `order`、排到最后编译，同一份 JSON 程序构造时被拒，解析时通过（评审 49）。没有选“算子先声明再编译”的两阶段接口：多一个所有算子都要实现的扩展点，只为了这个顺序；按定义排序之后，每个读已经在它所有可能的写之后编译。统一 schema 里有别的组合才声明的列，这一点由逐组合的数据流检查和每个臂单独编译把关。
- **节点 id 只能是标识符**（字母、数字、`_`）。版本引用 `col.x@node` 要能写出每个节点；含 `.` 或 `-` 会被解析成字段访问或减法。这是在扩展语法和收紧 id 之间选了后者（评审 4）。
- **行源节点不能被版本引用**（`VERSION_REF_ROW_SOURCE`）。所有行源向同一个槽位追加行，没有“某个节点的版本”可读（评审 5）。
- **行源和它们共用的列版本在编译时检查**（设计 4.6）。所有行源把自己追加的行写进每一列的同一个共享版本，而一行没写就是缺失（见“执行与宿主”），所以在一条路径上：写不可空列的第一个行源之前，每个行源也要写这一列（`ROW_SOURCE_BEFORE_COLUMN`，指向没写的那个行源，提示同时写这一列，或者声明为可空，例如 `"recall.best_score": { "type": "float64?" }`，再用 `??` 处理缺失）；之后的行源也要写（原有的 `ROW_SOURCE_AFTER_COLUMN`；列由行源以外的节点产出时，提示改为把行源移到那个节点之前，因为这时写这一列也没用）；别的节点已经写出这一列自己的版本之后，行源把自己追加的行写进这个当前版本（见“排序之后注入的行写进当前版本”）。这两种情况运行时会让每个同时运行两个节点的请求在提交时失败，放在编译期，错误指向造成问题的节点。行为变化：自定义行源在 `MultiSourceRecall` 之前、自己不写 `recall.*` 的配置现在编译失败（原来能运行，前一个行源的行读到旧数据），按提示把 `recall.*` 声明为可空即可。后备按它所替代节点的位置检查（评审 13）：主节点失败后已经回滚，不是后备的前驱，所以两者都对照这个位置之前的状态检查；这个位置之后的状态是两者都可能留下的，即可能追加了行、可能写了自己的版本。两者的效果可以不同。后备的输出列和主节点完全相同，同一种效果的检查只取决于之前的状态和这些列，所以每种效果检查一次，错误指向有这种效果的节点（两者都有时指向主节点），不重复报告。原来行源检查只看时间线上的主节点，后备只核对输出列和必需的输入：给写列的节点配一个行源后备，就绕过了上面三项检查，后备追加的行在不可空列里线上读到池里的旧数据、回放读到 0；给行源配一个写列的后备，则绕过了 `COLUMN_MULTIPLE_PRODUCERS`。这样的配置现在编译失败。没有选“主节点和后备的效果必须相同”：满足这些检查的混合配置能正确运行，检查本来就按效果做。

## 执行与宿主

- **排序之后注入的行写进当前版本**（设计 4.6、5.2）。交叉混排和固定位置注入（广告、运营位）是业务逻辑，不做内置算子，由自定义算子用公开的算子接口实现；框架要保证的是它们写得出来。混排只是重排（`RowOrder`，`SetOrder`）。注入在打分和截断之后才调用外部源，要追加行、给这些行写分数、再放到指定位置（`RowSource | RowOrder`）。原来行源只能写所有行源共用的那个版本：打分节点写过自己的版本之后，注入者再写分数列会让读取方切到共用版本，那里没有打分节点的值，所以编译期拒绝（`ROW_SOURCE_SHADOWS_VERSION`），注入的行只能另写一列再合并。现在规则只在一处（`RequestState.OutputSlot`）：已经有节点提交了这一列的版本时，行源 `Output` 拿到的就是这个当前版本，追加行的值写在里面，这一列不再提交，读取方照常读到所有行；还没有版本、或者当前是共用版本时和原来一样。原来担心的复杂度都不存在：行源只写自己追加的行，失败的尝试回滚时这些行在每个槽位里都被释放（后备复用它们，读到的是自己的值，有测试）；节点运行期间没有别的提交，所以解析出来的槽位在一次尝试里不变；槽位按表的存储容量建立，本来就容得下之后追加的行。效果：`col.x@node` 读到的版本里也有之后注入的行的值（这一行加入时这一列的当前版本），日志里这一列的产出者仍是写这个版本的节点。仍然要求行源写出它之前已经产出的非空列（`ROW_SOURCE_AFTER_COLUMN`，提示改为写这一列）：注入者要给自己的行写上排序依赖的不可空列，或者把这些列声明为可空。注入的行要用到的特征照常在读取它们的节点之前补拉，不需要算子处理。参考实现和它们的保证在 `CustomPlacementTests`（集成测试）：`SlotInjector@1` 通过上下文调用候选源（有界、录制、回放），跳过已经展示的候选，按位置放入；`Interleave@1` 按模式轮流取各来源的行，保持各自顺序。
- **参数触发在调用算子之前记录**（设计 12.6）。节点之后失败也算触发；按结果决定是否触发会让失败的请求从实验组里消失（评审 3）。
- **取消或中止的请求仍然发布 `$experiments` 记录和已捕获的探针**。慢请求更容易被取消，而慢往往与臂相关（评审 4）。例外：设置了 `CaptureLogs` 的请求（调试、预览）在任何情况下都不写持久日志（评审 5）。
- **后备流水线只用剩余时间**（设计 5.6）。设计只说“宿主可以选择返回它的结果”；实现统一为自动执行、不带实验、不重新计时，外部分配服务也受同一个截止时间约束（评审 3、4）。
- **计划发布按序号，组装出错整体放弃**（设计 10.3）。后台编译可能乱序完成，较旧的结果不覆盖较新的计划；`fallback_pipeline` 解析失败时主流水线也不发布（评审 3、4）。
- **衍生特征表达式抛异常只让该特征失败**（设计 6.7）。表达式后端对数据错误返回缺失值，抛异常只可能是缺陷；按数据源失败处理，不影响同一请求的其他特征。
- **召回源和模型调用的等待有自己的上界，不依赖客户端响应取消**（设计 4.8、5.6；评审 10、11）。节点尝试开始时定下绝对截止时刻，`OperatorContext.RetrieveAsync` 和 `InvokeModelAsync` 都经过 `BoundedCall`：等待在调用自己的 `timeout_ms`、节点截止时刻（取较早者）或调用方取消时结束，用 `WaitAsync(剩余时间, 调用方令牌)`，从不等客户端手里的令牌（令牌的回调同步执行，一个阻塞就卡住等待）。结果只有被框架在上界之内观察到完成才采用，谁先到只判一次：真正装上了的等待看等待本身的结局；没装上的（同步返回，或者在装上等待之前就完成、`WaitAsync` 原样返回）在框架看到它的那一刻按时钟、令牌和调用方判断。取舍：按时完成、只因抢占晚被看到的调用也算超时；框架只认它观察到的事实，按客户端声称的完成时刻判就给不出上界。等不到的调用被放弃，不取消也不再等：客户端的令牌一直有效，请求内存持有到它真正结束并且调用点记录完毕（`stratarec.io.abandoned` 计一次），召回缓冲区当场关闭，算子和录制都读不到被放弃的数据。分类与特征拉取一致，每次调用只完成、录制一次。调用自己的超时返回失败状态，由算子按失败处理（模型节点因此走后备）；预算用完或调用方取消抛 `OperationCanceledException`。1.0 之前的不兼容改动：`InvokeModelAsync` 的令牌参数换成 `int? timeoutMs`。代价：与节点共用预算的同步调用不分配；自身超时更短的调用在发出前建一个关联取消源和定时器（约 160 B），取消源必须在发出前建好，客户端拿到的令牌才带着自己的超时，所以不推迟、不复用；被放弃的客户端占用的线程和内存要等它自己结束，框架只计数。
- **宿主示例 `samples/StrataRec.Samples.Host` 是嵌入引擎和写扩展的指南，用代码写**。一个 ASP.NET Core 服务：`AddStrataRec` 加载它自己的工作区，`POST /recommend/{pipeline}` 把 HTTP 请求转成 `RecRequest`；四个扩展点（特征连接器、召回源、模型客户端、算子）各有一个小实现，和内置组件注册在同一个 `PlanEnvironment` 里，工作区按类型名引用。每个组件的注释写契约的规则（取消、预算、不按行分配、缺失值怎么报）和这样写的理由，算子的配置类同时是它的 JSON Schema。测试用 `WebApplicationFactory` 在进程内启动服务，放在单独的 `tests/StrataRec.Samples.Host.Tests`，不放进集成测试项目：引用 Web 项目的测试项目会带上 ASP.NET Core 共享框架，共享框架里也有的包（`Microsoft.Extensions.Logging.Abstractions` 等）就不再复制到输出目录；集成测试在子进程里从自己的输出目录启动 `stratarec.dll`，CLI 的依赖必须在那里。合在一起时 CI 的干净构建就失败了，本地因为输出目录里留着旧的 dll 没有发现。
  - 带自定义组件的工作区由宿主自己的二进制检查和运行（`dotnet run -- stratarec validate -c config`，`run`、`explain-plan`、`schema` 等全部命令同样可用，见下面的 `StrataRec.CommandLine`）：官方 CLI 只认内置组件和随它发布的可选包，不认识的类型名是加载错误。宿主的二进制用 CLI 同一套命令和服务同一个 `PlanEnvironment`，校验通过的就是服务接受的；CI 里原来跑 `stratarec validate` 的地方改跑它。没有选让 CLI 按路径加载插件程序集：版本和依赖要和宿主一致，加载失败的方式也多一种，而宿主的二进制本来就有这些组件。
  - 截止时间由服务定（示例默认 1000 ms），不由调用方传：冷进程第一个请求要 JIT，所以示例放得宽；生产服务按延迟目标设，预热之后再报告就绪。
  - 写示例时暴露出宿主要自己做的几件事：把 JSON 转成 `RequestInputs` 并按 `request_schema` 先校验一遍，才能区分调用方的错（400）和引擎的错（500）；把结果写成 JSON；启动时主动解析一次引擎，配置有错才会在启动时失败；加载的警告没有出口；带自定义组件就用不了 CLI。这些都放进了框架（下面三条），示例的端点只剩传输。
- **失败的请求带类别，调用方的错在分配实验之前按引擎的规则查出**（设计 3.4）。`RecResult.ErrorKind` 是 `UnknownPipeline`、`InvalidRequest`、`DeadlineExceeded`、`Failed` 之一，宿主不解析错误文本就能回答 404、400、504、500；输入错误另带 `ErrorPointer`（`/inputs/user_id`）。
  - 输入在分配实验之前检查：跑不了的请求不该去问实验平台，后备流水线是给失败的流水线准备的，不接手调用方写错的请求。强制的桶未知或冲突也是 `InvalidRequest`，不带指针（它是调试选项，不在请求体里）。
  - 规则只有一份（`RequestSchema`，在 Pipeline）：执行器绑定输入、宿主读 JSON 请求体、CLI 读请求文件都用它，措辞是配置错误那一套 JSON 说法。宿主读输入用的是读的那一刻的计划，引擎执行时按它实际运行的计划再查一次，以引擎为准：中间换了发布、新计划多了一个必填输入，结果仍是带指针的 `InvalidRequest`，不是 500。检查不分配。回放也先检查：`ReplayAsync` 解码录制的输入之后、解析臂之前，按回放的计划检查一次，不合法就是带指针的 `InvalidRequest`，不运行后备，和线上对同一个请求的回答一致。原来回放跳过这一步，新发布多了一个必填输入时，没有后备的回放是 `Failed`，有后备的竟由后备“成功”服务，离线比较会把线上会拒绝的请求当成一次正常的降级（评审 33）。后备自己要求的输入请求里没有，仍是 `Failed`，回放和线上一样。
  - `DeadlineExceeded` 只表示流水线开始之前截止时间就用完了（分配实验用掉了），什么都没执行；流水线执行中超时属于 `Failed`，因为那时节点的预算、跳过和后备都已经按截止时间做过决定。
  - 后备流水线只拿到它自己声明的输入（输入都已声明时直接用原对象，不分配）：后备通常用更少的信号（热门列表不需要用户），不必为它不读的输入改 schema。它要求的输入请求里没有，或类型不同，是配置的错，请求以 `Failed` 结束，错误里两条流水线的原因都有。这种不兼容在加载和 `validate` 时就给出警告，报在主流水线的 `/fallback_pipeline`：后备要求主流水线没有声明的输入（`FALLBACK_INPUT_UNDECLARED`）、主流水线里可选而后备里必填（`FALLBACK_INPUT_OPTIONAL`）、同名不同类型（`FALLBACK_INPUT_TYPE`）。是警告不是错误：主流水线照常服务，只是失败时接不住；严格的 CI 用 `--warnings-as-errors`。`validate -p` 也编译它的后备流水线并报告未知的后备，与加载用同一段代码（`ConfigWorkspace.WithFallbacks`），原来未知的后备要到加载时才发现。
  - JSON 请求体用 `JsonDocument` 读，再用 `StrictJson` 查重复的成员和不成对的代理转义，报在第二次出现的位置；没有用 `JsonDocumentOptions.AllowDuplicateProperties = false`：它只抛 `JsonException`，说不出位置，也查不出代理转义。`JsonObject` 不能用来读请求体：它在第一次枚举成员时才对重复的名字抛 `ArgumentException`，越过宿主的 400 路径成了空体的 500（评审 32）。`JsonDocument` 也收下原文不是 UTF-8 的字符串和成员名（一个原始的 `0xFF`、截断的多字节序列），读它们时才抛异常，所以 `StrictJson` 也用 `Utf8.IsValid` 查每个字符串和成员名的原始字节：字符串报在它自己的指针，成员名写不出指针，报在所在的对象，说是第几个成员；消息不引用这些字节，提示让调用方按 UTF-8 发送。ASCII 和合法的非 ASCII 文本都不分配（评审 33）。
  - 结果只有一种 JSON 文档（`RecResultJson`），服务和 `stratarec run` 都输出它：输出列放在每一项的 `columns` 里，int64 的 ID 是 JSON 数字（原来 `run` 写成字符串），缺失和非有限的浮点是 `null`，另有 `request_id`、`error_kind`、`error_pointer`、`elapsed_ms`。这是 `run` 输出格式的不兼容改动。
  - float32 列的值按 float32 的最短往返形式输出（`0.08`，不是它扩展成的 double `0.07999999821186066`），结果的 JSON、`run --format text`、候选解释和回放报告都一样；float64 列仍是 double 的最短往返形式。值在 `ScalarValue` 里仍然是扩展后的 double，只是记住它来自 float32 存储（`FromFloat32`），相等和哈希只看 double，所以比较不受来源影响。输出列是表达式，表达式里的浮点都是 float64，所以只有正好是一个 float32 列的输出列（`"score": "col.score.final"`，最常见的写法）保留 float32，回放包也记它为 float32；有运算的输出列是 float64 的值，照 double 显示。没有在输出时按“这个 double 恰好是某个 float32”来判断：float64 列里同样的数会被写成另一个 double，回放报告里两个不同的值可能显示得一样。日志和回放包的编码不变（float32 列仍写精确的 double，按类型读回），它们给程序读，已有的文件照常回放。CLI 报告原来把浮点四舍五入到 6 位小数，比 1e-6 小的分数显示成 0，回放差异里两个不同的值也可能一样，现在都按上面的规则精确输出。组合打分的说明按输出列的精度书写，float32 列时算式的结果就是列里的值；各项是 float64，只在 float32 表示得了时（有限、不被冲成 0、不是次正规数）按 float32 写，否则按 double 写，不然 `1e100 × 1e-100` 会写成 `Infinity × 0 = 1`（评审 35）；精确的各项在 `terms` 里。代价：服务返回的 float32 值读成 double 时是 `0.08`，不再是存储的那个 double，调用方要精确的值时转回 float32。
  - int32 输入越界时，提示改成 int64 并保留可空性（`int32?` 提示 `int64?`）：照抄 `int64` 会把一个可选输入变成必填。
- **`AddStrataRec` 在宿主开始监听之前加载工作区**（设计 3.4）。加载在一个托管服务的 `IHostedLifecycleService.StartingAsync` 里做：通用主机先等所有服务的 `StartingAsync` 完成，再调用各服务的 `StartAsync`，ASP.NET Core 的服务器在自己的 `StartAsync` 里开始监听，所以服务一能应答，每个计划都已加载。没有放在 `StartAsync` 里依靠注册顺序：宿主打开 `HostOptions.ServicesStartConcurrently` 后，各服务的 `StartAsync` 并发运行，后注册的服务和服务器会在加载完成之前开始（评审 33）。代价：别的服务的 `StartingAsync` 不能指望计划已经加载。配置有错误时抛出列出全部错误的 `ConfigException`，服务启动不了；警告写进宿主的日志（事件 1003）。原来在第一次解析引擎时同步加载，宿主要记得在启动时解析一次，警告也被丢掉。相对的 `ConfigRoot` 从宿主的内容根目录算，`PlanEnvironment` 没有 `BaseDirectory` 时用配置根目录，绑定里的相对路径不再取决于进程的当前目录。没有加健康检查包：能应答就是就绪的，存活和就绪的区分、预热由宿主决定。不是通用主机的宿主（只有一个 `ServiceProvider`）自己调用 `LoadWorkspaceAsync`。
- **节点按 manifest 上线，不兼容、撤销和过期都是状态，不是异常**（设计 10.1、10.3、10.4）。`RecEngine.LoadManifestAsync` 依次：记下 manifest 的 `min_accepted_seq`（每条流水线见过的最大值，也包括没有应用的 manifest 上的，设计 10.3 第 6 条）；`seq` 低于它是 `Revoked`；不比正在服务的新（同一个 manifest 也算）是 `Stale`；`requires` 不是二进制能力的子集是 `Incompatible`，列出缺少的能力。这三种都不下载、不编译。读不到产物、编译失败、绑定加载失败是 `Rejected`，只有它重试可能成功。原来不兼容的 manifest 只会在编译时报“未知算子”，分不出是二进制缺能力还是配置写错，而发布控制器要的正是这个区别（设计 10.4 第 3、4 条）。能力检查只在 `ManifestBuilder.CheckCapabilities` 一处，引擎和 CLI 报同一个 `MANIFEST_INCOMPATIBLE`（指向 `/requires`）。
  - 撤销在上线那一刻再查一次：一个 manifest 编译期间，另一个 manifest（哪怕它自己不兼容）宣布了更高的 `min_accepted_seq`，正在加载的计划就不上线。只对按 `seq` 加载生效，本地加载的票号不算。节点还检查指针指向的 manifest 属于自己的流水线和环境，指错了不会加载成另一条流水线。
  - `AddStrataRec` 设置 `Releases` 时服务 manifest 而不是工作区：启动时每条流水线都必须应用成功，否则宿主不启动，异常列出每条流水线的状态和原因；只服务一部分流水线，或者后备流水线从未加载，请求都会悄悄失败，所以后备流水线也必须在 `Pipelines` 里。之后每条流水线各有一个任务按间隔轮询自己的指针，只有新的 id 才加载（见下一条）。`Applied`、`Stale`、`Revoked`、`Incompatible` 对同一个 id 是最终结果，不再尝试；`Rejected` 和读不到指针或 manifest 按倍增的间隔重试，上限 `MaxRetryInterval`（默认 5 分钟）。编译失败本来是确定的，但要把它和暂时的失败（存储还没一致、表的来源宕机）分开需要更多状态，上限已经限住了重编译的成本。指针消失时继续服务当前计划。每次尝试的结果交给可选的 `IReleaseStatusReporter`（设计 10.3 第 5 条），它抛出的异常只记日志。时钟是 `ReleaseOptions.TimeProvider`，不从 DI 取，应用里注册的时钟不会悄悄改变轮询。
  - **每条流水线单独轮询，状态上报不在等待链上**（外部评审）。原来一个任务依次处理所有流水线，并原地等待每次上报：卡住流水线 A 的上报，B 已发布的新版本过了 25 个轮询周期还没应用，紧急撤销的时效取决于最慢的那条流水线和上报方。现在：每条流水线一个轮询任务，一次加载、一次挂起的指针读取只推迟它自己；不同流水线可能同时编译（引擎的加载本来线程安全），代价是 CPU 和内存的峰值。后台的结果进一个有界队列（每条流水线 4 个、至少 16 个），由一个任务按尝试的顺序逐个上报，上报方从不被并发调用；队列满了丢最旧的（事件 1014），新的结果更能说明节点的状态。上报的令牌在 `ReportTimeout`（默认 30 秒）后取消（事件 1015），下一个上报仍等这次调用返回：不理会令牌的上报方只拖住上报，不拖住发布。启动时仍然逐条上报完再加载下一条，宿主启动失败之前，控制器已经知道原因。上报晚于尝试，所以结果带上尝试开始的时刻（`ManifestLoadResult.AttemptedAt`，按轮询的时钟）。读指针的令牌在 `PointerTimeout`（默认 30 秒）后取消，按读取失败退避重试；manifest 和产物的读取属于加载，不设超时（大表的加载本来就慢）。两种超时用系统时钟，测试推进的手动时钟只管轮询和重试。停止宿主时先由框架直接取消每个进行中的调用、再取消轮询，所以等的回调包括这些调用令牌上的（评审 36 的要求：调用的令牌嵌套在轮询的令牌下，只经链接取消时，停止不会等它们的回调，容器会在源清理到一半时释放它）
  - 控制面的扩展（`IManifestSource`、`IArtifactStore`、`IReleaseStatusReporter`）和其他扩展一样，拿到的是框架的 `ObservedCancellationSource` 的令牌（站点 `release`；manifest 的下载属于引擎的加载，站点 `plan_load`），取消时回调在线程池上运行、抛出的异常被计数，不会从宿主或调用方的计时器线程抛出、终止正在服务旧计划的进程（评审 35）。下载算作加载的一部分：先登记再下载，释放引擎也会取消它，和等待表加载时一样。停止宿主等轮询结束，也等这次取消的回调跑完，都以宿主的停止期限为界：容器随后释放扩展，回调做清理时不能发现它们已被释放（评审 36：一度完全不等回调，停止期限还很充裕，容器就在清理进行到一半时释放了 manifest 源）；期限到了就不再等；此后轮询里出现的异常属于正在停止的宿主，安静地结束，不再作为未观察的异常出现（评审 37）。只等回调结束，不再抛出回调的异常：它由取消源观察，重新抛出的任务没人观察。日志器或指标监听器抛出的异常只丢掉那条记录，不改变重试、上报和轮询：原来读指针失败时写日志抛出，后台任务就永久结束，节点看起来正常、却再也不接收新的发布。每条流水线的轮询外面还有最后一层防护（事件 1013），缺陷也不会让后台任务结束；被它打断的尝试按被拒绝处理，退避后重试。指针换到新的 manifest 时，上一个的结果（最终与否、重试时刻）全部清掉（评审 36：一次尝试在记下结果之前抛出——描述异常时读 `Message` 本身抛出——新 id 就沿用上一个的“最终”，轮询还活着，却再也不加载它）；描述扩展的异常一律用不会抛出的 `ExceptionText.Of`。计划加载的遥测（事件 1001–1008、`stratarec.plan.loads`）同样不抛出：原来日志器在计划上线之后抛出，加载会把已经上线的计划报成异常。
  - 不在本地磁盘保存 last-known-good（设计 10.3 的第 2、3 个来源）。落盘的 manifest 和产物是又一种要兼容的格式，还要处理写了一半的文件，理由同“节点本地的磁盘快照不在框架里做”；控制面不可用时的启动由宿主组合 `IManifestSource` 解决，例如先问控制面，失败时读镜像里内置的基线指针。
  - `stratarec publish -s <store> <manifest>` 是最小的发布控制器（设计 10.1 第 3 条，紧急停止是 `stratarec revoke`，见下文；没有分批推进）。指针是 store 下的 `pointers/<环境>/<流水线>.json`，内容 `{ "manifest": "sha256:…" }`；节点忽略不认识的成员，控制器以后加字段不影响旧节点。发布前按节点的方式把产物读一遍，指针永远不指向节点读不到的 manifest；`seq` 必须比当前指向的大，回滚也要一个新的 `seq`（设计 10.2）；低于任一方的 `min_accepted_seq` 也拒绝，节点会把它当作已撤销。指针已经指向同一个 manifest 时什么都不写、成功退出，所以 CI 里的发布步骤可以重跑。
  - `build` 不给 `--seq` 时构建“下一个发布”：读 store 里这条流水线、这个环境的指针，`seq` 取它指向的 manifest 加一，沿用它的 `min_accepted_seq`（设计 10.2：普通发布沿用上一版的值），并把它写进 `previous`，于是 `diff --to <新 manifest>` 不用 `--from` 就比较这次发布改了什么；还没有发布过时是 1。原来默认总是 1，每次发布都要使用者自己查当前的 `seq`，第二次发布必然先撞上 `PUBLISH_NOT_NEWER`；`previous` 设计里有，`build` 却从来不写。配置和已发布的一样（只差这三个字段）时不产生新发布：`build` 输出已发布的那个 manifest，`publish` 随后报“已经发布”，所以 CI 里 build 加 publish 整个重跑也不会多出一个内容相同的发布。指针或它指向的 manifest 读不到时报错，提示修好或显式给 `--seq`：猜一个序号，`publish` 也会因为同样的原因失败。指针指向别的流水线或环境的 manifest（手工复制或改过的指针）时同样报错（`POINTER_MANIFEST_FOREIGN`），`publish` 也一样：那个 `seq` 说明不了这条流水线发布到哪里，拿它编号或比较新旧，要么平白跳号，要么把正确的发布当作“不比已发布的新”拒绝（评审 37）。“配置没变”是和 `build` 自己写出的形式比较：别的工具写的 manifest 省略了取默认值的字段时，内容 id 不同，会多出一个内容相同的发布；这只多一个序号，不会错发，所以没有为它改 manifest 的身份定义。`build` 生成的 `seq` 最大到 2^53 − 1，即最大安全整数：manifest 是 RFC 8785 规范化的 JSON，整数按双精度写，到它为止的整数都能精确写出，超过它的就不一定。`--seq` 超出范围是用法错误（转换不了的值仍是解析器自己的用法错误：评审 38 发现范围检查读取转换失败的值时抛出，进程以 134 退出，`--deadline-ms` 原来也是这样），已发布的到了最大值时报 `SEQ_EXHAUSTED`。别的工具写的 manifest 文件里有写不准的整数时，它没有内容 id，报 `MANIFEST_NOT_CANONICAL`（评审 38，原来是未处理的异常）；store 里的 manifest 存进去时已经规范化过，读取不受这个上限限制。显式给 `--seq` 时不读指针，留给自己编号的发布控制器。代价：`build` 的输出取决于 store 当时的指针，同一份配置在两个 store 里构建出的 manifest 可能不同；两次构建同时进行会算出同一个 `seq`，后发布的一个被 `PUBLISH_NOT_NEWER` 拒绝，不会错发。不检查能力：发布用的二进制不一定是服务的那个，缺能力的节点自己报 `incompatible`。同一台机器上的两次发布由锁文件互斥，后来的一次报 `PUBLISH_BUSY`、提示稍后重试；跨机器的条件写入要靠对象存储，不在这里做。构建成功时也打印警告：原来只在失败时和错误一起打印，`validate` 报过的警告到了发布这一步反而看不到。
  - `stratarec revoke -s <store> -p <流水线> [-e <环境>] <实验>...` 是紧急停止（设计 10.6）：把指针当前指向的 manifest 去掉这些实验，`seq` 加一，`min_accepted_seq` 设为它自己的 `seq`，`previous` 指向原来那个，写进 store 并立即移动指针。不编译、不校验：去掉实验不会让有效的发布变得无效（设计 11.6），所以停止只需要节点的轮询间隔加一次编译，不需要仓库和 CI。产物按节点的方式读一遍；`requires` 重新计算，所以二进制回滚之后，去掉依赖新能力的实验得到的 manifest 能被旧二进制接受（设计 10.4）：绑定里的类型都计入，只有被撤销的实验写过名字（字符串值或成员名：节点的 `model`、召回配额的键、参数值）、而保留下来的配置没有写到的模型和候选源绑定不再计入，只有被撤销的实验用到的新客户端类型因此不再要求（评审 39：原来每个类型都留着，旧二进制仍报 `incompatible`）。客户端实例只为用到它的节点创建，所以不再被引用的绑定不需要它的类型。没有反过来“只计入写了名字的绑定”：算子可以用配置的默认值或代码里的名字引用绑定，原始 JSON 里看不到，那样会漏算，缺类型的节点报可重试的 `rejected` 而不是 `incompatible`（评审 40）；现在的规则只在被撤销的实验恰好写了这个名字、而保留的配置靠默认值使用它时漏算；这是接受的限制（评审 42 再次指出）：缺这个类型的节点反正服务不了基线，结果只是它报 `rejected`（保留当前计划、退避重试）而不是 `incompatible`，不会服务错的计划；要精确，得在 manifest 里记录每个绑定由谁使用，而旧二进制会拒绝带新字段的 manifest，正好是二进制回滚要读它的时候。撤销要求的绑定类型不超过它撤销的那个 manifest，所以前一次停止去掉的类型不会在下一次停止里回来（评审 42：绑定产物仍列着它，逐次重算又把它加回，能接受第一次停止的旧二进制不能接受第二次）。这以那个 manifest 的 `requires` 可靠为前提：旧版本构建的或手工改过的 manifest 少写了类型，撤销照样少写，撤销不修复历史上的漏算（评审 43），后果同上。`build` 计入绑定里的全部类型。读指针和写指针都在指针的锁里，和 `publish` 互斥，中间插不进别的发布。重复执行什么都不改、成功退出（实验已被已发布的撤销去掉时说明是哪一个撤销的），停止可以放心重试；有一个实验名不认识就报错（提示相近的名字或列出已发布的实验），什么都不撤销。
  - 停止要持续下去。设计里是“控制器状态中标记为已停止”，这里不另存状态，而是从 store 推出来：已发布的 manifest 是撤销（`min_accepted_seq` 等于 `seq`）时，沿 `previous` 往回走过连续的撤销，收集它们去掉的实验和当时的产物哈希；`build` 原样发布其中某个实验时报 `EXPERIMENT_REVOKED`，位置是发布文件里这个实验的条目，提示先从发布文件里去掉，或者用 `--restore` 原样恢复。没有这个检查，停止之后 CI 的下一次例行发布就会把出问题的实验原样带回来。产物变了（owner 的修复）照常发布；一次普通发布之后检查就结束：它没带上的是有意去掉的，带上的是有意恢复的。从发布文件里去掉这个实验之后，构建结果和撤销本身一样，`build` 报“未变化”，停止继续有效。已发布的 manifest 又带上了被撤销的实验（别的控制器把它恢复了），它就不算被撤销（评审 39：原来 `build` 对和已发布内容完全相同的配置也报错）。撤销历史中间有一段读不到时，读不到的那一段只警告（`REVOCATIONS_UNKNOWN`），读到的撤销照样拦截。没有在 `publish` 检查：发布文件是做这个决定的地方，`publish` 只移动指针（和它不查能力同理）；用 `--seq` 自己编号的控制器自己保存停止状态。没有把停止状态写进指针文件或 manifest：那要多一种格式，每次发布还要把它搬过去；从撤销链推出来不需要新的状态。
  - `stratarec status -s <store>` 列出 store 发布的内容：每个指针指向的 manifest、`seq` 和下限、是否撤销、发布的实验，以及正在生效的停止（撤销链去掉的实验，`build` 会把它们挡在外面）。原来要看线上是什么，只能自己读指针文件再去 blob 目录里找 manifest；紧急停止之后更需要一眼看到“停了什么、谁停的”。只读 store，节点实际应用了什么由节点上报（设计 10.3 第 5 步），这里不猜。一个指针读不到就报错（退出码 1），其余照常列出，不让一个坏指针挡住全部：内容不是合法字符串、文件名不能是指针、目录读不了都算读不到（评审 40：它们原来让整个命令以未处理的异常结束），`-e` 只列那个环境的目录；目录是枚举出来的，不先问它是否存在：进不去的目录在 `Directory.Exists` 看来不存在，会被当成“没有发布”（评审 42）；位置上是普通文件时系统报的也是“找不到”（ENOTDIR），所以再看路径上有没有文件，有就是读不到（评审 43）；store 目录不存在是用法错误，多半是 `-s` 写错了。
  - 命令写不了的东西报诊断，不抛异常（评审 43：原来只打印异常和堆栈，退出码 1 又是“配置有错”，使用者会去查已经通过校验的配置）。`build`、`publish`、`revoke` 写不了 store 时报 `STORE_UNWRITABLE`，位置是 `--store`，消息是系统给的、带着路径；`build --manifest` 和 `run --record` 写不了文件时报 `OUTPUT_UNWRITABLE`，位置是那个选项；退出码都是 1。输出文件的目录不存在就创建，和 `init`、`schema --out`、`run --record` 一致（`build --manifest` 原来不建）。`run --record` 写不了时照样打印结果，请求已经执行了。读不到的东西仍在读的地方报（`ARTIFACT_UNAVAILABLE`、`POINTER_UNREADABLE`），所以命令外层只把剩下的 I/O 错误归给 store。
- **`stratarec` 的命令是一个库（`StrataRec.CommandLine`），工具只是调用它**。宿主的二进制用自己的 `PlanEnvironment` 调用 `StrataRecCommandLine.InvokeAsync`，得到全部命令，选项、输出和退出码与官方工具相同，`schema`、`operators` 也列出它自己的算子。单独成库是因为打包成工具（PackAsTool）的项目不能被项目引用。每个命令用 `with { BaseDirectory = … }` 把环境放进它读的工作区，所以 `PlanEnvironment` 改成了 record。官方的 `stratarec` 只剩一个环境：内置组件、`StrataRec.Llm` 和 `redis@1`。
- **请求路径上的扩展点在请求线程上直接调用，只约束异步部分**（评审 18、19）。连接器、召回源、模型客户端、分配 provider 和缓存的分布式层都是这样：方法在返回任务之前做的同步工作没有上界，合同写明 I/O 要异步做；返回任务之后的等待以绝对截止时刻和调用方令牌为界。框架第一次看到结果已经完成时（同步返回，或者装上等待之前就完成），按那一刻的时钟和调用方令牌判断，迟到的结果不采用。没有选每次调用都切到线程池：每个请求多一次调度延迟和分配，只为防住写错的实现；加载期的签名查询（`GetSignatureAsync`）不在请求路径上，所以整个放到线程池（评审 16）。代价：同步阻塞的实现会拖住请求线程，框架只保证不采用它迟到的结果。
- **召回源、模型和特征拉取各有一份等待实现，守同一组不变量**。`BoundedCall` 管单次调用，`FeatureFetcher` 管一次拉取的几百个分批：所有分批共用一个取消源和截止时刻，同步返回的分批在调用点当场完成、不分配，分批写共用暂存区的视图，分类多一个 `partial`。两边真正相同的只有十几行；合成一个原语要把这些差异做成参数，并改动已被分配测试锁定的热路径，风险大于收益。改一份时对照另一份：（1）等待以绝对截止时刻和调用方令牌为界，不等客户端的令牌；（2）每个外部调用从发出前到客户端真正结束、调用点记录完毕，持有一次请求内存；（3）客户端的令牌在它结束之前一直有效；（4）调用方取消算 `cancelled`，超时（包括预算用完、`TimeoutException`）算 `timeout`，其余算 `error`；（5）在调用点完成并录制恰好一次，完成本身抛异常（例如录制钩子出错）时也不再从失败路径完成第二次；（6）被放弃的调用写入的数据不被读取，录制里也没有；（7）同步返回、不需要自己的取消源的调用不分配；（8）结果只在框架于上界之内观察到它时才算：装上了的等待由等待的结局决定，其余（同步完成、`WaitAsync` 的快捷路径）在框架看到它的那一刻判断，两边各由一个 `Observed` 函数负责。两边的测试逐条覆盖这些不变量，并用故障注入确认违反任何一条都会失败。行为变化：同步连接器冷启动时（JIT、忙碌的机器）超过数据源超时，这次调用就超时；示例的内存数据源因此写明 `timeout_ms: 1000`。两边的等待都由 `WaitAsync` 计时，它把剩余时间截断到整毫秒：等待最多比截止时刻早约 1 ms 结束，剩余不足 1 ms 时立即超时。不向上取整：那样等待会在截止时刻之后结束，截止之后才完成的结果会被采用。
- **交给扩展的取消令牌，回调只在线程池上运行，抛出的异常被观察**（评审 20、外部评审）。`CancellationTokenSource` 的取消在取消方的线程上同步运行令牌上注册的回调，回调抛出的异常从取消里抛出；在 `CancelAfter` 的计时器线程上，这会结束进程（召回源注册一个抛异常的回调，500 ms 超时之后请求正常失败，进程随后以 134 退出）。规则只在 `ObservedCancellationSource` 一处：框架交给不属于自己的代码（算子、连接器、模型客户端、召回源、分配 provider、缓存存储、日志 sink，以及服务发布的节点读指针、读制品和上报状态的扩展）的令牌，不论因截止时刻、超时、放弃等待取消，还是从调用方的令牌传过来，都经 `CancelAsync` 取消：令牌当场变为已取消，回调在线程池上运行，抛出的异常计入 `stratarec.cancellation.callback_errors{stratarec.token}` 并写日志，不从任何线程抛出，也不留下未观察的任务。从调用方令牌传过来的取消也不再同步运行扩展的回调（行为变化）：调用方常用带超时的令牌源，它的计时器线程同样会被打崩；所以调用方的 `Cancel()` 不再抛出扩展回调的异常。框架不等这些回调，等待仍以截止时刻和调用方令牌为界（上一条的（1））；取消源等持有令牌的一方结束后才释放（（3））；但持有方看到取消标志就可能结束，这时回调还排在线程池里，而 `CancellationTokenSource.Dispose` 会清空登记的回调，排队的回调就一个也不运行，回调的任务照样成功（评审 22）。所以释放时立即停计时器、解除链接，底层的释放等还没跑完的回调跑完再做。取消和释放在一个整数状态上会合，状态位只用对这一个字段的原子 `Or` 设置，所以全局有序：并发的几次取消（计时器、链接的令牌、框架放弃等待）只有抢到“取消中”位的一方调用 `CancelAsync`，记下回调的任务后再置“已发布”位，其余的不加回调，它发布之后返回它的任务，之前返回已完成的任务（只有获胜者返回的任务完成，才说明回调已经运行）；释放置“请求释放”位，看返回的旧值：没有取消就立即底层释放，已发布就在回调之后释放，取消还没发布就交给取消方（它置“已发布”时会看到请求）。两方对同一个字段的原子操作必有先后，后到的看到先到的，恰好一方负责；第一次释放安排好一切，之后的释放直接返回；底层释放由另一个位保证只做一次；经基类 `Cancel` 的取消在返回之前已经跑完回调，不用等。原来用一个字段做一次比较交换：并发的第二次取消拿到已完成的任务，可能先占住字段，让释放不等真正的回调；第二次释放把“交给取消方”的标记当成可以立即释放；经基类 `Cancel` 取消后释放一直等一个不存在的发布者（评审 23，三种都实际复现）。测试在只有一个线程池线程、并且占住它的子进程里，两种交错各跑 2000 轮，每个回调都要恰好运行一次、每个源最后都释放；旧实现每 2000 轮丢 58 到 69 次。每个源多一个引用和一个整数，只有释放时回调还没跑完才多分配一个延续。没有选已经取消的源干脆不做底层释放、交给 GC：代价更低，但释放后访问令牌不再抛 `ObjectDisposedException`，这是外界判断令牌已释放的唯一信号，测试和排查都靠它；扩展创建的等待句柄也只能等终结器。没有选捕获回调的异常：它从 `CancelAfter` 的计时器内部抛出，框架接不到。计时器沿用设置时的执行上下文（系统计时器带上它，`CancelAfter` 不带）：压制它，带追踪的请求里每个计时器都要分配一个上下文；好处是取消和它的日志属于请求自己的追踪。代价：每个带计时器的取消源多 24 B（系统计时器外包的一层），每个请求约多 480 B；带自身超时的调用 160 B → 208 B；共享预算、同步返回的调用仍不分配（评审 20 时测的；下面的释放协议每个源又多一个引用和一个整数，评审 23 测得每个请求再多 96 B）。测试在子进程里用系统计时器逐个站点确认进程存活、请求在预算内结束、异常被计数和记录。
- **算子在预算用完之后才返回，按超时处理，不论它返回什么**（设计 5.6）。规则只在 `AttemptBudget.RanOut` 一处：调用方没有取消，并且截止时刻已过或预算的定时器已经取消了节点令牌（定时器可能比时钟早一点触发，两者任一即算）。成立时不提交输出，候选表回到尝试之前（见下一条），按 `on_failure` 处理，说明是 “timed out after N ms”。原来只有算子抛出取消才算超时，没看令牌、在预算之后才成功返回的算子照样提交，负载高时请求会拿到超出预算的结果，节点预算就不再是上界。执行器不放弃算子本身，仍然等它返回：算子在请求线程上改候选表和行选择，放弃它就会有两方同时写请求状态。所以 CPU 密集的算子超出预算时，节点照样晚于截止时刻结束，只是结果不用；自定义算子如果自己做 I/O（不经 `RetrieveAsync` / `InvokeModelAsync`），要自己用 `CancellationToken` 或 `BudgetRemaining` 限时，并持有请求内存直到调用结束。代价：原来勉强在预算之后完成的节点现在走后备。
- **失败的节点尝试让候选表回到尝试之前**（设计 4.6、4.8、5.6；评审 10）。规则只在 `CandidateTable`：执行器在每次尝试前取 `Checkpoint()`，任何失败（异常、`Fail`、超时、晚成功、提交校验失败）都 `Rollback`：恢复行选择；释放尝试期间追加的物理行（行数和剩余可追加数退回，这些行在每个槽位里缺失、未填充，实体索引里不再有它们的键）；丢弃尝试期间建立的槽位（见下一条）。原来只恢复行选择：后备召回按 `FindRow` 去重时把失败主节点留下的死行当成已有候选，而回放跳过失败的主节点，同一份录制回放出不同的结果。检查点之前已有的行保持原状，包括被过滤掉的行，后面的行源仍不能把它们召回来，所以 `FindRow` 的去重不变。`RowSelection.Restore` 改为内部方法，表以外只能整体回滚。回滚不能跨过 `Compact`（只在节点成功后做）。其余按行的状态已核对：`OutputBindings` 只在成功时提交；特征回填和预取按键匹配存活行，不按物理行号；被放弃的 I/O 只写租借的缓冲区。约束：后备会复用释放的物理行，所以尝试结束之后任何东西都不能再写候选表；框架的 I/O 边界从不写表，自定义算子不能让后台工作直接写表。
- **算子看到的候选表是只读视图**（设计 5.6）。`OperatorContext.Table`（以及 `ExplainContext.Table`）是 `CandidateTableView`：实体键、按名次排列的存活行、按键查行、还能追加多少行。改表只能经过上下文：`Retain`、`Truncate`、`SetOrder`、`AppendRows` 按节点声明的效果检查，`Output` 只给节点自己的输出列。原来交出的是整张表，自定义算子能直接改行选择、追加行、压缩、取检查点和回滚，绕过效果检查；而规划、实验足迹、失败回滚和回放都依赖声明的效果。`EvalContext` 对引擎以外不透明，同样不再交出表和请求的参数数组。视图是表上的一个结构体，没有复制，读的是表当前的状态；内置算子用的读取都在视图上，没有拿掉算子需要的东西。剩下的口子是 `Read` 返回的列缓冲本身可写：做成只读要改所有内核和列类型，代价远大于收益；约定是读到的列不写。
- **编译好的计划不可变，公开面也是只读的**（设计 12）。一个计划被它的所有并发请求共用，又交给宿主查看（`RecEngine.TryGetPipeline`、`EffectivePlan`、`PlanDiff`）；原来它的公开成员是数组、`Dictionary` 和 `JsonObject`，还有公开 setter，宿主为了显示把 `plan.Nodes` 排个序、改一下节点定义，就改了所有请求在跑的东西，而且没有任何报错。现在从计划可达的集合都是 `ImmutableArray<T>`（局部索引是 `FrozenDictionary`），用 `ImmutableCollectionsMarshal` 直接包装编译器建好的数组，不复制；节点和日志点的定义是 `JsonElement`，`EffectivePlan.ToDocument` 每次给调用方一棵自己的新树；`PlanSchema` 的修改方法是 internal。实验编译器要在节点都编译完之后才能定的成员（触发站点、读参数的实验）用 internal setter，并让 `StrataRec.Experiments` 看到 Pipeline 的 internal 成员；没有改成先算好再构造，因为那要调整编译顺序，诊断的顺序会跟着变。热路径上的代价是零：`ImmutableArray` 是数组外面的结构体，`foreach` 和索引与数组相同；拉取器的入口改收 `ReadOnlySpan<int>`，否则不可变数组作为 `IEnumerable` 传进去会装箱。没有选更进一步的做法：每个从计划可达的类型（算子实例、编译后的表达式、特征定义）都冻结，或者给宿主一份计划的拷贝。前者要改所有算子的写法，后者每次查看都复制整份计划；它们防的都是强制转型之类的故意绕过，而这里要防的是顺手改了共享的东西。以只读接口公开、底层可变的集合（`Fallbacks`、`Warnings`、`PlanSchema.Columns` 等）也保持原样，理由相同。一个反射测试遍历从 `ExecutionPlan` 可达的计划类型，遇到公开 setter、数组、可变集合或 JSON 树就失败，所以新加的成员不会悄悄退回可变的写法。

- **失败尝试建立的槽位在回滚时丢弃，之后读起来和从未写过一样**（设计 4.6、13.4）。规则也只在 `CandidateTable` 一处：表记下槽位建立的顺序，检查点记下当时建立了几个，回滚把之后建立的槽位（失败节点自己的输出，或者它第一个写的共享行源槽位）连同填充位图一起丢掉，数组留到请求结束时归还。所以执行器对每次尝试都取检查点，不再只对有行效果的节点。原来这些槽位留着，理由是失败节点的输出不提交、没有人读；但 `col.x@node` 这种固定版本引用直接读该节点自己的槽位，不经过输出绑定：节点写了 99 之后超时并被跳过，线上读到 99，回放跳过录制为超时的尝试、从没建立这个槽位，读到缺失（评审 11）。丢弃之后两边都是“槽位不存在”，任何读取路径（当前版本、固定版本、算子的 `Read`、日志、输出）都读到缺失，读取方不用改。没有选在读取时检查“这个版本提交过没有”：标量后端、向量后端和 `OperatorContext.Read` 各要一份，新加的读取路径还得记得。尝试之前就存在的共享行源槽位不丢，只释放尝试追加的行，之前成功的行源写的行保持原值。代价：没有行效果的节点每次尝试多复制一次行顺序（5,000 行约 20 KB，从请求内存租借，不产生托管分配；与只对有行效果的节点取检查点相比，测得的延迟差别在噪声之内）。约束：节点只写自己的输出槽位，行源只写自己追加的行；回滚撤销不了写进已有槽位里其他行的内容，框架内置算子都遵守，自定义算子由作者保证，框架不检查。
- **一行在一个槽位里，没有被写过就是缺失**（设计 4.4、4.6）。规则只在 `CandidateTable`：新建的槽位里每一行都是缺失、未填充，包括槽位建立之前就已追加的行；追加的行和回滚释放的行在每个已有槽位里同样。写入方用 `Set`，或批量写值之后用 `SetValid`，标记自己写的行；忘了标记的行是缺失而不是错的值，不可空列会在提交时失败（见下一条）。原来没有有效位图的列算作全部有效：一个行源第一个写某列时，之前行源的行读到池里的旧数据，并且算作有效。两个行源写同一列时共用一个版本，各自只写自己追加的行。算子直接创建的临时列缓冲仍是“没有位图就全部有效”，它们只在写过的行上被读。所以写入方要对照真实的表槽位测试（测试中的 `TableWrites`）：写进临时缓冲区，漏标测不出来（评审 13：表达式写 bool 列时不标记，原有测试全部通过）。没有选的做法：列缓冲默认全部缺失（规则不再只属于表，所有临时缓冲区都要改）；用“前 N 行未写”之类的第二种表示省掉标记（每个读取方都要认识它）；让密集写入方声明“写了全部存活行”（多一个用错就静默出错的接口）。代价：表中每个槽位从建立起就带有效位图（5,000 行 632 B），整列写入多一次按行置位，同一个字的位先在寄存器里攒齐再写；示例流水线每请求多分配 8 B（候选表多了记录槽位建立顺序的字段），延迟约 +2%。
- **提交时不可空列在每个存活行上都要有值，`default` 不补缺失**（设计 4.3、4.6）。提交先按非有限值规则替换（有 `default` 用默认值，否则缺失），再按 64 行一个字比较存活位图和有效位图，有一行缺失就让节点失败，说明是 “left non-nullable column 'x' without a value on N of M live rows”。原来位图为空就当作全部有效、不检查；有位图时缺失的行用 `default` 填上，没写的行于是会悄悄变成默认值，与设计 4.6“`default` 不会填充一个没有产出者的列”相反。现在 `default` 只替换存不下的值：非有限值在提交时，超出 int32 范围的值在写入时。“一行都没写”和“写了缺失”合成一个检查、一条说明（原来分别是 “did not write non-nullable column” 和 “wrote a missing value into non-nullable column”）。行为变化：自定义算子把缺失写进带 `default` 的不可空列，或者没写全存活行，原来得到默认值或旧数据，现在节点失败，按 `on_failure` 处理。
- **行源后备的表容量按主节点和后备中较大的预留**（设计 4.8、5.6）。候选表的容量在请求开始时按各行源节点的行数上限确定；配置了 `fallback:` 的位置，取主节点和这次臂组合下所选后备节点上限中较大的一个。失败的主节点追加的行由回滚收回、后备复用，同一位置留下的只有一方的行。原来失败不撤销追加的行，曾按两者之和预留（提交 4e32cd9，否则主节点配额 1、后备配额 3 时后备只剩 1 行）；有了回滚就不再多预留。
- **`ModelScorer@1` 在加载时检查每个可能用到的模型版本**（设计 6.9）。每个版本：签名里的每个输入都必须在 `inputs` 里有映射，每个映射的输入都必须正好声明打分算子为它构造的张量（见下一条），每个映射的输出都必须是 float32、形状 `[-1]`（每行一个值，批维度动态）；否则加载失败，错误指向 `/inputs/<名字>`、`/outputs/<名字>`，缺少输入时指向 `/model`，提示说明打分算子支持什么。原来只核对名字，类型或形状不符、少给输入的版本也能加载，然后每个请求都失败或走后备。签名里有、`inputs` 没给的输入是错误，因为模型签名没有“可选输入”的约定。规则只在 `ModelTensorRule` 一处，三个模型算子共用（见“成对和列表级重排”）。
- **`ModelScorer@1` 的输入张量由列的类型决定，不看模型签名**（设计 6.9；1.0 之前的不兼容改动）。float32、float64、bool（0/1）的列或上下文值送 float32 `[rows]`；int32、int64 送 int64 `[rows]`，值精确；`vec<float32,N>` 送 float32 `[rows, N]`，按行连续；上下文值广播到每一行。可空、字符串、文本和列表类型在编译时就是 `MODEL_INPUT_TYPE`，指向 `/inputs/<名字>`，不需要客户端，`stratarec validate` 也能报；签名声明的张量和构造的不一样是 `MODEL_TENSOR_MISMATCH`，hint 给出两种改法：改签名，或者映射一个签名要的类型的衍生特征。原来每个输入都先求值成 float64 再转 float32，整数列超过 2^24 的值送进模型时被舍入，探针记录的却是原值，训练和服务看到的值不一样；向量列根本不能用。不让签名决定（比如签名声明 float32 就把 int 列转成 float32）的理由：回放按行输入的摘要匹配模型输出，摘要包含元素类型和形状（见“模型输出按实体和输入摘要匹配”）；回放引擎和 `validate` 编译计划时不加载模型客户端，不能依赖签名（`linear@1` 这类立即回答的客户端有签名，远程模型服务没有）；如果签名决定张量，同一份配置有没有取到签名会构造不同的张量，回放会把每行的输入都报成变了。现在只看配置就知道送了什么。模型要 float32 而列是整数时，映射一个 float32 衍生特征，这正是设计 6.9 第 2 条要的：训练和服务只有一份变换的定义。输入都是普通引用，所以直接从列的存储按存活行复制进一块从请求租借的缓冲，分批是它的切片，不再经过 float64 的中间列（示例流水线每请求少约 90 B）。代价：原来把整数列声明为 float32 的模型现在加载失败，要改签名或改映射；改成 int64 签名之后，旧引擎录下的这些调用在新引擎上回放时每行都是 `inputs_changed`（摘要里的元素类型变了），要重新录制，或者用旧引擎回放。浮点输入的摘要不变，旧录制照常回放（评审 26 实测）。`linear@1` 是浮点模型的替身，签名只声明 float32 `[-1]`，收到其他张量的调用失败；映射整数或向量列给它，加载时的检查先报出来。`random@1` 可以按真实模型的签名声明张量（见“`random@1` 是绑定层的替身”）。
- **成对和列表级重排：`PairwiseRanker@1`、`ListwiseReranker@1` 重排前 `window` 行，与 `ModelScorer@1` 共用一套编译和取值**（设计 5.9、6.9）。三个算子的绑定、版本、输入编译、逐版本签名检查和取值是同一份代码（`ModelCallCompiler`、`ModelInput`），张量规则只在 `ModelTensorRule`：每行贡献的值由列类型决定（上一条），前导维由算子的布局决定，逐行 `[rows]`，成对 `[pairs, 2]`（排名高的一行在前），列表 `[1, rows]`；上下文值对每个批次元素广播，分别是 `[rows]`、`[pairs]`、`[1]`。签名的维度规则对三个算子相同：动态维（行数、对数、列表长度）必须声明 `-1`，因为写成固定值的批次维遇到别的大小会在运行时失败；固定维（成对的 2、列表批次的 1、向量的 N）声明成那个值或 `-1`，签名用 `-1` 表示任意。这对 `ModelScorer@1` 是放宽，向量的 N 现在也可以声明 `-1`。
  - 成对：窗口里每一对都比较一次。行的分数是期望胜场 Σp，对 (i, j) 给 i 加 p、给 j 加 1 − p；不数 p > 0.5 的场次，因为那样丢掉模型的把握程度，还要逐对规定平分。平分按 `entity_id`，不按进入时的顺序。偏好是 NaN 或不在 [0, 1] 时节点失败，不截断：输出 logit 的模型截断之后按噪声排序，看不出错；失败则走 `on_failure`，配 `skip` 时保持原顺序。
  - `max_pairs`（默认 1225，即窗口 50）是加载期上限：`window · (window − 1) / 2` 超过它是配置错误，请求期不截断。设计原来写超过时只比较排名靠前的对：那样靠后的行比较次数少，期望胜场不可比；窗口是静态配置，对数在加载时就确定。`max_pairs` 本身最多 2^29：每个输入把每对的两行取进一个数组，再大就放不下，原来要到请求期才因溢出失败（评审 28）。代价：窗口不能随请求变化。
  - 列表级：一次调用，没有 `batch_size` 也没有上限：列表是模型的输入单位，拆开会改变模型看到的内容，`window` 已经限制了一次调用的大小。按分数重排的规则与按列排序相同：高的在前，NaN 在后，平分按 `entity_id`。
  - 回放：两种调用都不带逐行的键，按整次调用的输入摘要录制和匹配，因为输出属于一对或整个列表，不属于某一行。代价：映射输入的张量（类型、形状或值）变了，受影响的调用在回放里就是 `not_recorded`，节点按 `on_failure` 处理；不能像 `ModelScorer@1` 那样按实体合成。窗口里换了行或换了顺序，只在改变了这些张量时才算变：两行的映射值相同时，交换它们得到同一个摘要，复用录下的输出也是对的，因为模型看到的就是同样的输入；要按候选身份匹配，把 `entity_id` 映射为模型输入（评审 27）。
  - 效果都声明为 `RowOrder | ColumnWriter`，`score_col` 可选。效果按算子静态声明，不随配置变；不写 `score_col` 时多出的 `ColumnWriter` 不影响任何判断：拉取屏障只看 `RowSource`、`RowFilter`，同一 `order` 的依赖检查有 `RowOrder` 就成立，足迹和非空产出检查看编译时记录的输出列。`score_col` 必须是可空的浮点列，因为窗口外的行没有分数；没有声明时是 `float32?`。
  - 指标 `stratarec.model.pairs`（标签 `stratarec.model`）：节点每次运行，在发出调用时加上这次的对数，调用后来失败也算，它计的是成本；只在有监听时计数，回放不计。
  - 评审 26 建议的两项加固一起做了：取列时每个输入核对一次缓冲的实际类型与声明类型完全一致（同一类的不一致原来会被接受）；`linear@1`、`random@1` 要求输入的首维等于 `BatchSize`。
- **生成类算子在可选包 `StrataRec.Llm`，提示词用 Mustache，第一个算子是 `LlmReranker@1`**（设计 5.9 第 1–5 条、13.4 第 7 条）。框架不运行模型：大模型由用户实现的 `IModelClient` 接入（文本进、文本出），框架负责模板、调用、解析回答和回放。包与 `StrataRec.Redis` 一样放在 `src/`，核心包不引用它，CLI 引用并注册。扩展包里的模型算子要用到的绑定、版本与签名检查、带种子的调用，从 `StrataRec.Pipeline` 公开成 `BoundModel` 等少数类型，不用 `InternalsVisibleTo`：第三方写模型算子需要同样的东西。
  - Mustache：模板没有逻辑，需要计算的值做成衍生特征，训练和服务共用一份定义，提示词里不出现第二种表达式语言。不做 HTML 转义，提示词不是 HTML，`{{x}}` 与 `{{{x}}}` 相同，这是有意与 mustache(5) 不同。不支持 partial 和改分隔符（加载错误）：每个模型输入一个模板，改分隔符会让错误的偏移难以对应。名字在加载时按节点的作用域解析（`ctx.*`、`param.*`，`rows` 区段里的 `col.*` 和 `rank`），记为节点的读取，所以特征先拉好；未知名字给出近似名。缺失值显式：可空引用必须在同名区段里使用，否则加载错误；`{{^rows}}`（窗口非空才调用，永远不渲染）和对必有值的标量开区段（总会渲染）也是加载错误。float32 按 float32 的最短往返形式渲染，`0.1` 显示为 `0.1`。区段最多嵌套 32 层：绑定和渲染每层递归一次，原来 60 万字符的深层模板在加载时就让栈溢出、进程退出（评审 29）。渲染写进每个线程保留的一个 builder，所以线程渲染过之后，每次请求只分配交给模型的提示词字符串；超过 256 Ki 字符的 builder 不保留，这么长的提示词每次还要分配 builder，因为让每个线程一直占着这么大的内存更不划算。Mustache 的解析器和语法树是包内部的类型，公开的只有 `PromptTemplate`：通用模板引擎不是这个包要长期兼容的接口。
  - 回答：必须是严格的 JSON 数组，只剥最外层的一层代码围栏，里面的反引号是内容（例如 JSON 字符串里的 ```，评审 29）；不从文字里抠数组，因为那会掩盖提示词的问题，行为也随模型变化。部分有效的回答很常见，所以不在窗口里的元素（包括不是合法 Unicode 的字符串，无论是 JSON 转义的还是客户端字符串里原样的孤立代理字符：后者在编码成 UTF-8 之前改写成转义，否则编码器把它换成 U+FFFD，可能正好是另一个实体的 ID，评审 30；它若紧跟在奇数个反斜线后面，本身就是一个非法转义的字符，改写成转义会和前面的反斜线拼成合法的 `\\uD800`，所以这时写成 U+FFFD，回答仍是非法 JSON，评审 31）和重复元素忽略并计数（`stratarec.model.answer_ids`，`outcome = used | unknown | repeated`）；一个有效元素都没有，或者不是数组，节点失败并引用回答开头，不改顺序，交给 `on_failure`；回答被截断时消息里说明，并提示调大 `max_output_tokens` 或缩小窗口。`answer` 没有默认值，由提示词决定：`rank` 省 token，`entity_id` 不会因为模型看错位置排错行。没列出的窗口行默认跟在后面（`keep`），也可以丢弃（`drop`）；效果静态声明为 `RowOrder | RowFilter`。
  - `max_output_tokens` 由客户端执行，因为只有客户端有分词器：客户端在 `ModelStatus` 里回报生成的 token 数和是否在上限截断，引擎在模型调用结束的同一处为所有模型算子计数（`stratarec.model.output_tokens`、`stratarec.model.truncated`），回放不计。设计原来写由算子停止读取，算子拿到的是完整的回答，无从停止。
  - 回放：调用按整次调用的摘要录制（提示词和 `max_output_tokens`；设了上限才进摘要，所以原有录制不变），种子是请求的种子，回放包里已有，不进摘要。录制保存回答原文、token 数和截断标记，回放返回同样的状态和消息；提示词只存摘要，不存原文，控制回放包的大小。代价：模板或提示词里的特征一变，调用就是 `not_recorded`，节点按 `on_failure` 处理；要看提示词原文，目前只能本地重新渲染。
  - 文本签名只检查元素类型是 text，不检查形状：各种推理服务对文本张量的形状约定不同（`[]` 或 `[1]`），而算子每个输入总是一个字符串。
  - 本地替身 `fixed_text@1`（`StrataRec.Models`）：设置声明文本输入和每个输出的固定回答，每次调用都回答它们，用于本地开发、测试和示例。
  - 第二期：`LlmAnnotator@1`（逐行标注）和 `GenerativeRetriever@1`（生成候选）。三个算子共用一个 `PromptTemplate`，按作用域区分：窗口（`rows` 区段，重排）、逐行（顶层的 `col.*`，标注）、整请求（只有 `ctx.*`、`param.*`，生成召回）；用了别的作用域才有的名字是加载错误，从别的算子拷来的模板在加载时就失败，而不是到模型的回答里才看出来。严格的数组遍历、围栏和引用回答只在 `LlmAnswer` 一处，元素怎么解释由各算子决定。`SlateGenerator@1` 不做：整页生成就是生成召回接大模型重排，没有单独算子的必要。
  - 标注每行一次调用（批大小 1，录制按实体做键）：一行的提示词只依赖这一行和请求，回答可以按实体复用，窗口变了也能逐实体回放；多行一次调用的回答绑在整个窗口上，窗口一变整次调用就是 `not_recorded`。代价：调用数等于窗口大小（默认 20，并发），每行分配提示词和调用对象，这是按外部调用分配，不是按候选。回答按列类型解析：文本去掉首尾空白和最外层围栏，空回答不可用；类别精确比较、区分大小写；bool 不区分大小写；数字用 JSON 数字语法，有限且在列的范围内。不可用的行就是缺失，不猜，不填默认值。有行缺失时节点是 `Degraded`，原因里写计数、第一个失败和第一个不可用的回答；所有调用都失败才是 `Failed`，交给 `on_failure`；一行的客户端抛异常只算这一行失败，预算用完或调用方取消仍让节点失败。指标 `stratarec.model.answers`（`outcome = used | unusable | failed`）。没有声明的列是 `text?`，有 `categories` 时是 `string?`。
  - 生成召回：一次调用，回答是实体 ID 的数组，最多用 `max_items` 个，它就是节点的行上限，决定候选表的容量。类型不对、重复、表里已有（`present`）、超过上限（`over_limit`）的元素跳过并计数；已有的行原地不动，因为行来源只追加、只写自己追加的行，失败时也只回收这些行，去标记别的来源的行就成了不能回滚的 `ColumnWriter`。超过上限之后的元素不再解释，但整个回答仍须是合法 JSON：截断的回答即使前面已有足够的 ID 也失败，与重排的严格规则一致。空数组是合法回答。生成的行和其他追加的行一样由拉取规划补齐特征；`rank_col` 是元素在回答中的位置，跳过的元素也占位置，与 `recall.best_rank` 一致。接在召回之后时，召回的归因列（`recall.*`）要声明为可空：生成的行没有这些值，按“缺失显式”不能写 0，加载时由 `ROW_SOURCE_AFTER_COLUMN` 指出。
  - 回放：单行调用的文本从“单独调用这个实体、输入相同”的成功录制合成，生成的 token 数和截断标记一并带回；多行调用的文本属于整次调用，不能拆分。合成不出来时，只用别的输入回答过的实体报 `inputs_changed`，其余报 `not_recorded`。按键取录制时还要求每行的输入摘要相同，失败的录制也一样：原来只比实体，同一模型、同一实体、另一个提示词（另一个节点）的失败会回答这次调用，挡住录制里它自己输入的成功回答（评审 30）。输入变了的调用即使录制里失败过，也按实体合成并报缺口，不重放那次关于别的输入的失败。
- **`GroupAggregate@1` 是分组统计的入门算子**（“范围调整”里组由成员决定的那种分组）。按一列分组（int64、int32、string）或者整张表一组，算 `count`、`sum`、`mean`、`min`、`max`、`std`（总体标准差）或 `rank`，写回组内每一行。用组合代替选项：每个作者最多两条是 `rank` 加 `ExpressionFilter`，请求内的分数标准化是不分组的 `mean`、`std` 加 `ExpressionScorer`，商家的组得分是按商家的 `max`；示例 `home_feed` 用前一种。`rank` 的顺序和 `TopK@1` 相同（缺失排最后、平分按 `entity_id`，同一个 `RowRanking`），所以组内名次留下的正是对这组做 TopK 会留下的行。缺失是显式的：分组键缺失的行不属于任何组，输出缺失；值缺失的行不参与统计，一组没有值时输出缺失；可能缺失的输出必须是可空列，声明成不可空时编译报错并提示。没有声明的输出列由节点隐式声明（`count`、`rank` 是 int64，其余 float64），声明了的可以是同类的另一种宽度（int32、float32）。输出是一个以列名为键的对象，实验可以单独增、改、删一项。值按 float64 读（同 `MmrDiversifier@1`）。分组用请求内存：字符串用列的字典码，整数排序后编号，不按行分配。`top_k_mean`、`logsumexp` 和父子表的 `ChildAggregate` 有实际需求时再加。分组列或值列有错时，输出不能声明的列标为不可用，读它的节点不再连带报错（同评审 41 的召回列）。`mean` 和 `std` 按行序用 Welford 递推：相同的值均值就是这个值、标准差恰好是 0；原来均值由和除以个数得到，差一个 ulp，再以它为中心算离差，相同的值标准差不为 0，标准化出 ±1（评审 44）。每步加的是 x/k − mean/k 而不是 (x − mean)/k，所以既不会因为求和溢出，也不会因为两个异号大值相减溢出而算不出可表示的均值（评审 45）；离差超过约 1e154 时平方仍会溢出，输出变成非有限值，按提交规则处理。这里的值是分数和特征，不为这种量级做缩放。
- **没有声明的输出列在每个臂组合里只有一种类型**（评审 44）。隐式输出由第一个编译到的变体声明类型，所有组合共用这一份 schema；另一个变体写成别的类型（实验把 `count` 改成 `mean`，或者加一个可能缺失的分组键让输出可空）时，原来按第一个类型编译：均值被写成整数，缺失的计数让请求失败，而校验全部通过。现在 `TryWriteColumn` 对已经隐式声明的列要求类型完全相同，否则报 `COLUMN_TYPE_MISMATCH`，位置是后编译的那个变体（实验的改动在臂的补丁里）。只差可空性时提示在 `columns` 里声明成可空类型，两个变体都能写；种类不同时提示写到另一列。没有选“自动取更宽的类型”：读这列的表达式和下游算子是按某个类型编译的，静默变宽会改变它们在其他组合里的行为。
- **配置里写 `null` 的地方，模型说不能为空就是绑定错误**（评审 44）。所有产物、算子配置和请求文件都经过 `ArtifactSerializer`：成员由 System.Text.Json 的 `RespectNullableAnnotations` 检查，集合的元素（`"outputs": { "x": null }`、`"source_order": ["a", null]`）由 `NullElements` 按成员的可空注解检查（序列化器不查元素）。错误在值的指针上，用 “must be …, got null.” 的说法，同其他绑定错误。原来只有回放包有自己的遍历，算子配置里的 null 一路传到读它的代码，变成没有位置的异常（流水线的列、请求输入、模型输出、召回的来源顺序和 `GroupAggregate@1` 的输出都会）。遍历的是文档，不是绑定出的对象，由序列化器自己的 `JsonTypeInfo` 引导（成员的 JSON 名字、集合和字典的元素类型、多态类型按鉴别字段）：位置就是 null 写在文档里的位置。先后试过遍历绑定出的对象：会执行只读的计算属性（返回 `this` 的无限递归，评审 45），位置要从对象重建，而 enum 键、`"01"` 这样的数字键、带小数秒的日期键读回来拼法变了，`HashSet`、`SortedSet`、`Stack` 去重、重排或倒序，指针指向别的值或不存在，键专用的转换器还会让诊断本身抛异常（评审 46）。根是集合时也走它的元素（实验补丁的段是字典），但根的元素可空性未知，元素为 null 时放过（补丁里的 null 是删除）；有自己转换器的成员和序列化器不当作对象、列表或字典读的类型不往里走；扩展数据的项在对象本身的层级。只查序列化器真正读的成员：有 setter、经构造参数或按 populate 填写的；忽略的（`[JsonIgnore]`）和只有 getter 的计算属性，序列化器跳过文档里的值，检查也跳过，原来照样检查，合法的输入被拒（评审 47）。忽略的成员连同同名的构造参数都不读；类型或选项上的 populate 只是偏好，结构体、数组、不可变或只读的集合退回替换，没有 setter 就不读，只有成员上明写的 populate 一定生效（序列化器不能填写时拒绝这份契约）；扩展数据成员不被填写时，归它的成员也不查（评审 48）。能不能填写由序列化器的转换器决定，它没有公开：能创建的集合（`JsonTypeInfo.CreateObject`）算能填写，此外还有序列化器能往里加元素、但不能创建的集合（只有带参数构造函数、派生自 `List<T>` 或 `Dictionary<K, V>` 的类型，只实现 `ICollection<T>` 的类型），按转换器填写的形状认（列表、集合、字典、队列、栈），数组和 `System.Collections.Immutable` 的集合除外。原来只看能不能创建，前一种被当成不填写，其中的 null 漏查（评审 49）。测试逐个类型和序列化器的实际行为对照。经构造参数填写的成员按参数的注解检查：文档读进的是参数，构造函数可以接收 null 再滤掉，属性的注解说的是滤过之后。有值的 `Nullable<T>` 按 `T` 走（它自己的类型信息是不透明的，原来里面的 null 元素漏掉了，评审 47）。文档里没有任何 null 时不遍历（字符串入口的严格检查顺带记下有没有 null，树入口先扫一遍；树里的 `JsonValue` 可以包着 CLR 的数组或对象，按它写出的 JSON 种类算，同样的 JSON 不因树的建法不同而漏查，评审 47），每个类型的成员只查一次，只在绑定时运行。`DataFile` 按字节读：先按文本读时非法字节被替换成 U+FFFD，被替换的 id 成了另一个 id（评审 46）；数据文件因此和工作区的其他 JSON 一样只能是 UTF-8（可以带 BOM），UTF-16 的文件报错并提示转存为 UTF-8。可空性只能来自注解：新的模型成员或配置成员按需要写成 `T?`，绑定就按它检查，不用另外登记。
- **结果按列构造，逐行的 `Items` 在第一次读取时才生成**。`PipelineResult` 和 `RecResult` 持有 `Columns`（`ResultColumns`：按名次排列的 id 数组，每个输出列一个 `ScalarValue[]`），`Items` 是由它生成的逐行字典，只生成一次：第一次读取时在锁里生成，之后不加锁读取（原来用比较交换发布，多个线程同时第一次读取时各自生成一份，只留一份；评审 44）。返回的行通常远少于召回的行，逐行字典最好用；少数宿主返回大量行再处理，按列读不必为每行建字典（5,000 行 8 列：列约 1 MB，逐行约 3.4 MB；性能审计）。`RecResultJson` 和 `stratarec replay` 都按列写，所以只把结果写成 JSON 的宿主也不再建逐行字典。没有选“请求里选结果形式”的开关：使用者要先知道有两种形式、在请求时选对，而按列构造、逐行按需生成，两种读法都不多付成本。手工构造结果（测试替身）用 `ResultColumns.FromItems`。
- **`SlidingWindowQuota@1` 按组排队**。每一步放“所在组在最近 `window − 1` 个名次里不到配额的最早一行”，语义不变；原来每一步从头扫描未放的行、再逐个数窗口，O(n²·window)，5,000 行两组各半连续排列时 9 ms。现在每组的待放行按原顺序排成队列，配额未满的组按队首的位置放进堆，放一行就把滑出窗口的那一行减掉，可能让它的组重新入堆；O(n log G)。等价性用随机分布（连续段、打乱、无组的行）与原算法逐一比对。分组键编号与 `GroupAggregate@1` 共用 `RowGroups`。
- **`MmrDiversifier@1` 按公式取相似度，λ 在 [0, 1] 内由编译保证**。每一步取 λ·分数 − (1−λ)·(与已选行的最大相似度) 最大的行，第一步只看分数；相似度是余弦，可以为负，任一方没有向量（或是零向量）时为 0。原来“最大相似度”从 0 开始取最大，等于把相似度截到非负：和所有已选行方向相反的行被当成无关的行，排序与公式不符（外部评审）。第一步取分数最高的行（λ = 0 时公式里的分数项都是 0，第一行也按分数选，不按进来的顺序）；没有分数的行排在所有有分数的行之后，按进来的顺序。原来没有分数记作 −∞，λ = 0 时为了不算 0·(−∞) 把分数项一律写成 0，−∞ 也变成了 0，没有分数的行排到有分数的行前面（评审 49）。λ = 1 时只按分数，不算相似度：有限但范数超出 float 范围的向量，余弦是 NaN，0·NaN 仍是 NaN，原来让顺序不再看分数（评审 49）。0 < λ < 1 时这种向量的相似度同样是 NaN，没有为这种量级做缩放；但“没有分数的行排在后面”不靠 −∞ 比较保证：还有有分数的行时，没有分数的行不参加选择。NaN 比 −∞ 还“小”，原来第一个剩下的行没有分数也会被选中（评审 50）。固定的 λ 编译时检查；参数形式的 λ 要求 `param_schema` 声明的 min、max 在 [0, 1] 内（`TryParam` 的 `within`，通用于需要取值范围的算子）：参数值按声明校验、实验不能放宽，所以运行时读到的值一定在范围内，不用每个请求再查，也不用选“截断”还是“失败”。超出时惩罚变成奖励（λ = 2 原来照样通过）。选择逻辑抽成 `Order`，测试拿一份直接按公式写的参考实现在随机小窗口上逐个对照，比再加完整示例更能守住算法语义。
- **`TopK@1` 按精确的排序键比较**（设计 5.7）。原来分数都转成 double 比较，超过 2^53 的不同 int64（例如按 `entity_id` 排序时的大 id）会相等，再按 id 升序平分，于是升序和降序给出同样的顺序。现在 int64、int32 用翻转符号位后的无符号 64 位键，float64、float32 用 IEEE 754 全序键（−0.0 当作 +0.0），降序取反；缺失和 NaN 仍排在最后，平分仍按 `entity_id` 升序，不按行分配。排序键只在 `RowRanking.TryGetSortKey` 一处。`MmrDiversifier` 例外：它对分数做浮点运算（相关性减去相似度惩罚），仍按 float64 读取，超过 2^53 的 int64 分数会丢精度。

## 特征拉取

一次拉取按 `max_batch` 拆成多个分批，每个分批是一次连接器调用。示例请求 5,000 候选时有两百多个分批，原来每个分批约 420 B，占请求分配的四分之三。下面几条让连接器同步返回的分批不再分配（按分批数翻倍的测试锁定为 0 B）。

- **一次拉取的所有分批共用一个暂存区**（设计 4.5、6.5）。分批在连接器线程上并发写入，超时被放弃的分批还可能在请求返回之后继续写，同时别的分批正在被回填读取。所以布局保证任何两个分批都不写同一块内存：定长值、向量、`string` 和 `text` 每个字段一个数组，按拉取内的键序号排列，每个分批只写自己那一段；每个分批的“已写入”位从 64 位字的边界开始，因为两个线程同时写一个字会丢位；列表字段每个分批一个缓冲区，因为列表的数据区会增长、搬移。`string` 先按引用暂存，回填时才做字典编码，因为字典也不能并发写。连接器拿到的 writer 是分批的视图：连接器同步返回后，同一个视图对象接着指向下一个分批；异步返回的调用独占自己的视图，直到连接器真正结束。没有选的做法：每个分批一套缓冲区（原做法：暂存对象、列数组、每字段一个列对象和一个字符串字典，再加每字段一次租借）；在请求内复用分批的暂存对象（被放弃的分批还在写，复用要等它真正结束，省下的只是对象本身，列和字典照样要建）；用原子操作写位图（每写一个值多一条带锁指令）。代价：分批很小时位图有浪费（`max_batch` 为 25 时每 25 个键占一个 64 位字）；写过列表的分批仍各有一个列表缓冲区；连接器不能保留 writer，`IStagedFeatureValues` 也只在 `Record` 调用期间有效；`SetString` 收到 null 直接让这次调用失败，否则要到回填编码时才在请求线程上出错。
- **一次拉取共用一个取消源和一个时间预算**（设计 4.8、5.4）。拉取开始时算一次预算，同时定下拉取的截止时刻（开始时刻加预算）；有分批要发出时，创建一个关联调用方令牌、到预算时取消的取消源，所有分批的连接器拿同一个令牌。原来每个分批一个关联取消源和一个定时器，等待时再建一个定时器。取消源按引用计数：拉取本身持有一份，直到所有分批发出；每个发出的分批持有一份，直到它的连接器真正结束；最后一份释放时才 Dispose，所以不理会取消、迟迟才结束的连接器手里的令牌一直有效。等待连接器不依赖这个取消源：异步返回的调用用 `WaitAsync(剩余时间, 调用方令牌)` 等待，剩余时间是截止时刻减当前时刻，最少为零，所以后发出的分批不会重新拿到完整预算。原因：取消源触发时，注册在上面的回调在触发它的线程上同步、逐个执行；连接器可以注册自己的回调（释放网络资源、等清理锁），其中一个阻塞，挂在同一个令牌上、排在它后面的等待就一直收不到取消，整个 `Ensure` 跟着卡住，源超时和请求截止时间都失去上界（Codex review 8）。分类不变：调用方令牌已取消算 `cancelled`；等待超时（`TimeoutException`），或连接器响应共用令牌抛出取消，算超时，失败文字相同。局限：调用方的取消通过关联令牌同步传到连接器的回调，阻塞的回调仍会拖住调用方自己的 `Cancel()` 调用，框架无法阻止。代价：每个异步返回的调用一个定时器（同步返回的调用不等待，仍然不分配）；后发出的分批实际等待略少于预算，少的是发出前面分批所用的时间（微秒级）。连接器的同步部分在发出它的线程上执行、没有上界（接口文档写明了），所以每个分批发出之前看一次截止时刻和调用方令牌，判断规则与“晚到的回答”是同一个（`CutOff`）：时间到了或调用方取消了，剩下的分批不再发出，按超时或取消失败，录成“未发送”，回放照录制结果失败，不访问连接器，也不用回放时的时钟重新判断。原来照样一个个发出，每个都拿着已取消的令牌、跑一遍自己的同步部分，延迟随剩余分批数增长（外部评审：50 个分批、第一个同步部分用完预算，49 个白白发出，约 1.1 s）。缓存回源的分批同样处理（它们不逐个录制）；分布式层的读取本来就这样做。上下文特征的各个源也是一个接一个发出的，同样在发出前判断：前一个源的同步部分里调用方取消了，后面的源不再发出（评审 49）。
- **同步完成的调用不分配**（设计 4.8、15）。拉取内部的调用返回 `ValueTask<FetchStatus>`：连接器同步返回时，记录调用、释放请求内存都在调用点当场完成，不建租约，也不建状态机；只有连接器真正异步时才分配等待要用的对象（租约、续体、状态机、限时等待和它的定时器）。内存规则不变：每个仍在运行的外部调用持有一次请求内存，直到连接器结束并且调用点记录完毕，`stratarec.io.abandoned` 仍然是每个仍在运行的调用计一次。没有用 `PoolingAsyncValueTaskMethodBuilder`：没人等待的预取永远不会把池化的状态机还回去。
- **`EntityKeyBatch` 是只读结构体**（1.0 之前的不兼容改动）。每次连接器调用一个批对象，分批多时是可测量的分配。连接器的 `FetchAsync` 仍按值接收（异步方法不能有 `in` 参数），`IFeatureCallHook.Begin` 和 `Replay` 改为 `in`。自定义连接器和钩子要重新编译；拿批对象的引用做键或判断是否同一批的代码不再成立。

## 本地特征表

第一阶段做了存储引擎（`src/StrataRec.Features/Local/`）：表、写入器、读取 API、更新来源的契约、`snapshot_files@1`，以及测试用的 `memory_updates@1`。第二阶段接入了 `local` 供给方式：绑定、宿主里的表生命周期、请求读取路径、回放和指标（本节后半）。第三阶段接入了 `cache` 供给方式（本节末尾）。Kafka 来源和节点本地磁盘快照还没有做。

- **单写线程、读取无锁：读者能碰到的东西要么发布后不再改，要么整体替换**（设计 6.6 第 3、4 条）。记录先写进页末尾的空闲区，再用一次 release 写把位置发布到索引槽；索引、页目录和字符串字典增长时复制到新数组、填完整之后再发布引用，旧数组不再写；读者用 acquire 读到位置之后才读键、页和记录，页号或字符串码超出手里的目录或字典时重新加载一次。完整规则写在 `LocalFeatureTable` 的注释里。没有选的做法：读写锁或 seqlock（读者在按行的路径上要重试，写得频繁时读者会被饿死）；每条记录一个对象（几百万个对象都要被垃圾回收器扫描）。x64 是 TSO，普通读写本来就有 acquire/release 语义，`Volatile` 只是不让 JIT 重排，所以压力测试（一个写线程、三个读线程，专用线程、固定工作量，`taskset -c 0,1` 下也通过）在 x64 上证明不了硬件重排类的错误。故障注入改的是程序顺序：先发布位置再写记录、读者不重新加载页目录、索引或字典在复制完成前发布，都能被测试抓到；字典那一项要把不同字符串的数量提高到百万级才稳定复现。CI 没有 ARM64，ARM64 上的内存序没有经过测试。
- **索引是一个键和位置交错的 `long[]`**（设计写的是 `IndexKeys`、`IndexPositions` 两个数组）。一次探测只碰一个缓存行，两个数组要碰两个。位置是 `(页号 + 1) << 32 | 页内偏移`，0 表示空槽，新数组不用初始化。装载率不超过一半；条目从不删除（删除是墓碑记录），读者的探测序列不会断开。int64 键分块查找：先读一块键的初始槽，再完成探测、解析记录，让一块键的缓存未命中同时进行，而不是一个键一个键地等。
- **字符串键用 XXH3-64（种子 0）对 UTF-16 码元求哈希，键和 `text` 都存 UTF-16**。`TextColumn` 存的是 .NET 字符串，查找时直接比较 `ReadOnlySpan<char>`，读写都不用转码。代价：以 ASCII 为主的数据多占一倍空间。哈希相同的键靠记录里的原键区分。
- **记录头带整条记录的长度，变长数据和定长部分在同一页里相邻**。记录是一段自包含的字节，压实时整段复制，只需要把字符串码重新编码。`list<string>` 的元素也存成表内字典的码。
- **字符串字典属于版本，压实时重建**。压实把记录复制到新版本时，字符串码重新编码进新版本的字典，不再使用的字符串随之丢弃。没有选全表共用一个只增不减的字典：高基数的 `string` 字段会让字典无限增长。
- **压实按字节触发，墓碑一直保留到 reload**（设计 6.6 第 4 条）。被替代的记录超过记录总字节数的一半、并且不少于 `CompactionMinBytes`（默认 1 MiB）时压实。按字节而不按条数，是因为变长记录大小不一；有下限是为了不让小表每几次更新就重建一次。压实在写线程上同步进行，期间更新等待，读者不受影响。压实按记录原来的页序复制，每个新页只开到装下剩余记录所需的大小（不超过 `PageSize`），通常不比原表大；按索引槽的顺序复制会把大小不一的记录混在一起，每页末尾空得更多，副本常常比原表还大。按页序复制也不保证不变大：新开的页按剩余字节开满一页，下一条记录比这页剩下的空间大时只能另开一页，开好的页就几乎空着。例如 `PageSize` 64 KiB，键 1 是空文本、键 2 是 4 万字符的文本：原表是一个小页加一个装键 2 的页，84,632 B；副本先开一个 64 KiB 的页放键 1，键 2 放不进，再开一页，146,072 B（评审 11）。墓碑在压实时保留，否则晚到的旧更新会让已删除的键复活；reload 从空表开始，快照就是那个位置上的全集，所以 reload 之后墓碑不再保留。
- **`max_bytes` 计当前版本的页、索引、页目录和字典，按字节精确执行**（评审 9、11）。写入之前算出它实际会增加的字节：新页、索引增长、字典里还没有的每个不同字符串（同一记录里重复的只算一次），以及加入它们时经过的每一次字典扩容。一次写入会超出、又有被替代的记录时，在旁边建一个不发布的压实副本，按副本重新计算；副本加上这次写入放得下才换上，否则丢弃副本并抛 `LocalTableFullException`，表完全不变（版本、字节数、generation）。自动压实和显式 `Compact` 用同一个构建过程，副本单独放得下才换上：自动压实放不下就静默放弃，被替代的字节翻倍之前不再尝试；显式 `Compact` 放不下就抛异常。副本可能比原表大（压实时页按剩余字节开满，下一条大记录放不进就要再开一页），所以这两处检查都会走到，各有回归测试。试算用的副本不能被写入器留住：提交内复用的字符串查找结果只在一次 `Commit` 里有效，由同一个 `finally` 清掉。代价：副本的最后一页正好装满，表离上限不到一页、又没有被替代的记录时，写入会失败，直到调大 `max_bytes`；上限通常比页大几个数量级，不为此缩小新页。空表本身超过 `max_bytes` 时建表就失败。压实和 reload 期间新旧两个版本同时存在，进程短时间需要约两倍的内存，`max_bytes` 不算这部分。`cache` 的记录头版本就是写入时间，按写入时间淘汰的入口是 `Compact(dropWrittenBefore)`；`cache` 写回的版本取拉取发起的时刻，否则发起得早、返回得慢的拉取会盖掉较新的结果。
- **读取是一次查找加按块填充**（设计 6.6“读取路径”）。`Lookup` 为每个键给出一个记录引用，同一张表的所有特征共用；多字段 `Fill` 把行按 128 行分块，先把每块记录要用到的缓存行都读一遍，让未命中同时进行，再逐个字段填这一块，记录在 L1 里被所有字段复用。按行的循环不做边界检查，安全靠每次调用开头的一次检查，检查的是副本：行、记录引用和读取说明先复制进从 `ArrayPool` 租来的数组，检查副本，循环只读副本。只检查调用方的 span 不够：行可以就是某个目标列自己的数组，写进第一个值就改了还没用到的行，下一行就落到列外（评审 9 的例子）；行也可以和非有限值计数重叠，或者在检查之后被别的线程改写。复制的代价在 500 行时每次调用约 1 μs，约占 30 个特征热缓存填充的 3%。缺失时填缺失的列在循环开始前就建好有效位图，即使最后没有缺失的行：循环里只要有一次调用，JIT 就把循环的状态放到栈上。填充位由调用方处理：每一行的每个字段都会被填，同一张行位图 OR 进每个槽位即可。`float32`/`float64` 的 NaN 和 ±∞ 原样存储，读取时按缺失处理并计数，向量分量原样返回，与暂存区回填（设计 4.3）一致。`text` 读取时要新建字符串，等文本列改存 UTF-8 之后才能不分配（设计 4.4）。
- **读取测量没有达到设计估计的 20 μs**。`LocalFeatureTableBenchmarks`：100 万条记录、每条 30 个特征（25 个 `float32`、2 个 `int64`、1 个 `bool`、1 个 `string`、1 个 64 维向量，约 400 B），一成的键不在表中，0 B 分配。在开发机（Xeon 6975P-C，KVM 虚拟机，.NET 8）上：同一组键反复读（数据都在缓存里）500 键 34 μs、5,000 键 490–505 μs；每次换一组随机键 500 键 51 μs、5,000 键 830–860 μs，其中查找本身 10 μs 和 120 μs。每个字段单独调用一次 `Fill` 时，500 键慢一倍多，5,000 键慢两倍（每个字段都把全部记录再走一遍，还要各复制一次行和记录引用）。热缓存时一个 `float32` 值约 1.5 ns，按列的循环每个值二十来条指令，已经到了这种做法的下限；换键之后多出来的部分主要是 TLB 未命中：4 KB 页随机访问 400 MB，虚拟机里还要走两级页表。要再快，可以试大页（.NET 的 GC 堆默认不用透明大页），或者为连续的同类型字段写按行读取的内核，等接入请求路径、有真实的特征组合之后再决定。
- **快照是 JSON Lines 数据文件加一个 manifest**（`snapshot_files@1`）。设计提到 Arrow 等列式格式；第一阶段选 JSON Lines：标准格式、能手写，错误能指到“文件:行”和 JSON 指针，也不引入 Arrow 依赖。快照覆盖的更新流位置写在 manifest（`snapshot.json` 的 `position`）里，不写在数据文件头：数据文件可以由多个任务并行写，最后写入 manifest（先写临时文件再 rename），读者不会看到半个快照。每次加载都是一次 reload：在读者看不到的新版本里构建，完整之后整体替换；失败就放弃新版本，读者继续用旧的。manifest 内容没变就不重新加载；第一次运行时，如果表的位置已经等于 manifest 的位置也跳过（从本地磁盘恢复之后接着跑）。`reload` 写 ISO 8601 时长（`PT1H`），设计里写的是 `1h`：配置只用标准语法。超出 `float32` 范围的数读成 ±∞，与 `memory@1` 一致（两者都用 System.Text.Json），之后按非有限值处理。加载吞吐（`LocalFeatureTableLoadBenchmarks`，10 万条上面那样的记录，每行约 1 KB）：经 `RecordBuilder` 直接写约 240 万条/秒，解析 JSON Lines 约 20 万条/秒，`RecordBuilder` 只占其中不到十分之一，其余是 JSON 解码（每行约 90 个数）。一行先写 `key` 和 `version` 时字段只扫描一遍，否则先跳过 `fields`、读完整行之后再解码它。
- **写入器的接口比设计多了几样**（设计 6.6 末尾的 `IFeatureTableWriter`）。`Begin` 和 `Delete` 另有 int64 键和 `ReadOnlySpan<char>` 键的重载，解码器不用为每条消息建 `EntityKey` 或字符串。`RecordBuilder` 是值类型句柄，要显式 `Commit`：解码到一半出错的消息不提交就是放弃，下一次 `Begin` 会丢弃它。`Delete` 返回是否因版本过旧被忽略。`BeginReload`、`CompleteReload`、`AbortReload` 对应设计中“建好新版本后整体替换”；reload 期间不能 `Checkpoint`，位置只随完整的 reload 前进。
- **交叉特征（cross 实体）不能放进本地表**。`LocalTableSchema.FromCatalog` 直接拒绝并提示用 `fetch`：交叉特征的键空间没有上限，正是设计表中 `fetch` 适用的情形。
- **绑定写成 `"mode": "local"`，`max_bytes` 和 `bootstrap` 与 `mode` 平级**（设计 6.4 把 `max_bytes`、`max_lag_ms` 放在嵌套的 `local` 对象里）。每个设置只属于一种模式，写了另一种模式的设置是错误，指针指到那个设置，提示删掉它或者改模式：从 `fetch` 改成 `local` 的绑定不会留下一个静默失效的 `timeout_ms`。平级之后每个设置只有一个位置，错误指针也短。设置和模式的对应关系只写在 `FeatureSourceResolver.ModeSettings` 一处，测试用反射核对它覆盖绑定类型的每个属性：以后加的设置忘了归属，测试就失败，而不是被另一种模式默默接受。连接器自己的设置（绑定里没有声明的成员）只属于 `fetch`；来源自己的设置写在 `bootstrap` 里面。`max_bytes` 写整数加 IEC 单位（`16MiB`），JSON Schema 的 `pattern` 和解析器接受同样的写法。`max_lag_ms` 和 `updates` 不做，见下一条。绑定的每个问题一次报完（另一种模式的设置、缺少的 `max_bytes` 或 `bootstrap`、未注册的来源类型、来源设置的错误），`stratarec validate` 不加载表，所以不需要快照文件。同一个数据源的每个实体一张表，每张表一个来源实例：来源可以有状态（流消费者），不能在两张表之间共用。
- **`max_lag_ms` 和 `updates` 不在框架里做**（设计 6.4、6.6 第 6 条）。设计让框架在追上更新流之前不就绪、运行期延迟超限时把读取方标成 `Degraded`，并用 `updates` 把快照来源和更新流来源串起来。都不做：（1）先追上再服务，现有契约就能做：来源在 `BeginReload` 之后加载快照、把更新流消费进这个版本，追上之后才 `CompleteReload`，然后继续写线上表；失败后引擎从表的位置重新运行来源，来源看到非空位置就跳过快照。追到什么程度算追上，由最了解更新流的来源决定。（2）延迟由来源测量和告警：Kafka 这类来源由宿主实现，消费者自己有按 offset 和按时间的延迟；框架要测，就得改契约让来源报告时间，测到的也不比来源自己的准。（3）运行期标 `Degraded` 不改变行为（值照常使用），却要在每个请求的读取路径上检查，回放还要记录当时的延迟状态；按表聚合的告警已经回答“特征是不是变旧了”。（4）`updates` 只是把两个来源串起来：一个来源本来就可以既加载快照又消费更新流（`IFeatureUpdateSource` 的文档写了这个做法），现在也没有内置的更新流来源。有了内置的更新流来源，或者多个宿主重复写同一套串联，再把它做进框架。
- **表的身份只有一条规则，在 `LocalTableSpec.Identity`**。身份是 RFC 8785 规范化的 {数据源、实体、键类型、物理字段和它们的存储类型（按字段名排序）、整个绑定、相对路径的基准目录（绝对路径）}。身份相同的计划共用一张表，切换计划时直接接手已经加载的表，不重新加载；改特征名、默认值、声明顺序、其他数据源、流水线和实验都不改变身份。绑定整体放进身份，而不是挑选几个设置：以后加的设置自动成为身份的一部分，不会因为漏加，让设置不同的两个计划共用一张表。代价是绑定的任何改动都会重新加载一次（例如只改 `reload` 周期）。快照的内容不在身份里：同一个绑定的新快照由来源按 `reload` 自己发现，不靠重新发布配置。身份只描述配置，共享还要求同一个运行时所有者（`LocalTableSpec.Owner`，按引用比较，和实例只在同一个工厂对象之间共享是同一条规则）：`local` 表是 bootstrap 来源的工厂，`cache` 表是连接器实例。原来只按身份共享，两个注册表不同的引擎共用一个宿主时，第二个引擎的来源从不运行，`cache` 表里是另一个引擎的连接器取回的行，最终分数改变，没有任何错误（外部评审）。所有者不放进身份：身份是规范化、稳定的配置描述。代价：两个引擎各自 `new PlanEnvironment()` 时内置工厂是不同的对象，不再共用表，各加载一份，和实例一致；要共用就共用同一个环境。分布式层（Redis）的键不含所有者：跨进程本来就要共享，进程之间只能比较配置，隔离边界是配置和 `key_prefix`。
- **基准目录在创建 spec 时固定成绝对路径，来源和身份用同一个值**。`LocalTableSpec.Create` 把基准目录按当时的当前目录变成绝对路径（为空就是当时的当前目录），用它创建来源，也把它写进身份；来源自己也把 manifest 路径在创建时变成绝对路径，直接用工厂创建的来源同样不会留着相对路径。原来身份里存的是传入的原值：为空或是相对路径时，相对的 `uri` 实际按读取时的当前目录解析，身份却一样，宿主会让指向两个目录的计划共用一张表，静默地服务另一个目录的数据；编译之后、后台开始加载之前改变当前目录，读的位置也跟着变（评审 12）。没有选“相对 `uri` 必须配绝对基准目录”：公开 API 本来就接受空的基准目录，固定下来就够了，不用给调用方加一条规则。spec 的构造函数改成私有，创建来源和计算身份只有这一个入口。
- **`uri` 的语法错误是配置错误，在 `/uri`**。`snapshot_files@1` 的工厂解析 `uri` 时，把预期的格式错误（`UriFormatException`，以及路径里的非法字符等 `ArgumentException`）转成 `FeatureUpdateException`，指针 `/uri`，hint 说明接受本地路径或合法的 `file://` URI；解析器统一映射到 `bindings:<环境>` 的 `/sources/<数据源>/bootstrap/uri`。原来 `file://%` 这样的值让 `new Uri` 直接抛异常，越过诊断流程，`validate --format json` 没有任何 JSON 输出（评审 12）。转换放在工厂的解析边界，不在解析器里捕获所有异常：解析器不知道哪些异常是配置错误。测试在单独的进程里运行真正的 `stratarec validate --format json`，快照目录删掉，确认输出是带指针和 hint 的 JSON，且不读快照文件。
- **就绪按计划判断，表的生命周期只在 `BindingHost`**（设计 6.6 第 6 条写的是节点就绪；原名 `LocalTableHost`，现在也管绑定的实例，见“绑定的实例”）。引擎加载计划时开一个 `BindingLease`，编译时向它取表（身份相同就取已有的），然后等这个计划的所有表完成首次加载，才把它设为当前计划；在此之前旧计划照常服务。按节点判断就绪的话，一个新计划的表还在加载时，节点要么停止服务，要么用还没有数据的表服务新计划，两者都不对。表的创建、共享、后台运行、重启、释放和停止都在 `BindingHost` 里，计划和请求只通过租约拿表，`Features` 只依赖 `ILocalTableProvider` 这个接口。
- **引擎的加载、发布和释放由一把锁排序**（`RecEngine` 的 `_publishGate`）。加载开始时在锁里登记自己和自己的租约，发布也在锁里；释放在锁里把引擎标成已释放，并取走所有登记中的加载和已发布的计划。于是：释放之后不会再有发布（发布前在锁里检查）；释放会取消还在进行的加载，它们抛 `ObjectDisposedException`；每个租约只由当时的所有者归还一次：发布之前属于加载，没有发布就在加载唯一的 `finally` 里归还，发布之后属于服务中的计划，计划被替换时或引擎释放时归还。释放会先归还在途加载的租约，不等它们自己结束，这样卡在编译里的加载也不会让表一直运行；之后加载的 `finally` 再归还一次是空操作。原来释放只遍历已发布的计划：等表加载的那个租约不在里面，发布时也不检查是否已释放，使用外部宿主时，加载完成后照样发布，释放过的引擎重新开始服务，这张表和它的来源永远不会被释放（评审 12）。外部传入的宿主仍然不由引擎关闭：它可能同时服务别的引擎，引擎只归还自己的引用，测试用两个共享一个宿主的引擎验证。
- **取消加载：开始时、等表时、发布前在锁里各检查一次**。`LoadAsync` 一开始就检查令牌；`WaitLoadedAsync` 在没有表、宿主不加载表、表已经就绪时也检查（原来只在等待循环里检查，这几种情况直接成功）；发布锁里在修改当前计划之前再检查一次。取消的加载抛 `OperationCanceledException`，当前计划不变，没有发布的租约在 `finally` 里归还，共享的表只少一个引用，别的计划照常用它的来源。原来表已经就绪或没有表时，取消的加载仍然返回 `Applied = true` 并替换当前计划，结果取决于表需不需要等（评审 12）。为了让测试确定地把取消和释放放进“等完表、发布之前”这个窗口，`RecEngine` 有一个内部的 `Publishing` 回调，只给测试用。
- **首次加载失败：计划不生效，下一次加载才重试**。诊断是 `LOCAL_TABLE_LOAD_FAILED`，位置是绑定（`bindings:<环境>` 加 `/sources/<数据源>`），消息里有数据文件和行号，hint 来自来源。设计说表超出 `max_bytes` 时“按数据源不可用处理”，这里改成拒绝计划：从没加载成功的表会让每个请求读它的特征都失败，在加载时拒绝，错误出现得更早、更清楚，旧计划也不受影响。失败的表不再交给任何计划，同一个配置再加载时建新表，真正重新读一遍；后台不自动重试首次加载：配置或数据有错时，自动重试只会不停地写日志，重新发布（或者修好数据后再加载）是更明确的重试时机。还没有服务过任何计划的引擎，这条流水线就一直没有计划，宿主看加载结果决定是否就绪。没有 `max_lag_ms`：现在只有快照来源，首次加载完成就是就绪。
- **首次加载之后来源失败：表继续用已有的数据服务，来源从 `Position` 重启，间隔加倍**（从 `RestartDelay` 1 s 开始，最长 `MaxRestartDelay` 5 min）。一次运行有进展（完成过一次 reload 或 checkpoint）就把间隔重置。进展看表的完成次数（`LocalFeatureTable.Completions`），不看位置：没有更新流的快照来源每次 reload 都停在空位置，按位置判断会永远认为没有进展。失败写日志（事件 1203，带位置、间隔和连续失败次数），计入 `stratarec.local.load.failures`；数据有多旧看 `time() - stratarec_local_load_last_success`，来源一直失败时这个值一直增长。
- **释放和关闭**。计划被替换后，它持有而新计划不共用的表停止来源；还在旧计划上执行的请求读自己钉住的版本，停止来源不用等请求结束。宿主关闭时取消所有来源，最多等 `ShutdownTimeout`（10 s），超时写日志。来源在单独的长期线程上启动：`snapshot_files@1` 在第一次 await 之前同步读完整个快照，不能占用调用方的线程或线程池。
- **停止来源不在调用方线程上运行来源的代码**。取消用 `CancellationTokenSource.CancelAsync()`：令牌立即进入取消状态，来源注册在令牌上的回调在线程池上执行。原来用 `Cancel()`，回调在释放租约或关闭宿主的线程上同步执行：回调阻塞时，关闭要等它返回之后才开始计时，`ShutdownTimeout` 不起作用；计划替换释放旧表也走这条路，新计划已经发布，`LoadAsync` 却可能一直不返回（评审 12）。一张表的“已停止”是来源的运行和取消回调都结束（`TableEntry.Completion`），关闭在同一个 `ShutdownTimeout` 里等所有表，包括之前被释放、还没停完的表；超时之后条目和它的 `CancellationTokenSource`（从不释放）留到两者都结束，表才离开宿主的集合。回调抛出的异常写日志（事件 1206），不抛给释放或关闭的调用方，也不会成为未观察的任务异常。测试覆盖阻塞和抛异常的回调，分别经过租约释放（计划替换）和宿主关闭两条路径，引擎层面另测一次计划替换。
- **请求读取路径集中在 `FeatureFetcher.Local.cs`**（设计 6.6“读取路径”）。一个节点需要某张表的特征时：取存活行中还缺这些特征的行，键去重之后 `Lookup` 一次，每行从这次查找里取自己键的记录，多字段 `Fill` 一次，再把行位图 OR 进各个槽位的填充位。不预取、不受拉取屏障约束、不经过暂存区：读取是同步的内存访问，预取只会提前占用请求内存，读到之后可能被过滤掉的行。同一个 wave 里先发出拉取，再做本地读取，本地读取和拉取的 I/O 重叠。每个请求每张表 `Pin` 一次，所以 reload 和压实不会让一个请求的几次读取看到不同的版本；更新流逐条写入的记录在同一个版本里可见（以后有 Kafka 时，同一个请求先后两次读取可能读到同一个键的新旧两条记录，每条记录本身是完整的）。已经部分填充的特征（行追加之后再读）只填没填过的行，节点读到的值在请求内不变。读取不分配（`text` 除外），测试和同一请求的第二次 `Ensure` 比较字节数，抵消 Debug 构建里异步状态机的分配；去重用的 `EntityKeyIndex` 由 `FeatureFetcher` 在构造时建一个，每次读取 `Reset`。
- **一次本地读取是一个批次，填充和录制都只用这一批记录**（`LocalReadBatch`）。批次是：要填的行、它们去重后的键（首次出现的顺序）、这些键一次 `Lookup` 得到的记录引用、每行的记录。`Pin` 固定的是版本对象，写入器在同一个版本里原地更新时会把索引槽改指新记录，同一个键查两次可能得到两条记录。原来录制时按键再 `Find` 一次，更新落在填充和录制之间时，请求用的是旧记录，回放包里却是新记录，回放和线上不一致（评审 12）；原来也不去重，共用一个外键的几行在一次 `Lookup` 里分别查找，可能拿到不同的记录。现在每个键只查一次，共用键的行拿到同一条记录，录制直接用这批记录引用，不再查索引。回归测试在 `stratarec.local.keys` 的 `MeterListener` 回调里更新 author 表（这个计数正好在填充之后、录制之前），再回放同一份录制，要求逐项相同。命中率按去重后的键计数，和拉取的 `stratarec.source.keys` 一样。
- **缺失和默认值只有一个定义：`FeatureDefinition.Absent`**（有默认值取默认值，否则缺失）。拉取的回填、非有限值替换、上下文特征和本地读取都用它，原来散在 `FeatureFetcher` 里的 `DefaultOrMissing` 去掉了。键不在表中、记录没有这个字段、外键或上下文键缺失、非有限值，都得到 `Absent`；外键失败时读它的本地特征失败，外键降级时它们降级，与拉取相同。测试把同一批记录分别通过 `local` 和 `memory@1` 读出来逐值比较，示例流水线两种绑定的结果和回放记录也逐项相同。
- **表没有加载就读：特征失败，不当作缺失**。空表会把每个键都答成“没有值”，结果看起来正常但全是默认值。只有不经引擎加载的计划会遇到（`validate`、`build`、`explain` 用 `UnloadedLocalTables` 编译），错误文字说明这一点。
- **回放：本地读取记成特征调用，回放包格式不变**（设计 13.4）。录制时每次读取记一次调用：键是读取的行的键，按存活行顺序去重，值是这次读取用的记录里存的值，没有记录就是缺失；回放时本地组和拉取组一样由录制回答，走暂存和回填，不读表。格式没变，旧的回放包和工具照常可用；回放专用的引擎（`stratarec replay`、`compare`）用 `Load = false` 的宿主（表和实例都不加载），不需要快照文件，表变了也照样逐项复现。同一配置上录制和回放取的是同一批行，键完全一致。录制时额外分配（键列表、记录数组），只有录制的请求付这个代价。
- **表的指标**（设计 13.1）：字节数和记录数（gauge，每次 reload 或 checkpoint 时记录）、压实次数、加载耗时（直方图）、加载失败次数、最近一次成功的时间（gauge，Unix 秒），读取命中率用 `stratarec.local.keys` 的 `outcome = hit | miss` 两个计数相除。最近成功写时间戳而不是年龄：年龄要有人定时刷新，时间戳只在成功时写一次，告警规则自己算 `time() - x`。标签（`stratarec.source`、`stratarec.entity`）建表时缓存，记录时不分配。计划加载的结果多了 `bindings_failed`（原名 `tables_failed`，现在也包括实例的加载失败）。
- **`stratarec schema bindings` 的两处修正**。原来带扩展字段的类型（连接器设置、来源设置）也生成 `additionalProperties: false`，合法的绑定会被编辑器标成错误；现在去掉。`mode` 的 `enum`、`max_bytes` 的 `pattern` 由代码里的 `AllowedValues`、`RegularExpression` 特性生成，不手写第二份。
- **组的供给方式只有一个描述：`GroupSupply`**。`FeatureSourceResolver.Group` 为每个组生成它：模式，以及这个模式持有的东西（`fetch` 是连接器、超时和分批，`local` 是表）。组直接存这个描述，计划构建、读取路径和拉取路径都按 `Mode` 判断。原来组只存连接器和表，模式由“表是不是空”推出来，`FeaturePlan.Create` 自己再按模式分支：加一种同时有表和连接器的模式时，这样推出来的模式就错了，而且没有任何地方会报错。现在按模式的判断都是列出每个取值、没有默认分支的 switch 表达式（解析器 4 处、`FeatureFetcher` 2 处）；全局关闭了 CS8524（没有覆盖未命名的枚举值），所以加一个模式时，每个要处理它的地方都编译不过（CS8509，警告视为错误）。编译器看不到的是绑定里模式的拼写和 JSON Schema 的 `enum`，由测试核对：每个模式的名字都能解析回它自己，`AllowedValues` 正好是这些名字。
- **`cache`：两层缓存在连接器之前，读取路径集中在 `FeatureFetcher.Cache.cs`**（设计 6.6）。第一层是进程内的本地表（`LocalTableMode.Cache`，记录版本就是写入时间），第二层可选（`cache.distributed`，契约是 `IFeatureCacheStore`）。只配第一层也完整可用。一次读取：表里新鲜的键直接填充，全部新鲜时就是一次本地读取，不分配；其余的键查第二层，第二层未命中、过期、记录不匹配或出错的键合并成一次连接器调用；回填之后写回，第二层来的只写本地表，连接器来的写两层。整次读取在数据源的预算之内（第二层和连接器返回任务之前的同步部分除外，见“请求路径上的扩展点在请求线程上直接调用”），第二层默认最多等预算的一半（`cache.distributed.timeout_ms` 可改），剩下的留给连接器。
  - **未命中时拉取表的全部字段**，不只是这个节点要的：写回的必须是完整记录，否则下一次读别的字段会把缺的字段当成“没有值”。代价是第一次多拉几个字段。
  - **写回不在请求路径上**。两层各有一个有界队列（本地按记录字节，默认 `max_bytes` 的 1/16、限制在 1 到 64 MiB；分布式固定 16 MiB），满了就丢弃并计数，下次未命中再拉。本地表的写线程作为这张表的更新来源运行，表的加载、取消和释放都沿用 `local` 的生命周期；空表就算加载完成（每个键都未命中）。
  - **只写回确定的结果**。连接器部分失败的分块不写回；请求不再等待的调用（第二层或连接器超时之后才返回的）结果既不读也不写回：可能不完整，写入时间也已经不对。连接器确认没有值的键写一条全部缺失的记录（负缓存），寿命相同。版本相同时保留先写的那条：同一毫秒内两次拉取同一个键，后到的写回被忽略（两次读到的值可能不同，这是按毫秒计版本的平局规则）。
  - **过期**：TTL 按键的稳定哈希浮动 ±10%，同一批写入的键不会同时过期。连接器失败时，`stale_if_error_ms` 窗口内的过期记录照常使用；窗口按选择兜底值的那一刻判断，不按读取开始时，等连接器期间越过窗口的记录不用（评审 19）。用了过期值的读取状态是 `Partial`，错误信息说明有几个键用了过期值；只有一个键都没有拿到值时读取才 `Failed`。超出 `max_bytes` 时先丢弃过了窗口的记录，仍超过上限的四分之三再按写入时间丢弃最早的，免得下一次写入又触发淘汰。配置了第二层时，最长保留时间（`ttl_ms` × 1.1 + `stale_if_error_ms`）要放得进 `TimeSpan`（约 2.9 万年），否则在绑定的那个设置上报错；原来能通过校验的配置在第一次写回时抛溢出异常（评审 19）。只有本地表时没有这个转换，不检查。
  - **第二层的记录自带写入时间和字段集指纹**（`StableHash` 的规范编码，每个字符串带标签和长度前缀，覆盖记录格式、键类型、字段名、类型和顺序；原来用制表符和换行拼接，字段名里含这些字符时两套不同的字段可以拼出同一个串，一套的值被当作另一套读出，评审 19。改编码让升级前写的记录都成了不匹配，代价等于一次目录版本变更），新鲜度按记录里的写入时间判断，多个实例写同一个键时后写的胜。指纹不同当作未命中（`mismatch`），不会读错；代价是两个目录版本同时在线（灰度）时互相覆盖对方的记录，命中率下降。存储的过期时间是记录可能的最长寿命（TTL 加最大浮动）加 `stale_if_error_ms`，减去已经过去的时间：过了这个时间，没有读者还能用它。已经过去的时间不取负值，结果至少 1 ms：等连接器期间时钟回拨，写入时间晚于当前时间，原来算出的过期时间超过上面校验过的最长保留时间，最长的合法设置溢出成负值（评审 21）；现在当作刚写入。
  - **第二层是绑定实例，身份只含存储自己的设置**（`store` 和 `timeout_ms` 之外），改等待时间不重连；本地表的身份含整个绑定，改任何 `cache` 设置都会换一张空表。第二层的时间用完后不再发送后续分块，余下的键直接交给连接器。释放第二层时先等写线程真正退出，开始释放后不再发新的批次（剩下的丢弃并计数），存储在 `finally` 里恰好释放一次；途中取消回调或指标监听器抛出的异常收集起来交给宿主记日志，监听器的异常不让写线程停下（评审 19）。
  - **`redis@1` 在单独的包 `StrataRec.Redis` 里**，核心包不依赖 StackExchange.Redis，宿主用 `AddRedis()` 注册。客户端用 StackExchange.Redis 3.x 的最新正式版（3.4.35）：原来停在 2.13，理由是 3.0 换了传输层（RESPite）、当时太新；3.x 已经发布五个月、出了多个补丁版本，再停在旧的大版本，修复和支持只会越来越少。升级没有改代码，它依赖的 `Microsoft.Extensions.Logging.Abstractions` 等 10.0.x 包本来就在用。Redis 不可达不让加载失败（它只是优化：计划先用连接器服务，客户端在后台重连，断线时命令立即失败、不排队）；秘密缺失、设置错误、服务器拒绝凭据让加载失败。拒绝凭据包括 NOAUTH/WRONGPASS，以及配置了 `user` 而 `ACL WHOAMI` 显示的不是它：默认用户没有密码的服务器会把认证失败的连接退回成 default 用户继续工作，只看连接是否失败抓不到（评审 19）；回答不了 `WHOAMI` 的服务器（Redis 6 之前、没有权限）信任这个连接。连上了就发一条命令判断（配置了 `user` 用 `ACL WHOAMI`，否则 `PING`），命令到达服务器，结论可靠；失败在整棵异常树里（含聚合异常的每个分支）找客户端的认证失败或服务器的 `NOAUTH`/`WRONGPASS`。没连上时客户端的失败说明不了原因，CI 里出现过一次要求密码的服务器、不带密码却加载成功。Codex 调查确定了两个原因（StackExchange.Redis 2.13 的源码，并用真实 Redis 确定性复现；升级到 3.4.35 后用旧逻辑仍然复现）：（1）收到拒绝时，客户端先通知连接结束、再发布拒绝的异常，连接返回、紧接着的命令在本地快速失败，拿到的异常里还没有认证失败；（2）客户端只保留一个连接的第一次失败，前面的连接被断开时，之后收到的拒绝永远不会出现在命令的失败里。所以拒绝要从看到它的那个连接读：“连不上就抛异常”的连接（`AbortOnConnectFail`）在放弃时读取客户端在它自己的连接上记下的拒绝，不受这两个问题影响。原来先建普通连接，没连上再用这种连接探测；但探测也可能在读到拒绝之前就超时或被断开，而主连接已经收到拒绝、还没发布（第三次 CI 偶发失败；评审 35 用门控固定了“主连接未发布 + 探测在认证前失败”的组合，加载成功）。上一版跨连接保留证据（探测前后各在主连接上发命令、订阅它的 `ConnectionFailed`），只抓得到已经发布的拒绝，补不上这个组合。现在顺序反过来：先做“连不上就抛异常”的连接，最多两次、每次只试一次；连上了它就是存储的连接（这个设置只影响首次连接，之后照常重连），再发一条命令判断凭据；被拒绝就让加载失败；两次都是普通失败（宕机、认证前被断开）才按宕机处理，再建一个在后台重连的普通连接，它已经发布的失败仍然读一次。第二次针对第二个原因：最初的连接被断开，之后的连接才收到拒绝。剩下分不清的只有一种：服务器在握手前断开两次连接、第三次才拒绝，这时按宕机处理，读请求走连接器，与允许 Redis 宕机时启动的取舍一致。无论从连接还是命令的失败里读，都先找 TLS 握手失败：客户端把它也报成认证失败，上一版新增的命令检查曾把证书不受信任报成缺少密码（评审 35）；TLS 握手失败报在 `/tls`，提示检查证书或关掉 `tls`。代价：服务器接受连接却不回答时，加载最多等三次连接超时（原来两次）。没有选读取客户端内部记下的拒绝（不是公开 API），也没有选看客户端的日志（同样有发布顺序的问题）。测试复现了三种情况：门控卡住客户端发布拒绝之前的日志、代理重置最初两个连接、门控加上代理重置之后的所有连接；旧实现都加载成功。测试里的门控每卡一次就占住一个线程池线程，客户端读回拒绝也在线程池上，所以测试提高了线程池的最小线程数。加载被取消后晚到的连接随存储一起释放，释放最多等一次连接超时。每个连接只试一次（`ConnectRetry = 1`）：3.x 的初连默认试 3 次，服务器接受 TCP 却不回答时一次加载要等约 8 s（评审 24）；没连上的连接本来就在后台继续重连，初连多试几次没有好处。读是每块一次往返：单机 `MGET`；集群的 `MGET` 不能跨槽，改为一批流水线 `GET`，键不加 hash tag，一个键空间分散到各分片。CI 只测单机，集群路径没有测试。每个 `cache` 数据源一个 Redis 连接（实例身份含数据源名），同一个 endpoint 也不共享：数据源通常只有几个，按 endpoint 共享要把连接放到实例身份之外、另管引用计数，等连接数成了问题再做。固定的默认值：加载时连接超时 2 s（服务器不回答时最多三次，见上），分布式层的写队列 16 MiB。
  - **回放**：一次缓存读取录成一次特征调用（键、读到的值、结束状态），回放和 `local` 一样从录制经拉取路径回答，不碰表、第二层和连接器；录制的是读取实际用到的值，不管来自哪一层。缓存组不预取：预取发生在读取之前，那时还不知道哪些键会命中。
  - **分配**（`CacheAllocationTests`，Release）：全部新鲜 0 B（100 和 4000 个键）；本地未命中、第二层命中每键约 32 B（键和记录引用交给写线程）；本地未命中、连接器回答每键约 65 B（另加编码后的记录）。
  - **示例没有改成 `cache`**：`user_store` 的特征流水线没有用到；`item_store` 改成 `cache` 会改变示例的表数量、事件计数和计时相关的测试。端到端测试在示例副本上把 `item_store` 改成 `cache`（`CacheEngineTests`，Redis 的在 `RedisCacheTests`）。
- **`local` 与 `memory@1` 的请求耗时**（`FeatureSupplyBenchmarks`：示例流水线、无实验，`item_store` 每个候选 8 个特征、`author_store` 经外键每个候选 1 个，两种方式用同一批记录，拉取方式每个数据源每次只调用一次）。开发机（Xeon 6975P-C，.NET 10）上，500 候选：拉取 188 μs、20.2 KB，本地 81 μs、15.5 KB；5,000 候选：拉取 1,714 μs、36.1 KB，本地 596 μs、16.3 KB。本地方式的分配基本不随候选数增长。差距主要是 `memory@1` 自己的成本（每个值从 `JsonElement` 解码，`string` 值每次新建），再加上暂存和回填；真实的远程连接器还要加上网络往返，所以这个比例只说明请求路径本身的开销，不是两种部署的对比。
- **记录引用不带版本，按记录读取的接口不公开**（设计 6.6）。`LocalRecordRef` 只对查出它的版本有意义：同一张表的另一个版本经过压缩，字符串编码重新编号，拿旧引用去读会静默读出别的字符串（越界由 `FillCore` 挡住，不会读到页外）。没有让引用记住版本、读取时逐行核对：每行多一次比较，结构体变宽，而唯一的调用方本来就对每个请求钉住一个版本、所有记录都从它读。`TableVersion` 的查找和填充（`Find`、`Lookup`、`Fill`、`Read`）以及 `LocalRecordRef`、`LocalFieldRead` 改为内部，公开的只剩统计；用户读本地表的特征走特征目录。以后要开放按记录读取，再让引用带上版本。

## 绑定的实例

模型客户端、召回源和特征连接器是绑定的实例（设计 6.4），可能是内置的，也可能是使用方写的。原来每次编译都新建，从不释放；持有连接、要先读文件或询问远程服务的实现需要知道框架什么时候创建、共用、调用和释放它们，才能放心接入。

- **契约从实现方的角度写，只写在一处**：`BindingContext` 的文档（三个工厂接口和 `ILoadable` 都指向它），内置的和使用方写的实例、三种实例都是同一套规则。框架保证：
  - `Create` 只在计划编译、还没有这个身份的可用实例时调用：引擎加载第一个用到它的计划时，前一个实例加载失败之后，以及每一次不服务的编译（`validate`、`build`、`explain-plan`），后者的实例从不加载、调用或释放；两个计划同时加载可能各建一个，多出来的不加载、不调用就释放。
  - 同一身份一个实例，引擎的所有计划和它们的并发请求共用；绑定不变的计划切换接手已经加载的实例，设置变了就建新的，在新计划服务之前加载好。
  - `LoadAsync` 最多一次，在线程池上，有上界、可取消，完成之前不用它服务任何计划；请求路径上不等任何本可以在加载时做的 I/O。
  - 请求的调用和签名查询都在加载完成之后。调用超时时引擎不再等它、取消令牌，但实例活到调用真正返回。
  - Dispose 恰好一次，在线程池上：不再有服务中的计划用它，也没有请求、被放弃的调用或签名查询还在它里面，加载（如果开始了）已经返回；开始 Dispose 之后不再有调用。可能没有加载就 Dispose（不加载的回放引擎、多出来的实例），也可能在加载失败之后。加载或调用一直不返回的实例一直不 Dispose，关闭时报告。

  实现方要做的：`Create` 只读、检查设置，不做 I/O，不占用需要释放的东西（不服务的编译从不释放实例），可能被并发调用；I/O、连接和秘密解析放在 `LoadAsync`；实例线程安全；遵守取消令牌（不遵守只会推迟释放）；Dispose 释放到目前为止拿到的一切；设置错误抛 `BindingException`，带设置的指针和 hint；秘密值不放进消息、异常和日志。没有分别写在三个工厂接口上：同一套规则抄三份，改一处就会漏两处。内置的 `memory@1`、`memory_list@1` 不守“`Create` 不做 I/O”：它们是样例和测试用的固定数据，在 `Create` 里读一个小的本地文件，换来不需要加载，单元测试可以直接用工厂建出来调用；代价是 `validate` 也要有这些文件。生命周期测试用计数的替身包住它们（以及一个要加载的模型客户端、一个要问模型服务才知道签名的客户端），不依赖真实的推理或存储。

- **一个计划一个绑定租约，表和实例都在里面**。`LocalTableHost` 改名 `BindingHost`、`LocalTableLease` 改名 `BindingLease`：计划编译时向自己的租约取表和实例（`IPlanBindings`），身份相同就拿已有的，切换计划时接手已经加载的实例，不重建。生命周期的规则只在两处：`BindingHost` 管共享、加载、释放和关闭，`BindingLease` 管一个计划持有什么、什么时候归还；`RecEngine` 只开租约、发布、退役，加载、发布和释放的排序不变（见“本地特征表”）。没有为实例另开一种租约：两种租约要分别和发布排序，归还的时机也是两套，出错的地方翻倍。
- **实例的身份**是 RFC 8785 规范化的 {段（`models`、`candidate_sources`、`sources`）、逻辑名、类型、绑定自己的全部设置、基准目录（绝对路径）}，并且只在同一个工厂对象之间共享，两个注册表不同的引擎不会共用实例。框架自己解释的设置（`client`、`timeout_ms`、`max_batch`）不在里面，改超时不会重新加载模型。设置整体放进身份，理由和 `LocalTableSpec.Identity` 相同。逻辑名也在身份里，因为工厂拿到它（错误和日志用它称呼实例）；代价：两个名字绑定同一个模型文件或服务、同样的设置时是两个实例，各加载一次。凭据只以引用出现，所以身份里没有秘密值，秘密轮换不换实例。
- **表在计划退役时释放，实例要等计划的最后一个用户离开**。两条规则不同，因为表的读取钉住了版本：请求读自己钉住的版本，停掉来源不影响它；实例没有版本可钉，还在运行的请求、它在超时时放弃的调用都还会用它。所以租约有一个计数：请求进入（`TryEnter`）到请求结束；请求的每次运行加入（`Join`），在它的请求内存最后一次 `Release` 时离开（`IRequestEndObserver`）。被放弃的调用持有请求内存直到客户端真正返回（见“执行与宿主”），所以这一刻之后请求的任何部分都不会再调用实例，不需要第二套计数。签名查询也是这个计数里的用户，从发出到客户端返回：租约退役时取消查询，但客户端还在 `GetSignatureAsync` 里时不释放它（只等加载返回的话，加载超时或被拒绝的计划会在查询中途释放客户端，有回归测试）；取消查询本身也是一个用户，直到客户端注册在查询令牌上的回调都运行完，租约退役和调用方放弃走同一个取消入口。租约退役并且计数归零时，实例还给宿主；宿主在线程池上等实例的加载返回，再 Dispose（`IAsyncDisposable` 优先，否则 `IDisposable`），不在请求或客户端的线程上执行实例的代码。退役后进入失败的请求重新读当前计划；引擎释放之后请求抛 `ObjectDisposedException`，包括它从没服务过的流水线；释放时还在运行的请求照常完成，实例在它们结束之后释放。后备流水线进入自己的租约，主流水线运行之后引擎被释放的话，请求返回主流水线的结果，和没有后备一样。回放也进入租约：回放不调用客户端，但一条规则管所有运行，比依赖“这次运行不会调用”更不容易出错。代价：每个请求多几次原子操作。
- **实例在计划服务之前加载，不在请求路径上**（`ILoadable`）。引擎等计划的表完成首次加载时，也等它的实例加载完，任一失败就停止等待。加载在线程池上运行，有上界（`BindingHostOptions.LoadTimeout`，默认 2 分钟）；失败或超时的计划被拒绝，`BINDING_LOAD_FAILED` 指向绑定，实例抛 `BindingException` 时指向那个设置并带它的 hint，例如 `bindings:prod /models/ctr_model/credentials`。失败的实例不再交给任何计划，同一个绑定再加载时建新实例、真正重试，与表的首次加载失败一样，后台不自动重试。实例不会在加载还在运行时被 Dispose：释放先取消加载，等加载和这次取消的回调都返回再 Dispose（回调可能先结束加载、再用实例做清理，与表的来源停止相同；关闭和释放谁先取消，都等第一次取消的回调）；加载或取消回调一直不返回的实例一直不 Dispose，关闭时报告。关闭在同一个 `ShutdownTimeout` 里等所有表的来源停止、所有实例 Dispose，超时写日志（事件 1210：还有请求或被放弃的调用在用的实例，或者加载、Dispose 没有返回的实例）；日志或 Dispose 抛出的异常只记录，不结束也不跳过任何等待（与表的停止相同）。
- **模型签名改成异步，在加载时取得；需要等待时计划编译两次**（设计 6.9；1.0 之前的不兼容改动）。`IModelClient.GetSignature` 改成 `GetSignatureAsync(model, version, CancellationToken)`：真实客户端的签名要等它读完模型文件，或者问模型服务。SPI 只改这一处，检查的位置不变，仍在 `ModelScorer` 编译时：编译向租约要签名，已有答案的直接检查；还要等的是 `Pending`，这次编译跳过；`BindingLease.CompileAsync` 编译一次之后，同时等所有未完成的查询（每个先等它的客户端加载完再问），上界是 `LoadTimeout`，再用答案编译一次，只有第二次的结果算数，到时没有答案的查询在第二次里是 `MODEL_SIGNATURE` 错误，hint 说明调大 `LoadTimeout` 或检查模型服务。要不要第二次编译，看第一次编译里有没有哪次检查被答了 `Pending`，不看编译结束时还有没有未完成的查询：查询可能在基线那一遍之后、某个臂那一遍之前回来，这样的编译只检查了一部分臂组合。原来按后者判断，这种时序下计划只编译一次，错误归到某个臂上，归属随时序变化；所有检查都是 `Pending`、查询又恰好在编译结束前回来时，签名完全没有检查（单元测试确定地复现这个时序，集成测试原来偶发失败）。每个（客户端、模型、版本）只问一次，两次编译和各个验证阶段共用答案；客户端加载失败时签名不检查，错误是那次加载失败，只报一次。没有选的做法：把检查推迟到编译之后（检查要知道节点、配置键和臂组合，`UnifiedCompilation` 的归属和去重要另做一遍）；在编译里同步阻塞地等（模型多时串行，且占着加载线程）；在请求路径上第一次调用时检查（违背加载时检查）。客户端的签名方法整个在线程池上运行，包括第一次 await 之前的同步部分：原来在编译线程上直接调用，方法在返回任务之前同步阻塞（同步询问元数据）时，编译连 `Pending` 都拿不到，`LoadTimeout` 和调用方的取消都不起作用，超过上界之后同步返回的答案还被当作已知（评审 16）。代价：引擎加载检查模型签名的计划通常编译两次，原来立即回答的客户端（`linear@1`）只编译一次；只有检查时每个答案都已经回来，才只编译一次，这时每项检查都做了，所以测试不能假定一定编译两次（评审 17）；计划加载不在请求路径上，这个代价只在发布时付。没有选“先在编译线程上试一次、未完成才放到线程池”：同步部分正是会阻塞的部分。查询等客户端加载时随计划取消：查询占着租约，租约要等最后一个用户离开才归还客户端，客户端没有人持有才取消加载，原来计划被取消后，这三者要到 `LoadTimeout` 才放开（外部评审）；另一个计划持有同一个客户端时加载照常进行，已经在客户端方法里的查询照旧等它返回。
- **静态编译不加载实例，需要加载才能回答的签名不检查**。`validate`、`build`、`explain-plan` 用 `UnloadedBindings`：实例照常创建，设置的错误照样报告，但不加载；签名只在客户端不需要加载并且立即回答时检查（`linear@1`），其余留给引擎加载时检查。所以静态检查不需要模型文件、网络和秘密；代价：版本名写错、模型输入名不符这类错误要到引擎加载时才发现。回放用的引擎（`Load = false`）同样不加载实例。
- **凭据只以引用出现**（`"credentials": "secret://<名字>"`，设计 6.4 第 4 条）。工厂创建实例时用 `BindingContext.SecretReference` 读出引用：不是 `secret://` 就是指向那个设置的配置错误，消息不引用写错的值，因为它可能就是误贴进来的凭据。实例加载时用宿主的 `ISecretResolver` 解析（DI 容器里注册的，或 `BindingHostOptions.Secrets`）；没有这个秘密、宿主没有秘密存储，都是 `BINDING_LOAD_FAILED`，指向那个设置并带 hint。解析出的值是 `Secret`，`ToString()` 是 `[secret]`，只有 `Reveal()` 读得到；框架不持有值，值从存储直接交给实例，诊断、日志、trace 和回放包里只有引用。不做缓存和轮换：实例每次加载解析一次，要轮换的实例自己再解析。测试确认值不出现在诊断、日志、trace 和回放包里，误写成值的凭据也不出现在诊断和日志里。
- **本地文件设置只有一条规则：`LocalPaths`**。基准目录在 `BindingContext.PinBaseDirectory` 固定成绝对路径（原来在 `LocalTableSpec`，理由见“本地特征表”），文件设置可以是相对于配置根目录的路径、绝对路径或 `file://` URI，别的 scheme 不是本地路径。本地表和 `snapshot_files@1` 用它，读本地文件的其他实现也应该用：`BindingContext.LocalFile` 把错误转成指向设置的 `BindingException`，各处接受同样的写法、拒绝同样的错误。
- **工厂接口改成 `Create(BindingContext)`**（1.0 之前的不兼容改动）。模型、召回源、连接器的工厂原来各自接收名字、设置和基准目录；`BindingContext` 还带着秘密存储，以后再加东西不用改三个接口。工厂只读设置、不做 I/O：实例由多个计划共享，I/O 放在 `LoadAsync`，只在引擎加载时做。`RecEngine` 的构造参数相应是 `bindings`（外部的 `BindingHost`，由调用方释放）或 `bindingOptions`（引擎自建宿主的选项：秘密存储、加载和关闭的上界），只能给一个。

## 日志

- **没有消费者时不采样、不捕获**。没有日志管道且请求没有 `CaptureLogs` 时，所有批次都会被丢弃，白白消耗 CPU 和内存。
- **漏斗组的 key 只能读请求输入，且必须是标量**（设计 8.2）。组决定在请求开始时做出；key 若要等一次拉取，每个请求都会在召回之前阻塞在日志采样上（评审 4、5）。
- **探针对上下文特征同样是被动的**（设计 8.5）。只被探针读取的上下文特征不进入预取，否则每个请求都多一次拉取，无论是否被采样（评审 4）。
- **durable 投递以返回值和钩子表达，不内置磁盘缓冲**（设计 8.6）。`Submit` 返回 Queued/Spilled/Dropped/Closed；内存队列满时调用 `DurableOverflow` 钩子，由宿主决定是否落盘；sink 用 `LogBatchRejectedException` 声明永久不可写的批次，避免一个坏批次堵住整个 durable 流（评审 4）。`DisposeAsync` 的等待有上限，不依赖 sink 配合取消（评审 5）；到时还没写出的批次计为丢弃（评审 6）。
- **非有限向量记为缺失**。一个分量是 NaN 的向量整体记为缺失，部分向量对训练没有意义。
- **不做个人数据过滤**（设计 8.9）。推荐需要这些数据，内部记录和调试查看是正常用法；不暴露给外部系统由运行环境和数据权限负责。曾经实现过敏感级别、`purpose` 声明和缓冲区清零，已按此决定全部移除。

## 表达式

- **哈希的规范编码**（设计 5.7）。`float64` 中 −0.0 按 0.0、所有 NaN 按 `0x7FF8000000000000` 编码。IEEE 754 不规定定义域错误产生的 NaN 的符号和载荷，优化器和 SIMD 重写都可能改变它，`hash01` 结果不能随之变化。离线复算哈希也要这样规范化（评审 4）。
- **`hash01` 有两份编码实现**。表达式后端用栈上缓冲区写编码，标量路径不经过数组池；与 `StableHash.Builder` 的一致性由测试锁定。
- **int32 越界的派生特征，不可空又没有默认值时整个特征失败**（设计 4.3、4.6；评审 6）。和节点输出、非有限值是同一条规则：不可空的列装不下替换出来的“缺失”，读取方按不可空编译、不检查有效位。没有选择让类型推断因为“可能越界”而变成可空：那样所有 int32 派生特征的读取方都得写 `??`，而越界在实践中很少见。失败的特征对所有读取方都一样：节点按 `on_failure` 处理；输出读到它时请求失败（之后由后备流水线兜底）；探针不让请求失败，读到它的列记为缺失，过滤条件视为 false。
- **`int(x)` 向零截断，没有 `int64` 值时是缺失**（设计 7.5、7.6）。`float64` 的 NaN、±∞ 和截断后超出 `[-2^63, 2^63)` 的值没有对应的 `int64`；CEL 在这里报运行期错误，这门表达式语言不抛错，所以结果是缺失，`float64` 的 `int()` 结果总是可空，用 `??` 给替代值。没有选：饱和到边界或按补码回绕（编出一个数，等于把缺失静默变成数）；像 int32 窄化那样保持不可空、越界时让整个特征失败（窄化越界很少见，浮点运算里的 `x / 0.0`、`log(0.0)` 却很常见，一行的 NaN 不该让整列失败）。`int()` 只接受数值，bool 写 `b ? 1 : 0`，也不解析字符串（文本到数值的转换属于特征生产）。`double()` 和 `int64` 参与浮点运算时一样取最近的 double。这是唯一能把有值的输入变成缺失的提升运算，向量化后端在操作数的有效位上再清掉这些行，差分测试覆盖。函数集合在 1.0 之前还在增减，能力名仍是 `expr_functions@1`：旧二进制加载用到新函数的配置时报 `EXPR_UNKNOWN_FUNCTION`，不会静默算错。
- **`lookup(table, key, default)` 在 key 缺失时返回 `default`**（设计 7.4 的例外）。第三个参数本身就是调用方给出的缺失处理；改成缺失会让现有打分表达式变成可空类型而无法编译。

## 可观测性

指标名称、单位和标签写在 `StrataRecMetrics`（`src/StrataRec.Core/Diagnostics`）的文档注释里，这里只记取舍。

- **直方图用 `InstrumentAdvice` 给出建议边界**（设计 13.1）。耗时按 √2 递增（0.1 ms 到约 13 s，35 个边界，每桶宽约 41%），行数、键数、字节数按 2 递增。导出为指数直方图时宿主会忽略这些建议。
- **请求级指标和请求 span 由 `RecEngine` 记录**。一次请求就是一次 `IRecEngine.ExecuteAsync`，包含分配、主流水线和后备流水线：由后备流水线返回的结果计为降级，不计为错误（设计 5.6）；被调用方取消的请求计为错误，因为慢请求更容易被取消，而慢往往与臂相关。直接调用 `PipelineExecutor` 只得到节点、数据源、模型、列和内存指标。
- **执行器不自己补建请求 span**。它只在当前 span 是已记录的 StrataRec span 时创建节点和 I/O 子 span。如果 `RecEngine` 的 span 被采样掉之后执行器再试一次，对根请求来说每次都会生成新的 trace id，按 trace id 采样的采样器第二次可能放行，等于把采样率翻倍。直接用执行器的宿主可以用 `StrataRecTracing.StartRequest` 包住调用。
- **按臂的请求指标用单独的名字**（`stratarec.arm.request.*`）。一个请求在每个分配到臂的层各记一次；如果和请求级指标同名、只靠 `arm` 标签区分，按流水线求和就会把多层请求重复计算。
- **标签键都带 `stratarec.` 前缀**。采集链路会自己加标签（例如 Kubernetes 的 `node`），短名字会冲突。
- **数据源健康按窗口判断**（设计 13.2）。一个窗口（10 秒）内至少一半调用失败就判为失败，判断翻转时才写一条日志；没有调用的窗口不改变判断。按连续失败次数判断在低流量下会来回翻转。部分成功（`partial`）算健康。
- **汇总日志由定时器刷新，定时器只弱引用日志对象**。被丢弃的执行器不会被自己的定时器留住；窗口内最后的计数在进程退出时可能丢失，精确计数看指标。
- **日志 sink 失败按状态变化记录**：开始失败时写一条（带异常），恢复时写一条（带失败次数）。宿主钩子（`DurableOverflow`、`Rejected`）抛异常和被 sink 永久拒绝的批次按窗口汇总。
- **调用方取消不算依赖超时**。外部调用（特征源、召回源、模型）被调用方取消时，不记耗时、不记错误、不进健康判断，否则客户端断开会被当成依赖变慢。算子拿到的节点令牌同时受节点预算控制，分不清两者，所以请求状态另外保留调用方的令牌。请求本身仍计为错误（见上）。
- **越界计数只按流水线记录**（`stratarec.column.out_of_range`；设计 13.1 写的是 `{node,column}`）。int32 窄化发生在表达式后端和上下文特征写入处，计入每请求共享的计数器，那里不知道列；按列归属要在每个写入点传标签。int32 列通常很少，按流水线报警之后再查具体列。
- **被调用方中止的节点记为 `aborted`**，耗时和行数照记（评审 6）。否则节点延迟分布恰好漏掉调用方等不及而放弃的慢尝试。
- **每请求多约 60 B**。为了携带事件日志、span、调用方令牌和当前位置的状态，请求状态和特征拉取器多了几个字段。记录指标本身不分配：挂上 `MeterListener` 时和不挂时分配的字节数相同；被采样掉的请求多一个未记录的 `Activity`（约 0.4 KB）；被记录的请求为每个节点和每次外部调用各建一个 span。
- **数据源缺失比例按（数据源，特征）计数，只数数据源回答了的键**（设计 13.1：`stratarec.source.values`，`outcome = present | missing`）。缺失比例是 `missing / (present + missing)`。按特征而不是只按数据源：一个数据源有几十个字段，坏了一个字段时，按数据源合计的比例只动几十分之一，看不出来；特征由目录限定，和节点 ID 一样是有界的标签，只要数据源合计的宿主用 view 去掉 `stratarec.feature`。数的是一次读取的去重键，每个请求的特征一次：失败或超时的分块不计（那是 `stratarec.source.errors`，它的暂存区也不读），`cache` 用过期记录兜底的键也不计（它的连接器调用失败了）；没有键的行（外键或上下文键缺失）没有向数据源要，不计；默认值不算有值，数据源返回的非有限值算有值（替换计入 `stratarec.column.nonfinite`）。`partial` 的分块里，连接器没写的键都算缺失：暂存区没有逐键的失败信号，分不出“失败”和“没有值”。三种供给方式各在拿到结果的地方数：拉取数暂存区“已写”位图（每 64 个键一次 popcount），读取时数；预取了却没有节点读的拉取（例如只有没运行的后备节点需要它），在请求结束、归还请求内存之前补数，数据源回答了就算被要过（评审 25）；`local` 读用这次读取唯一一次查找的记录，`cache` 有未命中时在解析完成后一起数。只在有监听器时计算（`Instrument.Enabled`），没有监听器的请求只付这个判断；有监听器时拉取每个特征扫一遍位图，`local`、`cache` 每个特征扫一遍去重键的有效位；标签数组每个计划建一次，计数不分配（`BaselineMetered` 分配不变）。回放不计数：回放不是流量。有未命中的 `cache` 读取，请求在解析完成前中止时不计。
- **内存的两种异常写事件日志，不加指标**（设计 13.2）。一是宿主的 `IBufferPool` 在归还时抛异常：其余缓冲照常归还，这几个留给 GC，`BufferReturnFailed` 按窗口汇总，`Release` 不再抛出。最后一次 `Release` 常常在连接器的线程上、作为被放弃调用的后续执行，异常在那里没有人接，而且原来抛出会跳过剩下的缓冲。二是请求返回 30 秒后缓冲仍被占着（`BuffersHeld`，每个请求报一次就不再跟踪）：被放弃的调用还没结束，通常是客户端不理会取消令牌。它占着的不只是缓冲，还有请求用到的计划实例，计划切换后旧实例就一直释放不了；`stratarec.io.abandoned` 只在请求返回时计数，看不出调用后来有没有结束。只跟踪返回时仍有调用在跑的请求：定时刷新正常推进时，列表的长度不超过这类请求的速率乘以 30 秒加一个窗口（日志后端卡住、刷新停了就没有这个上界）；平常的请求不进列表、不做检查，只是请求内存多三个引用，每请求固定多 24 B。30 秒是固定值，不做成配置：被取消的调用正常几毫秒内就结束，半分钟还在跑就是没理会令牌。设计 13.1 的“池中保留的字节数”没有做：默认的 `ArrayPool<T>.Shared` 不公开这个数，自定义的池可以自己报。

- **候选解释由执行器通用记录，算子的说明是可选的钩子**（设计 13.3）。执行器只用它对每个节点都知道的东西：节点声明读写的列，以及节点前后的行选择。所以自定义算子不写代码也能被解释。`IExplainableOperator` 让算子补一句原因和几个数值；内置的过滤、截断和组合打分实现了它。
  - 钩子在提交之前调用，这时列解析到的正是算子读到的版本，流动列还没换成新写的值。提交随后失败时，钩子写的内容随尝试一起丢弃，这一步记为 `rolled_back`，状态取尝试之前的，也就是表恢复之后的样子。钩子抛出的异常只写进原因，不影响请求。
  - 目标在行源节点之后按键找一次，用表已有的键索引。之后一直跟随它，不再按键查找：压缩时存活的行按名次排到前面，物理行就是名次减一。
  - 名次没有逆映射。改变了行集或顺序的节点之后，扫一遍存活的行，扫到最后一个存活的目标就停。没有为常态路径维护逆映射；代价是开启解释时这一步与存活行数成比例。
  - 算子说明里的表达式只在目标行上求值，但编译好的表达式按物理行写结果，所以结果写进一列按表容量从请求内存租借的缓冲，每种结果类型一列，名次扫描的位图也按表容量租借。这两部分随候选数增长（评审 34 指出原来写的“与候选数无关”不成立）。接受这个代价：只有调试请求才有，相当于多一个节点写一列，随请求归还；要按目标紧凑求值，就得给表达式后端加一种输出映射，为调试功能改动热路径的代码不值得。GC 分配不随候选数增长，有测试（250 和 4000 个候选）。
  - 不开启时没有新对象，只多几个引用字段：Release 下执行器每次运行多 16 B，引擎每个请求多 32 B。
  - 上限是常量 100。超过上限，或 ID 的键类型与流水线不符，都是 `InvalidRequest`，在分配实验之前返回，不带指针：它和 `force_arms` 一样是调试选项，不在请求体里。执行器只检查个数，另一种键类型的 ID 在执行器里永远找不到，所以键类型不同的后备流水线不会因为解释而失败。
  - 后备流水线服务时，解释的是它那次运行，结果里写明是哪条流水线。
  - 限制：用 `col.x@node` 固定版本读的列，显示的是当前提交的版本；回滚的一步不带列值，因为尝试写的都撤销了。

## 回放

回放包的结构见 `stratarec schema replay_bundle`（`src/StrataRec.Artifacts/Model/ReplayBundle.cs`），这里只记取舍。

- **回放包的布局一变就升格式版本，读取时先看版本再解析结构**。不在同一个版本号下原地修改布局，哪怕那个版本只在主干上出现过：已经录下的包无从分辨自己是哪种布局。读取器只读当前版本；其他版本在 `/format` 处拒绝并提示用当前构建重新录制，不把旧布局当作当前版本的结构错误报告。先读版本时和完整解析一样跳过开头的 BOM（字符串入口原来没跳，带 BOM 的旧包报成了布局错误，评审 48）。没有选择兼容读取旧版本：回放包是调试用的短期产物，重新录制的代价小于维护多套读取逻辑。
- **持久化格式的版本是日期加当日序号**（`stratarec.replay_bundle/2026-11-14.1`；缓存记录头是 `uint32` 的 `2026111401`）。日期说明一份数据是什么时候的布局，同一天再改就是 `.2`，按文本也能排序；原来的 `/1` 到 `/4` 不保留任何兼容读取（1.0 之前）。算子和客户端的类型版本（`TopK@1`、`memory@1`）仍是序号：它是每个节点都要写的标识，短、常见，只在破坏性地改配置时加一。

- **在框架的调用点录制和回放，不在连接器里**（设计 13.4）。特征拉取由 `FeatureFetcher` 的调用点经 `IFeatureCallHook` 录制（读连接器解码后的暂存缓冲区，按键记录值），召回源和模型调用经 `OperatorContext.RetrieveAsync` / `InvokeModelAsync`。宿主注册的连接器、模型客户端和算子不用实现任何东西就能录制和回放。没有选择包装 `IFeatureSourceConnector` / `IModelClient`：包装层看不到超时、跳过等执行决定，回放时也要重写按键匹配。代价：自定义算子如果绕过这两个方法直接调用客户端，不会被录制，回放时会真的调用外部服务。
- **录制按请求开启，关闭时只多几个字段**。`DebugOptions.Record` / `PipelineRequest.Record` 默认关闭；关闭时每次外部调用多一次空检查，每请求多约 40 B（请求状态和拉取器上的字段），不做任何按行的工作。开启时分配与请求拉取的数据量成正比，示例请求约 95 KB、多约 0.4 ms，不适合全量常开；按比例常开录制以后再做。
- **计时决定取自录制，回放不计时**（设计 13.4、10.8）。回放的截止时间是 1 小时，不设节点超时：节点的 `min_remaining_ms` 比较用录制时该节点的剩余时间，每次尝试按录制的结果（`ran`、`deadline_exceeded`、`timed_out`）处理，外部调用按录制的状态返回。没有用录制的耗时驱动虚拟时钟：配置一改，调用的顺序和并发就变了，模拟出来的决定在线上从未发生过。代价：修改后的配置里新增的节点没有录制的时间，视为时间充足，永远不会因时间被跳过或超时。
- **数据先按调用精确匹配，再按值合成**。同一数据源、同样的键和顺序、并且包含全部所需字段的调用原样重放，包括超时和失败。只覆盖部分字段的调用不算精确匹配：否则其余字段会被报成缺口，而录制里别的调用其实取到过它们。配置改变了键、字段或分批时，按（数据源、实体、键、字段）从录制中成功的调用取值；取不到的值是缺失，并按原因计入缺口报告（`not_recorded`、`type_changed`、`limit_exceeds_recording`、`inputs_changed`）。录制的值换成新类型时有损（例如超出 float32 范围）也算 `type_changed`，精确匹配和合成用同一条规则，不让溢出变成 ±∞ 混进结果。合成的调用状态是 `ok`：录制中超时的分批不会映射到新的分批上，那些键的值只是缺失。失败调用的数据从不使用。召回源按节点匹配：节点重放并占用自己录制的调用；录制里没有调用的节点（例如配置新加的）复制该数据源返回过的最长列表，不占用任何调用，所以节点的执行顺序变了也不会抢走别的节点的录制；要的数量超过录制、而录制当时已到上限时，报 `limit_exceeds_recording`。
- **模型输出按实体和输入摘要匹配**。每行输出按实体 id 和该行全部输入的 XXH3 摘要记录，只在输入没变时使用；输入变了算缺口（`inputs_changed`），输出缺失。没有选择忽略输入直接复用：那会在特征改动后静默地显示旧分数。哪些输入按行切分只看张量约定：首维等于 `batch_size` 的输入每行取自己的切片，其余输入（共享的用户向量、文本）整体计入每一行的摘要，不按长度能否整除来猜。摘要包含每个输入的元素类型和形状，按行切分的输入不计批维度，所以换一种分批仍然匹配，而同样的数值换一种形状不会。同一实体可能以不同输入被打分多次，合成时按（实体、摘要）查找。回放也不调用模型客户端（设计 5.9、10.8）。因此修改模型绑定（例如线性模型的权重）不改变回放结果；评估模型本身的改动要用实时模式或草稿预览。
- **回放抛出录制时的异常类型**。模型客户端抛出的异常连同类型身份录制（`error_type`）。回放时 `TimeoutException` 仍是 `TimeoutException`，取消仍是 `OperationCanceledException`；其他类型如果回放进程已经加载、派生自 `Exception` 并有 `(string message)` 构造函数，就用录制的消息重新创建，否则抛出带原类型名的 `ReplayedCallException`。这样经 `InvokeModelAsync` 处理特定客户端异常的算子在回放时走同一条路，节点失败的说明也不变。没有选择统一成一种回放异常：那会改变按约定使用调用接口的算子的控制流。代价：需要更多构造参数的类型、回放进程没有加载的类型，算子看到的是 `ReplayedCallException`。
- **异常类型按身份查找，只在已加载的程序集里找**。身份是类型（封闭泛型取泛型定义）的完整名、定义它的程序集的简单名，以及各类型参数的身份。回放只看已加载、简单名相同的程序集，在它们定义的类型里找完整名相同的那一个；泛型的定义和每个参数分别这样找，再组合。没有选择只记完整名：两个程序集可以定义同名类型，按名字挑第一个会让算子接住另一种异常。也没有选择交给 `Type.GetType` / `Assembly.GetType` 解析：它们会跟随类型转发、加载新的程序集，回放包不应该让回放进程加载代码。找不到或找到不止一个（同名程序集加载了两次）都不猜，回退到 `ReplayedCallException`。`TimeoutException` 和 `OperationCanceledException` 也按身份判断，只有核心库的这两个类型才走超时、取消的路径；别的程序集里的同名类型是它自己。代价：数组等构造类型作为类型参数时回退；枚举一个程序集的类型时，运行时可能为解析基类型加载它的依赖。
- **回放用录制的臂，不重新查询分配**。实验平台的分配变了，同一请求在线上会进入别的臂，但回放要比较的是同一处理下配置的差别。`--arms` 可以指定别的臂；回放计划里没有的臂和请求输入会被去掉，并写进报告的说明。
- **回放不是流量**。回放不记指标、事件日志和 span，不写持久日志（探针捕获到结果里）。否则回放录制下来的失败（例如特征源报错）会把一个健康的依赖判为失败，CI 的批量回放也会混进延迟分布。没有选择加 `replay` 标签区分：所有看板和告警都得过滤它。录制则不改变任何观测：被录制的请求照常计入。
- **后备流水线是包里单独的一次运行**（`role: fallback_pipeline`）。回放时主流水线失败，就用这份录制回放后备流水线；录制中主流水线失败却没有运行后备流水线（时间已用完，设计 5.6），回放也不运行。
- **中止的请求也交付回放包，内容是中止那一刻的快照**。被调用方取消或因缺陷中止的请求没有结果，`RecResult.Recording` 带不出回放包，所以录制经回调交付：`DebugOptions.OnRecording` 收到整个请求的回放包，`PipelineRequest.OnRecording` 收到一次运行的录制。返回和中止都会调用回调；回调抛出的异常只记日志，不改变请求的结果，取消照常传给调用方。中止时立即构建录制，不等任何调用。召回源和模型调用的等待在调用方取消时就结束，调用点把它记为 `cancelled`，这正是请求看到的；快照时调用点还没有记录的调用（例如算子发出后没有等待的调用）记为 `outstanding`，它的键和模型输入摘要在调用开始时就已记下；之后才完成的调用的数据不在包里。回放中止的包时，引擎复现录制里每个已完成位置的决定，在录制没有完成的第一个位置停下（录制中正在执行的节点再记一次 `aborted`），报告这次运行被中止，不给出结果。两边都中止的对比算相同；对比报告里中止计入错误率，和线上指标一致。没有选择等在途调用完成再交付：不理会取消的连接器会让取消迟迟到不了调用方。也没有选择把录制挂在异常上（`Exception.Data` 或专用异常类型）：调用方得改写 catch 才拿得到，取消的异常类型也会变。代价：快照之后才返回的数据丢了，修改后的配置如果用到这些调用，回放按取消处理；在查询分配阶段就中止的请求还没有运行流水线，没有回放包。
- **被放弃的调用按请求看到的录制**。超时被放弃的召回源和模型调用记为 `timeout`，不带数据（召回源不记返回的 id，模型不记输出），因为请求没有用到它们；客户端之后才返回的东西不进入录制。节点按超时结束、晚到的成功被丢弃时，调用本身照实记为 `ok`，节点尝试记为 `timed_out`，回放按尝试的结果处理，不使用这次调用的输出。回放时这些调用直接按录制的结果返回，不等待。
- **中止位置的实验触发按录制恢复**。中止时正在执行的位置可能已经触发了实验：到达了站点、节点读了臂改过的参数、走了后备。这次曝光已经发生，计入了实验记录。回放在这个位置停下，不重新执行它，因为执行到一半的位置无法复现。所以录制在中止的节点上记下这个位置从开始到中止新触发的实验（`triggered`，只出现在中止的节点上），回放停在这里时按 id 恢复，只恢复回放计划里存在、并且在回放的臂下已分配的实验。这样相同配置上回放的触发集合与录制完全相同。没有选择回放时给中止节点补记它的全部参数触发：取消可能发生在节点读参数之前（例如还在拉特征），那会多出没有发生过的曝光。代价：修改后的配置即使改了这个位置的触发条件，回放也只恢复录制的事实；录制的请求在每个位置开始时多复制一份触发状态，不录制时没有这份开销。
- **值编码复用日志编码，类型写在值旁边，但保留非有限值**。`null` 是缺失；NaN 和 ±∞（包括向量的分量）写成字符串 `"NaN"`、`"Infinity"`、`"-Infinity"`，日志里仍然写成 `null`。回放包必须如实保留请求看到的值：并不是每条路径都会先把非有限值换成缺失或默认值（设计 4.6），暂存的原始向量和直接求值的输出表达式就不会，按缺失录制会让回放走另一条路（`has()` 变成假、结果出现差异）。两者共用同一个编码器，回放包只是打开一个选项，没有另写一套。每个值按旁边记录的类型解码，类型不兼容时报出 JSON 指针。
- **对比指标的定义**（设计 10.8）。Top-K 重合度 = 交集 / 两个 Top-K 中较长者，短列表不会抬高重合度；Kendall τ 只在两边共有的条目上计算，少于两个时为空；分数分布变化用双样本 KS 统计量，另给同一条目的分数差；两者都只用有限的分数，NaN 和 ±∞ 按每一边单独计数报告：它们没有位置可排，混进去会让 KS 失去意义，NaN 还会让排序比较不再自洽。降级率的分母是全部请求，分子只算成功但降级服务的请求；失败的请求只算错误，不算降级。特征缺失率包括数据源本身缺失和回放包里没有的值。录制模式下外部 I/O 立即返回，延迟只反映引擎计算，不能用来评估依赖延迟。配置增删的输出列在差异中单独列出，不逐条重复。
- **`replay` 和 `compare` 只有用上了每个包才算通过**。没有包、包全部读不出来、或者一个都没比较成，以 2 退出；部分包读不出来也以 2 退出，但照常输出报告，JSON 里带 `status`（`ok`、`partial`、`failed`）和读不出来的包数。CI 用退出码判断对比是否通过，只覆盖一部分包（或一个都没覆盖）的指标不能当作干净的结果放行。没有选择部分成功时返回 0 只在报告里标出：CI 步骤通常只看退出码。

## 配置错误

- **JSON 绑定错误只在一处翻译，用 JSON 的说法**（`JsonBindingErrors`，设计 7.4 第 8 条、9.1）。产物、算子配置、日志探针、实验补丁的各段和 `run` 的请求文件都经过它，同一种错误在哪里都是同一句话：未知键（有接近的就给 did you mean，否则列出允许的键）、值的种类不对（`'order' must be an integer or null, got the string "350".`，长值截断）、整数越界或带小数、缺少必需的键（提示里给出这个键的含义，取自 `[Description]` 或程序集旁的 XML 文档；单文件发布没有 XML 文档，只是少了这条提示）。翻译沿着错误路径同时走目标类型的 `JsonTypeInfo` 和文档本身，期望的种类来自类型、实际的值来自文档，不解析 System.Text.Json 的英文消息：那些消息里有 .NET 类型名，行号是重新序列化之后的；只有我们自己的转换器写的消息直接采用。错误码和指针不变。值的错误（特征默认值、参数值、enum、表条目、请求输入）统一用 “must be …, got …”。只在出错时运行，绑定成功的路径不受影响。翻译用 System.Text.Json 实际读值的契约：多态类型按 discriminator 取派生类型；字符串枚举用读值的那个转换器写出每个值，得到真实的名字；看不出形状的第三方转换器给通用消息，不猜种类（评审 32）。描述错误本身从不抛异常：文档里读不出的部分（非法 Unicode、重复的键）先作为带位置的错误报告，字符串入口失败后用严格的 JSONC 重读；不是 `JsonException` 的异常只在文档能解释它时翻译，否则照常抛出，当作程序错误（评审 32）。键里有 `'`、`]`、`.` 时错误路径可能有几种读法，只采用文档里恰好成立的那一种；零种或多种时报它们共同的祖先和通用消息，宁可笼统也不给一个错误的具体结论。
- **同一份文档，从哪个入口读都是同一个结论**（Gemini 的 JSON 审查，核实后采纳一部分）。工作区文件先由 `Jsonc` 严格读取（语法、重复的键、Unicode、深度）再绑定；字符串入口（发布清单、回放包、内容存储里的产物）原来直接交给序列化器，序列化器默认保留重复键的最后一个值，只在绑定失败后才严格重读：同一份带重复键的文档，作为文件被拒绝，作为字符串被接受。现在 `ArtifactSerializer.Deserialize(string)` 先做同样的检查（不建树，只走一遍读取器），再从同一份字节绑定；`ArtifactSerializer.Options` 也设 `AllowDuplicateProperties = false`，给自己用这套选项的宿主。`memory@1` 和 `memory_list@1` 的数据文件原来各自用宽松的 `JsonDocument` 读（两份相同的代码），现在共用 `DataFile.Read`，同样严格。`Jsonc` 只负责读取：它原来还有一套没有被任何产品代码用到的反序列化选项和 `Deserialize`，注释却说“每个产物都用它”，两套规则只会分叉，删掉了。保留的差异各有用途：手写的文件是 JSONC，HTTP 请求体是严格 JSON（重复键由 `RequestSchema` 拒绝）；产物成员用 snake_case，字典键原样；产物省略可选的 null，结果文档用 null 表示缺失；回放包保留非有限浮点，服务结果写成 null；内容哈希用独立的 RFC 8785 规范化。没有接入源生成：绑定只在加载时发生，不在请求路径上；宿主的自定义算子配置也要绑定，源生成会要求扩展作者把类型登记进一个上下文；目标也不是 AOT。
- **位置在打印时计算，编译不读文件**。产生诊断的代码只报产物、JSON 指针和表达式偏移（`ConfigDiagnostic.Offset`，可选）；CLI 打印时才读对应的 JSONC 文件（`JsoncLocator`），把指针换算成行列，输出 `file:line:col: error CODE /pointer: message`，终端和编辑器能直接跳转；`--format json` 多出可选的 `file`、`line`、`column`，读输出的程序不受影响。对象成员定位到键（编辑器在键上标拼错和缺少），数组元素定位到值，表达式错误定位到字符串里那个字符（算上转义和多字节字符）。指针在文件里找不到时（合并或补丁之后的视图）回到最近的祖先，绝不猜一个行号。显示的路径是 `-c` 给的目录加上工作区内的相对路径，从当前目录就能打开。没有文件的诊断（store 里的 manifest、臂新增的列和参数）照旧打印。产物标签到文件先按完整标签匹配（ID 可以含空格），找不到才去掉格式明确的臂组合后缀，找不到就不给文件，绝不指向另一个文件（评审 32）。表达式偏移以 UTF-16 单位计，原样写的非 BMP 字符的低代理有自己的列。文本输出在定位到的诊断下面打印那一行（去掉缩进）和指向列的 `^`：表达式的错误常在一个很长的字符串的中间，终端里的读者不必去数第 93 列。超过 100 个字符的行只显示列附近的一段，用 `...` 标出截断；`^` 前的填充按码点计算：制表符照抄；组合符、格式字符不占位，不管它在哪个区段；宽字符（中日韩文字、全角符号、emoji 区段、补充表意平面）填一个全角空格；其他字符占一格，补充平面里窄的字符也是一格（评审 34：原来把所有代理对都算宽，也把宽区段里的组合符算宽）。所以中文配置里也对得上。只在文件里找到了位置时才打印（找不到时位置是文件的第一行，不画一个错误的箭头）；JSON 输出不变。表达式错误的消息为了单独阅读引用了整个表达式（“at offset 53 in '…'”），打印了源码行时改用 `ConfigDiagnostic.Brief`，不再把表达式重复一遍：多行的 `let` 公式原来会把整段公式连同换行塞进第一行。消息本身不变，日志、JSON 和没有源码行的输出照旧带着偏移和表达式。
- **类型错误指向出错的部分**。二元运算只有一边错时指向那一边，两边都错或各自合法、组合起来不合法时指向运算符；函数指向从左往右第一个类型不对的参数，从不指向函数名；参数各自合法但彼此不符（`dot`、`cosine` 维度不同）时指向后一个；`contains`、`in` 的容器不是列表时指向容器，否则指向元素；`??` 指向右边，`?:` 指向 else 分支；参数个数不对指向整个调用。
- **一个错误只报一次：出错的声明标为不可用，引用它的地方不再报错**（`PlanSchema.MarkUnusable`）。类型写错的列、参数、请求输入、特征，配置错误的节点、漏斗组（每一条报了错的路径，评审 32）、实体键，无效的臂都这样处理；原来一个 `int46` 会连带报出四到七个错误。没有给出错的声明注册一个占位类型：占位类型要么引出不存在的类型错误，要么让本该失败的引用编译通过。编译照样失败，因为声明本身的错误已经报了。代价：修好第一个错误之后，可能冒出原先被遮住的错误。
- **类型名的拼写只在一处规定**（`ConfigTypes`）：列和请求输入、特征、参数各自接受哪些类型，拼错时给出 did you mean（`int46` → `int64`，`double` → `float64`），提示列出的就是这个位置实际接受的类型。提示只推荐这个位置真正接受的写法：参数写成 `int32?` 时建议 `int64`，不建议同样不被接受的 `int32`（评审 32）。
- **JSON 整数按原文精确判定**（`JsonIntegers`）。`.0` 和指数写法只在恰好等于一个整数时接受，判断不经过 double，也不经过 decimal：double 分不清相邻的大整数，decimal 超过 28 位有效数字会舍入，两者都会把一个非整数或另一个整数当成写下的值（`[9007199254740993.0]` 原来被读成 9007199254740992，评审 32）。普通整数先直接读 int64，不分配。它是公开的 API，所以自己也按 RFC 8259 的数字语法检查，不依赖调用方先用 JSON 解析器过一遍：前导零（`01`）、小数点后没有数字（`1.`）不是数字（评审 33）。指数的绝对值超过“原文长度 + 19”才直接判为越界或非整数：很长的尾数能抵消同样大的指数（`1` 后面两千个 `0` 再 `e-2000` 就是 1），固定的界限会在尾数足够长时判错；超过这个界限时，尾数的有效数字无论怎样排列都到不了 int64 的范围，也补不成整数。
- **`run` 的请求文件和产物一样严格绑定**：拼错的成员（`inptus`）原来被静默忽略，到运行时才报“输入缺失”，现在是带位置的错误。
- **CLI 的 JSON 输出不做 HTML 转义**：输出给终端和程序，不嵌进网页，默认编码器会把 `'` 写成 `\u0027`，消息就难读了。
- **内置客户端（`linear@1`、`memory@1`、`memory_list@1`）严格检查设置**：不认识的设置和类型不对的值都是错误，位置是绑定里的 JSON 指针，提示相近的名字（数据文件里的成员报在 `/data_file`，消息写出文件和文件内的位置）。原来拼错的设置被忽略、用默认值，`"activaton": "sigmoid"` 静默变成恒等激活；类型不对时抛出没有位置的异常。`init` 和示例绑定的正是它们，也是用户最先改的地方。包装它们的客户端只把它们认识的设置转过去。客户端创建时的其他异常（读不到文件等）报在绑定上（`MODEL_CONFIG`、`CANDIDATE_SOURCE_CONFIG`），和特征源的 `CONNECTOR_CONFIG` 一致；原来候选源的这类错误报在引用它的召回节点的 `/quotas_param` 上。召回节点有源绑定失败时，仍然声明自己的列，并报告每一个失败的源，读这些列的节点不再连带报 `EXPR_UNKNOWN_NAME`。拼写建议的规则移到 Core（`Spelling`），产物和绑定共用一条规则，Artifacts 因此引用 Core（依赖方向不变）。

## 计划工具

- **一种写法指定配置（ref），按语法先判断 manifest id，再看文件系统**（设计 13.4）。`sha256:<64 位小写十六进制>` 是 store 里的 manifest；否则已存在的目录是工作区，已存在的文件是 manifest 文件（它的产物也在 `--store` 里）。没有引入 `kind:` 这类前缀：id 本身没有歧义，不发明新语法。`-c` 保持原义（工作区），`--manifest` 是和它互斥的另一种选择，`compare --baseline` 和 `diff --from/--to` 接受任何一种 ref。manifest 文件的 id 和 `build` 一样由 manifest 模型的 RFC 8785 规范形式算出，不按文件字节：重新排版或加注释的文件 id 不变，和 store 里的 blob 对得上。
- **回放结果的差异按条目比较，不按名次**。原来逐个名次比较两边，同一名次上是两个不同的条目时，把它们的列值并排列出，对哪一个都说明不了什么。现在每个条目和它自己比较：在两边各排第几（只在一边的写 `absent`），以及它自己变了的列值；报告还给出两边共有的条目数（`in_both`）。这是 `replay --format json` 中 `changes` 的不兼容改动：原来是 `{rank, recorded_id, replayed_id, columns}`，现在是 `{id, recorded_rank, replayed_rank, columns}`。
- **命令行解析不了的命令退出 2**（评审 34），和各命令自己发现的用法错误一样：未知选项、选项缺值都是用法错误。System.CommandLine 默认退出 1，而 1 表示配置有错误，`diff` 的 1 表示有差异，脚本不能把一个拼写错误读成这些。出错时只打印错误、拼写建议和一行 `See 'stratarec run --help' for the usage.`：System.CommandLine 默认在错误后面打印整页帮助（`run` 有 25 行），错误被埋在上面。没有给命令时仍打印帮助，那时命令列表正是要看的。命令的校验器按 token 判断参数有没有给，不读值：`-b` 缺值时读它的值会抛异常，原来让进程崩溃。
- **回放包可以直接作为参数**：`stratarec replay -c feed b.json`，也可以给多个文件（shell 通配）或目录；`-b` 仍然可用。`run --record` 打印可以照抄的回放命令，路径按 shell 引用，以 `-` 开头的相对路径写成 `./-b`，否则会被读成选项（评审 34）。`run --format text` 给出可读的结果（每行一个条目、trace、候选解释）；默认仍输出服务返回的 JSON 文档。
- **回放时，请求跑过的每条流水线都要有配置**（设计 13.4）。回放包的 `runs` 记着请求跑过的流水线：主流水线，失败后转去的后备流水线，各自带录制时的 manifest。少了后备流水线的配置，主流水线一失败回放就停在失败上，看起来像配置改出了差异，其实是没加载（评审 24）。所以 CLI 为每个包按 `runs` 准备引擎，配置的来源按命令行定：只给 `--store` 时，每条流水线都用它录制时的 manifest，调试线上请求不需要先找到当时的 git 提交；`--manifest` 只替换它那条流水线（必须是包自己的流水线），后备流水线仍用录制时的 manifest，“换一份主流水线的配置看效果”不会顺带换掉后备；`-c` 的工作区提供所有流水线。主流水线总在其中：没有主运行的包（被裁剪过）用包顶层的 manifest 回放主流水线，外部调用都是缺口，和在工作区上一样（评审 25）。`compare` 的两边按同样的规则准备。缺了哪条流水线的配置（store 里没有那个 manifest、工作区没有那条流水线，或者在工作区上录制的包，它的 id 是 `workspace:<流水线>/<环境>` 这样的标签，store 里找不到），这个包就计为 `unresolved`，说明是哪条流水线、哪个 manifest、怎么回放，不挡住其他包。引擎按“流水线 → 配置来源”的组合缓存：同一版本的包共用一个引擎，后备流水线换过版本的请求各用各的。直接调用 `RecEngine.ReplayAsync` 的宿主，引擎没加载录制里跑过的后备流水线时，回放报告的 notes 会写明。
- **manifest 没有配置根，绑定里的相对路径按当前目录解析**，和不设基准目录的宿主一样。只读 manifest 的命令里只影响样例和开发用的内存夹具：`memory@1`、`memory_list@1` 在创建实例时就读 `data_file`（见“绑定的实例”），不加载的编译也要找得到它们；线上的绑定指向外部服务。`run --manifest` 像节点一样加载全部绑定（本地表的快照、模型文件），所以在节点的工作目录里运行。读 manifest 的命令（`run`、`explain-plan`、`diff`、`replay`、`compare`）报的错误里出现当前目录下的路径时，多打印一行，说明相对路径是按哪个目录解析的，否则读者只看到一个意外的绝对路径；只在错误里真有这样的路径时才打印，`--format json` 时不打印。`run` 原来只接受工作区，发布之前或之后想试一个 manifest，只能回放录制过的请求；现在任意请求文件都能在 manifest 上跑，录制的包按打印出的命令从 store 回放（以文件给出的 manifest 不一定在 store 里，命令里带上 `--manifest <文件>`）。请求的 `pipeline_id` 不是 manifest 发布的那条流水线时，在加载之前就报 `REQUEST_INVALID`，退出码 2：这是请求文件的错，和请求的其他错误一样。只加载这个 manifest 的流水线：计划有后备流水线时打印警告，这次运行里请求失败不会转去后备（要试后备，在工作区上跑，或者回放线上录制的包，回放按 `runs` 加载每条流水线录制时的 manifest）。没有加 `--root` 选项，也没有把夹具改成加载时读文件（那要推翻已记录的取舍），等真有需要再做。
- **某个桶组合的有效计划从编译好的统一计划里取，按请求选择变体的同一个方法选，不重新合并补丁**（`EffectivePlan`）。显示的就是实际执行的，编译器的缺陷会在这里暴露，而不是被第二套合并实现重复一遍。`explain-plan --arms` 打印它，`diff` 比较两份它的文档形式，两者不会不一致。只因某个臂才存在的节点、参数、探针，只出现在包含这个臂的组合里。输出统一用 RFC 8785 规范形式：store 里存的是规范字节，成员顺序和工作区不同，不统一的话同一份配置会打印成两样。
- **`diff` 默认比较基线和每个臂单独生效的组合，两个臂同时生效的组合只用 `--arms` 指定**。组合对的数量随臂数平方增长，而且编译时已经逐个校验过；基线上的改动会在每个组合里重复出现，按组合看正是要的结果。只在一侧存在的臂，它的组合标成 `missing_on`，不比较，也不替它编造计划，否则臂的全部内容都会被报成改动；实验换了层，只在实验这一条上报告。比较的是设计 13.4 列出的节点、配置、参数和探针（加上漏斗组和输出），不比较绑定、目录、请求结构和 policy：这些改动在 `diff` 里看不到。退出码按 diff(1)：0 无差异，1 有差异，2 出错。两侧都先编译完再报告，诊断的产物前面加 `--from ` 或 `--to `，一侧坏了不挡另一侧。
- **JSON 差异逐叶比较**（`JsonDiff`）：只在一侧的成员算一条改动，带整个值；数组整体比较，因为元素没有稳定的标识；JSON `null` 和成员不存在不同；改动按指针的序数顺序输出。
- **编辑器支持来自工作区里提交的 JSON Schema**（设计 9.1）。每类文件在顶层写 `"$schema"` 指向 `schemas/<kind>.schema.json`，编辑器据此补全、悬停、报错，不需要插件。
  - Schema 由服务这个工作区的二进制写出（`stratarec schema --out`，`init` 也写），所以包含宿主自己的算子：宿主示例的 Schema 是用宿主自己的二进制写出的，里面有 `CategoryBoost@1`。没有在仓库根放一份公共的 Schema：同一个框架版本，不同的宿主有不同的算子。
  - `$schema` 不计入内容 ID：读文件时先去掉它，再绑定、哈希、存储，所以 `build` 上传的字节、manifest 和 `diff` 都不受它影响。内容 ID 标识部署的东西，`$schema` 只给编辑器用；它的值是相对路径，换个目录布局就会变；给仓库里所有文件批量加上 `$schema` 也不该产生新发布，或者让大表重新下载。只认顶层的字符串：其他类型的值是 `ARTIFACT_SCHEMA /$schema`，hint 给出这个文件该写的路径；嵌套在别处的 `$schema` 仍按未知键报错。`run` 的请求文件也一样。
  - 流水线按节点的 `op` 校验 `config`，每个算子一组 `if {op: const} then {config: …}`。没有用 `oneOf`：它只报“最接近的那一支”的错误，未知的 op 会显示成误导人的类型错误。`op` 是枚举，带 VS Code 的 `enumDescriptions`。只有算子的配置有必填成员时才要求写 `config`，否则允许 `null`，和引擎把缺失或 `null` 的配置读成 `{}` 一致。
  - 实验臂的 Schema 是流水线可修改视图的合并补丁形式：去掉所有 `required`，每个值都可以是 `null`（删除）；封闭对象里未知的键只能是 `null`：切换节点的 `op` 时要删除旧算子独有的配置成员，新算子的 Schema 里没有它们，删除不存在的成员也不改变什么，带值的未知键照样报错（评审 34，原来保留 `additionalProperties: false`，合法的切换会被标红）；臂的顶层（分区清单）仍然封闭，分区既不能删除也不能拼错；数组整体替换所以 `items` 不变，`if` 不变（补丁里写了 `op`，`config` 仍按那个算子检查），分区本身不能为 `null`（引擎拒绝删除整个分区）。一个条目是新增（必须完整）还是修改，取决于基线，按类型生成的 Schema 看不到基线，所以它从不拒绝合法的补丁，这一部分留给 `validate`。可修改的分区只有一份清单（`PatchableView.Sections` 由 `ExperimentArtifact` 的分区拼出），Schema 和补丁校验用的是同一份。
  - 描述先取 `[Description]`，没有就取 XML 文档注释的摘要（`MemberDocs`），所以悬停能看到字段说明。代价是 Schema 的字节取决于二进制旁边有没有 XML 文档：生成和检查要用同一个二进制，单文件发布、不带 XML 文档的二进制写出的 Schema 没有描述。
  - 过期检查是 `validate` 的警告 `SCHEMAS_STALE`，不另做 `--check` 命令：CI 本来就跑 `validate`，加 `--warnings-as-errors` 就会失败，开发者本地也看得到。是警告不是错误，因为它不影响部署。只在 `schemas/` 存在时检查，忽略 CRLF 差异，不管目录里的其他文件。`--out` 只改写内容变了的文件。
  - fixtures 不加 `$schema`：它们是连接器的数据，`$schema` 会被当成一个 ID。宿主示例里给 curl 用的请求体也不加：服务的端点是严格的，未知成员是 400。
  - Schema 用了 VS Code 的非标准关键字 `allowComments`、`allowTrailingCommas`、`enumDescriptions`。2020-12 把未知关键字当注解；ajv 的 strict 模式会报错，要关掉。
- **`stratarec init` 生成最小可运行的工作区**（设计 10.1）。新流水线从一份能跑的小工作区开始，而不是从删减过的示例开始：示例演示全部功能，删的时候不知道哪些能删。生成的工作区包含用户要改的每一种文件（policy、目录、`local` 绑定、一条从召回到 top-k 的流水线、一个改权重的实验、发布文件、夹具和一个带分配的请求），生成后 `validate` 零错误零警告，`run` 离线就能跑；init 最后打印接下来可以照抄的命令。测试按生成的文件跑这几条命令，模板改坏了测试会失败。模板是一个 C# 文件里的原始字符串，没有用嵌入资源或 `dotnet new` 模板：唯一的替换（流水线 ID）由编译器检查，文件、说明和打印的命令用到的名字（实验、臂、请求文件）放在一处。流水线 ID 先按标识符校验再替换，不需要 JSON 转义；实验 ID 固定为 `exp_freshness`，不随流水线变。每个文件（夹具和请求也是）都是 JSONC，开头的注释说明它是什么、先改哪里。参数只有目录、`--pipeline` 和 `--force`，不做交互式提问，其余在生成的文件里改。目录里有可见的条目时不写，并指出挡住的是哪个文件：输错的目录不应被撒满工作区文件；隐藏条目不算（先 `git init` 再生成是常见做法，init 也不写隐藏文件，不会覆盖它们）。`--force` 只覆盖同名文件，从不删除，也不经过工作区里的符号链接写入：链接会把写入带到工作区外，覆盖别处的文件（评审 31）；用户指定的根目录本身是链接没关系，那是用户选的位置。所有检查在写任何文件之前做完，读不了目录也是带提示的诊断。打印的命令按 POSIX shell 的规则引用（必要时用单引号），目录名里有空格、`$`、反引号、引号或反斜线也能照抄（评审 31）。

## 工程

- **只支持 .NET 10，CI 只用 Linux**。宿主都在 .NET 10 及以上，所以目标框架是 net10.0、C# 14，CI 用 SDK 10 构建，测试跑在 .NET 10 运行时上。原来以 net8.0 为目标，CI 用 SDK 8 和 SDK 10 各构建一次，测试却都跑在没有人部署的 .NET 8 运行时上；为了 SDK 8 的编译器（Roslyn 4.11），banned-API 分析器停在 3.3.4（评审 5），语言停在 C# 12。现在分析器用 5.x，框架自带的 System.Text.Json 和 System.Diagnostics.DiagnosticSource 不再显式引用。换运行时之后：每请求的分配逐字节不变（`PipelineBenchmarks`、`FeatureSupplyBenchmarks`），耗时少 10%–25%；`TensorPrimitives` 在 net10.0 上改用运行时的向量数学，`exp`、`log` 等的末位可能和 .NET 8 不同（本机 `log(1.5)` 差 1 ulp，差多少取决于运行时和硬件），同一个二进制里标量和逐行的结果仍然逐位一致（设计 5.7 第 4 条）。
- **依赖跟着目标框架的版本线，其余用最新稳定版**。与运行时同一版本线发布的包（`Microsoft.Extensions.*`、`System.Numerics.Tensors`、`System.IO.Hashing`，测试用的 `Microsoft.AspNetCore.Mvc.Testing`）停在 10.0 的最新补丁，不升到 11.0：库的目标是 net10.0，依赖 11.0 的 `Microsoft.Extensions.*` 会让 .NET 10 的宿主越过共享框架自带的版本，把整套依赖抬到 11.0；`Mvc.Testing` 要和 ASP.NET Core 共享框架同一个主版本。目标框架改到下一个版本时一起升。其他依赖用最新稳定版：`JsonSchema.Net` 9.7、`System.CommandLine` 3.0（它也以 net10.0 为目标，升级没有改代码）、`xunit.v3`、`StackExchange.Redis`、`BenchmarkDotNet`、分析器；CI 的 actions 同样用最新的大版本。
- **测试用 xUnit.net v3，跑在 Microsoft Testing Platform 上**。xUnit 2 只做安全维护。v3 的测试项目是可执行程序；`dotnet test` 按 global.json 的 `test.runner` 走 MTP，不再带 VSTest（`Microsoft.NET.Test.Sdk`、`xunit.runner.visualstudio`）：只有一种运行方式，`dotnet test` 和直接运行测试程序的选项相同（筛选用 `--filter-class`、`--filter-method`，不是 VSTest 的 `--filter`）。接受 `CancellationToken` 的调用都传 `TestContext.Current.CancellationToken`（分析器 xUnit1051 要求），测试超时或被取消时，等待和请求随之停下，不用等到各自的超时。集成测试程序集保留自己的入口：子进程测试用它跑会让进程退出的场景，其他参数交给 xUnit 的 MTP 入口。CI 的 TRX 报告按项目命名（`-p:TestReports=true`），默认的文件名是时间戳，同时结束的程序集会写到同一个文件。一个测试原来用测试 SDK 带来、没人加载的程序集作“能按名字加载、但没有加载”的样本，SDK 去掉后改用单元测试从不加载的 `System.CommandLine`。
- **内存分配预算是估算**（设计 15）。“每请求 ≤ 2 KB”不是硬指标，允许一定偏差。当前示例流水线（`PipelineBenchmarks.Baseline`）每请求：5,000 候选约 35.6 KB，500 候选约 19.7 KB，只有 Gen0（原来分别约 227 KB 和 45 KB；`author_store` 改成本地表之前是 36 KB 和 20 KB）。按键和按分批的工作都不再分配，连接器同步返回的分批是 0 B（原来约 420 B，见“特征拉取”）。5,000 候选时其中约 17 KB 是 `memory@1` 解码字符串：`JsonElement.GetString` 为每个值新建一个字符串，约 500 行读到 `item.category`；这属于第 15 节单独计量的字符串解码，引擎这边的字符串可以忽略。其余约 18–19 KB 与候选数无关，按 500 候选的抽样：返回给宿主的结果约 4.5 KB（第 15 节不计）；节点预算和拉取的取消源、定时器约 2.5 KB；每次拉取的对象（键索引、暂存区、待完成记录、字段子集）约 0.5 KB，示例请求约 6 次；候选表、表中字符串列的字典、请求状态和节点上下文约 6 KB；算子、模型和召回调用约 1.2 KB。
- **不做请求状态池**（设计 4.8 表中第二行）。请求级的对象随请求数增长，不随候选数增长，交给 GC 足够；值得优化的是随候选数和特征数增长的部分（列缓冲、位图，已经从请求内存租借）。能放进池的部分（`RequestState`、`CandidateTable`、`RowSelection`、`OutputBindings`、`FeatureFetcher`、表中字符串列的字典、节点上下文）合计约 6 KB，约占剩余分配的三分之一。池化要为每个对象写重置逻辑，漏掉一处就会把上一个请求的数据带进下一个请求；请求返回后，被放弃的 I/O 还持有请求内存，状态只能在最后一次 `Release` 时归还，可能在连接器线程上。每请求 20–40 KB 的 Gen0 分配在每秒数千请求时是每秒几十到一百多 MB，Gen0 回收的成本与存活对象成正比，而回收时这些对象大多已经死亡。更划算的是先做局部的：节点预算复用一个取消源（`TryReset`），按计划缓存拉取的字段子集，表中字符串列的字典按计划预设容量。原来写的是“压测显示 GC 暂停或分配速率与请求状态有关时再做”，现在定为不做（2026-11-14）：池化是为一个不随候选增长的量增加一整套重置约定。
- **性能审计（2026-11-14）的取舍**。原则：随候选数、特征数增长的开销值得在一处内聚地优化，请求级的固定对象交给 GC；不为不是瓶颈的收益增加使用者要理解的约定。做了：`SlidingWindowQuota@1` 的重复扫描（见“执行与宿主”）；结果不再先建 K×C 的中间矩阵；向量输入的 shape 一次建成（每个输入每批少一个数组）；召回来源的字典码每个来源查一次而不是每行一次；字符串主键追加时一次预留字典容量（5,000 个键 583 KB → 约 204 KB）。分批追加时每次至少翻倍、但不超过表还能追加的行数：只按每批的需要预留会让字典每批都重新分配，5,000 个键每批 500 个反而比逐个 `Add` 多分配（866 KB 对 583 KB；只翻倍时最后一批会扩到表的两倍）；评审 44；`memory@1` 的 `list<int64>` 用租借的缓冲解码。没有做：表达式后端换成手写 SIMD（融合公式 5,000 行约 37 µs、零分配，不是瓶颈）；字符串的请求级驻留池（列本来就是字典编码，缓存命中时分配不随候选数增长）；结果或请求对象池；录制时逐值 JSON 的优化（只在录制时发生）；采样上限很小时的阈值选择（只在采中的请求上，按实际负载再定）；`memory@1` 按行查 JSON 属性（只用于本地和测试，本地表是生产路径）。
- **架构审计（2026-11-14）的取舍**。做了：`replay` 的结果项与服务结果共用一个写法（原来另写一份，把输出列平铺进结果项，列名为 `id`、`rank` 时写出重复成员）；扩展算子解析并登记读取是一步（`TryResolveRead`，原来先 `Scope.TryResolve` 再记得 `RecordSymbol`，漏掉第二步时特征不会被预取；`RecordSymbol` 不再公开）；依赖调用结束方式的翻译列出全部取值（新增一种结束方式时编译失败，而不是落进默认分支）；内置模型客户端共用名字列表的读取和未知设置的诊断（`random@1`、`fixed_text@1` 也给出相近的名字）。没有做、留待公开 API 定型时一起定：已发布计划的只读检查视图（现在 `TryGetPipeline` 给出可变的 `ExecutionPlan`）；模型签名“已知、延后、未检查、失败”的显式结果（现在后三者都是 null）；本地表记录引用携带所属版本。数据流规则与它的作用域放进同一个协作者、补丁视图的贯通护栏、最小编译夹具，在下次改动那些规则时一起做。
- **基于示例的测试默认不计时，测预算的测试显式选择原始预算**。示例保留真实的预算（`ctr_ranker` 给模型 50 ms，超时回退到 `ctr_backup`），用来演示预算和回退。晚到的结果一律按超时处理，冷启动的模型调用在繁忙的 CI 上会超过 50 ms，比较两次实时运行的测试就会一次回退、一次没有，结果对不上。所以测试默认用示例的一份副本：其中每个 `timeout_ms`（节点及其实验补丁、特征源、模型、召回源）和请求文件的 `deadline_ms` 都提高到一分钟，`on_failure` 不变，测试自己构造的请求也用一分钟的截止时间；测预算本身的测试选择 `SampleTiming.AsWritten`，由门控的客户端决定调用何时返回，不和时钟赛跑。放宽只有一处（`tests/Shared/SampleBudgets.cs`），基准测试也用它：基准度量的是流水线的工作量，冷启动碰到预算就成了度量回退。放宽只替换文本里的数字，注释和格式不变，测试照常按文本修改副本；遇到不认识的 `*_ms` 设置、一处都没放宽，或编译出的计划里仍有低于一分钟的节点预算或拉取预算（没写 `timeout_ms` 的拉取源用框架默认的 50 ms）时直接报错，不会悄悄失效。比较两次实时运行的测试先逐个节点比较结果（`LiveRunAssert`），时间因素再混进来时，失败信息会指出哪个节点、为什么回退。没有沿用逐个测试改超时字符串的做法：同一条规则散在多处，示例一改就悄悄失效。代价：默认的测试不覆盖示例真实预算下的行为，这部分只由选择 `AsWritten` 的测试覆盖；挂住的调用要等一分钟才让测试失败。
- **测试里的预算只切断测试想切断的调用**。一个预算由一次拉取的所有分批共用（节点预算、请求截止时间同理）：短预算切断的是截止时刻之前没被观察到的所有调用，不只是测试想挂住的那个。CI 上实测过：正常回答的分批 90 ms 内就做完了，但同时运行的其他测试占满了线程池（4 核、5 个线程、几十个工作项排队，GC 暂停只有一百多毫秒），完成的回调 1.4–2.9 s 后才执行，晚于 1.5 s 的预算，有的分批被判为超时；同一时段，等待排空 20 ms 的日志管道关闭用了 3–4 s。所以：单元测试的特征测试台（`FeatureTestRig`）默认的源预算和请求截止时间都是一分钟，与示例测试的“不计时”一致；需要一部分调用正常回答、另一部分被切断时，由测试自己切断：等调用钩子显示其余调用都已判定，再取消调用方令牌（同步回答的调用在 `EnsureAsync` 返回之前就已判定）；集成测试要在某个调用进行中取消请求时，从这个调用发出时计时（`CancelOnceCallStarts`，看调用的 span），不从请求开始时计时，被切断的调用要一分钟才回答。只防止测试挂住的上界（等一个永不自己结束的调用、一个要一分钟的调用）放宽到 30 s。超时的分类和预算的上界由“所有调用都挂住”的测试覆盖，这时预算只可能切断测试想切断的调用。代价：结果有成有败的测试里，失败一方是 `cancelled` 而不是 `timeout`，两者走同一段失败处理（分批标记失败、暂存不被读取），分类另有测试。仍然依赖时钟的有两类：测请求截止时间本身的端到端测试，截止时间之前的节点要在截止时间内跑完；选择 `SampleTiming.AsWritten` 的测试，不测的预算也按原样。
- **确定性的范围**（设计 5.7）。计划、请求输入、时间、外部响应和执行决定（超时、跳过、后备）都相同时，排序结果、分数、选中的变体和采样决定相同。耗时、`seq`、producer id 等运行元数据不在保证内，回放对比时要排除。
- **`stratarec run` 的截止时间可以覆盖：`--deadline-ms`**。CLI 每次只跑一个请求，进程是冷的，第一个请求还要 JIT 编译它执行的代码：示例请求的 200 ms 是给预热好的服务的，在慢机器或繁忙的 CI 上会用完（CI 曾因此失败，节点都成功、请求截止时间到了，错误是 “no time left before the request deadline”）。请求失败并且用掉了截止时间（不少于九成）时，CLI 在标准错误上提示原因和这个选项。只覆盖请求的截止时间，节点和数据源的预算不变：那些是被演示的配置。没有选预热：先跑一遍同样的请求，会让真实连接器的调用、日志和录制都发生两次。也没有改示例的 200 ms：示例演示真实预算。CI 运行示例时用 `--deadline-ms 10000`。
- **数据流规则和它的作用域暂不合并成一个对象**（设计 11.5 第 3 条）。每条规则写在两处：`PlanBuilder.ValidateDataFlow` 里怎么检查，`DataFlowScopes` 里由哪些节点决定；后者只在组合数超过上限、按作用域检查时用，新增规则忘了登记作用域，小配置的测试照样全绿。合并成“每条规则一个对象，同时给出检查和作用域”是正确的方向，但这是约一千行、最难的一段代码，刚经过多轮评审稳定下来，现在重写的风险大于收益：新增规则时才真正出现遗漏的风险。现在的护栏：生成式差分测试的多层模式（4–5 层、上限 8–16，组合空间超过上限）逐组合对照合并后的普通编译，一条没有作用域的规则会在某个组合上放行而被它抓到；植入的三层规则保证去掉按作用域的检查就失败；另有作用域的专门测试。约定：给 `ValidateDataFlow` 加规则时，在同一个改动里给 `DataFlowScopes` 加作用域，并在生成器里加能触发它的原子；下一次加数据流规则时先做这次合并。
- **真实依赖下的负载和故障演练不在本仓库的 CI 里**（设计 15）。尾延迟、GC、超时后仍在运行的调用占住的请求内存、日志积压、发布传播时间，这些数取决于部署环境（特征存储、模型服务、机器规格、并发），在 CI 的共享机器上测出来的数既不稳定也不能代表线上，做成门禁只会误报。仓库里有的是与环境无关的保证：分配预算测试（按候选数）、BenchmarkDotNet 基准（CI 只试跑）、Redis 的真实容器测试、每个外部依赖的超时和放弃路径的确定性测试（放弃的调用持有请求内存直到真正结束、后台上报不拖住发布等）。上线前由使用方在自己的环境里用 `StrataRec.Samples.Host` 或自己的宿主接真实依赖压测，并在压测中注入延迟和故障；固定环境的基线和性能门禁等有了这样的环境再定。


## 范围调整

框架的核心目标是：整体性能好、整体分配低、用户体验好、容易调试、开发和测试。`design.md` 是起点，不是约束；一项设计带来的复杂度超过它对这个目标的贡献时，就简化、推迟或不做。

- **父子层级表（偏移数组嵌套）不做；组按它和成员的关系分两种情况**（设计 4.7）。嵌套表的难点（父表过滤后子表怎么办、子表截断后父表的汇总值过期、表达式怎么区分两张表的列）会散落在执行器、拉取、后备恢复、日志和回放里，一致性只能靠两张表一起改；物品在组之间移动（混排、广告插进某一行）还要重建偏移数组。
  - **组由成员决定**（按商家分组的搜索结果）：一张表，组键是外键实体（例如 `col.item.merchant_id`），组的特征照常按键去重拉取；组的得分和组内名次由分组聚合算出、回填到组内每一行（`sum`、`mean`、`max`、`top_k_mean`、`logsumexp`），每组保留前几项用组内名次加过滤；分组展示由宿主按组键排列结果。分组聚合算子有实际需求时再加。
  - **组先于成员存在**（多行首页：先提名候选行、用行级模型过滤，再按每一行自己的召回源和数量取内容；物品可以出现在多行里；版面规则作用在行上）：框架现在不原生支持，由使用方组合实现，例如宿主先调用排行的流水线，再把选中的行作为请求输入交给排物品的流水线，或者写自定义的行源算子。已知代价：实验按流水线定义，同时改行和物品的实验要拆成两个实验，并由实验平台把它们分给同一组用户。
  - **将来原生支持时的方向：一个请求几张扁平表，用键列关联，不嵌套。** 子表声明父表，子表的一行由（父键, `entity_id`）标识；节点只写一张目标表，可以读其他表，父表的列按请求内的外键实体读取（父行已淘汰时读到缺失）；跨表汇总用分组聚合；父行淘汰时子行不级联删除，输出时按父表顺序 join，孤儿行不出现，要省掉后续拉取就显式过滤。现在的格式都能按增量扩展（节点加可选的 `table`，缺省就是唯一的表；日志的行标识加表名；回放包有版本号；结果加可选的分组结构），所以不提前定格式。等组合方案的代价（拆实验、宿主胶水）在真实业务里显现时再做。
- **`fetch_missing` 不做**（设计 8.5）。这是响应之后的后台拉取：探针缓冲区和请求内存要活过请求本身，拉取还要有自己的超时、并发上限和失败计数，而它只满足“离线训练要的特征比线上用的多”这一种需求。训练用的额外特征，可以离线按键和时间点关联，或者加进线上的拉取。
- **本地磁盘缓冲不在框架里做**（设计 8.6）。落盘和重启后补发取决于部署环境（磁盘、容器生命周期），由宿主通过 `DurableOverflow` 钩子实现。
- **节点本地的磁盘快照不在框架里做**（设计 6.6 原来的“定期把表写到本地磁盘，重启时从磁盘恢复”）。它只让同一个节点上的重启更快，数据仍在远端快照和更新流里；常见的部署里 Pod 重建后本地盘是空的，用不上。表的二进制转储会成为一种要兼容的格式：记录布局一变就要有版本和迁移，还要处理写了一半、校验失败、磁盘满和模式变了的文件。实测 `snapshot_files@1` 单线程加载 100 万条记录（168 MB 的 JSON Lines，7 个字段含一个 4 维向量）用 1.6 s，约 64 万条/秒，中等规模的表启动不慢。真要加快启动，该改的是加载快照本身：多个分片文件并行解析，或者换二进制的快照格式，这对每次启动都有效，包括新节点。
- **不做日志量的静态预算，`policy.jsonc` 没有 `log_bytes_per_request_budget`**（设计 8.6）。设计里 CI 按“采样率 × 最大行数 × 每行字节数”估算每个请求的日志量，与策略里的预算比较。这个字段原来能写、进了 Schema，却没有任何代码读它，设成 0 也照样通过校验，让人以为日志量受了保护（外部评审）。估算本身也站不住：探针的行数取决于请求的候选数，字符串、列表的宽度只能猜，估出来的数既挡不住真实的大请求，也会误伤。删掉字段（之后写它按未知键报错）；实际的保护是有界队列（`best_effort` 满了丢弃并计数，`durable` 溢出计数），观测用逐探针的批次数（送达或丢弃）和队列深度的指标。以后有了可靠的估算规则再加回来。
- **不统计每个探针的字节数和池中保留的字节数**（设计 13.1）。前者要在 sink 序列化之前估算字节数，后者要池暴露内部状态，调试价值抵不上成本。
- **核心不内置模型推理运行时；ONNX、流式、分页现在都不做，但不排除以后以扩展包的形式做**（设计 6.4、6.9、18.2）。服务是分布式的，模型由独立的推理服务提供；框架虽然用 C# 实现，不应把模型限定在 ONNX 这类某一种运行时或格式，所以核心里不做 `local_onnx@1`。重点是编排；扩展包可以有，前提是核心不依赖它、它本身不过度复杂：`StrataRec.Llm` 就是这样一个包，也是写扩展算子的示例，使用方完全可以不用它、自己写大模型算子。流式输出（`ExecuteStreamingAsync`）和分页现在不做，以后需要时再按扩展的方式加，接口不为它们预留。模型经 `IModelClient` 接入，推理服务的协议客户端（KServe v2、TF Serving 或公司内部的协议）由使用方按自己的服务实现，注册后由绑定按类型名引用。框架内置静态、确定性的示例客户端，供测试、样例和本地开发：`linear@1`（线性打分）、`random@1`（随机打分的替身，见下一条）、`memory_list@1`（固定列表召回）、`memory@1`（内存特征）。
- **`random@1` 是绑定层的替身，分数只由模型能看到的那部分输入决定**（设计 6.4 第 1 条、5.9）。开发、测试环境把真实模型的逻辑名绑定到它，设置声明它模仿的签名，算子加载时的签名检查照常通过，流水线和实验不改。设置有两种写法：名字数组（每个张量都是 float32 `[-1]`，逐点模型最常见的样子），或者名字到 `{ "type", "shape" }`，照抄真实模型的签名；成对和列表级模型用后一种（输入 `[-1, 2]`、`[1, -1]` 等）。一条规则覆盖所有形状：对每个输出，声明形状以输出形状开头的输入是“逐元素”的，其余是共享的；输出每个元素的分数取（模型逻辑名与输出名的哈希、种子、按名字序数排列的各输入：逐元素的取这个元素的切片，共享的取整个输入）规范编码的 `StableHash` 的高 24 位，乘 2^-24。所以一行的分数只看这一行（和共享输入），一对的偏好只看这两行及其先后，列表里一行的分数只看它在列表中的那一片：与位置、分批和其他元素无关，换请求种子就换分数，离线可以复算；24 位在 float32 里精确且小于 1。名字、类型和形状不进哈希，两种写法对同样的值给同样的分数，原来的录制不受影响。每个输出至少要有一个逐元素输入，否则配置错误：输出的大小和变化只能来自它们。浮点按 float64 规范编码，−0.0 与 0.0、各种 NaN 不区分，同 `hash01`；int64 按 int64 编码。种子取绑定的 `seed`（各请求同一组分数），否则取调用的种子（模型算子都传 `ctx.request.seed`）；都没有时调用失败，不默认成常数：缺失不静默变成值，要固定只需在绑定里写 `seed`。完整写法的输入必须写 `type`，不设默认值。代价：输入相同的元素同分（真实模型也如此，平分按 `entity_id`）；不接受没有输入的签名；与真实模型不同，一对和它反过来的一对是两次独立的抽样，不是 p 与 1 − p，所以成对重排的结果取决于进入时的顺序（成对算子每对只发一次，排名高的在前）；列表里一行的分数不看列表中的其他行，所以列表级重排的结果只取决于窗口里有哪些行；列表级模型的上下文向量要声明成 `[1, N]`，写成 `[1, -1]` 就成了逐元素输入。
- **常用、复杂、值得框架优化的场景由框架做，其余接入由使用方实现**。本地特征表继续开发（见“本地特征表”和“尚未实现”）；`cache` 供给方式先做本地内存和 Redis 两种存储。召回服务没有通用协议，请求字段（用户向量、过滤条件、分页）和返回结构各家不同，所以不内置召回客户端（`grpc_ann@1`、`grpc_retrieval@1`），由使用方实现 `ICandidateSource`。读 Redis 等特征存储的连接器同理（键和值的格式各家不同），由使用方实现；框架内置的 Redis 只是 `cache` 的分布式层（`redis@1`），由引擎写入，不是特征的来源。更新流（Kafka）和对象存储（`s3://`）的快照暂不内置，凭据、SDK 和部署方式取决于环境，宿主可以实现 `IFeatureUpdateSource`；内置的 `snapshot_files@1` 只读本地文件。
- **不负责流量分配，桶由外部实验平台分配**（设计 11.1、11.2、10.2、12.6）。哪些用户进入哪个实验、比例、扩量、长期对照和分流单元都属于实验平台：分配要和平台的用户口径与分析一致，引擎再算一次，同一个用户在两边的分组可能不同。所以删掉内置分流（`TrafficAssigner`：域、各层的盐和分流单元、桶范围），manifest 和发布文件里不再有 `assignment` 和桶范围。`allocation/` 改名 `releases/`，只写本环境的目录、绑定、表和在线实验所在的层；分配和桶范围的字段按未知键报错（原来对旧目录和旧字段有专门的迁移提示，1.0 之前没有要迁移的使用者，删了）。引擎这边保留层：层是一组互斥的实验，校验据此判断哪些桶可能同时命中。分配由请求带入（`RecRequest.Assignment`，网关已经问过平台），或者由宿主实现的 `IAssignmentProvider` 查询：它拿到流水线、请求 ID、请求输入（用户 ID 等）和计划的层、实验与桶，与请求共用截止时间；两者都没有时只跑基线。空列表也是平台的回答（没有桶），不再去问 provider。provider 拿到的上下文是只读结构体，计划的层、实验和桶是每个计划建一次的只读视图，查询不为它分配；以后加字段用可选的 init 属性，已有实现不用改。平台 ID 和引擎 ID 的对应由实现负责，框架不保存映射配置，因为各平台的 ID 格式不同。收到的分配怎么映射只在一处：不在计划里的桶记为未知并忽略（实验不在这个 manifest 里、拼错、平台先于发布开始分配）；重复的桶算一次；同一层出现两个不同的桶时这一层按基线执行，两个都记为层冲突。没有选“取第一个”：平台返回的顺序不是约定，结果会随它变化，也不能运行没校验过的组合。被忽略的桶和原因写进实验记录（`ExperimentRecord.Ignored`，按 ID 排序，没有时是空数组、不分配）、回放包（格式改变，旧的包直接拒绝并提示重新录制，不做迁移）和指标（`stratarec.request.arms.ignored`，按 `outcome` 区分 `unknown` 和 `layer_conflict`，不带桶的 ID，因为未知的 ID 来自平台、取值没有上界）。只为分流检查存在的计划加载结果 `rejected`（事件 1003）随之删除。`force_arms` 仍然严格，未知或同层冲突让请求失败；空列表强制只跑基线，请求文件里的 `force_arms: []` 也一样（CLI 原来把空列表当作没写，评审 18）。provider 守等待的不变量（3）：放弃等待时（超时或调用方取消），用 `CancelAsync` 取消它的令牌，回调不在请求线程上运行，取消源等 provider 真正结束才释放；原来随方法返回就释放，计时器停掉，或者调用方取消时还没轮到的注册被删掉，只靠令牌结束的 provider 就永远挂着（评审 18）。取消回调抛出的异常写日志（事件 1102）。分配之前被拒的请求（未知流水线、非法 `force_arms`、provider 超过截止时间）实验记录为空；分配之后、执行之前预算用完的请求带上生效的桶、被忽略的桶和 manifest，与已经计入的指标一致。两者都没有回放包。域也删掉了：平台的长期对照就是不带分配的请求，平台保证互斥的实验可以放进同一层。代价：校验假定不同层的桶都可能同时命中，平台放在不同域、实际不会相遇的两个实验，修改重叠时也要放进同一层；本地运行实验要在请求文件里写 `assignment`，或者用 `--arms`。
- **草稿预览、实时回放推后**（设计 10.7、10.8）。两者都依赖控制面；本地已经可以用 CLI 运行工作区、录制和回放请求。
